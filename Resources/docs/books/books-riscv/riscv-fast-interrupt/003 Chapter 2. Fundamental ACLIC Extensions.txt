
Chapter 2. Fundamental ACLIC Extensions
This section lays the foundation for fast interrupt handling.

To achieve this, it builds upon the hart-level behavior of AIA, and integrates a subset of Advanced Platform
Level Interrupt Controller (APLIC) functionality into a hart-local interrupt controller.

At config-time, the interface differs from AIA, but the same structures for configuration as in the APLIC are
used.

An ACLIC is made up of two major components:

 1. Hart-local APLIC Domains providing direct delivery of interrupts to the hart (Non-ISA)
 2. Indirect CSR physical control interface to hart-local APLIC domain registers (Smidctrl/Ssidctrl)

The latter is additionally made up of

 1. Interrupt control interface for pending and enable bits based on IMSIC
 2. New indirect CSRs for accessing the remaining state of the hart-local APLIC domains

In addition, extensions are defined for accelerating nested preemption (Smnip/Ssnip).

2.1. Hart-local APLIC domains (Non-ISA)
The APLIC was designed as a multi-hart interrupt controller. In the context of an ACLIC, APLIC domains
are used tightly coupled with a single hart. The domains used here are a simplified subset of the full
domain definition of the APLIC.

2.1.1. Interrupt domain mapping

An APLIC has one or more interrupt domains, each associated with a subset of RISC-V harts at one
privilege level.

An ACLIC system requires at most two domains. It only requires one domain if M-mode but not S-mode
has been implemented, and two domains if M- and S-mode are implemented.

The root domain is always at machine level. If supervisor level is implemented, interrupts can be delegated
to a supervisor-level domain, which is the only child domain (Child Index '0') of the root domain.

2.1.2. Simplifications to domain state

The APLIC contains a per-domain configuration register, which, among other things, allows selecting the
delivery mode.

In an ACLIC system, DM is fixed to 0 (direct delivery mode).

The following, additional restrictions are applied:

                                            bits 31:24   read-only 0x80
                                            bit 8        IE = 1 (read-only)
                                            bit 7        read-only 0

                                                  bit 2        DM = 0

The IE bit is fixed to 1, as its functionality is subsumed by the xstatus.xIE bits at the hart. The BE bit is now
reserved. Endianness is controlled exclusively by the setting in the xstatus register at the hart.

Further simplifications are:

 ⚫ The Child Index field in the sourcecfg[i] register is always '0' when D=1 (i.e. delegation to child
   domain). This is only possible in Machine mode. In Supervisor mode, D=0, as there is no child domain.
 ⚫ As the ACLIC operation is based on direct interrupt delivery, xmsiaddrcfg[h] and genmsi registers are
   not required.
 ⚫ Interrupt delivery control (IDC) structures are not needed, as the domain has a fixed relationship with
   one hart, and IDC functionality is already provided by hart-local CSRs.
 ⚫ The hart index inside the target registers is read-only zero, as only one hart is supported.

APLIC registers or fields not required here shall be read-only zero.

2.1.3. Interrupt delivery

The APLIC rules of direct interrupt delivery apply. External interrupt signals are supplied to the hart from
the respective domain. The interrupts from the root domain appear as MEIP (Machine External Interrupt-
Pending), and interrupts from the child domain appear as SEIP (Supervisor External Interrupt-Pending).

A hart-local APLIC domain signals the priority and identity of the highest priority pending-enabled
interrupt to the hart. This information influences the arbitration between major and minor interrupts that
is ultimately reflected in the xtopsi CSRs.

2.2. Interrupt domain control interface (Smidctrl, Ssidctrl)
Smidctrl depends on the Smcsrind and Smaia extensions. Ssidctrl depends on the Sscsrind and Ssaia
extensions.

                   Many AIA features like programmable IPRIO may not be needed in resource-constrained
                   systems. Since these are already controlled by WARL registers, implementations can save area
                   by choosing to not support them.

                   A minimal implementation of the AIA mvip CSR is suggested by the AIA specification:
                  "When supervisor mode is implemented, the minimal required implementation of mvien and
                   mvip has all bits being read-only zeros except for mvip bits 1 and 9, and sometimes bit 5, each
                   of which is an alias of an existing writable bit in mip. When supervisor mode is not
                   implemented, registers mvien and mvip do not exist."
                   Further, resource-constrained implementations of these extensions are expected to implement
                   the iprio array of major interrupts as read-only zeros.

The interrupt control interface contains the hart-level interface to operate a hart-local APLIC, by building
on the hart-level features of AIA.

Indirect CSR access to APLIC domains is provided to subsume the memory-mapped register interface in a
hart-local configuration.

This approach has several advantages:

 ⚫ Built-in privilege level protection: CSRs are clearly mapped to a privilege level. Therefore, no additional
   protection e.g. through PMP is required. Especially in systems without memory translation, this is
   beneficial for saving valuable memory protection resources
 ⚫ Atomic access: Atomic read/write, read & set and read & clear instructions are available for CSRs
 ⚫ Resource efficiency: Due to smaller access granularity and range, implementations using indirect CSRs
   can be more resource efficient.
 ⚫ Platform-independent: Memory-mapped base addresses are platform-defined. This places an
   additional configuration burden in the hands of a user. CSR-based interfaces always use the same CSR
   register numbers

This is achieved by reusing the allocated indirect CSR space for the interrupt pending and enable bits in an
IMSIC. Additional indirect CSR access is provided to the remaining state.

2.2.1. Interrupt control interface based on IMSIC interface

ACLIC provides access to interrupt pending and enable bits of the hart-local APLIC domains using the
same mechanisms as access to interrupt pending and enable bits in the interrupt files of an IMSIC.

The AIA eidelivery and eithreshold CSRs defined for the Incoming Message Signaled Interrupt
Controller (IMSIC) are not included in the scope of Smidctrl/Ssidctrl.

                 It is not anticipated that ACLIC implementations would allow dynamically switching
                 eidelivery into other modes. If e.g. MSI delivery is required in a system, it is recommended to
                use the full AIA implementation with IMSIC. Therefore, no dynamic selection of ACLIC
                 operation via eidelivery is provided.

In an ACLIC, xtopei is implemented and reports the current highest-priority pending-and-enabled
interrupt of the connected APLIC domain. It reports the minor interrupt identity in IID, and the
configured priority number in IPRIO.

  xtopei
   XLEN-1:26         (reserved)
   25:16             IID
   15:8              (reserved)
   7:0               IPRIO

                 As eithreshold is not implemented, any interrupt that has its enable bit set to one is
                considered enabled for the purpose of reporting it in xtopei.

In an ACLIC, registers eipk and eiek serve the same functionality as with eidelivery = 1 in an IMSIC, i.e.
they are the pending and enable bits for an interrupt source k. The eip and eie arrays act as an alias of the
pending and enable bits of the connected APLIC domain.

                 For an inactive source, the corresponding bits in eipk and eipk are read-only zero. In
                addition, the AIA defined rules "Precise effects on interrupt-pending bits" apply.

                 Providing access to APLIC pending and enable bits at the hart-level has several advantages
                 over using an IMSIC with interrupt delivery from an APLIC

                 ⚫ It removes unnecessary resource duplication between IMSIC and APLIC when integrated
                    with a single hart.

                        ⚫ It simplifies the handling of level-sensitive interrupts, avoiding additional checking of the
                          pending flag in the APLIC in a handler of a level sensitive interrupt.
                        ⚫ It simplifies the register interface, as CSR instructions have single bit operations

2.2.2. Indirect CSR access to hart-local APLIC domain configuration

To have full control over the necessary APLIC registers, the following indirect CSR access is added. The
registers xireg4 through xireg6 are reserved and raise an illegal instruction exception when xiselect is in
the range 0x1000-0x10FF.

Interrupt Priority (iprio)

When XLEN = 32, each xireg register controls the ACLIC priority setting of four interrupts.

xiselect xireg size xireg state

0x1000        4B                 acliciprio0

…             …                  …
0x10FF        4B                 acliciprio255

Indirect access to acliciprio[k] mirrors target[k*4].iprio up to target[k*4+3].iprio.

When XLEN = 64, only the even-numbered registers exist and each register controls the priority setting of
eight interrupts. Indirect access to acliciprio[k] mirrors target[k*8].iprio up to target[k*8+7].iprio.

The layout of acliciprio[k] for XLEN = 32 is as follows:

         31                             24 23                         16 15                          8 7                          0
                  target[k*4+3].iprio           target[k*4+2].iprio           target[k*4+1].iprio           target[k*4+0].iprio
                          8                             8                             8                             8

and for XLEN = 64 like:

         63                             56 55                         48 47                         40 39                         32
                  target[k*8+7].iprio           target[k*8+6].iprio           target[k*8+5].iprio           target[k*8+4].iprio
                          8                             8                             8                             8
         31                             24 23                         16 15                          8 7                          0
                  target[k*8+3].iprio           target[k*8+2].iprio           target[k*8+1].iprio           target[k*8+0].iprio
                          8                             8                             8                             8

APLIC domains do not implement target[0]. When accessing acliciprio[0], the bits corresponding to
target[0] are read-only zero.

When XLEN = 64 and xiselect is an odd value in the range 0x1000-0x10FF, attempting to access xireg
raises an illegal instruction exception.

Source Configuration (sourcecfg)

When accessing the source configuration via indirect CSR, only the lower 16b are accessible, as the rest of
the register is reserved.

When XLEN = 32, the xireg2 and xireg3 registers combined control the source configuration of four
interrupts.

xiselect xireg2/3 size xireg2 state                     xireg3 state

0x1000        4B               aclicsourcecfg0          aclicsourcecfg1

…             …                …                        …
0x10FF        4B               aclicsourcecfg510 aclicsourcecfg511

Indirect access to aclicsourcecfg[k] mirrors sourcecfg[k*2][15:0] up to sourcecfg[k*2+1][15:0].
Access to aclicsourcecfg[0][15:0] is read-only zero.

When XLEN = 64, only the even-numbered registers exist and the xireg2 and xireg3 registers combined
control the source configuration of eight interrupts. Indirect access to aclicsourcecfg[k] mirrors
sourcecfg[k*4][15:0] up to sourcecfg[k*4+3][15:0].

The layout of aclicsourcecfg[k] for XLEN = 32 is as follows:

       31                                                    16 15                                                   0
                           sourcecfg[k*2+1][15:0]                                 sourcecfg[k*2+0][15:0]
                                    16                                                     16

and for XLEN = 64 like:

       63                                                    48 47                                                  32
                           sourcecfg[k*4+3][15:0]                                 sourcecfg[k*4+2][15:0]
                                    16                                                     16
       31                                                    16 15                                                   0
                           sourcecfg[k*4+1][15:0]                                 sourcecfg[k*4+0][15:0]
                                    16                                                     16

State Enable

Additional control is provided for the newly added registers acliciprio[k] and aclicsourcecfg[k].

If the Smstateen extension is implemented, then the bit 53 (ACLIC) in mstateen0 is implemented. If bit 53
(ACLIC) of a controlling mstateen0 CSR is zero, then access to the new CSRs (acliciprio[k],
aclicsourcecfg[k]) by S-mode or a lower-privilege mode results in an illegal instruction exception.

If the Smstateen extension is implemented, then bit 58 (IMSIC) in mstateen0 is implemented, even though
IMSIC is not present. If bit 58 of a controlling mstateen0 CSR is zero, then access to the CSRs reused from
the IMSIC (stopei, eipk and eiek) by S-mode or a lower-privilege mode results in an illegal instruction
exception.

2.3. Nested Interrupt Preemption Support (Smnip & Ssnip)
The Smnip extension depends on the Smidctrl extension and adds nested preemption support at machine
level.

The Ssnip extension depends on the Ssidctrl extension and adds nested preemption support at supervisor
level.

The extensions enable higher-priority interrupts to preempt lower-priority interrupts efficiently in a
nested fashion. It provides additional state to resume execution of the previous handler after a nested
preemption.

2.3.1. Changed and new CSRs at Machine Level

                   Number      Name                Description
   (NEW)           0x346       mistatus            Interrupt status
   (NEW)           0x347       mithreshold         Interrupt enable threshold
   (NEW)     0x348             mtopsi              Top signed interrupt
   (Changed) 0x342             mcause              Cause register

Additionally, this extension adds an indirect CSR

miselect mireg4 size mireg4 state

0x1000       XLEN          miconfig

The registers mireg, mireg2, mireg3, mireg5, and mireg6 are reserved when miselect is 0x1000.

New Interrupt Configuration (miconfig) CSR

  miconfig fields
   bits               description
   XLEN-1:20          (reserved)
   19:16              snipbits (if Ssnip is implemented)
   15:12              (reserved)
   11:8               mnipbits
   7:6                (reserved)
   5                  sipu (if Ssip is implemented)
   4                  mipu (if Smip is implemented)
   3                  snipen (if Ssnip is implemented)
   2                  mnipen
   1:0                (reserved)

miconfig is a WARL register used to configure the behavior of interrupts.

If Ssnip is implemented, the fields snipbits and snipen of miconfig control nested interrupt preemption
behavior for supervisor level.

The supervisor-level CSR siconfig is a subset of miconfig. Reading or writing a field of siconfig reads or
writes the corresponding field of miconfig.

The fields mnipen and snipen enable this extension at M-mode and S-mode, respectively. Enablement of
the extension refers to activating the modified operative behavior specified in Section 2.3.3.

If Ssnip is not implemented, then snipbits and snipen are read-only 0. If Ssip is not implemented, then
sipu is read-only 0. If Smip is not implemented, then mipu is read-only 0.

The field miconfig.mnipbits/snipbits defines how many most-significant priority bits participate in
nested interrupt preemption grouping. Interrupts whose priorities differ only in less-significant bits cannot
preempt each other. The highest legal value of miconfig.mnipbits/snipbits is IPRIOLEN. A mask for
filtering out the less-significant priority bits that do not participate in nested interrupt preemption at mode
x is:

  NIPPRIO_MASK = ~((2^(IPRIOLEN - xiconfig.xnipbits)) - 1)

                 For example, if miconfig.mnipbits=4, NIPPRIO_MASK=11110000, i.e. the four MSBs are
                participating in interrupt preemption.

New Interrupt enable threshold (mithreshold) CSR

A new WLRL M-mode CSR, mithreshold, determines the priority cutoff used to mask lower-priority
interrupts (see Section 2.3.3).

  mithreshold
   XLEN-1:9        (reserved)
   8:0             iprio[8:0]        Interrupt-enable threshold

The field mithreshold.iprio implements exactly IPRIOLEN+1 bits.

                 In contrast to existing threshold mechanisms in AIA, this CSR applies to major and minor
                 interrupt identities.

                Because IPRIO = 0 is a valid value for major interrupts with a default priority greater than
                 external interrupts, mithreshold.iprio = 0 does not enable all interrupts, and the field needs
                 to be one bit wider than IPRIOLEN in order to allow a threshold that enables all interrupts.

                 An interrupt threshold is needed in an efficient implementation of synchronization protocols
                like Priority Ceiling Protocol (PCP) that are used with preemptive interrupt schemes.

New Interrupt Status (mistatus) CSR

A new M-mode CSR, mistatus, holds consolidated state related to interrupts. This CSR aliases several
fields of mstatus. This CSR intends to consolidate the state which may need to be saved/restored in
interrupt handling supporting nested preemption. Additionally, it aliases mstatus.mie, which allows setting
the interrupt enable flag while reading the register.

  mistatus
   Bits            Field                       Description
   XLEN-1:30       (reserved)
   29:28           mpp[1:0]                    Previous privilege mode, mirror of mstatus.mpp
   27              mpie                        Previous interrupt enable, mirror of mstatus.mpie
   26              mpelp                       Previous Expected Landing Pad State, mirror of
  mstatus.mpelp
   25:21           (reserved)
   20:19           VS[1:0]                     Vector extension status, mirror of mstatus.VS
   18:17           FS[1:0]                     Floating-point extension status, mirror of
  mstatus.FS
   16:8            pithreshprio[8:0] Previous mithreshold.iprio value
   7               psppush           Previous stack pointer push (only if Smcsps is
  implemented)
   6           sppush                          Stack pointer push (only if Smcsps is

  implemented)
   5:1              (reserved)
   0                mie                         Alias of mstatus.mie

New Top Signed Interrupt Status (mtopsi) CSR

The mtopsi CSR is provided for efficiently handling major and external interrupts in a scheme where
interrupts are dispatched by software, and nested preemption is supported.

A read of mtopsi returns information about the highest-priority pending-and-enabled interrupt, that also
exceeds the priority threshold specified by the mithreshold register, at machine level, in this format:

  mtopsi
   XLEN-1:16        SIID     Signed Interrupt Identity
   15:9             (reserved)
   8:0              IPRIO

If an external interrupt i is the highest-priority pending-and-enabled interrupt, SIID is equivalent to the
minor interrupt identity of i. Else, if a major interrupt i is the highest-priority pending-and-enabled
interrupt, SIID is the two’s complement representation of the negated major interrupt identity of i. Else, if
no interrupt is pending-and-enabled, SIID is 0.

                  The intention of providing a signed version of interrupt identity is to index into a table with
                 decreasing memory address per major identity and increasing addresses for minor identities.
                  A signed table index can be extracted through an arithmetic right shift.

If the priority number for the reported interrupt is in the range 1 to 255, IPRIO is simply that number. If the
interrupt’s priority number is zero or greater than 255, IPRIO is set to either 0 or 255 as follows:

 ⚫ If the interrupt’s priority number is greater than 255, then IPRIO is 255.
 ⚫ If the interrupt’s priority number is zero and interrupt i has a default priority higher than a machine
   external interrupt, then IPRIO is 0.
 ⚫ If the interrupt’s priority number is zero and interrupt i has a default priority lower than a machine
   external interrupt, then IPRIO is 255.

Else, if no interrupt is pending-and-enabled, IPRIO equals mithreshold.iprio.

                  Reading mithreshold.iprio as IPRIO field allows software to use this priority as threshold
                 for spurious interrupts handlers. If it would return zero, software may need special handling of
                  spurious interrupts to prevent writing 0 to the threshold register.

A write to the mtopsi CSR performs the following stepwise actions:

 1. The source register bits [16:8] are written to mithreshold.iprio
 2. The reported interrupt identity is claimed by clearing its pending bit if possible.
 3. The interrupt threshold is raised by writing the reported IPRIO value to mithreshold.iprio

If a read and write of the mtopsi CSR are done together by a single CSR instruction (CSRRW, CSRRS, or
CSRRC), the value returned by the read indicates the claimed interrupt.

Changed Cause (mcause) CSR

When miconfig.mnipen is one, the exception code in mcause is modified as follows:

If a trap was taken on an external interrupt, the Exception Code field reports the minor interrupt identity.

Else, if a trap was taken on a major interrupt identity, the Exception Code field reports the two’s
complement representation of the negated major interrupt identity.

                 The representation of exception code on interrupts is aligned with the SIID field in mtopsi.

2.3.3. Operation

Based on NIPPRIO_MASK derived from xiconfig.xnipbits, a nested preemption priority threshold is
given as

  NIP_THRESHOLD = (xithreshold.iprio & NIPPRIO_MASK)

When xiconfig.xnipen is one, an interrupt source is considered disabled irrespective of its interrupt-
enable bit, when the following condition holds:

  IPRIO >= NIP_THRESHOLD

where IPRIO is the value reported in the xtopsi CSR, if the interrupt source is the highest priority pending-
enabled one.

                  The highest possible priority value of IPRIO is 0. When xithreshold.iprio and
                 NIPPRIO_MASK is 0, the nested interrupt preemption threshold is 0 and thus, all interrupts
                  are considered disabled.

                  The lowest priority value reported by a pending-enabled interrupt in IPRIO is 255. When
                 xithreshold.iprio is 256 or larger, no interrupts are disabled by the thresholding
                  mechanism.

                  IPRIO is derived from the configured priority or default priority order according to the rules
                 defined in AIA.

Trap behavior

The existing trap behavior is modified as follows:

When a trap is taken into level x, the current value of xithreshold.iprio is written to xistatus
.pithreshprio.

Additionally, if the trap was taken on an interrupt, xithreshold.iprio is set to xtopsi.IPRIO. This
automatically raises the interrupt-enable threshold. Also, the interrupt is claimed by clearing the pending
bit if possible.

If a double trap occurs while in M-mode, xistatus.pithreshprio is unchanged.

                 Synchronous exceptions do not modify the value of xithreshold.

Returns from Handlers

The behavior of an xret instruction is modified as follows:

xret sets xithreshold.iprio to xistatus.pithreshprio.

This automatically restores the interrupt-enable threshold to the level of the previous context.

2.3.4. State Enable

If the Smstateen extension is implemented, then the bit 53 (ACLIC) in mstateen0 is implemented. If bit 53
(ACLIC) of a controlling mstateen0 CSR is zero, then access to the new CSRs sistatus, sithreshold, and
stopsi by S-mode or a lower-privilege mode results in an illegal instruction exception.
