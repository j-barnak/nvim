What is a variable in a program?
A variable in a program is a symbolic name that represents a storage location in the computer’s
memory, used to hold a value. It allows programmers to store, retrieve, and manipulate data by
referring to that name rather than the actual data itself.

Key Features:

   ●​ Name: A variable has a unique identifier, or name, chosen by the programmer, which is
      used to access its stored value.
   ●​ Value: The value of a variable is the data it currently holds, which can be of different
      types (like integers, strings, etc.).
   ●​ Binding: A variable is bound to its value, meaning the name is associated with a value
      or object in memory.

So, when we write, in Python `x = 10`, here, x is a variable that is bound to the value 10. The
name x acts as a reference to the location in memory where the value 10 is stored.

How do you create variable bindings in SML/NJ
Let blocks are the primary mechanism for creating variable bindings in SML/NJ. Here's a basic
syntax for a let block:

fun days2ms days =
  let
     val hours = days * 24.0
     val minutes = hours * 60.0
     val seconds = minutes * 60.0
  in
     seconds * 1000.0
  end;

We can create blocks within blocks too, e.g.:

fun days2ms days =
  let
     val hours = days * 24.0
  in
     let
       val minutes = hours * 60.0
     in
       let
          val seconds = minutes * 60.0
       in
          seconds * 1000.0

      end
    end
  end;

And what is the difference between variables in C and in SML/NJ?
   ●​ C: Variables in C can be mutable, meaning their values can be modified after they are
      declared.
   ●​ SML/NJ: Variables are immutable by default, meaning their values cannot be changed
      once they are initialized.

Which techniques could you use to explain this difference more formally?
We could use operational semantics! Operational semantics is a formal way to describe how
programs execute, specifying the behavior of a programming language by defining how each
statement or expression in the language changes the state of the program step by step. It does
so by providing rules that explain how the execution of a particular language construct (like
assignment, conditionals, loops, etc.) affects variables, memory, and control flow.

Key Concepts:

   1.​ State: The state of a program typically refers to its variables and the values they hold at
       any given point in time, as well as other runtime information like the program counter.
   2.​ Transition Rules: Operational semantics uses transition rules to show how the
       execution of a statement or expression transforms the program state from one step to
       the next. For example:
           ○​ If x := 5 is executed, the state changes by binding x to the value 5.
            ○​ If x := x + 1 is executed, it evaluates x, increments its value, and updates the
               binding of x in the state.

Why do these rules look like fractions? What's the meaning of them?
They look like fractions because they are written as implication rules in logic, with the top part
(premises) representing conditions that must be met, and the bottom part (conclusion)
representing the result. Let's consider the rule for addition, for instance:

  e0 → v0          e1 → v1
----------------------------------
   e0 + e1 → v0 + v1

Premises (top): e0 → v0 and e1 → v1 mean that expressions e0 and e1 evaluate to values
v0 and v1, respectively.
Conclusion (bottom): The expression e0 + e1 evaluates to v0 + v1. In other words, after
evaluating both e0 and e1, their values are added.

The top part of the "fraction" (premises) must hold for the bottom part (conclusion) to be valid.
Each arrow (→) represents evaluation: on the left, we have expressions, and on the right, we
have the values they evaluate to. This kind of structure provides a formal way to reason about
the behavior of expressions in a programming language.

Why is operational semantics useful? What can we do with it?
Operational semantics is a method of defining the meaning of programming languages by
describing the effects of executing their constructs. It provides a formal framework for
understanding and reasoning about how programs execute. Here are some key benefits and
uses of operational semantics:

    1.​ Formal Specification: It provides a rigorous way to specify the behavior of a
        programming language. This helps in creating precise and unambiguous descriptions of
        language features and constructs.
    2.​ Program Verification: By defining the operational rules of a language, we can reason
        about the correctness of programs. It allows for the formal verification of properties such
        as safety, security, and correctness of programs based on their operational behavior.

   3.​ Compiler Construction: It aids in the design and implementation of compilers.
       Understanding how different constructs execute helps in translating high-level code into
       machine code while preserving the intended behavior.
   4.​ Debugging and Testing: Operational semantics helps in debugging by providing a clear
       understanding of what each construct in a program does. This can be used to create test
       cases that cover various execution paths and ensure correctness.
   5.​ Language Design: It helps in designing new programming languages or modifying
       existing ones by providing a clear framework for understanding the implications of
       language features and constructs.
   6.​ Performance Analysis: Understanding the operational semantics can aid in
       performance analysis by revealing how different constructs affect execution time and
       resource usage.
   7.​ Educational Tool: It serves as a useful educational tool for teaching programming
       language concepts and the fundamentals of how programming languages are executed.

According to these rules, our variables have immutable semantics. How
can we see that by looking into the rules?
We can observe this property by examining how the rules handle variable bindings and the
absence of any "assignment" operation that would modify an existing variable's value.
   1.​ No Rule for Re-assignment:
          ●​ In these rules, there is no mechanism for changing the value of a variable once it
              has been bound. For example, we do not see any rule like C + {name: v0} →
               C + {name: v1} that would update an existing variable binding from one value
              (v0) to another (v1).
          ●​ Every time a new binding is created (e.g., in the let-binding rule), a fresh variable
              is introduced, but once a variable is assigned a value, that value does not
              change.
   2.​ The Let-Binding Rule:
          a.​ This rule shows that a new binding (name = v0) is added to the environment (C
               + {name: v0}) when evaluating the let expression, but it never modifies any
               existing binding in the context C.
           b.​ The context C remains unchanged outside the scope of the let expression. If
               name was already bound in C, the new binding {name: v0} shadows the old
             one within the scope of the let, but the original binding remains intact outside
             that scope.
   1.​ Evaluation is based on fixed bindings:
          ○​ When an expression e0 evaluates to v0, this result is stored in the context as a
             permanent association until that context is discarded or overridden by a new,
             independent let block. There is no operation to overwrite the value of name
             once it's been bound.
   2.​ Absence of mutation operations:
          ○​ In languages with mutable variables (like C or Python), we would expect to see
             rules involving assignment statements (e.g., name = new_value). However,
             these operational semantics lack any such rule, meaning that variables, once
             assigned, cannot be changed.

Thus, immutability is enforced by:

   ●​ Context updates in a purely additive manner: When a new binding is created, it only
      affects the current scope without altering previous bindings.

   ●​ Lack of mutable operations: The rules don't include any that would change the value
      of a bound variable.

But, if we have something like let name = 1 in let name = 2 in
name end end, are we not changing name?
It seems like we're "changing" the variable name, but what you're observing here is shadowing
rather than mutation. In immutable semantics, each let introduces a new binding for the
variable within its own scope, temporarily hiding or shadowing the previous binding without
actually changing it.

Let’s break down the example:

let name = 1 in
  let name = 2 in
    name
  end
end

Step-by-step evaluation:

   1.​ Outer let name = 1:
           ○​ This binding introduces name = 1 in the outer context. The environment is now
              C = {name: 1}.
           ○​ Inside this let, we have another let expression to evaluate.
   2.​ Inner let name = 2:
           ○​ Within the body of the outer let, a new let introduces name = 2.
           ○​ This does not modify the outer name = 1 binding. Instead, it creates a new
              binding for name that shadows the previous one, so within the scope of this
              inner let, name refers to 2.
           ○​ The environment inside this inner scope is C + {name: 2}.
   3.​ Evaluating the inner name:
           ○​ The expression name in this inner block refers to the most recent binding, which
             is name = 2. Therefore, the result of this inner let expression is 2.
   4.​ Back to the outer scope:
          ○​ After the inner let finishes, we go back to the outer scope, where the original
              binding name = 1 still exists. The inner binding of name = 2 is now discarded,
              and the environment returns to C = {name: 1}.
           ○​ The final name in the outer scope now refers to 1.

Key Insight: No Mutation, Only Shadowing

This example shows shadowing rather than mutation. The name in the outer let is never
changed. Each let creates a new, independent binding that exists only within its own scope.
Once you exit that scope, the previous binding remains intact.

In languages with mutable variables, this situation would involve actual modification (mutation)
of the name variable. However, in languages with immutable semantics like SML/NJ, variable
bindings are fixed once they are made. New bindings can temporarily shadow old ones, but they
never modify them.

So, what would the semantics with actual mutable variables look like?
In this case, we'd need rules that allow a variable's value to be updated (mutated) after its initial
binding. With immutable variables, we create new bindings in new scopes (shadowing).
With mutable variables, we directly change the value associated with a variable in the current
environment. In mutable semantics, we'd introduce a rule for assignment. This rule would
update the value of a variable that has already been declared, unlike shadowing where a new
binding is created. Let’s go through what this would look like.

For example:

   ●​ C(name) = ℓ1: Variable name is bound to location ℓ1.
   ●​ S(ℓ1) = 5: The value stored at location ℓ1 is 5.

Why are new stores created during the evaluation of expressions? For
instance, when evaluating addition, we go from S0 to S1 and then S2.
The changes in the store across different steps in the operational semantics, as depicted in the
image, can indeed be described as side effects.

In programming language semantics:

   ●​ Side effect refers to any change in the state of the program that persists beyond the
      local scope of an expression or function. This includes things like modifying variables,
      writing to memory, printing to the console, or updating files.
   ●​ Pure expressions (without side effects) always return the same value for the same
      inputs and don't alter any external state. In contrast, an expression that has side effects
      may return a different result or alter the state of the system (like memory or variables)
      each time it is evaluated.

In your operational semantics:

   ●​ Evaluating an expression (like a sum) produces new stores at each step (e.g.,
      S0→S1→S2). This shows that the evaluation of expressions can modify the store, which
      is the state of the program. Such modifications are side effects because the state (store)
      is globally affected by the operation.
   ●​ For example, in an assignment operation (name := e), evaluating e changes the store
       by updating the memory location bound to name, producing a new store. This
       modification is a side effect of the assignment.

These transformations of the store are side effects, since they involve changes to the global
state of the program, and those changes persist and can influence the future execution of the
program.

This seems to be the default semantics of C. Does C have the notion of
immutable variable names?
C does not explicitly distinguish between mutable and immutable variables in the same way
languages like Kotlin, Scala, or SML do because of its historical roots and design philosophy.

Here’s why:

1. C’s Historical Context and Simplicity

C was designed in the early 1970s as a systems programming language to be simple, fast, and
efficient. The primary goal was to give programmers direct control over the hardware,
particularly in writing operating systems like Unix. This led to a focus on:

   ●​ Low-level memory management.

   ●​ Flexibility in controlling data storage and manipulation.

In this context, immutability was not a priority. Instead, C focused on mutable variables and
pointers, allowing programmers to change values as needed for system-level operations. The
idea of distinguishing variables by immutability vs mutability (as a language-level construct)
wasn't as important as providing low-level access to memory.

2. Pointer-Based Mutability

C relies heavily on pointers, which allow direct manipulation of memory. In C, a variable can be
reassigned or modified freely unless explicitly declared as const. The use of pointers and
direct memory manipulation provides a level of mutability that was seen as more important than
strict immutability.

For example:

int x = 10;
x = 20; // mutable by default

Here, x is mutable by default, and nothing prevents it from being reassigned.

3. The const Keyword for Immutability

While C does not enforce immutability by default, it does provide the const keyword, which
allows a variable to be declared as immutable (read-only). However, the use of const is
optional and not as strongly enforced or idiomatic as in languages like Kotlin, Scala, or SML.

For example, in C:

const int y = 10;
y = 20; // Error: assignment of read-only variable ‘y’

This is C's way of providing immutability, but it’s something the programmer has to opt into,
rather than the language making it a fundamental distinction between val and var like Kotlin or
Scala.

4. Flexibility and Performance Focus

C’s design philosophy centers on giving developers flexibility and control over their programs.
Adding immutability at the core language level would introduce constraints that go against C’s
ethos of letting the programmer decide how memory and values should be handled. Because C
is used in performance-critical applications (e.g., OS development, embedded systems),
mutability by default aligns with the need for efficiency and control.

5. Modern Languages Evolve from C

Languages like Kotlin, Scala, Rust, and even SML have evolved over time, building upon ideas
like immutability that became more prominent in software design for reliability, safety, and
concurrency. These newer languages recognize the benefits of distinguishing between mutable
and immutable variables at the language level:

   ●​ Concurrency: Immutable data structures prevent race conditions and make parallel
      processing easier.
   ●​ Safety: Immutable variables reduce unintended side effects, making code easier to
      reason about and less error-prone.

C's design predated many of these concerns, and while it's possible to simulate immutability
with const, it's not enforced in the same manner as more modern languages.

Summary

C doesn’t make a strict distinction between mutable and immutable variables because:

   ●​ It was designed with simplicity and flexibility in mind, focusing on performance and
      low-level control.
   ●​ Immutability wasn’t a key concern during its development.
   ●​ It uses the const keyword for immutability, but this is optional and not central to the
      language.

Newer languages evolved with the goal of safety, concurrency, and immutability, thus making
mutability vs. immutability a central part of their design.

Can you implement a Python interpreter for the language with mutable

Let's implement these semantics in our existing Python code, which currently handles let
bindings but not mutable variables.

Here's an overview of the steps needed to extend your code:

   1.​ Introduce a Store class to manage memory locations (store) that map locations to
       values.
   2.​ Modify the Let construct to allocate memory locations for variables and add them to
       the store.

   3.​ Introduce an Assign class for the assignment operation name := e.
   4.​ Update the eval methods to manage both the environment (which maps variables to
       memory locations) and the store (which holds the actual values in memory).

Implementation Plan:

1. Store Class:

The store will hold the mutable state (like a dictionary) that maps memory locations to values.
Each variable will get a fresh memory location when it’s introduced.

class Store:
    def __init__(self):
        self.store = {}
        self.next_loc = 0

     def allocate(self, value):
         loc = self.next_loc
         self.store[loc] = value
         self.next_loc += 1
         return loc

     def update(self, loc, value):
         if loc in self.store:
             self.store[loc] = value
         else:
             raise KeyError(f"Location {loc} not found in store.")

     def lookup(self, loc):
         return self.store[loc]

     def __repr__(self):
         return str(self.store)

2. Modify the Let Expression:

When creating a new variable, we will allocate a fresh memory location for it, store its initial
value, and update the environment to map the variable name to this location.

class Let(Expression):
    def __init__(self, name, exp_def, exp_body):
        self.name = name
        self.exp_def = exp_def
        self.exp_body = exp_body

     def eval(self, env, store):
         # Evaluate the expression to get the initial value
         e0_val = self.exp_def.eval(env, store)
         # Allocate a fresh location in the store for the variable
         loc = store.allocate(e0_val)
         # Create a new environment where 'name' maps to this location
         new_env = dict(env)
         new_env[self.name] = loc
         # Evaluate the body of the let expression in the new env:
         return self.exp_body.eval(new_env, store)

3. Add the Assign Class:

This new class will handle assignments (name := e). It looks up the variable’s memory
location from the environment, evaluates the expression to get a new value, and updates the
store at that location.

class Assign(Expression):
    def __init__(self, name, exp):
        self.name = name
        self.exp = exp

     def eval(self, env, store):
         # Look up the location associated with 'name'
         if self.name in env:
             loc = env[self.name]
             # Evaluate the expression to get the new value
             new_val = self.exp.eval(env, store)
             # Update the store at this location
             store.update(loc, new_val)
             return new_val
         else:
             sys.exit(f"Undefined variable {self.name}")

4. Modify Var and Num Classes:

We need to modify the Var class to look up the value from the store using the memory location
found in the environment.

class Var(Expression):
    def __init__(self, name):
        self.name = name

     def eval(self, env, store):
         # Check if the variable exists in the environment

          if self.name in env:
              loc = env[self.name]
              # Look up the value from the store
              return store.lookup(loc)
          else:
              sys.exit(f"Undefined variable {self.name}")

class Num(Expression):
    def __init__(self, num):
        self.num = num

     def eval(self, env, store):
         return self.num

Let’s write a simple example to show how mutable variables work:

if __name__ == "__main__":
    # Create an empty environment and store
    env = {}
    store = Store()

     # let x = 5 in x := 10 end
     let_exp = Let("x", Num(5), Assign("x", Num(10)))

     # Evaluate the let expression
     result = let_exp.eval(env, store)

     # Print the store after the assignment
     print(f"Final store: {store}")

Breakdown:

   ●​ The Store class manages memory locations and stores variable values.
   ●​ The Let expression allocates a memory location for a variable and updates the
      environment and store.
   ●​ The Assign expression updates the value of a variable by modifying the store.

This implementation follows the operational semantics that we wrote, where:

   ●​ The environment C holds variable names mapped to memory locations.
   ●​ The store S holds values at those memory locations.
   ●​ Assignments update values in the store, while variable lookups retrieve values from it.

Who invented operational semantics?
Operational semantics, a fundamental approach to formally defining the behavior of
programming languages, was invented by Gordon D. Plotkin in the early 1980s. His seminal
paper, "A Structural Approach to Operational Semantics" (1981), laid the foundation for the
systematic and structured study of operational semantics as we know it today.

Gordon Plotkin's Role

   ●​ "A Structural Approach to Operational Semantics" (1981):
         ○​ Plotkin introduced the notion of defining the semantics of programming
             languages by specifying how individual language constructs execute.
         ○​ The framework focuses on small-step semantics (describing the individual
             steps of computation) and big-step semantics (describing how expressions are
             evaluated to values in a single step).
         ○​ He emphasized a structured and rule-based approach, using inference rules
             and inductively defined judgments, which became a standard in the field.

Precursors and Related Work

While Plotkin formalized operational semantics, earlier influences contributed to its
development:

   1.​ John McCarthy (1960s):​

          ○​ Developed formal semantics for Lisp in terms of recursive functions, providing
              an early example of describing program behavior in mathematical terms.
   2.​ Peter Landin (1960s):​

          ○​ Introduced ideas of operational reasoning in his work on abstract machines and
             the SECD machine, a precursor to Plotkin's structured operational approach.
   3.​ Dana Scott and Christopher Strachey (1960s–1970s):​

           ○​ While primarily known for denotational semantics, their work influenced the
              formalization of programming languages and inspired alternative semantic
              frameworks.

Gordon D. Plotkin: A Short Bio

Gordon David Plotkin is a prominent computer scientist and logician known for his
groundbreaking work in programming language theory, operational semantics, and formal

methods. Born in Scotland in 1946, Plotkin earned his Ph.D. from the University of Edinburgh in
1972 under the supervision of Rod Burstall. His dissertation focused on lambda calculus and
its applications in programming languages, laying the foundation for his later work in
semantics.

Plotkin became a professor at the University of Edinburgh, where he remained a central figure
in the School of Informatics. His influence extends beyond academia, as his research has
deeply shaped the understanding of programming languages and computational logic. Plotkin
has received numerous accolades, including a fellowship from the Royal Society, recognizing
his outstanding contributions to theoretical computer science.

Contributions to Computer Science

1. Structural Operational Semantics (SOS)

   ●​ Plotkin’s "A Structural Approach to Operational Semantics" (1981) introduced a
      systematic, rule-based framework for defining programming language behavior.
   ●​ SOS became a cornerstone in programming language theory, influencing how
      researchers and practitioners define and analyze language semantics.

2. Denotational Semantics and Domain Theory

   ●​ Plotkin made significant contributions to denotational semantics, working on ways to
      mathematically model the meaning of programs.
   ●​ He explored the connections between domain theory (developed by Dana Scott) and
      operational reasoning, deepening the understanding of how programs compute.

3. Full Abstraction

   ●​ Plotkin worked on the concept of full abstraction, particularly for programming
      languages like PCF (Programming Computable Functions). Full abstraction ensures that
      the semantic model captures all observable behaviors of a program.

4. Logic in Computer Science

   ●​ He contributed to the development of logical frameworks and their applications in
      computer science, including reasoning about programs and formal verification.

5. Abstract Machines and Lambda Calculus

   ●​ Plotkin analyzed the lambda calculus and its relation to programming languages,
      particularly regarding call-by-name and call-by-value evaluation strategies.
   ●​ His work informed the design of abstract machines and the operational reasoning used
      in compilers and interpreters.

6. Bisimulation and Process Calculi

   ●​ Plotkin collaborated on research involving bisimulation, a key concept in process calculi
      and concurrency theory. This work helped formalize notions of equivalence between
      computational processes.

7. Probabilistic and Quantum Computing

   ●​ Later in his career, Plotkin explored probabilistic and quantum models of computation,
      contributing to the understanding of how these paradigms relate to traditional
      computation.

8. Influence on Programming Languages

   ●​ His research influenced the design and semantics of programming languages like ML,
      Haskell, and others, particularly in areas like type systems, evaluation strategies, and
      compiler correctness.

Legacy

Gordon Plotkin's work has shaped the theoretical foundations of programming languages and
computational systems. His pioneering contributions, particularly in operational semantics,
remain a cornerstone of computer science education and research, making him one of the most
influential figures in the field.
