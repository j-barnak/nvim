Consider the program below. Where do you think each variable will be
allocated?
This program shows local and global variables defined in C:

#include <stdio.h>

int global_var = 17;

int fun(int parameter) {
  printf("%p, %lu, parameter\n", &parameter, (size_t)&parameter % 100);
  int local_fun = parameter + 1;
  printf("%p, %lu, local_fun\n", &local_fun, (size_t)&local_fun % 100);
  return 7 * local_fun;
}

int main() {
  printf("%p, %lu, global_var\n", &global_var, (size_t)&global_var % 100);
  int local_main = global_var + 13;
  printf("%p, %lu, local_main\n", &local_main, (size_t)&local_main % 100);
  global_var = fun(5 * local_main);
  return 3 * global_var;
}

In this C program, the variables will be allocated in different sections of memory, depending on
whether they are global or local, and whether they belong to a function. Here's where each
variable will be allocated:

1. Global Variables:

   ●​ global_var:
           ○​ Location: The global variable global_var is allocated in the data segment
              (specifically in the initialized data segment). This is because it is defined outside
              of any function and initialized with a value (17).
           ○​ Lifespan: global_var persists for the lifetime of the program (from startup to
              program termination).

2. Local Variables (Function Parameters and Function Local Variables):

   ●​ parameter (in fun function):

          ○​ Location: This is a parameter of the fun function, which is treated like a local
              variable. It will be allocated in the stack frame of fun. Each time fun is called, a
              new stack frame is created, and parameter is stored in that frame.
         ○​ Lifespan: It only exists while fun is executing, and its memory is freed once the
            function returns.
   ●​ local_fun (in fun function):
          ○​ Location: This is a local variable in the fun function, so it will also be allocated
              in the stack frame of fun. Like parameter, it will exist only during the execution
              of fun and will be destroyed afterward.
         ○​ Lifespan: It exists while fun is executing and is destroyed when the function
            returns.
   ●​ local_main (in main function):
          ○​ Location: This is a local variable in the main function, so it will be allocated in
              the stack frame of main. Since main is called only once and lasts for the
             program's duration, local_main will stay in memory for as long as main is
             running.
          ○​ Lifespan: It exists for the duration of the main function, which typically means
             until the program terminates.

Summary of Memory Allocation:

   ●​ Data Segment (Initialized):
         ○​ global_var
   ●​ Stack (Local Variables and Parameters):
         ○​ parameter (in fun)
          ○​ local_fun (in fun)
          ○​ local_main (in main)

Execution Flow:

   ●​ global_var is initialized in the data segment.
   ●​ local_main is allocated on the stack when main starts, and its value depends on
       global_var.
   ●​ When fun is called from main, parameter and local_fun are allocated in the stack
       frame of fun.
   ●​ After fun returns, the stack frame of fun is destroyed, and the result is stored back into
       global_var.

Each time you print the address and remainder, you are observing the addresses where these
variables are stored in memory, and the modulo operation (% 100) provides a convenient way
to distinguish memory locations by checking the last two digits of the address.

What is a stack frame?
The stack frame (also known as activation record) is a section of memory that holds local
variables, function parameters, return addresses, and other data that a function uses during its
execution. When a function is called, a new stack frame is created, and when the function
finishes, that stack frame is destroyed. The stack is called a "stack" because it's like a stack of
plates: each function's data gets "pushed" onto the stack when the function is called, and
"popped" off the stack when the function returns.

Key Characteristics:

   ●​ Automatic Memory Management: The stack grows and shrinks automatically as
      functions are called and return. When a function is called, its frame is pushed onto the
      stack. When the function returns, the frame is popped off the stack.
   ●​ Fast Access: Accessing data on the stack is very fast because the stack pointer (sp)
      keeps track of where the top of the stack is.
   ●​ Limited Size: The stack is limited in size (typically a few megabytes), and deep
      recursion or allocating large amounts of data on the stack can lead to a stack overflow.
   ●​ Lifetime: Variables in the stack frame exist only as long as the function is running. Once
      the function returns, these variables are no longer accessible, and the memory is
      reclaimed.

Example:

In the fun function of your C program, both parameter and local_fun are allocated in the
stack frame for fun. When fun is called, space is allocated on the stack for these variables,
and when fun returns, this space is reclaimed.

And what is a data segment, where the global variable is located?
The data segment is a section of memory used to store global and static variables. These
variables persist for the entire lifetime of the program.

The data segment is divided into two parts:

   ●​ Initialized Data Segment: This stores global and static variables that are initialized with
      a value at the start of the program (e.g., int global_var = 17;).
   ●​ Uninitialized Data Segment (BSS): This stores global and static variables that are not
      explicitly initialized (e.g., int uninitialized_global_var;). They are initialized to
      zero by default.

Key Characteristics:

   ●​ Global and Static Variables: Global variables (like global_var in your program) and
      static variables (variables declared with the static keyword inside a function or
      globally) reside in this segment.
   ●​ Lifetime: Variables in the data segment exist for the entire duration of the program. They
      are initialized when the program starts and persist until it ends.
   ●​ Not Automatically Managed: Unlike stack memory, which is automatically managed,
      data in the data segment remains allocated for the entire run of the program, whether or
      not it’s actively being used.

Example:

In your C program, global_var is allocated in the initialized data segment because it’s a
global variable with an initial value (17). It exists throughout the program's execution and its
memory is not released until the program ends.

It seems that the program's memory is divided in multiple segments then?
That's correct. A typical program's memory is divided into the following segments:

   1.​ Text Segment: Contains the actual compiled code (machine instructions).
   2.​ Data Segment:
          ○​ Initialized Data: Stores initialized global and static variables.
          ○​ Uninitialized Data (BSS): Stores uninitialized global and static variables (default
              initialized to zero).
   3.​ Heap: Dynamically allocated memory (using malloc, new, etc.). The heap grows
       upwards as memory is dynamically allocated.
   4.​ Stack: Stores function call information, local variables, and function parameters. It grows
       downwards as new functions are called and stack frames are created.

Why do we need to store local variables on a stack? Can't we allocate them
statically, like we do with global variables?
In principle, we cannot allocate local variables always at the same address (as if they were
statically allocated) in typical C programs. Local variables need to have unique addresses on
each function call, especially in recursive or reentrant functions. If local variables were statically
allocated (always at the same address), recursive calls or multiple invocations of the same
function would overwrite each other’s data. Here’s why:

   ●​ Recursion: If a function is called recursively, each instance of the function needs its own
      set of local variables. If local variables were always allocated at the same address,
      recursive calls would share the same memory for these variables, leading to incorrect
      behavior because values would be overwritten.

   ●​ Reentrancy: Functions in C can be called concurrently (e.g., via threads). If local
      variables were statically allocated at the same address, multiple concurrent calls would
      overwrite each other’s data, leading to race conditions.

Could you give an example of a function that would fail if local variables
were statically allocated?
Yes. Consider, for instance, the program below:

#include <stdio.h>

int st_fact(int n) {
  static int result = 1;
  result = n;
  result *= (result <= 1) ? 1 : st_fact(result - 1);
  return result;
}

int dy_fact(int n) {
  int result = 1;
  result = n;
  result *= (result <= 1) ? 1 : dy_fact(result - 1);
  return result;
}

int main(int argc, char** argv) {
  for (int i = 2; i < 2 * argc; ++i) {
    printf("%d: st_fact = %d, dy_fact = %d\n", i, st_fact(i), dy_fact(i));
  }
  return 0;
}

The reason your program produces different results for the static (st_fact) and dynamic
(dy_fact) versions of the factorial function lies in how static variables behave compared to
dynamically allocated local variables.

Key Differences in Behavior:

   1.​ Static Allocation (st_fact):
           ○​ The static int result = 1; inside st_fact ensures that the variable
              result retains its value between function calls. Once initialized, the value of
              result persists across multiple invocations of st_fact, and it is shared across
              all calls to this function.
           ○​ Why this affects the result: When st_fact is called for n = 2, it sets result
              = 2. The next time st_fact is called (for n = 3), result still holds the value

               from the previous call (result = 2), and this value is used as the base for the
               calculation instead of resetting to 1. As a result, once st_fact sets result to a
               value less than or equal to 1, the recursive calls always short-circuit (returning 1),
               which is why you see 1 as the output for st_fact after the first call.
   2.​ Dynamic Allocation (dy_fact):
           ○​ The int result = 1; in dy_fact creates a new variable result on the
               stack for each call to dy_fact. This ensures that the variable result starts
               fresh (with result = 1) for every function invocation.
           ○​ Why this gives correct results: Since each call to dy_fact initializes result
              independently, the recursion proceeds as expected. Each recursive call
              computes result based on the correct value of n passed into the function.
              Therefore, the function behaves correctly and returns the correct factorial values.

Example Walkthrough:

Let’s go through a specific call to see the difference more clearly:

First call: st_fact(2) and dy_fact(2)

   ●​ st_fact(2):
           1.​ static int result = 1; → Initializes result (but only the first time the
               function is called).
           2.​ result = 2; → result is now 2.
           3.​ Recursively calls st_fact(1) → Since n == 1, assigns 1 to result.
           4.​ Returns 1.
   ●​ dy_fact(2):
           1.​ int result = 1; → A new result variable is created with an initial value of
               1.
           2.​ result = 2; → Updates result to 2.
           3.​ Recursively calls dy_fact(1) → result = 1; (from initialization in
               dy_fact(1)).
           4.​ Returns 2 * 1 = 2.

Subsequent call: st_fact(3) and dy_fact(3)

   ●​ st_fact(3):
           1.​ result still holds the value 1 from the previous call (st_fact(2)).
           2.​ result = 3; → Updates result to 3.
           3.​ Recursively calls st_fact(2) → st_fact(2) returns 1 because result is
               still 1.
           4.​ Returns 1.

   ●​ dy_fact(3):
           1.​ A new result variable is created with an initial value of 1.
           2.​ result = 3; → Updates result to 3.
           3.​ Recursively calls dy_fact(2) → dy_fact(2) returns 2.
           4.​ Returns 3 * 2 = 6.

Conclusion:

   ●​ Static variables are shared across function invocations and retain their values between
      calls, which can lead to unexpected behavior in recursive functions like st_fact. The
      static variable doesn’t reset, leading to incorrect results in this case.
   ●​ Dynamic variables are reallocated on the stack for each function call, ensuring that
      each call has its own fresh storage for local variables. This allows recursive functions to
      work correctly, as seen in dy_fact.

The static version leads to incorrect results because the static variable persists across calls
and causes the recursive function to behave improperly after the first call.

So, if I am compiling a language that does not support recursion, then I
could allocate all the local variables statically?
Well, more or less. In addition to recursion, indirect function calls (such as those made
through function pointers) present a challenge for static allocation of local variables. We will talk
about that later. But, in the absence of recursion and indirect calls, you can happily allocate all
the variables statically. This is because, without recursion, there is no risk of multiple active calls
to the same function, meaning each function only ever needs one instance of its local variables.

Why Static Allocation Works Without Recursion:

In non-recursive programs, each function is called, executed, and returns before any other calls
to the same function can happen. Since there is no chance of re-entering a function while it is
still active (as recursion would allow), the program only ever needs one copy of each function's
local variables.

This means that:

   ●​ No stack is required for local variable storage.
   ●​ Each function's variables can be placed in fixed memory locations known at compile
      time, typically in a global or static memory area.

Fortran and COBOL in Their Early Days:

   ●​ Fortran: Early versions of Fortran (before Fortran 90) did not support recursion.
      Therefore, all local variables could be statically allocated in memory, just as you

      described. This design allowed for simpler and more efficient memory management, as
      there was no need to maintain a call stack for local variables.
   ●​ COBOL: Early COBOL programs also lacked recursion support. The language was
      primarily used for business applications, and recursion was not a common pattern in
      such applications at the time. This allowed COBOL compilers to allocate all variables
      statically, as the memory footprint of the program could be determined at compile time.

Key Benefits of Static Allocation:

   ●​ Simplicity: Without recursion, static allocation simplifies both the compiler's task and the
      runtime's memory management. There is no need to allocate and deallocate memory for
      variables dynamically, and there is no stack frame to manage.
   ●​ Efficiency: Static allocation can lead to faster execution, as variables are accessed
      directly via known memory addresses, avoiding the overhead of stack manipulation.

Limitations:

   ●​ Lack of recursion: Since each function’s local variables are statically allocated,
      recursion is impossible without risk of overwriting previous values.
   ●​ Limited parallelism: Static allocation also restricts concurrent execution of the same
      function (e.g., in multithreading), as all threads would share the same variable memory,
      leading to race conditions unless carefully managed.

Modern Static Allocation and Recursion:

While modern languages support recursion and dynamically allocate local variables on the
stack, some static languages (e.g., embedded systems or low-level programming in C) still use
global or static variables when recursion is not involved. In such cases, you can sometimes
manually control static allocation for performance reasons, but this generally requires careful
programming.

What's an indirect call? Why do they complicate static allocation?
An indirect function call is a call through a pointer. For instance, consider the program below:

#include <stdio.h>

int foo(int x) {
  return x + 1;
}

int bar(int x) {
  return x * 2;
}

int call_fun(int (*fptr)(int), int val) {

    return fptr(val);
}

int main() {
  printf("%d\n", call_fun(foo, 3));                        // calls foo: should return 4
  printf("%d\n", call_fun(bar, 3));                        // calls bar: should return 6
}

When calling call_fun(foo, 3) and call_fun(bar, 3), the exact function (foo or bar)
being called is determined at runtime via the function pointer fptr. Therefore, the local
variables and return addresses for foo and bar can't be statically allocated at compile time, as
the target function is only known during execution.

Indirect Function Calls and Static Allocation:

     1.​ Unpredictable Call Targets:
            ○​ In the case of indirect function calls (where the function to be called is determined
               at runtime, such as through function pointers), the exact function being called
               might not be known at compile time.
            ○​ If you don't know the specific function in advance, you can't pre-allocate memory
               for its local variables because multiple different functions could be called at the
               same point in the code, each requiring different local variable storage.
     2.​ Dynamic Call Context:
            ○​ Indirect function calls often require managing dynamic call contexts, which
               include the return address, the function's parameters, and its local variables.
               Since the target function is not known until runtime, you can't assign a fixed
               memory location to store its context (parameters and return address).
            ○​ For example, the return address must be stored dynamically based on the
               specific function being called. In static allocation, there's no way to guarantee a
               unique return address location for each function when the call is indirect.
     3.​ Function Pointers and Recursion:
            ○​ If a function is called through a pointer, or if recursion is involved (where a
               function calls itself), you can't simply reuse the same memory locations for the
               local variables and return addresses of each function call.
            ○​ Example: Consider a function pointer calling fun1() in one case and fun2() in
               another case. Each function has different local variables, and if these are
               statically allocated, calling fun1() would overwrite the memory used by
                fun2(), leading to incorrect behavior.

Why Static Allocation Fails with Indirect Calls:

With static allocation, the memory layout for each function is determined at compile time. If
function pointers or indirect calls are involved, the compiler can't determine at compile time:

   ●​ Which function will be called.
   ●​ Where to store the return address.
   ●​ How to pass parameters (since parameter types and locations might differ across
      functions).
   ●​ How to handle local variables (which could be of different types and sizes for different
      functions).

Because of these unknowns, dynamic allocation using a stack (or heap, in some cases) is
necessary. This allows:

   ●​ Dynamic storage of return addresses: Each function call, whether direct or indirect,
      needs its own space to store the return address.
   ●​ Dynamic allocation of parameters and local variables: Each function call must have
      its own memory allocated for its parameters and local variables, especially when
      recursion or function pointers are involved.

Static Allocation Works Only Without Indirect Calls:

In languages that don't allow function pointers or indirect calls, the absence of dynamic control
over which function gets called makes it easier to allocate local variables statically. But as soon
as indirect calls are introduced, dynamic memory management becomes necessary to handle
the flexibility that such calls provide.

Fortran and COBOL:

   ●​ Early versions of Fortran and COBOL also avoided indirect calls through function
      pointers, which further enabled static allocation.
   ●​ Without function pointers or recursion, the call graph of the program is fully known at
      compile time, making static allocation straightforward.

Conclusion:

   ●​ In languages without recursion or indirect function calls, static allocation is feasible
      because the memory layout of function calls is fully known at compile time.
   ●​ However, if a language supports indirect function calls (e.g., through function
      pointers), recursion, or closures, dynamic memory management (typically using a
      stack) is necessary to properly handle the flexible call structure and variable lifetimes.

You mentioned a "call graph". What's that?
A call graph is a directed graph that represents the calling relationships between functions in a
program. Each node in the graph represents a function, and each edge (directed arrow) from
one node to another indicates that the first function calls the second function during execution.

Key Concepts of a Call Graph:

  ●​ Nodes: Represent functions in a program.
  ●​ Edges: Directed edges indicate a call from one function to another. If function A calls
     function B, there will be an edge from the node representing A to the one representing B.

Types of Call Graphs:

  1.​ Static Call Graph:
         ○​ Constructed by analyzing the source code.
         ○​ Represents all possible calls between functions based on the code structure.
         ○​ Typically does not account for dynamic or indirect calls, as these cannot be
             determined by just analyzing the code without running the program.
  2.​ Dynamic Call Graph:
         ○​ Constructed by tracking the actual calls made during the execution of the
             program.
         ○​ Can capture indirect calls (e.g., through function pointers or virtual methods),
             recursion, and conditional calls.
         ○​ Depends on the specific inputs and paths taken during execution.

Why Call Graphs Are Important:

  1.​ Program Analysis:
         ○​ Call graphs are a fundamental tool in compiler design, program optimization,
            and static analysis.
         ○​ They help in determining the dependencies between functions and understanding
            how the execution flows from one function to another.
  2.​ Memory Management:
         ○​ As we discussed earlier, static allocation of variables is possible if the call graph
            is acyclic (i.e., there are no recursive calls) and all function calls are known at
            compile time (no indirect calls). If the call graph contains cycles (indicating
            recursion), the program must use dynamic allocation, typically via the stack.
  3.​ Performance Optimization:
         ○​ Call graphs help in inlining functions (replacing a function call with the
            function’s body), identifying hot spots (frequently called functions), and dead
            code elimination (removing unused functions).
  4.​ Recursion Detection:
         ○​ By analyzing the call graph, compilers or developers can detect recursive calls if
            a node has a path back to itself, indicating that the function can call itself directly
            or indirectly.
  5.​ Code Coverage:
         ○​ Call graphs are useful in testing to check how much of the code is exercised by a
            particular set of inputs or during specific tests. Functions that are never called
            can be identified for further testing or removal.

Call Graph Cycles and Recursion:

A cycle in a call graph means that a function can eventually call itself, either directly or indirectly,
leading to recursion. When recursion is detected, the compiler knows that dynamic memory
management (via stack frames) is required for local variables and return addresses.

How Call Graphs Relate to Optimization:

    ●​ Tail Call Optimization: When compilers recognize tail recursion (a function calling itself
       as its last operation), they can optimize the recursion by reusing the same stack frame,
       avoiding the overhead of a new call. Analyzing the call graph can help identify such
       cases.
    ●​ Inlining: Inlining decisions—replacing function calls with the body of the function—can
       be guided by call graph analysis to improve performance for small or frequently called
       functions.

Is it possible to use clang and LLVM's opt to see a call graph?
Yes, you can use Clang and LLVM's opt tool to generate and visualize a call graph of a
program. Here's how you can do it:

Steps to Generate and View a Call Graph:

1. Compile the C Program to LLVM Intermediate Representation (IR)

First, use Clang to compile your C program into LLVM IR, which is necessary to analyze the
program using LLVM's optimization tools (opt).

clang -S -emit-llvm program.c -o program.ll

This will generate the LLVM IR for the C program in a file called program.ll.

2. Use opt to Generate the Call Graph

LLVM provides the -dot-callgraph option in the opt tool, which outputs the call graph in
DOT format. Here's how to run it:

opt -dot-callgraph program.ll

This command will generate a file named callgraph.dot (or several files if there are multiple
functions).

3. Visualize the Call Graph

To visualize the call graph, you can use a graph visualization tool like Graphviz. Graphviz's dot
command can convert the .dot file into an image.

dot -Tpng callgraph.dot -o callgraph.png

This will create an image file (callgraph.png) containing the call graph that you can view.

4. Examine the Output

Once you have generated the image, you can open it to explore the function calls in your
program. The nodes represent the functions, and the directed edges show which functions call
others.

Let's produce code for static functions. What are the assumptions that we
can make?
There are a number of assumptions that will simplify our job:
   1.​ All the functions have different names. This is valid, for our programming language is
       totally static.
   2.​ We have an infinite surplus of virtual registers. That means that we don't need to worry
       about saving the state of registers.
   3.​ Every function has only one formal parameter. And all the parameters of functions have
       different names.
Under these assumptions, code generation becomes relatively easy. See below the code
generator for function definitions:

def visit_named_fn(self, exp, prog):
    # The address of the function is known and static.
    func_label = self._convert_name_to_addr(exp.name)
    prog.add_label(func_label)

    # Let's assume that all the functions have different names.
    # That's ok, otherwise the program would not compile due to
    # a type resolution conflict. Let's create a virtual register
    # to hold the function's name:
    return_addr = f"{exp.name}_ret_addr"

    # Save the return address. Assume it's passed through "ra"
    # Thus: memory[return_addr] = value(ra)
    prog.add_inst(AsmModule.Add(return_addr, "ra", "x0"))

    # Remember: Every function has only one parameter.
    # Get the parameter, which we assume to be in a0:
    prog.add_inst(AsmModule.Add(exp.formal, "a0", "x0"))

    # Generate the function body:
    return_var = exp.body.accept(self, prog)

    # Place the return value in a0:
    prog.add_inst(AsmModule.Add("a0", return_var, "x0"))

    # Jump back to the caller:
    prog.add_inst(AsmModule.Jalr("x0", return_addr))

   ●​ Function Labeling: Functions are still statically labeled using
      prog.add_label(func_label). To get the address of this label, we assume that we
      have a function that translates names into addresses, e.g.,
      self.convertname_to_addr(exp.name).
   ●​ Return Address in Virtual Register: The return address is saved in a virtual register
      (return_addr), which is used later for returning to the caller.
   ●​ Parameter Handling: Since there is a single parameter, it’s passed in the a0 register
      and copied into a virtual register representing the parameter name.
   ●​ Return Address: The Jalr instruction is used to return to the caller via the saved return
      address in the virtual register.

And below we have the code generator for function applications:

def visit_named_app(self, exp, prog):
    # Generate code for the actual parameter of the call:
    param_value = exp.actual.accept(self, prog)
    # Pass parameter in a0
    prog.add_inst(AsmModule.Add("a0", param_value, "x0"))

    # Static jump to the function. Notice that we need the name of the
    # function to be available at this point. This code generation approach
    # would not work with indirect calls:
    func_label = self._convert_name_to_addr(exp.function.name)
    prog.add_inst(AsmModule.Jal("ra", func_label))

    # Get the return value (which will be in a0):
    ret_var = self.next_var_name()
    prog.add_inst(AsmModule.Add(ret_var, "a0", "x0"))
    return ret_var

   ●​ Parameter Passing: The parameter is computed and placed in the a0 register using the
       virtual register param_value.
   ●​ Static Function Call: The function is called using a static jump (Jal) to its label, with
       the return address saved in ra.
   ●​ Return Value Handling: The return value is copied from a0 into a virtual register
       (ret_var) for use after the function call.

Can you show an example of how that works?
Let's consider the functions inc and sqr in the figure below. They will be treated as named
functions with statically known labels, and the function application inc (sqr 4) will be treated
as two nested function calls: first calling sqr(4), then passing the result to inc.

Explanation of Generated Code:

   1.​ Function sqr:
           ○​ The parameter y is passed in the register a0. We copy it to the virtual register y.
           ○​ We compute y * y using the mul instruction and store the result in result.
          ○​ The result is moved back to a0 as the return value, and the program jumps back
             to the caller using the stored return address.
   2.​ Function inc:
           ○​ The parameter x is passed in a0. We copy it to the virtual register x.
           ○​ We compute x + 1 using the addi instruction and store the result in result.
          ○​ The result is moved to a0, and the program jumps back to the caller using the
             return address.
   3.​ Main Application:
          ○​ First, sqr(4) is called by placing 4 in a0 and jumping to sqr.
           ○​ After sqr(4) returns, the result is in a0. We immediately call inc by jumping to
               its label with the result of sqr(4) in a0.
           ○​ The final result of inc(sqr(4)) is in a0, and at this point, the program ends (or
              could perform further operations).

Summary:

This generated code respects the assumptions we made:

   ●​ No recursion or indirect function calls.
   ●​ Static function names and parameter names.
   ●​ No stack manipulation; return addresses are saved in virtual registers.

The code for both sqr and inc follows the same pattern: saving the return address, handling
the parameter, computing the result, and returning the value via a0. The main application just
chains the function calls, passing the result of sqr(4) into inc.

Is this convention of using ra to save return addresses and a0 to pass
parameters what we call the ABI?
Yes, the behavior you describe—how the return address is saved and how parameters are
passed—relates to the Application Binary Interface (ABI).

What is an ABI?

An ABI is a set of rules and conventions that define how binary programs interact at runtime. It
ensures compatibility between compiled code, libraries, and the operating system. Specifically, it
governs:

   1.​ Function Calling Conventions:
          ○​ How arguments are passed to functions (e.g., in registers like a0 or on the
             stack).
          ○​ How the return value is delivered (e.g., in a register like a0).
          ○​ Where the return address is stored (e.g., in ra).
   2.​ Register Usage:
          ○​ Which registers are caller-saved (must be preserved by the caller) and which are
              callee-saved (preserved by the callee).
   3.​ Memory Layout:
          ○​ Stack growth direction and alignment.
          ○​ Location of global and static variables.
   4.​ Binary Format:
          ○​ Details like how shared libraries are loaded and symbols are resolved.

Your Code and the ABI

If your code saves the return address in the ra register and passes parameters in a0, it is
following a specific calling convention—a subset of the ABI. In the context of RISC-V, for
example:

   ●​ The return address is typically stored in ra (x1).
   ●​ The first argument is passed in a0 (x10).
   ●​ If a function needs to return a value, it's usually placed in a0 as well.

This means your code adheres to a calling convention compatible with the RISC-V ABI, which
ensures that your functions interact correctly with other code that follows the same ABI.

Why is the ABI Important?

When all components of a program (libraries, OS, etc.) follow the same ABI:

   ●​ Compiled code from different sources can interoperate seamlessly.
   ●​ Programs can call system functions and libraries without needing recompilation.

the importance of an ABI. Here’s how it works in this context:

Lua and C Interoperability

Lua uses the C API to enable interaction between Lua scripts and C functions. This API relies
on a shared ABI, ensuring the Lua interpreter and compiled C libraries can communicate
seamlessly.

   1.​ Lua Calling C:​

          ○​ When Lua calls a C function, it passes arguments through a predefined

          ○​ The C function then performs its operations, places the return values back on the

   2.​ C Calling Lua:​

           ○​ C can also call Lua functions using the same stack mechanism. The C code

ABI’s Role in this Interoperability

The shared ABI ensures:

   ●​ Function Calls: The Lua interpreter, written in C, follows the same calling convention as

   ●​ Data Representation: Lua's stack and data structures (like Lua values) are consistent in

   ●​ Binary Compatibility: Precompiled Lua interpreters and C libraries can interoperate as

Implementing activation records for a language where everything is
statically allocated is very simple, right?
Yes, that's correct! An activation record (also known as a stack frame) is a block of memory
used to manage the data a function (or procedure) needs during its execution. It is typically
created whenever a function is called, and it stores all the information required to manage the
execution of that function, such as parameters, local variables, return value, and the return
address.

In a language where everything is statically allocated, the structure of an activation record
would indeed be simpler. Here's a breakdown of the typical contents of an activation record in
such a language:

Activation Record Contents:

   1.​ Parameters (Arguments):
          ○​ The values passed to the function (or procedure) by the caller are stored here.
          ○​ These parameters are often placed in a specific order, depending on the calling
              convention of the language.
   2.​ Local Variables:
          ○​ These are variables that are declared and used inside the function.
          ○​ Local variables only exist during the function's execution and are stored in the
              activation record.
   3.​ Return Value:
          ○​ The function's return value (if any) needs to be stored somewhere so it can be
              accessed by the caller after the function completes execution.
          ○​ The return value may be stored in a specific register or in a designated space
              within the activation record.
   4.​ Return Address:
          ○​ This stores the address where the program should continue after the function
              returns.
          ○​ When a function finishes executing, it uses the return address to jump back to the
              point in the program where it was called.

Statically Allocated Language:

In a statically allocated language, the memory layout is simpler because the sizes of all
variables (both local and global) and parameters are known at compile-time. There is no need
for complex memory management mechanisms like heap allocation or dynamic memory
resizing, which simplifies the structure of the activation record.

   ●​ Fixed Size: Since the size of all variables, parameters, and return values is known in
      advance, the activation record has a fixed size.

   ●​ Static Allocation: Memory for variables is allocated in a predefined memory region (like
      the data segment), rather than dynamically allocated at runtime.

Simplification in Statically Allocated Languages:

In languages with static allocation:

   ●​ You don’t need a heap or dynamic memory allocation.
   ●​ The activation record layout is predictable, fixed, and the locations of all parameters,
      local variables, and return addresses are known at compile-time.

Thus, the activation record would only need to contain:

   ●​   The parameters passed to the function.
   ●​   The local variables declared inside the function.
   ●​   The return value (if necessary).
   ●​   The return address to jump back to the caller.

In a language where everything is statically allocated, recursion might be limited or unsupported
because each function would have a fixed memory location (which could lead to overwriting of
data), and re-entrant functions would be difficult to manage.

The previous example uses "virtual registers", e.g., registers that simulate
variable names, as already discussed in a previous class. Do you
remember what a virtual register really is?
The concept of "virtual registers" is quite common in intermediate representations (IR) used by
compilers. Virtual registers are placeholders or abstract names for values that haven't been
mapped to actual machine registers yet. They are commonly used during the early stages of
compilation, particularly before Register Allocation. As an example, the instruction add
sqr_ret_add ra x0 uses a virtual register (sqr_ret_add), and two physical registers: ra
and x0.

Why Use Virtual Registers?

   1.​ Abstraction: Virtual registers allow the compiler to treat values and variables as if there
       are an infinite number of registers. This makes it easier to express computations without
       worrying about the physical limitations of the hardware (e.g., the number of registers
       available on a machine).
   2.​ Simplicity: Virtual registers make it easier to represent the semantics of a program
       during the Intermediate Representation (IR) phase. Compilers often use IRs that are
       closer to the source code (SSA, for example), where each value has its own unique
       "register" (virtual register) to simplify analysis and optimization.

   3.​ Optimization: Compilers can perform a wide range of optimizations on the code without
       needing to assign physical registers. Once optimizations are complete, the final step is to
       map the virtual registers to the real physical registers of the target machine.

Register Allocation

In the final stages of compilation, the compiler uses a process called register allocation to map
virtual registers to physical machine registers. The graph coloring algorithm is often used
here:

   ●​ Virtual registers are treated as nodes in a graph.
   ●​ An edge is drawn between two virtual registers if they are live (i.e., their values are
      needed) at the same time.
   ●​ The goal is to assign a physical register to each virtual register in a way that minimizes
      spills (where values need to be stored in memory because there aren't enough
      registers).

Examples in Common IRs:

   ●​ LLVM IR: LLVM uses a large number of virtual registers in its intermediate
      representation. It defers register allocation until later in the compilation process, after
      performing optimizations.
   ●​ SSA (Static Single Assignment): Each variable is assigned exactly once, and virtual
      registers naturally fit into this model. Register allocation is then performed to map these
      variables to physical registers.

In summary, virtual registers provide flexibility and allow compilers to focus on optimization
without worrying about hardware constraints until the final stages of code generation.

How would you generate code for anonymous functions then, assuming
that we don't have closures?
Anonymous functions, also called lambda functions or function literals, are functions that do
not have a name. They can be created dynamically, and we often pass them as arguments to
other functions. In this case, the same code generation principles apply as with named
functions, but we treat them as if they have no pre-defined name. To generate code for
anonymous functions, we need to approach it differently. The key challenge is that we can't
rely on static function names. Instead, we need to generate a unique label for each anonymous
function at runtime (during code generation). This allows us to refer to the function even though
it has no name in the source code.

Here’s how we can modify the code generation to support anonymous functions:

Steps to Generate Code for Anonymous Functions:

   1.​ Assign a Unique Label to Each Anonymous Function: For each anonymous function,
       we can generate a unique label dynamically during code generation. For example, we
       could name anonymous functions anon_func_1, anon_func_2, etc.
   2.​ Adjust Function Call Code: When calling an anonymous function, we use its
       dynamically assigned label.

Let’s modify the visit_named_fn and visit_named_app methods to work with anonymous
functions.

The new visit methods:
def visit_fn(self, exp, prog):
    """
    Generate code for an anonymous function (Fn).
    """
    # Save the address of the function in a variable:

    addr_var = self.next_var_name()

    # Generate a unique label for the anonymous function.
    # Generates a unique label like 'anon_func_1', 'anon_func_2', etc.
    func_addr = self.next_fn_label()
    prog.add_inst(AsmModule.Addi(addr_var, "x0", func_addr))

    func_after = self.next_fn_label()
    prog.add_inst(AsmModule.Jal("x0", func_after))

    # Here's where the function starts:
    prog.add_label(func_addr)

    # Allocate space on the stack for the return address and local variables.
    prog.add_inst(AsmModule.Addi("sp", "sp", -4)) # Assuming a word size of 4.
    prog.add_inst(AsmModule.Sw("ra", 0, "sp"))     # Store the return address.

    # Handle the function's formal parameter (parameter passed in register 'a0').
    # Store parameter into the formal variable.
    prog.add_inst(AsmModule.Add(exp.formal, "a0", "x0"))

    # Generate the function body:
    return_var = exp.body.accept(self, prog)

    # Move the result of the function body into the return register 'a0'.
    prog.add_inst(AsmModule.Add("a0", return_var, "x0"))

    # Restore the return address and the stack pointer.
    prog.add_inst(AsmModule.Lw("ra", 0, "sp"))
    prog.add_inst(AsmModule.Addi("sp", "sp", 4))

    # Jump back to the caller.
    prog.add_inst(AsmModule.Jalr("x0", "ra"))

    # Set a label at the end of the function
    prog.add_label(func_after)

    return addr_var   # Return the generated label for this anonymous function.

def visit_fn_app(self, exp, prog):
    """
    Generate code for applying an anonymous function.
    """
    # The function being applied is an anonymous function, so we need the label:
    # Accepting the function will generate or retrieve its label.
    func_label = exp.function.accept(self, prog)

    # Generate code for the actual parameter (expression) of the function call:
    param_value = exp.actual.accept(self, prog)
    # Pass the parameter in register a0.
    prog.add_inst(AsmModule.Add("a0", param_value, "x0"))

    # Jump to the anonymous function's label:
    # Static jump to the function using its generated label.
    prog.add_inst(AsmModule.Jal("ra", func_label))

    # Retrieve the return value (stored in register 'a0').
    ret_var = self.next_var_name()
    # Store the return value in a new variable.
    prog.add_inst(AsmModule.Add(ret_var, "a0", "x0"))
    return ret_var

Key Changes and Explanations:

   1.​ visit_fn for Anonymous Functions:
          ○​ Label Generation: We dynamically generate a unique label for each anonymous
             function using self.next_fn_label(). This is crucial because anonymous
             functions don’t have names, so we need to assign them labels during code
             generation (like anon_func_1, anon_func_2, etc.).
          ○​ Function Body Generation: The function body is generated just like before, but
             now we use the dynamically assigned label for the anonymous function.
          ○​ Stack Management: We handle the stack the same way as for named functions,
             storing and restoring the return address, and making sure the return value is
             placed in the a0 register.
   2.​ visit_fn_app for Anonymous Function Calls:
          ○​ Parameter Handling: We generate code for the actual parameter of the function
             call and pass it in register a0.
          ○​ Retrieve Function Label: Since we are dealing with an anonymous function, we
             can’t jump to a static name like before. Instead, we generate or retrieve the label
             of the anonymous function by calling exp.function.accept(self, prog).
             This will return the label that was generated when the anonymous function was
             defined.
          ○​ Jump to the Function: We use the Jal instruction to jump to the function’s label
             (whether it's anonymous or named).
          ○​ Return Value Handling: After the function returns, we store the return value
             (from register a0) into a temporary variable for later use.

Helper Method:

We also need a helper method to generate unique labels for anonymous functions. Here’s a
simple version:

def next_fn_label(self):
    """
    Generate a unique label for anonymous functions.
    """
    if not hasattr(self, '_fn_count'):
        self._fn_count = 0
    self._fn_count += 1
    return f"anon_func_{self._fn_count}"

This method keeps track of how many anonymous functions we’ve seen so far and generates a
unique label for each one.

Conclusion:

With these changes, the code generator can now handle anonymous functions. We generate
unique labels for them and handle function calls dynamically based on those labels. The
approach is similar to named functions, except we don't rely on exp.name and instead generate
labels on the fly.

But, in practice (like when we compile a typical C program) how does the
CPU find the first instruction to execute?
In practice, when you compile a C program (or any program) to machine code, the CPU doesn't
automatically know where to start executing. There are a few key mechanisms that tell the CPU
which instruction is the first one to execute. Let's break this down:

1. Executable Format:

When you compile a program, the machine code is wrapped in a specific executable format
(e.g., ELF for Linux, PE for Windows, Mach-O for macOS). This format contains not only the
machine instructions but also metadata that includes information such as:

   ●​ The entry point: This is a special address where the program execution begins.

   ●​ The program header: Information about memory segments and how they should be
      loaded into memory.

In the case of ELF files (used in Linux), this information is stored in the header, where the entry
point address is explicitly defined.

2. The Role of the Operating System:

The operating system plays an important role in starting program execution. When you run a
program (e.g., by typing ./myprogram in a terminal):

   ●​   The operating system loader reads the executable file (e.g., the ELF file).
   ●​   It looks for the entry point address in the file's header.
   ●​   The OS sets up the program's memory (loading sections like code, data, stack, etc.).
   ●​   Finally, the CPU's program counter (PC) is set to the entry point address, and
        execution begins.

3. Entry Point in C Programs:

In C programs, the typical entry point is the main() function. But this isn't the first function to
run! When you compile a C program, the compiler generates extra code that gets executed
before main(). This code is typically part of the runtime library (e.g., crt0.o in Linux). The
general sequence is:

   ●​ The startup code (from the runtime) sets up things like the stack, heap, and
      environment variables.
   ●​ Once the startup code has initialized the environment, it calls the main() function.

The startup code is located at the entry point that the OS loader finds in the executable file.

4. First Executable Instruction:

The first executable instruction is typically part of the startup code, not the main() function.
For example, on Linux, this is located in crt0.o, which is linked into your program. The
instruction at the entry point might involve setting up the stack or initializing memory, and from
there, control is eventually passed to main().

5. CPU's Program Counter (PC):

The CPU knows which instruction to execute first because:

   ●​ When the OS starts the program, it loads the program into memory.
   ●​ The program counter (PC) is set to the entry point (as defined in the executable's
      header).

   ●​ The CPU then fetches the instruction at the address in the PC and starts executing.

Summary:

   ●​ When you compile a program, the compiler generates machine code wrapped in an

   ●​ The executable contains metadata, including the entry point, which tells the operating

Code like (fn x => fn y => x + y) 2 3 creates closures. We had

Yes, you're correct! The first function application in the expression (fn x => fn y => x +

What is a Closure?

A closure is a function along with its "environment," which consists of the bindings of free
variables at the time the closure is created. It allows a function to carry its context with it, even
when it is executed outside that context. Here’s how it applies to your example:

Function Definition:​
​
fn x => fn y => x + y

This is a curried function. It takes one argument x and returns another function:​
​
fn y => x + y

Notice that in the inner function fn y => x + y, the variable x is free because it is not locally
defined in the inner function. Instead, x is captured from the environment of the outer function.

First Application: When you apply 2 to the outer function:​
​
(fn x => fn y => x + y) 2

The result is a new function:​
​
fn y => 2 + y

This is a closure. It contains:

   1.​ The function fn y => x + y.
   2.​ The environment where x is bound to 2.

Second Application: When you apply 3 to the resulting closure:​
​
(fn y => 2 + y) 3

The result is: 2 + 3 = 5

Why is the Closure Useful?

Closures are essential in functional programming because they allow functions to:

   ●​ Capture and retain state (e.g., x in this case).
   ●​ Be treated as first-class values that can be passed around and executed later with their
      context intact.

In the example above, the closure fn y => 2 + y retains the value of x as 2, enabling the
inner function to use it when y is later applied.

How are closures implemented?
Well, there are many different ways to implement closures. Let me introduce you to a technique
called "closure conversion", which is super cool! Closure conversion is a technique used in the
implementation of functional programming languages to manage closures explicitly during
compilation or interpretation. It transforms a program with nested functions (and their free
variables) into one where all functions are "flat" and explicitly carry their environments as
additional parameters. This enables efficient implementation of higher-order functions and
supports features like lexical scoping.

What is Closure Conversion?

In functional languages, a closure consists of:

   1.​ A code pointer to the function's definition.
   2.​ An environment that maps the function's free variables to their current values.

Closure conversion restructures the program so that:

   ●​ Every function explicitly includes its environment as an additional argument.
   ●​ Environments are represented as explicit data structures (e.g., records or tuples).

Steps in Closure Conversion
Identify Free Variables: Free variables are those used inside a function but defined outside it.
For example:​
​
fn x => fn y => x + y

   ●​ In fn y => x + y, x is a free variable.
   ●​ Create an Environment: Collect all the free variables into a structured environment
      (e.g., a tuple or record).

Modify the Function: Rewrite the function to explicitly take the environment as an argument.
For example:​
​
fn y => x + y

becomes:​
​
fn (env, y) => #x env + y

where env is the environment containing x.

Create a Closure: A closure is then represented as a pair of:

   ●​ A reference to the modified function.
   ●​ The environment containing the free variables.

Adjust Function Applications: Function applications must pass the environment explicitly. For
example:​
​
let
    val closure = (function_pointer, environment)
in
    function_pointer(environment, argument)
end

Example of Closure Conversion

Given the following expression:

(fn x => fn y => x + y) 2 3

Step 1: Identify Free Variables

   ●​ In fn y => x + y, the free variable is x.

Step 2: Create an Environment

   ●​ When x is bound to 2, the environment becomes something like {x = 2}.

Step 3: Modify the Function

Rewrite the inner function to take the environment explicitly:

(fn (env : {x : int}, y : int) => (#x env) + y);

Step 4: Create a Closure

When applying 2 to the outer function:

(fn x => fn y => x + y) 2

it creates a closure:

closure = (fn (env, y) => (#x env) + y, {x = 2})

Step 5: Adjust Applications

When applying 3 to the closure:

function_pointer(environment, 3)

Why is Closure Conversion Important?

   1.​ Supports Lexical Scoping: Free variables are captured correctly and used in the
       appropriate context.​

   2.​ Facilitates Compilation: By converting closures into explicit structures, compilers can
       generate efficient code for languages that support higher-order functions.​

   3.​ Target Language Compatibility: It simplifies translating functional languages into
       intermediate representations or machine code that may not directly support nested
       functions.

Is Closure Conversion the same as Lambda Lifting?
Closure conversion and lambda lifting are related techniques in the implementation of
functional programming languages, but they are not the same. They address similar challenges
in managing free variables in functions, but their goals and mechanisms differ significantly.

Closure Conversion

   ●​ Goal: To explicitly represent closures (functions and their environments) in a way that
      can be efficiently implemented in lower-level code, like machine code or intermediate
      representations.
   ●​ How It Works:
          ○​ Transform functions to take an explicit environment parameter.
          ○​ Capture free variables in a structured environment (e.g., a tuple or record).

        ○​ Represent a closure as a pair of the function's code pointer and its environment.
  ●​ Key Characteristics:
        ○​ Preserves the lexical scoping of the original program.
        ○​ Used in runtime implementations, especially when higher-order functions are
           common.
        ○​ Closures remain first-class values (can be passed as arguments, returned, etc.).

Example:​
​
fn x => fn y => x + y

After closure conversion:​
​
val closure = (fn (env, y) => (#x env) + y, {x = 2})

Lambda Lifting

  ●​ Goal: To eliminate nested functions by "lifting" them to the top level, converting a
     program into one where all functions are top-level functions.
  ●​ How It Works:
        ○​ Identify free variables in nested functions.
        ○​ Add these free variables as explicit additional parameters to the lifted function.
        ○​ Transform the function's definition and all calls to it.
  ●​ Key Characteristics:
        ○​ Makes nested functions unnecessary.
        ○​ Results in a "flat" program, where all functions are at the top level.
        ○​ Often used in static compilation to simplify program structure.

Example:​
​
let
    val f = fn x => fn y => x + y
in
    f 2 3
end

After lambda lifting:​
​
fun lifted_f(x, y) = x + y
lifted_f(2, 3)

Relationship Between the Two

   ●​ Both deal with free variables in functions.
   ●​ Lambda lifting is a special case of transforming nested functions, but it doesn't use
      environments or create closures. It is most useful when you want to flatten functions
      statically.
   ●​ Closure conversion is more general and accommodates runtime environments,
      supporting features like passing closures as first-class values.

You can think of lambda lifting as a transformation that removes nested functions, while
closure conversion retains them but makes their dependencies explicit.

Who invented closure conversion?
Closure conversion, as a formal concept in the compilation of functional programming
languages, has been studied and developed over decades by multiple researchers in the fields
of programming languages and compiler theory. However, it is difficult to attribute the invention
of closure conversion to a single individual because it emerged as a solution to the challenges
of implementing lexical scoping and higher-order functions.

Key Historical Context:

   1.​ John C. Reynolds:

          ○​ In his seminal 1972 paper "Definitional Interpreters for Higher-Order
              Programming Languages", Reynolds described techniques for interpreting and
              implementing higher-order functions, including the idea of managing free
              variables explicitly. While not using the term "closure conversion," this work laid
              the groundwork for understanding closures.
   2.​ Lisp and Early Functional Languages:
          ○​ Early implementations of Lisp in the 1960s and 1970s used mechanisms akin to
              closure conversion to support lexical scoping. These implementations needed to
              represent environments for nested functions.
   3.​ Formalization in Compiler Research:
          ○​ Closure conversion was formalized as a key transformation in the compilation of
              functional languages like ML and Scheme in the 1980s and 1990s. Researchers
              such as Guy Steele, Mitchell Wand, and Andrew Appel contributed to
              formalizing and optimizing closure conversion in compiler settings.
   4.​ Cardelli and Compilers for Functional Languages:
          ○​ Luca Cardelli and others wrote extensively about the representation of functions
              and environments in the context of implementing functional languages,
              influencing how closure conversion is taught and understood.

Conclusion:

The concept of closure conversion evolved organically as part of solving practical and
theoretical problems in the implementation of functional programming languages. If you’re
interested in a foundational text, Reynolds' 1972 paper is an excellent place to start for
understanding the theoretical origins of many related concepts.

Is this the same Reynolds from "The Craft of Programming"?
Yes, the John C. Reynolds who wrote The Craft of Programming (1981) is the same renowned
computer scientist who made foundational contributions to programming languages, type theory,
and formal methods. He was a pioneer in many areas of computer science, and his work has
had a lasting impact on the design and implementation of programming languages. Here are
some of his major contributions:

1. Definitional Interpreters for Higher-Order Programming Languages (1972)

  ●​ Reynolds' seminal paper introduced the idea of a definitional interpreter, a high-level
     model for understanding and specifying the semantics of programming languages. This
     paper also formalized concepts related to closures and lexical scoping, which are
     fundamental in functional programming.

2. System F (Polymorphic Lambda Calculus)

  ●​ Independently of Jean-Yves Girard, Reynolds discovered the second-order lambda
     calculus (also known as System F), which introduced parametric polymorphism.
  ●​ System F serves as a theoretical foundation for type systems in programming
     languages, influencing languages like Haskell, OCaml, and Rust.

3. Separation Logic

  ●​ Reynolds, along with Peter O’Hearn and others, developed separation logic, a formalism
     for reasoning about programs that manipulate memory.
  ●​ This work has been instrumental in verifying the correctness of concurrent and
     imperative programs, and it is widely used in tools like Facebook’s Infer.

4. Programming Language Semantics

  ●​ Reynolds introduced and refined key ideas in programming language semantics,
     including:
         ○​ Continuations: His work on continuations has influenced control flow
             mechanisms, such as coroutines and exception handling.

          ○​ Logical Relations: He used logical relations to prove properties of polymorphic
             languages, such as type safety and representation independence.

5. The Craft of Programming

   ●​ This book emphasizes formal reasoning about programs and algorithm design,
      promoting correctness-by-construction methodologies. It bridges theoretical computer
      science and practical programming.

6. Hygienic Macros

   ●​ Although not directly attributed to him, his exploration of scoping and bindings laid the
      foundation for ideas like hygienic macros in Scheme and other languages.

7. Parametricity and "Theorems for Free!"

   ●​ Reynolds formalized the concept of parametricity, which states that polymorphic
      functions behave uniformly across all their types. This idea led to Wadler’s famous
      "Theorems for Free!", allowing for reasoning about program properties directly from their
      type signatures.

Legacy:

Reynolds was a towering figure in theoretical computer science, blending mathematical rigor
with practical applications. His work underpins much of modern programming language theory
and has influenced the design of languages and tools for decades. Beyond his technical
contributions, his writings, such as The Craft of Programming, have inspired generations of
computer scientists to think deeply about the principles of programming.
