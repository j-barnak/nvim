
Code Generation for Statements
All the code that we have produced in the last class was for constructs that
always return a value (expressions). But imperative programs also have
statements. Do you know what a "statement" is?
In imperative programming languages like C, constructs like if-then-else and while loops are
statements rather than expressions. This means they control the flow of the program but do
not return a value. When generating code for these constructs, the focus shifts from computing
and returning values to manipulating the program's control flow.

Let’s break down how code generation changes for these control-flow constructs:

Key Differences Between Expressions and Statements:

   ●​ Expressions: Always return a value. Examples include arithmetic operations, boolean
      operations, and function calls. Code generation for expressions focuses on evaluating
      sub-expressions and returning results via registers.
   ●​ Statements: Do not return values; instead, they alter the program's control flow (e.g.,
      jumping to different code blocks). Examples include if-then-else, while loops, and
      assignment statements. Code generation for statements focuses on managing the
      program counter and generating branches and jumps.

Can you give me semantic rules for typical statements, e.g., if-then-else,
while, etc?
I'll provide an overview of operational semantics rules for typical imperative constructs like
if-then-else, while loops, and assignment. As we had previously discussed, in operational
semantics, we describe the execution of programs as transitions between configurations
(which include the state of memory, control flow, etc.). For statements, we typically express how
the program moves from one configuration to the next. See below examples of small-step
operational semantics, where the execution is broken into atomic steps:

1. Assignment Statement: x := e

The assignment statement x := e evaluates the expression e and stores the result in the
variable x. The semantics specify how the state is updated.

Explanation:

   ●​ Premise: The expression e evaluates to a value v in the current state s.
   ●​ Conclusion: The program state is updated so that the variable x is now mapped to the
       value v. The notation s[x \mapsto v] means that the state s is modified such that x
       now holds v.

2. If-Then-Else Statement: if b then S1 else S2

The if-then-else statement evaluates the boolean expression b. If b evaluates to true, it
executes the first statement (S1); otherwise, it executes the second statement (S2).

Explanation:

   ●​ True Condition: If b evaluates to true in state s, the execution proceeds with the
       statement S1 in the same state s.
   ●​ False Condition: If b evaluates to false, the execution proceeds with S2 in the same
       state s.

3. While Loop: while b do S

The while loop evaluates the boolean expression b. If b is true, it executes the body S and
then repeats the process. If b is false, it terminates the loop.

Explanation:

   ●​ True Condition: If b evaluates to true, the loop body S is executed, and after that, the
       entire while loop is executed again (hence the transition to S; while b do S).
   ●​ False Condition: If b evaluates to false, the loop terminates, and the state s remains
      unchanged (the program just proceeds with whatever comes after the loop).

4. Sequence of Statements: S1; S2

The sequence S1; S2 means that S1 is executed first, and then S2 is executed.

Explanation:

   ●​ The first rule handles the case where S1 reduces in multiple steps to a sub-statement
       S1', so the sequence continues with S1' followed by S2.
   ●​ The second rule handles the case where S1 finishes, and the execution continues with
       S2.

5. Skip Statement: skip

The skip statement does nothing and simply returns the current state.

Explanation:

   ●​ The skip statement doesn’t alter the state, so the program proceeds with no changes.

Putting It All Together:

With these rules, we can now formally describe how typical imperative constructs work in terms
of transitions between states. Here’s how they fit into code generation and execution:

   ●​ Assignments change the values stored in variables.
   ●​ If-then-else branches execution based on a condition but doesn’t return values like the
      expression-based if does.
   ●​ While loops repeatedly check a condition and execute a block of code.
   ●​ Sequence connects multiple statements into one, ensuring they run in order.

These rules form the basis of operational semantics for imperative programs and dictate how
control flows through a program. They help in defining how constructs behave, how the state is
updated, and how execution proceeds from one step to the next.

How would you generate code for an if-then-else statement?

Unlike the if-then-else expression, the C-style if-then-else statement doesn't return a
value. Its purpose is to execute one block of code if a condition is true and another block of
code if the condition is false. After either block, the program continues to the next statement.

Code Generation Strategy:

   1.​ Evaluate the condition: Generate code to evaluate the condition.
   2.​ Branch based on the condition:
          ○​ If the condition is true, jump to the "then" block.
          ○​ If the condition is false, jump to the "else" block (if it exists).
   3.​ Continue execution: After either the "then" or "else" block is executed, the program
       continues with the next statement.

Code Example for if-then-else Statement:
def visit_ifThenElseStmt(self, stmt, prog):
    """
    Generates code for a C-style if-then-else statement.
    """
    # Step 1: Evaluate the condition
    cond_reg = stmt.cond.accept(self, prog)

    # Step 2: Generate labels for the 'else' block and end of the if-then-else
    else_label = prog.new_label("else")

    end_label = prog.new_label("end_if")

    # Step 3: Branch to the 'else' block if the condition is false (cond_reg == 0)
    prog.add_inst(AsmModule.Beq(cond_reg, "x0", else_label))

    # Step 4: Generate code for the 'then' block
    stmt.then_block.accept(self, prog) # Execute 'then' block code
    prog.add_inst(AsmModule.Jump(end_label)) # Skip 'else' block after 'then' block

    # Step 5: Generate code for the 'else' block (if it exists)
    prog.add_label(else_label)
    if stmt.else_block:
        stmt.else_block.accept(self, prog) # Execute 'else' block code

    # Step 6: End of the if-then-else statement
    prog.add_label(end_label)

Explanation:

   ●​ No Value Return: Unlike an expression, this if-then-else statement doesn’t return a
      value, so we don't need to manage registers for results.
   ●​ Branching for Control Flow: The generated code uses conditional branches (Beq) and
      unconditional jumps (Jump) to control which block (then/else) gets executed.
   ●​ Labels: Labels are used to mark the "else" block and the end of the entire
      if-then-else statement so that the program can jump over blocks as needed.

And how would you generate code for a C-Style "while" loop?
A C-style while loop repeatedly executes a block of code as long as a condition holds true.
Like the if-then-else statement, it does not return a value, but it controls the program's flow.

Code Generation Strategy:

   1.​ Loop Condition: Evaluate the loop's condition at the beginning of each iteration.
   2.​ Branch on Condition: If the condition is true, execute the loop body; otherwise, jump to
       the end of the loop.
   3.​ Repeat: After executing the body, jump back to evaluate the condition again.

Code Example for while Loop:
def visit_whileStmt(self, stmt, prog):
    """
    Generates code for a C-style while loop.
    """
    # Step 1: Generate labels for the start of the loop and the end of the loop
    loop_start = prog.new_label("loop_start")
    loop_end = prog.new_label("loop_end")

    # Step 2: Start of the loop
    prog.add_label(loop_start)

    # Step 3: Evaluate the condition
    cond_reg = stmt.cond.accept(self, prog)

    # Step 4: Exit the loop if the condition is false
    prog.add_inst(AsmModule.Beq(cond_reg, "x0", loop_end))

    # Step 5: Generate code for the loop body
    stmt.body.accept(self, prog) # Execute loop body

    # Step 6: Jump back to the start of the loop to recheck the condition
    prog.add_inst(AsmModule.Jump(loop_start))

    # Step 7: End of the loop
    prog.add_label(loop_end)

Explanation:

   ●​ No Value Return: The loop does not return any value; its sole purpose is controlling the
      flow of the program by repeatedly executing the loop body as long as the condition
      holds.
   ●​ Labels for Repetition: The loop has two key labels: one for the start of the loop
      (loop_start) and one for the end (loop_end). The program jumps between these
      labels to repeat the loop body or exit the loop when the condition is false.

    ●​ Conditional Branching: The condition is checked using a Beq instruction. If the
        condition evaluates to False (0), the program jumps to loop_end and exits the loop. If
       True, it continues executing the loop body.
    ●​ Unconditional Jump: After executing the body, the program jumps back to
       loop_start to re-evaluate the condition.

Our while contains two jumps: a conditional test and an unconditional one.
Would you be able to generate the while with only one dynamic jump?
Yes! Typical compilers use a common optimization called a loop inversion (also called
do-while conversion) to reduce the number of jumps in a loop, which improves efficiency by
removing the unconditional jump back to the condition.

How Loop Inversion Works:

Instead of placing the condition check at the start of the loop, typical compilers such as GCC
place it at the end of the loop body. This allows the loop to execute the first iteration without a
jump to the condition check, avoiding the unconditional jump altogether after the first iteration.

Here's how it works:

   1.​ Initial Jump to Body:
           ○​ At the start of the loop, there's a branch that skips the loop body if the condition is
                false.
   2.​ Single Conditional Check in Each Iteration:
           ○​ After each iteration of the loop body, the condition is checked at the end.
           ○​ If the condition is still true, the control jumps back to the start of the loop body.

This method removes the need for an unconditional jump at the end of each iteration and
requires only one conditional branch per iteration.

   1.​ Initial conditional jump to the loop body (if cond is true).
   2.​ After each loop body execution, check cond again (branch if true, exit if false).

Why is the inverted loop faster?
The inverted loop has two advantages over the original code:

   ●​ No Unconditional Jump: In the traditional while loop, you'd need a jump to the
      condition check after every iteration. By placing the condition at the end of the body, you
      eliminate the unconditional jump.
   ●​ Reduced Branch Misprediction: With fewer jumps and branches, the processor can
      better predict the branch directions, reducing the chances of branch misprediction.

It seems that the inverted loop is a C-style do-while. Is that the case?
Yes, you're absolutely right! The loop inversion optimization transforms a while loop into
something that behaves like a do-while loop in C.

In a do-while loop, the loop body is executed at least once before the condition is checked.
This is exactly what happens in the inverted loop generated by GCC. Here's a breakdown:

While Loop in C:
while (cond) {
    // loop body
}

   ●​ The condition is checked before the loop body executes.
   ●​ If the condition is false initially, the loop body is skipped entirely.

Do-While Loop in C:
do {
    // loop body
} while (cond);

   ●​ The loop body is executed at least once, regardless of the initial value of cond.
   ●​ The condition is checked after the loop body executes.

Inverted While Loop ≈ Do-While Loop

When a typical compiler like GCC applies the loop inversion optimization, it transforms the
traditional while loop into an inverted form that behaves like a do-while loop:

   1.​ Initial check: The condition is checked once before the first iteration (just like a while
       loop), but this is done with an initial branch that skips the loop entirely if the condition is
       false.
   2.​ Loop body execution: The loop body is executed at least once (like a do-while loop).
   3.​ Condition after body: After the loop body, the condition is checked again, and if true,
       the loop continues. This is just like the condition in a do-while loop being evaluated
       after each iteration.

Conclusion:

The optimized version does behave like a do-while loop, but the key difference is that the
initial condition is still checked before the first iteration to ensure the loop doesn't run if the
condition is initially false. In contrast, a pure do-while loop in C always runs the loop body at
least once without any prior condition check. However, for subsequent iterations, the condition is
checked after the loop body, making the control flow similar to a do-while.

Can you give me a visitor that produces an inverted loop?
To invert the while loop into something like a do-while loop, we need to change the order of
the loop's condition check and the body execution. In the inverted loop structure:

   1.​ The body of the loop will execute first.
   2.​ After executing the body, the condition will be checked.
   3.​ If the condition is true, the loop continues; otherwise, it exits.

Here's a new version of visit_whileStmt that implements this structure:

def visit_whileStmt(self, stmt, prog):
    """
    Generates code for an inverted while loop with an initial condition check.
    """
    # Step 1: Generate labels for the body of the loop and the condition check
    loop_body = prog.new_label("loop_body")
    loop_end = prog.new_label("loop_end")

    # Step 2: Initial condition check (if the condition is false, skip the loop)
    cond_reg = stmt.cond.accept(self, prog)
    prog.add_inst(AsmModule.Beq(cond_reg, "x0", loop_end))

    # Step 3: Start of the loop body
    prog.add_label(loop_body)

    # Step 4: Generate code for the loop body
    stmt.body.accept(self, prog) # Execute loop body

    # Step 5: Condition check after the body is executed (inverted loop check)
    cond_reg = stmt.cond.accept(self, prog)
    prog.add_inst(AsmModule.Bne(cond_reg, "x0", loop_body))

    # Step 6: End of the loop (when condition is false)
    prog.add_label(loop_end)

Notice that for a do-while-like loop, we must still check the condition before entering the loop
to avoid running the body when the condition is false right from the start. Without that, the loop
would always execute the body at least once, which doesn't match the behavior of a regular
while loop in C.

Explanation:

   1.​ Initial Condition Check:​
       Before entering the loop, we evaluate the condition. If the condition is false (cond ==
       0), we immediately jump to loop_end, bypassing the body of the loop entirely. This is
       similar to how a regular while loop works.
   2.​ Loop Body Execution:​
       If the condition is true at the start, we enter the loop body.
   3.​ Inverted Loop:​
       After executing the body, we check the condition again. If it remains true, we jump back
       to the start of the body (loop_body). Otherwise, we fall through and exit the loop.

This way, the code behaves like a normal while loop but uses the more efficient inverted loop
structure inside. The surrounding condition ensures that we only enter the loop if the condition is
true initially, avoiding the do-while behavior where the body would always execute at least
once.

We have been calling these graphs we draw "Control-Flow Graphs". Is
there a formal definition for these graphs?
A Control-Flow Graph (CFG) is a fundamental concept in computer science, particularly in the
fields of compiler design, program analysis, and optimization. It is a directed graph that
represents the flow of control through a program during its execution.

Key Components of a Control-Flow Graph:

   1.​ Nodes (Basic Blocks):​
       In a CFG, each node represents a basic block. A basic block is a straight-line sequence
       of instructions with:
            ○​ One entry point: the first instruction is the only point where control can enter the
               block.
            ○​ One exit point: control can leave the block only at the last instruction (except for
               conditional branches at the end).
   2.​ A basic block doesn't contain any control flow instructions (like jumps or branches)
       except at the end.
   3.​ Edges (Control Flow):​
       The edges between nodes represent the possible control flow between the basic
       blocks. An edge from block A to block B indicates that after executing the instructions in
       block A, the program might transfer control to block B. This happens when:
            ○​ There's a conditional branch at the end of block A that may lead to block B.
            ○​ Block A ends with an unconditional jump to block B.
            ○​ Block A naturally falls through into block B (in the absence of jumps or branches).

CFG in Optimizations:

When optimizing loops (e.g., using loop inversion, as we discussed), the CFG changes.
Instead of checking the condition first, the compiler may rearrange the flow to execute the loop
body before the condition (similar to a do-while loop). The CFG would reflect this
transformation by adjusting the edges and nodes to reflect the modified control flow.

Summary:

A Control-Flow Graph is a graphical representation of all the possible paths a program might
take during its execution. It is a vital tool in program analysis and optimization, helping compilers
and developers understand how control moves through a program, where optimizations can be
applied, and what parts of the code might be unreachable or need more attention.

Why are CFGs important?
Control-flow graphs are important for a number of reasons:

   1.​ Program Analysis and Optimization:​
       Compilers use CFGs to perform various analyses and optimizations, such as:
            ○​ Dead code elimination: Removing code that can never be executed based on
               the flow.
            ○​ Loop optimizations: Analyzing loops to improve performance, such as through
               loop unrolling or invariant code motion.
            ○​ Data-flow analysis: Determining the possible values that variables can take at
               different points in the program.
   2.​ Pathfinding:​
       CFGs allow compilers to find paths through the program. For instance, it helps determine
       whether a certain block of code can be reached or whether an infinite loop might exist.
   3.​ Code Generation:​
       When generating machine code, the compiler can traverse the CFG to produce more
       efficient jump and branch instructions.
   4.​ Testing and Verification:​
       CFGs are also useful in software testing, where they help ensure that every possible
       path through the program is tested (a concept known as path coverage).

Could you give me a visitor that produces code for a C-style for loop?

Here's how you would structure a visitor for a typical for loop. A for loop has four parts:

   1.​ Initialization: This is executed once at the beginning of the loop.
   2.​ Condition: Checked before each iteration to decide whether to continue looping.
   3.​ Increment: Executed after each iteration of the loop.
   4.​ Body: The code inside the loop that is executed for each iteration.

Let's create a visitor that generates assembly code for this structure:

def visit_forStmt(self, stmt, prog):
    """
    Generates code for a typical C-style for loop.
    """
    # Step 1: Generate labels for the loop condition, body, and end
    loop_cond = prog.new_label("loop_cond")
    loop_body = prog.new_label("loop_body")
    loop_end = prog.new_label("loop_end")

    # Step 2: Initialization (executed once before the loop starts)
    stmt.init.accept(self, prog) # Generate code for the initialization statement

    # Step 3: Jump to the loop condition
    # (to avoid executing the body without checking the condition first)
    prog.add_inst(AsmModule.Jump(loop_cond))

    # Step 4: Loop body
    prog.add_label(loop_body)
    stmt.body.accept(self, prog)                # Generate code for the body of the loop

    # Step 5: Increment (executed after the body for each iteration)
    stmt.incr.accept(self, prog) # Generate code for the increment expression

    # Step 6: Condition (executed before each iteration
    # to check if we should continue looping)
    prog.add_label(loop_cond)
    cond_reg = stmt.cond.accept(self, prog)
    # If cond != 0, jump to loop_body
    prog.add_inst(AsmModule.Bne(cond_reg, "x0", loop_body))

    # Step 7: End of the loop
    prog.add_label(loop_end)

This structure captures the typical behavior of a for loop in languages like C, ensuring the
initialization is done once, the condition is checked at each iteration, and the increment is
executed after the body on each loop iteration.

How can we model a "break" statement that exits the surrounding loop?
Well, let's first discuss how to model an AST node for a break statement and then how to
implement the visit_breakStmt to generate the appropriate assembly code for it.

Modeling the AST Node for a break Statement

A break statement is used to exit the nearest enclosing loop prematurely. To represent this
premature exit in the AST, we could create a simple node with no specific fields because the
break statement doesn't depend on any values or conditions; it just transfers control to the
statement after the loop. Here's a possible structure for a BreakStmt class in your AST:

class BreakStmt:
    def __init__(self):
        # No fields are necessary since break has no arguments
        pass

     def accept(self, visitor, prog):
         return visitor.visit_breakStmt(self, prog)

This BreakStmt class has an accept method that will call the visitor's visit_breakStmt
method, passing in the BreakStmt node and the current program object (prog).

How would be code generation for the break statement?
In code generation, when we encounter a break statement, we need to jump to the end of the
loop, which means the loop must have a known exit point (label). To do this, we need a way to
pass the loop’s exit_label to the break statement.

Storing Loop Context

One way to track the current loop's exit_label is by using a stack of labels inside the visitor.
Each time we enter a loop, we push its exit_label onto this stack. When generating code for
a break, we can use the label at the top of the stack to generate a jump to the end of the loop.

Here's an example of how you can modify the visitor to handle this:

   1.​ Add a Stack for Exit Labels: The visitor will need a stack to track the exit labels of
       loops.

class CodeGenerator:
    def __init__(self):
        # Stack for loop exit labels
        self.exit_label_stack = []

   2.​ Modify the visit_whileStmt and visit_forStmt Methods: Before generating the
       body of the loop, push the exit_label onto the stack. After generating the body, pop
       the label off the stack. For the while loop, see the code below (for the for loop, you
       would do something similar with the loop_end label):

def visit_whileStmt(self, stmt, prog):

    loop_start = prog.new_label("loop_start")
    loop_end = prog.new_label("loop_end")

    # Push the exit label onto the stack
    self.exit_label_stack.append(loop_end)

    prog.add_label(loop_start)
    cond_reg = stmt.cond.accept(self, prog)
    prog.add_inst(AsmModule.Beq(cond_reg, "x0", loop_end))
    stmt.body.accept(self, prog)
    prog.add_inst(AsmModule.Jump(loop_start))

    # Pop the exit label off the stack
    self.exit_label_stack.pop()

    prog.add_label(loop_end)

   3.​ Implement visit_breakStmt: When visiting a break statement, generate a jump to
       the label at the top of the exit_label_stack (which is the end of the current loop).

def visit_breakStmt(self, stmt, prog):
    # The break should jump to the current loop's exit label
    if not self.exit_label_stack:
        raise Exception("Break statement not inside a loop")

    # Get the label for the current loop's end
    exit_label = self.exit_label_stack[-1]
    prog.add_inst(AsmModule.Jump(exit_label))

Explanation:

   1.​ visit_whileStmt and visit_forStmt: These methods push the loop_end label
       onto the exit_label_stack before generating the loop body. When the loop ends,
       they pop the label off the stack.
   2.​ visit_breakStmt: This method generates a jump to the label at the top of the
       exit_label_stack, effectively breaking out of the loop.

Summary:

   ●​ The BreakStmt AST node is simple because break doesn't take arguments.
   ●​ The visitor keeps track of the nearest loop's exit label using a stack
      (exit_label_stack), allowing nested loops to work correctly.
   ●​ The visit_breakStmt generates a jump to the current loop’s exit_label, making
      the break statement functional.

    def accept(self, visitor, prog):
        return visitor.visit_continueStmt(self, prog)

Step 2: Handling Continue Labels in the Visitor

We now modify the code generator to handle continue statements. We will introduce a
continue label stack in the same way we did with the exit_label_stack for break
statements.

Modifying visit_whileStmt and visit_forStmt

Just like we track exit labels for break, we will track continue labels for continue. For a
while loop, the continue label should be the loop condition check. For a for loop, it should be
the increment step. In a while loop, we jump back to the condition check when encountering a
continue statement:

def visit_whileStmt(self, stmt, prog):
    loop_start = prog.new_label("loop_start")
    loop_end = prog.new_label("loop_end")

    # Push the exit and continue labels onto the stack
    self.exit_label_stack.append(loop_end)
    # In a while loop, we recheck the condition at the start of the loop
    self.continue_label_stack.append(loop_start)

    prog.add_label(loop_start)
    cond_reg = stmt.cond.accept(self, prog)
    prog.add_inst(AsmModule.Beq(cond_reg, "x0", loop_end))
    stmt.body.accept(self, prog)
    prog.add_inst(AsmModule.Jump(loop_start))

    # Pop the labels off the stack after the loop
    self.continue_label_stack.pop()
    self.exit_label_stack.pop()

    prog.add_label(loop_end)

In a for loop, we jump to the increment step when encountering a continue statement.

def visit_forStmt(self, stmt, prog):
    loop_cond = prog.new_label("loop_cond")
    loop_body = prog.new_label("loop_body")
    loop_end = prog.new_label("loop_end")
    loop_incr = prog.new_label("loop_incr")                             # Increment step for the loop

    # Push the exit and continue labels onto the stack

    self.exit_label_stack.append(loop_end)
    self.continue_label_stack.append(loop_incr)

    # Initialization
    stmt.init.accept(self, prog)

    # Jump to the condition check first
    prog.add_inst(AsmModule.Jump(loop_cond))

    # Loop body
    prog.add_label(loop_body)
    stmt.body.accept(self, prog)

    # Increment step
    prog.add_label(loop_incr)
    stmt.incr.accept(self, prog)

    # Condition check
    prog.add_label(loop_cond)
    cond_reg = stmt.cond.accept(self, prog)
    prog.add_inst(AsmModule.Bne(cond_reg, "x0", loop_body))

    # Pop the labels off the stack after the loop
    self.continue_label_stack.pop()
    self.exit_label_stack.pop()
    prog.add_label(loop_end)

Step 3: Implementing visit_continueStmt

The visit_continueStmt method will generate a jump to the current loop’s continue label,
which is the label at the top of the continue_label_stack.

def visit_continueStmt(self, stmt, prog):
    # The continue should jump to the current loop's continue label
    if not self.continue_label_stack:
        raise Exception("Continue statement not inside a loop")

    # Get the label for the current loop's continue point
    continue_label = self.continue_label_stack[-1]
    prog.add_inst(AsmModule.Jump(continue_label))

Summary:

   ●​ BreakStmt jumps to the exit_label of the nearest loop to exit the loop.
   ●​ ContinueStmt jumps to the continue_label of the nearest loop, skipping the rest of
      the loop body and re-evaluating the loop condition or increment.

   ●​ We use two separate stacks, one for exit_labels (for break) and one for
       continue_labels (for continue), to keep track of nested loops.

This setup will allow you to correctly handle both break and continue statements inside
nested loops in your code generation.

How would you generate code for a switch statement?

To generate code for a switch statement in RISC-V, we first need to define the structure of the
switch statement in the AST. Below is the representation of the SwitchStmt AST node,
followed by the implementation of the visit_switchStmt method for code generation.

Representation of the SwitchStmt AST Node
class SwitchStmt:
    def __init__(self, switch_expr, cases, default_case=None):
        """
        Represents a C-style switch statement.

         :param switch_expr: The expression to evaluate for the switch.
         :param cases: A list of tuples (case_value, case_body), where:
                       - case_value is the value for this case.
                       - case_body is the block of code for this case.
         :param default_case: The block of code for the default case.
         """
         # Expression whose value determines the branch
         self.switch_expr = switch_expr
         # List of (case_value, case_body) pairs
         self.cases = cases
         # Block of code for the default case
         self.default_case = default_case

    def accept(self, visitor, prog):
        """
        Accept a visitor for code generation.
        """
        return visitor.visit_switchStmt(self, prog)

Implementation of visit_switchStmt
def visit_switchStmt(self, stmt, prog):
    """
    Generates code for a C-style switch statement with proper fall-through handling.
    """
    # Step 1: Evaluate the switch expression and store the result in a register
    switch_reg = stmt.switch_expr.accept(self, prog)

    # Step 2: Generate labels for each case and the default case

   case_labels = [prog.new_label(f"case_{i}") for i in range(len(stmt.cases))]
   default_label = prog.new_label("default") if stmt.default_case else None
   end_label = prog.new_label("end_switch")

   # Step 3: Store the target of a break unconditional jump, if any
   self.exit_label_stack.append(end_label)

   # Step 4: Generate comparison and branch instructions for each case
   for i, (case_value, _) in enumerate(stmt.cases):
       case_label = case_labels[i]

      # Allocate a temporary register and load the case value into it
      temp_reg = self.next_var_name()
      prog.add_inst(AsmModule.Addi(temp_reg, "x0", case_value))

      # Compare the switch expression with the case value and branch if equal
      prog.add_inst(AsmModule.Beq(switch_reg, temp_reg, case_label))

   # Step 5: Jump to the default case if no matches are found (if default exists)
   if default_label:
       prog.add_inst(AsmModule.Jump(default_label))
   else:
       prog.add_inst(AsmModule.Jump(end_label))

   # Step 6: Generate code for each case
   for i, (_, case_body) in enumerate(stmt.cases):
       prog.add_label(case_labels[i]) # Label for the case
       case_body.accept(self, prog)   # Generate code for the case body
       # Fall-through to the next case unless break is used

   # Step 7: Generate code for the default case (if it exists)
   if stmt.default_case:
       prog.add_label(default_label)
       stmt.default_case.accept(self, prog)

   # Step 8: Pop the exit label off the stack after the switch
   self.exit_label_stack.pop()

   # Step 9: End of the switch statement
   prog.add_label(end_label)

Explanation

  1.​ Switch Expression Evaluation:
         ○​ The switch expression is evaluated, and its value is stored in a register
            (switch_reg).
  2.​ Case Labels:
         ○​ Each case is assigned a unique label for branching.
  3.​ Branching Logic:
         ○​ For each case, the generated code compares the value of the switch_reg with
            the case value. If they are equal, execution jumps to the corresponding case
            label.

   4.​ Default Case:
          ○​ If no cases match, the code jumps to the default case label (if it exists). If there's
              no default case, it jumps to the end of the switch.
   5.​ Case Body Execution:
          ○​ The body of each case is executed, followed by a jump to the end of the switch to
              avoid "fall-through" behavior.
   6.​ End Label:
          ○​ Marks the end of the switch statement, ensuring that execution resumes normally
              after the switch.

Handling the break statement within a switch
We handle break statements within switches pretty much as we do in loops: by using the
exit_label_stack to manage the break target for the switch statement, we streamline
handling control flow, particularly in cases where break statements are used. Here's how it
works:

   1.​ Consistency with Loops: Using the exit_label_stack ensures that break behaves
       uniformly across all constructs (while, for, switch).
   2.​ Fall-Through Logic: By omitting the unconditional jump to end_label in each case,
       we naturally allow for fall-through behavior unless explicitly overridden by a break
       statement. This aligns with C-style switch semantics.
   3.​ Simplified Break Handling: Since the target of break is stored in
       exit_label_stack, the logic for generating break instructions remains unchanged
       across constructs. It simply jumps to the top of the stack.

Step-by-Step RISC-V Assembly Translation

   1.​ Evaluate the switch expression:
          ○​ The value of x is already in register x5.
   2.​ Branch to case labels:
          ○​ Compare x5 with the values for each case. Branch to the corresponding label if
              the value matches.
   3.​ Execute case body and jump to the end:
          ○​ Each case body will execute its respective instructions and then jump to the end
              of the switch statement.
   4.​ Default case handling:
          ○​ If no case matches, jump to the default case.
   5.​ End of the switch statement:
           ○​ Resume execution after the switch.

Explanation of the Assembly Code

  1.​ Immediate Value Loading (addi):
         ○​ The addi instruction loads the immediate value for each case (1 and 2) into a
             temporary register (t0, t1, etc).
  2.​ Branch if Equal (beq):
         ○​ The beq instruction checks if x5 (the value of x) matches the immediate value in
             t0. If true, it jumps to the corresponding case label.
  3.​ Unconditional Jump (j):
         ○​ After executing the code for a specific case, an unconditional jump ensures that
            execution skips the remaining cases and the default case.
  4.​ Function Calls (call):
         ○​ The call instruction represents a function call to do_something,
             do_something_else, or handle_default.
  5.​ Default Case Handling:
         ○​ If no match is found, the program jumps directly to the default_case label.
  6.​ End of the switch:
         ○​ The end_switch label marks the point where the program continues after the
             switch statement.

What is the complexity of running this implementation of the switch
statement?

The current implementation of the switch statement uses a sequence of comparisons
(branches) to determine the matching case, resulting in O(n) complexity, where n is the number
of cases.

Explanation of O(n) Complexity

   1.​ Sequence of Branches: Each case requires a comparison between the switch
       expression value and the case value.
   2.​ Linear Scan: The program evaluates cases sequentially until a match is found or all
       cases are exhausted. This linear scan means the time complexity grows with the number
       of cases.

Trade-offs and Limitations

   ●​ Small Case Sets: This approach is simple and works efficiently when the number of
      cases is small.
   ●​ Dense Case Values: If the case values are dense and numeric (e.g., 1, 2, 3, ...), more
      optimized approaches like a jump table could be more efficient.
   ●​ Sparse Case Values: For non-contiguous or non-numeric cases, hash tables or decision
      trees might be better alternatives.

Is it possible to implement faster switch statements?

If you want to improve performance, consider the following:

1. Jump Table

   ●​ Complexity: O(1) for dense, contiguous case values.
   ●​ How It Works: Precompute a table where each index corresponds to a case value. The
      switch expression's value is used as an index to jump directly to the correct case.
   ●​ Pros:
         ○​ Fast lookup for dense, numeric cases. Cons:
         ○​ Wastes memory if the case values are sparse.

Example Assembly:

slli t1, x5, 2                       # Multiply switch value by 4 (word size)
la t2, jump_table                    # Load address of the jump table
lw t3, 0(t2, t1)                     # Load jump target from the table
jr t3                                # Jump to the target

​
2. Binary Search

   ●​ Complexity: O(log ⁡n) for sorted case values.
   ●​ How It Works: Use a binary search over the case values to find the matching case.
   ●​ Pros:
         ○​ Works well for sparse case values. Cons:
         ○​ More complex to implement in assembly.

Example:
​
case_values = [1, 3, 7, 10]
targets = [case_1, case_3, case_7, case_10]
# Perform binary search on `case_values`

3. Hash Table

   ●​ Complexity: O(1) average, O(n) worst-case.
   ●​ How It Works: Use a hash function to map case values to jump labels.
   ●​ Pros:
         ○​ Efficient for sparse, non-contiguous case values. Cons:
         ○​ Overhead of maintaining a hash table.

Example:
​
case_map = {1: case_1, 3: case_3, 7: case_7, 10: case_10}
target = case_map[switch_value]

So, a "good" switch statement involves only numeric cases, right? Which
early languages introduced thi kind of statement?
The earliest programming languages to feature switch statements with numeric cases were
designed with optimization opportunities in mind, particularly for numeric comparisons. These
"good switches" are well-suited for performance improvements, such as jump tables, because
they map numeric case values directly to executable code locations.

Key Early Languages with switch

ALGOL W (1966)

One of the first languages to include a case statement for numeric values.

case x of
    1: statement1;
    2: statement2;

    default: statement3;
end case;

Optimization: Numeric cases allow the use of jump tables, and its influence shaped later
languages.

FORTRAN (via Computed GOTO, mid-1950s)

While not a switch statement per se, FORTRAN's Computed GOTO provided a similar
concept. Depending on the value of I, the program jumps to label 10, 20, or 30:

GOTO (10, 20, 30), I

Optimization: This inspired efficient jump table generation.

PL/I (1964)

Introduced a formal SELECT statement for branching:

SELECT (X);
     WHEN (1) CALL FOO;
     WHEN (2) CALL BAR;
     OTHERWISE CALL DEFAULT;
END;

Optimization: Its numeric nature made jump table use possible.

C (1972)

One of the most famous and enduring implementations of switch, explicitly designed for
numeric values. Example:

switch (x) {
    case 1:
        foo();
        break;
    case 2:
        bar();
        break;
    default:
        baz();
}

Optimization: The simplicity of C’s switch syntax and numeric cases made it ideal for jump
tables.

Pascal (1970)

Introduced case as part of its structured programming design. Example:

case x of
     1: writeln('Case 1');
     2: writeln('Case 2');
     else writeln('Default');
end;

Optimization: Pascal's strict typing made numeric optimization straightforward.

Why Numeric Cases Are Ideal for Optimization

   1.​ Predictable Execution:
          ○​ Numeric cases (e.g., integers) are easy to map directly to memory offsets.
   2.​ Jump Table Feasibility:
          ○​ Dense numeric ranges enable direct indexing into a jump table, achieving
              O(1)O(1) time complexity.
   3.​ Compiler Simplicity:
          ○​ Numeric cases simplify compiler implementation for branching logic compared to
              string or complex case types.

Early Limitations and Developments

   ●​ Sparse Numeric Cases: Languages like C allowed sparse case values (e.g., 1, 100,
       1000), requiring additional handling (e.g., binary search or chains of comparisons).
   ●​ Non-Numeric Cases: Later languages like Ada and Java introduced switch
      statements supporting non-numeric cases (strings, enums), which complicate
      optimization.

Conclusion

The "good switches" — numeric case-based switches in early languages like ALGOL W,
FORTRAN, and C — laid the foundation for efficient jump table optimizations. These early
implementations remain highly relevant, especially in languages like C and its descendants.

   4.​ Efficient Use of Hardware:​

   5.​ Legacy in Systems Programming:
