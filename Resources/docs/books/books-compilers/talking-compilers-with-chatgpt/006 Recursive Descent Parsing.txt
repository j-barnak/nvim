Last class, we wrote a data structure to represent expressions. How can
we convert a string, in the postfix format, to this structure, assuming that we

The function compute_prefix below parses and converts an arithmetic expression written in
prefix notation (where the operator comes before the operands) into a tree-like data structure,
with nodes representing different arithmetic operations (like addition, multiplication, etc.).

def compute_prefix(lexer):
    """
    Examples:
        >>> lexer = Lexer("+ 3 * 4 2")
        >>> e = compute_prefix(lexer)
        >>> e.eval()
        11

        >>> lexer = Lexer("+ * 3 4 2")
        >>> e = compute_prefix(lexer)
        >>> e.eval()
        14
    """
    token = lexer.next_valid_token()

    if token.kind == TokenType.NUM:
        # Base case: return the value if it's a number
        return Num(int(token.text))

    elif token.kind in Token.operators:
        # Recursive case: evaluate the operands
        a = compute_prefix(lexer)
        b = compute_prefix(lexer)

        if token.kind == TokenType.ADD:
            return Add(a, b)
        elif token.kind == TokenType.SUB:
            return Sub(a, b)
        elif token.kind == TokenType.MUL:
            return Mul(a, b)
        elif token.kind == TokenType.DIV:
            return Div(a, b)

    else:
        raise ValueError(f"Unexpected token type: {token.kind}")

This code builds an expression tree for prefix expressions by recursively parsing the input and
constructing a tree of nodes for the operations. Each node represents a number or an arithmetic

operation, and the recursive nature of the function allows it to handle nested operations
correctly.

   ●​ Output: A tree-like structure of nodes representing the arithmetic operations, which can
      later be evaluated.

That was kinda easy! Why?
The fact that the strings are in prefix notation (also known as Polish notation) is the key
reason why this problem is relatively easy to solve. Let me explain why this makes things
simpler, and why it feels more like a straightforward process rather than traditional parsing. In
prefix notation, the operator comes first, followed by its operands. The major advantage of this
format is that there is no need for parentheses or precedence rules to dictate the order of
operations. This means the order of tokens in the expression directly reflects the structure of the
expression, which allows for linear, single-pass parsing. Here’s why it’s easier:

   1.​ Natural left-to-right processing:
          ○​ When reading the expression from left to right, you always know exactly what the
             next operator or operand should be.
          ○​ For example, when you encounter an operator like +, you know that the next two
             tokens must be its operands, so you can just recursively process those.
   2.​ Recursive calls mimic the tree structure:
          ○​ The way you process tokens matches the natural construction of an expression
             tree:
                  ■​ You see an operator, then you process its first operand, then its second
                      operand.
                  ■​ This directly builds the tree-like structure without any need for
                      backtracking or complex parsing logic.

   3.​ No need for operator precedence:
          ○​ In many parsing problems (like infix notation), you have to deal with operator
             precedence and associativity, which makes parsing more complicated. You’d
             need to figure out which operator applies to which operands based on the rules
             of precedence (e.g., multiplication before addition).
          ○​ In prefix notation, the order of operations is explicit. There is no ambiguity
             because you always process the operator first, followed by its operands, in the
             exact order they appear.
   4.​ Simple recursion:
          ○​ In infix notation, parsers often require more complex strategies like recursive
             descent parsing, precedence climbing, or shunting-yard algorithms. These
             methods are needed to handle the complexity of operator precedence,
             parentheses, and left/right associativity.
          ○​ With prefix notation, however, a simple recursive approach works because the
             expression naturally unfolds in the correct order as you process the tokens.

Then, a general methodology to write parsers is to come up with a
grammar, and then write a recursive descent parser for it, right?
The general methodology for writing parsers—especially recursive descent parsers—follows
these steps:

1. Define the Grammar

   ●​ The first step is to describe the structure of the language (or the expressions you're
      parsing) using a formal grammar, often in Backus-Naur Form (BNF) or Extended BNF.
   ●​ The grammar should specify how valid sequences of tokens can be formed, typically
      defining rules for each type of construct (e.g., expressions, terms, factors, operators).

2. Break Down the Grammar into Functions

   ●​ Each rule of the grammar corresponds to a function (or method) in your recursive
      descent parser.
         ○​ Base cases (like num) are handled directly by returning a value (or building a
             corresponding AST node).
         ○​ Recursive cases (like operators followed by two sub-expressions) are handled by
             calling the parsing function recursively.

3. Use Recursive Descent

   ●​ The parser function processes the input token by token. When it encounters a token that
      matches a grammar rule, it processes it (and possibly calls itself recursively) to handle
      sub-expressions.
   ●​ This approach mirrors the structure of the grammar:
         ○​ Each function in the parser corresponds to a rule in the grammar.
         ○​ Each call to a parsing function corresponds to applying a rule.

4. Return an Abstract Syntax Tree (AST)

   ●​ A key task of parsing is to transform the input into a more structured form, such as an
      abstract syntax tree (AST).
   ●​ Each function in the recursive descent parser typically returns an AST node representing
      the result of parsing that part of the input.

Can you come up with a grammar for expressions in infix notation?
First attempt:

E ::= num
    | '(' E ')'
    | E '+' E
    | E '-' E
    | E '*' E
    | E '/' E

Can you use this grammar to write a recursive descent parser?
Not really! It is left-recursive, which makes it tricky to use directly in a recursive descent parser,
because left-recursion can lead to infinite recursion in such parsers. In recursive descent
parsers, when a rule calls itself as the first thing in a production (left-recursive), it leads to infinite
recursion. In that example above, a parser would first try to parse E, which immediately leads to
another attempt to parse E, and this goes on indefinitely.

Could you rewrite the grammar, to remove the left recursion?
Yes, here's a version of the grammar without left recursion:
E ::= num E'
     | '(' E ')' E'
E' ::= '+' E E'
     | '-' E E'
     | '*' E E'
     | '/' E E'
     | ε

Is there a general algorithm to remove left recursion from grammars?
Yes, there is an algorithm. Here's how it works:
Identify left-recursive productions: Look for any rules where the left-hand side of the
production (A ::=) appears as the first symbol on the right-hand side (A α).
Rewrite the grammar: Replace the left-recursive rules with a right-recursive structure. For
every left-recursive non-terminal A, split its productions into:

    ●​ One set of productions where A does not appear on the right-hand side (let's call these
        β).
    ●​ Another set where A appears as the first symbol (let's call these α).

Then, replace the left-recursive rule with a right-recursive version by introducing a new
non-terminal A' (often called the "tail" or "prime" version of A).

Example: For a production of the form:
A ::= A α | β

Convert it into:
A ::= β A'
A' ::= α A' | ε

from Exp import *
from Lexer import *

class Parser:
    """
    This class implements a parser for infix arithmetic expressions.

    The parser uses the following grammar:

    E ::= num F
        | '(' E ')' F

    F ::= '+' E F
        | '-' E F
        | '*' E F
        | '/' E F
        | empty

    Example:
    >>> lexer = Lexer("2 + 3 + 4")
    >>> parser = Parser(lexer)
    >>> e = parser.E()
    >>> e.eval()
    9

    >>> lexer = Lexer("2 * 3 * 4")
    >>> parser = Parser(lexer)
    >>> e = parser.E()
    >>> e.eval()
    24

    >>> lexer = Lexer("(2 + 3) * 4")
    >>> parser = Parser(lexer)
    >>> e = parser.E()
    >>> e.eval()
    20

    >>> lexer = Lexer("4 * (2 + 3)")
    >>> parser = Parser(lexer)
    >>> e = parser.E()

>>> e.eval()
20

>>> lexer = Lexer("2 * 3 + 4")
>>> parser = Parser(lexer)
>>> e = parser.E()
>>> e.eval()
10

>>> lexer = Lexer("2 - 3 - 4")
>>> parser = Parser(lexer)
>>> e = parser.E()
>>> e.eval()
-5
"""
def __init__(self, lexer):
    self.lexer = lexer
    self.current_token = self.lexer.next_valid_token()

def eat(self, token_type):
    if self.current_token.kind == token_type:
        self.current_token = self.lexer.next_valid_token()
    else:
        raise ValueError(f"Unexpected token: {self.current_token.kind}")

def E(self):
    """
    Parse the base case (numbers or parenthesized expressions).

   This case implements the productions:

   E ::= num F
       | '(' E ')' F
   """
   token = self.current_token

   if token.kind == TokenType.NUM:
       self.eat(TokenType.NUM)
       num = Num(int(token.text))
       return self.F(num)

   elif token.kind == TokenType.LPR: # '('
       self.eat(TokenType.LPR)
       node = self.E()
       self.eat(TokenType.RPR) # ')'
       return self.F(node)

def F(self, left):
    """
    Parse the continuation of an expression (right recursion).

   This case implements the productions:

   F ::= '+' E F
       | '-' E F

             | '*' E F
             | '/' E F
             | empty

         Notice that we must pass the left side of the expression to it, otherwise we
         would not be able to build the expression node.
         """
         token = self.current_token

         if token.kind == TokenType.ADD:
             self.eat(TokenType.ADD)
             right = self.E()
             return self.F(Add(left, right))

         elif token.kind == TokenType.SUB:
             self.eat(TokenType.SUB)
             right = self.E()
             return self.F(Sub(left, right))

         elif token.kind == TokenType.MUL:
             self.eat(TokenType.MUL)
             right = self.E()
             return self.F(Mul(left, right))

         elif token.kind == TokenType.DIV:
             self.eat(TokenType.DIV)
             right = self.E()
             return self.F(Div(left, right))

         # If no more operators, return the current node.
         return left

The grammar provides the wrong result for "2 * 3 + 4". Why?
That happens because the grammar does not recognize any precedence between * and +. It
solves the operands right-to-left. and 3 + 4 comes first (in the right-to-left order). Thus, the
grammar is right associative (what is not what we want!) and it does not define the precedence
of the multiplicative operators over the additive operators. More generally, the grammar is
ambiguous, something that is a big problem!

What are ambiguous grammars?
Ambiguity occurs when a grammar can produce more than one parse tree (or derivation) for the
same string. In the grammar you provided, the ambiguity comes from the fact that there are no
explicit rules for operator precedence or associativity. As a result, multiple valid parse trees
can be created for expressions with more than one operator.

Consider the following example expression: num + num * num

According to the grammar:

   1.​ We can interpret the expression as:
          ○​ First, apply + to the first two nums, then multiply the result by the third num.
           ○​ This corresponds to the parse tree: (num + num) * num.
   2.​ Alternatively, we can interpret the expression as:
           ○​ First, multiply the last two nums, and then apply + to the first num and the result of
              the multiplication.
           ○​ This corresponds to the parse tree: num + (num * num).

Both interpretations are valid according to the grammar, leading to two different parse trees.
This ambiguity arises because the grammar does not enforce any precedence between the
operators (+, -, *, /), nor does it define associativity (whether operations should be grouped
left-to-right or right-to-left).

How do we know if a grammar is ambiguous? Is there a general algorithm
to find that out?
Not really. The problem of determining whether a grammar is ambiguous is undecidable. In
formal language theory, it has been proven that there is no general algorithm or method that can
decide whether an arbitrary context-free grammar (CFG) is ambiguous. This undecidability
stems from the fact that the problem involves checking if there are two or more distinct parse
trees for the same string generated by the grammar, and this task cannot be automated for all
possible grammars.

In essence, while for some specific grammars it may be easy to check for ambiguity manually,
the existence of a general procedure that works for every context-free grammar is impossible.
This result is akin to other undecidability problems in computer science, such as the halting
problem.

Therefore, while there are heuristics and techniques to analyze particular grammars, the
ambiguity problem in general cannot be decided algorithmically.

How did people show that the problem of determining if a grammar is
ambiguous was undecidable?
This undecidability can be understood in relation to the Post's Correspondence Problem (PCP),
which is a well-known undecidable problem in computability theory.

To elaborate, a grammar is considered ambiguous if there exists at least one string that can be
generated by the grammar in multiple distinct ways (i.e., there are two or more different parse
trees for the same string). There is no algorithm that can decide for every CFG whether it is
ambiguous or not.

The connection to the PCP arises because you can construct a reduction from PCP to the
ambiguity problem. If you could decide on ambiguity, you could also decide instances of PCP by
encoding them as grammars. Since PCP is undecidable, it follows that the problem of
determining grammar ambiguity must also be undecidable.

Thus, it is correct to say that the ambiguity of grammars is an undecidable problem, and this
conclusion leverages the properties of the Post's Correspondence Problem.

But can we sometimes demonstrate that a grammar is unambiguous?
Yes, sometimes. For instance, our grammar for prefix notation is not ambiguous:

E ::= num
    | + E E
    | - E E
    | * E E
    | / E E

Since the operators are explicitly part of the productions (e.g., + E E), there is no ambiguity in
deciding which operator applies at any point, because each production begins with a unique
operator symbol, and no production yields the empty string. For any string generated by this
grammar, the first operator in the string (e.g., +, -, *, /) uniquely determines the structure of the
parse tree. Once the first operator is identified, it’s clear that the next two sub-expressions will
be parsed as E. This fixed structure ensures that no two distinct parse trees can be formed for
the same string.

Notice, however, that the grammar below is still ambiguous, even though every production starts
with a different non-terminal:

E   ::= num F
     | '(' E ')' F
F   ::= '+' E F
     | '-' E F
     | '*' E F

     | '/' E F
     | ε

The production for F can generate the empty string, which allows expressions to stop at
arbitrary points, leading to ambiguity. The empty string production for F plays a role in the
ambiguity by allowing the parser to end a sub-expression (E) at different points. When F ::=
empty, it terminates the current expression, which can lead to different groupings of operators
and operands.

from Exp import *
from Lexer import *

class Parser:
    def __init__(self, lexer):
        self.lexer = lexer
        self.current_token = self.lexer.next_valid_token()

    def eat(self, token_type):
        if self.current_token.kind == token_type:
            self.current_token = self.lexer.next_valid_token()
        else:
            raise ValueError(f"Unexpected token: {self.current_token.kind}")

    def E(self):
        exp = self.T()
        token = self.current_token

         if token.kind == TokenType.ADD:
             self.eat(TokenType.ADD)
             right = self.E()
             exp = Add(exp, right)

        elif token.kind == TokenType.SUB:
            self.eat(TokenType.SUB)
            right = self.E()
            exp = Sub(exp, right)

        return exp

    def T(self):
        exp = self.F()
        token = self.current_token

        if token.kind == TokenType.MUL:
            self.eat(TokenType.MUL)
            right = self.T()
            exp = Mul(exp, right)

        elif token.kind == TokenType.DIV:
            self.eat(TokenType.DIV)
            right = self.T()
            exp = Div(exp, right)

        return exp

    def F(self):
        token = self.current_token

        if token.kind == TokenType.NUM:
            self.eat(TokenType.NUM)
            return Num(int(token.text))

        elif token.kind == TokenType.LPR: # '('
            self.eat(TokenType.LPR)
            node = self.E()
            self.eat(TokenType.RPR) # ')'
            return node

This last grammar has an indirect left recursion. Yet we could implement a
parser easily. When is left recursion a problem?
The grammar is indirectly left-recursive, meaning there's an intermediate production (like T or
F) before returning to the original rule (E). This doesn't lead to immediate infinite recursion
because the parser still consumes input as it processes these intermediate productions. So, the
recursion doesn't happen "infinitely" without progress.

Is there a general procedure to change a grammar like " E ::= num '+'
E | num '*' E | empty", so that the precedence of multiplication
becomes higher than addition's?
To make * have higher precedence than +, we need to separate them into different levels of
the grammar. The general rule is to create a new non-terminal for each precedence level.

   1.​ Create separate non-terminals:
          ○​ Introduce a non-terminal for each level of precedence. For example, use T for
             terms involving * and F for numbers or parenthesized expressions.
   2.​ Make the higher precedence operator appear deeper in the tree:
         ○​ Place the higher precedence operator (*) at the lower level (i.e., in the T
               production), and place the lower precedence operator (+) at the higher level (i.e.,
               in the E production).

The parser fails to correctly compute "2 - 3 - 4". Why?
Our current parser produces "3", instead of "-5". This happens because the parser is
right-associative. It parses "2 - 3 - 4" as "2 - (3 - 4)", and not as "(2-3)-4". In this grammar,
recursion happens on the right side of each operator (e.g., + E, * T), so the operations are
grouped from the right, making it right-associative.

Can you further modify it, so that the grammar becomes left associative?
A grammar is left-associative if operators are grouped from the left in cases of equal
precedence. This means that expressions like a - b - c are parsed as (a - b) - c (the left side is
evaluated first).

E ::= T EE

EE ::= '+' T EE
    | '-' T EE
    | empty

T ::= F TT

TT ::= '*' F TT
    | '/' F TT
    | empty

F ::= num
    | '(' E ')'

E' ::= '+' T E' and E' ::= '-' T E' allow an expression like a - b - c to be
parsed by first evaluating a - b (through recursion on E'), and then combining the result with
c. The recursion happens on the leftmost operand first. Similarly, T' ::= '*' F T' and T'
::= '/' F T' make sure that multiplication and division are also grouped from the left. In
short, when processing E' ::= '+' T E', we only move onto E' once we are done with T,
which comes on the left of E'.

            right = self.T()
            return self.EE(Sub(left, right))

        # If no more operators, return the current node.
        return left

        exp = self.F()
        return self.TT(exp)

    def TT(self, left):
        token = self.current_token

        if token.kind == TokenType.MUL:
            self.eat(TokenType.MUL)
            right = self.F()
            return self.TT(Mul(left, right))

        elif token.kind == TokenType.DIV:

            right = self.F()
            return self.TT(Div(left, right))

        # If no more operators, return the current node.
        return left

            return Num(int(token.text))

        elif token.kind == TokenType.LPR: # '('
            self.eat(TokenType.LPR)
            node = self.E()
            self.eat(TokenType.RPR) # ')'
            return node

So, is it the case that any context-free language can be parsed by a
recursive descent parser?
Alas, not really! While any context-free grammar (CFG) can be rewritten to remove left
recursion, there are other challenges that arise in recursive descent parsing, especially when it
comes to ambiguity and lookahead requirements.

Limitations of Recursive Descent Parsing:

   1.​ LL(k) Grammars: Recursive descent parsers are generally limited to LL(k) grammars,
       which means they are suitable for grammars that can be parsed with at most k tokens
       of lookahead in a left-to-right scan of the input and leftmost derivation of the parse
       tree.
           ○​ LL(k) grammar: A grammar where the parser can decide which production to
              apply based on the next k tokens in the input.

       However, not all context-free grammars are LL(k). Some grammars require more
       complex parsing strategies (such as LR parsing), or they may require more than k
       tokens of lookahead to resolve which production to apply.

   2.​ Ambiguity: Some context-free languages are inherently ambiguous. An ambiguous
       grammar is one where a given input can have more than one valid parse tree.
       Recursive descent parsers can struggle with ambiguity, since they typically expect a
       single, deterministic path through the grammar.
           ○​ Example: The classic dangling else problem in conditional expressions can lead
               to ambiguity in parsing.
   3.​ Non-Deterministic Grammars: Some CFGs are non-deterministic, meaning that the
       parser might not be able to decide which production to use without considering multiple
       options. Recursive descent parsers are deterministic, and if the parser encounters a
       point where it cannot decide between two options, it might fail.
   4.​ Left-Factoring: Even after removing left recursion, certain grammars may require
       left-factoring to make them compatible with recursive descent parsing. Left-factoring is
       the process of transforming a grammar to avoid common prefixes in different productions
       of a non-terminal, so the parser can decide which production to apply based on a single
       token or small lookahead.
           ○​ Example: A ::= α β | α γ Can be left-factored to: A ::= α A' and A' ::= β | γ

So, what's LL(k) languages? Or should I say LL(k) parsers?
You should refer to LL(k) parsers, not LL(k) languages. LL(k) describes a class of parsers and
grammars rather than a class of languages. Here's a breakdown of what LL(k) parsers are:

What is an LL(k) Parser?

An LL(k) parser is a top-down parser for context-free grammars that processes the input
left-to-right (L) and constructs a leftmost derivation (L) of the input string. The (k) part refers
to how many tokens of lookahead the parser can use to make decisions during parsing.

   ●​ L: The parser reads the input from left to right.
   ●​ L: The parser produces a leftmost derivation of the input, meaning it constructs the
      parse tree by expanding the leftmost non-terminal first.
   ●​ k: The parser uses up to k tokens of lookahead to decide which grammar rule to apply
      at each step. For example, LL(1) parsers use 1 token of lookahead.

Characteristics of LL(k) Parsers:

   1.​ Top-down Parsing: LL(k) parsers begin parsing from the start symbol of the grammar
       and try to match the input string to the grammar’s productions. They expand
       non-terminals by applying productions until they can match the input tokens.
   2.​ Predictive Parsing: LL(k) parsers are also called predictive parsers because they try
       to predict which production to use by looking ahead at the next k tokens in the input. In
       an LL(1) parser, for instance, the parser makes decisions based on just one token of
       lookahead.
   3.​ Deterministic: LL(k) parsers are deterministic. For any input, they follow a single path of
       decisions without backtracking or guessing. This determinism means that the grammar
       must be unambiguous and compatible with the predictive parsing strategy.
   4.​ Left-to-Right Parsing: The parser processes the input from the leftmost token to the
       rightmost token, consuming each token as it builds the parse tree.

Why are LL(k) parsers important?

   1.​ Efficiency: LL(k) parsers are typically very efficient, especially when k = 1, because
       they make decisions based on a small, fixed number of lookahead tokens. LL(1) parsers
       are often used in compiler design due to their simplicity and efficiency.
   2.​ Simple to Implement: LL(k) parsers can often be implemented as recursive descent
       parsers. Each non-terminal in the grammar corresponds to a function in the parser, and
       parsing can be accomplished using straightforward recursive functions.
   3.​ Limitations: Not all grammars are LL(k) for any finite k. In particular, LL(k) parsers have
       trouble with:
           ○​ Left recursion: Grammars with left recursion (e.g., E ::= E + T) can't be
               parsed by LL(k) parsers.

           ○​ Ambiguity: LL(k) parsers can’t handle ambiguous grammars (where an input
              string can have more than one valid parse tree).
           ○​ Lookahead: Some grammars require more than k tokens of lookahead to make
              decisions. In practice, most parsers use LL(1) (1 token of lookahead), but LL(2)
              or higher is needed for some more complex grammars.

So, is it an if-and-only-if situation between LL(k) grammars and recursive
descent parsers?
Yes, it is essentially an if-and-only-if relationship between LL(k) grammars and recursive
descent parsers. Here’s the reasoning behind both directions:

1. If a grammar is LL(k), it can be parsed by a recursive descent parser.

This is true. LL(k) grammars are specifically designed to be parsed using predictive parsing
techniques like recursive descent. Recursive descent parsers work by:

   ●​ Reading the input from left to right.
   ●​ Applying a leftmost derivation (i.e., expanding the leftmost non-terminal first).
   ●​ Using up to k lookahead tokens to decide which production rule to apply at each step.

Since LL(k) grammars allow for parsing decisions to be made with up to k tokens of lookahead,
recursive descent parsers can handle them effectively. Therefore, any LL(k) grammar can be
parsed by a recursive descent parser.

2. If a recursive descent parser can parse a grammar, then the grammar is
LL(k).

This is also true. For a recursive descent parser to work:

   ●​ The grammar must be predictive, meaning that at each step, the parser must be able to
      determine the correct production rule based on a bounded number of lookahead tokens.
   ●​ The grammar must be non-ambiguous and non-left-recursive (left recursion needs to
      be eliminated to avoid infinite recursion in a recursive descent parser).

These are precisely the characteristics of an LL(k) grammar. If a recursive descent parser can
successfully parse a grammar, then by definition:

   ●​ The grammar allows decisions to be made based on k lookahead tokens.
   ●​ It follows leftmost derivation.

Thus, the grammar must be LL(k) for some k.

In Summary:

   ●​ If a grammar is LL(k), it can definitely be parsed by a recursive descent parser.
   ●​ If a grammar can be parsed by a recursive descent parser, then it must be LL(k)
      (because the parser's ability to decide the next production based on bounded lookahead
      is a hallmark of LL(k) grammars).

Therefore, the relationship is if-and-only-if:

   ●​ A grammar is LL(k) if and only if it can be parsed by a recursive descent parser.

Recursive Descent Parsers and Non-LL(k) Grammars:

While recursive descent parsers are naturally suited for LL(k) grammars, they cannot handle all
context-free grammars. For example, grammars with left recursion or ambiguities might not be
suitable for recursive descent parsing without modifications, such as removing left recursion or
transforming the grammar to fit the LL(k) form.

What would be the asymptotic complexity of LL(k) parsing?
Well, the answer to this question depends a bit on how you detail the question itself. If we
consider a fixed grammar, and a fixed k, then the complexity of parsing is O(n), where n is the
size of the input string.

Why LL(k) Parsing is O(n) if we fix the grammar and the k:

   1.​ Single Pass over the Input:
          ○​ LL(k) parsers, including both recursive descent and table-driven variants, process
              the input from left to right, making a single pass over the input string. At each
              step, they:
                  ■​ Use the current token(s) and possibly the next k lookahead tokens to
                       decide which production rule to apply.
                  ■​ Consume tokens and build the parse tree incrementally.
          ○​ Since the parser processes each token once, the total work done is proportional
              to the length of the input, resulting in O(n) time complexity.
   2.​ Constant Lookahead (k):
          ○​ The k in LL(k) refers to the number of lookahead tokens that the parser might
              need at any point to make a decision. The value of k is constant for a given LL(k)
              grammar, so even though the parser may look ahead k tokens at each step, this
              lookahead doesn’t depend on the size of the input. Therefore, this constant
              lookahead doesn't affect the overall linear complexity.
   3.​ Predictive Parsing:
          ○​ LL(k) parsers are predictive parsers, meaning they can predict which production
              to use based on a bounded number of lookahead tokens. They don’t need to
              backtrack (unlike backtracking parsers), which is one reason why they achieve
              linear time complexity.

General Complexity of LL(k) Parsers:
If we consider any grammar, and any k, then these factors will contribute to the overall
asymptotic complexity. Given an arbitrary grammar, a parameter k, and an input string of length
n, the overall complexity can be affected by several factors, including both n and k. Here’s how
these can contribute:

   1.​ Input:
          ○​ Parsing requires us going over every token in the input; hence, it is at least O(n).
   2.​ Lookahead:
          ○​ If we don't fix the k (meaning that we want the complexity for any given k), then
              the size of the lookahead will be part of the complexity; hence, it will be at least
              O(k * n). However, k will be a constant if we fix the implementation of the parser.
   3.​ Grammar Depth:
          ○​ The depth of recursion in the grammar’s structure affects the constant factor in
              parsing. The time complexity, letting the grammar vary, will include terms like
              O(m * d * n), where m is the number of production rules and d is the depth of
              recursion. However, m and d are constants if we fix the grammar.
   4.​ Parsing Table Size (for Table-Driven Parsers):
          ○​ For an LL(k) parser implemented with a parsing table (non-recursive), the size of
              the table can grow exponentially with k, leading to space complexity of O(V *
              k^V), where V is the number of non-terminals. This space complexity doesn't
              usually affect the time complexity directly, but it is a factor in the practicality of
              larger k values.

Theoretical Worst-Case Complexity:

In the theoretical worst case, if you consider an arbitrary grammar and a variable k, the
complexity might look like this:

   ●​ Time complexity: O(k * m * d * n), where:
          ○​ k is the number of lookahead tokens,
          ○​ m is the number of production rules,
          ○​ d is the maximum recursion depth (which can vary depending on the grammar),
             and
          ○​ n is the length of the input string.
   ●​ Space complexity: The space complexity is usually linear in n, but for table-driven
      parsers, the size of the parsing table can grow exponentially in k, resulting in O(V * kV)
      for non-terminal V.

          ○​ Lucas contributed to the implementation of ALGOL 60, a language that
             introduced structured programming and influenced virtually every modern
             programming language.
          ○​ His work involved designing techniques for parsing and translating ALGOL
             programs into executable code.
   3.​ Vienna Definition Language (VDL):
          ○​ As part of the Vienna group, Lucas helped develop the Vienna Definition
             Language, one of the first tools for formally specifying the semantics of
             programming languages.
          ○​ VDL was famously used to define PL/I, introducing a mathematical approach to
             describing language behavior.
   4.​ Formal Methods and Semantics:

          ○​ Lucas advanced the field of formal methods, providing rigorous frameworks for
             reasoning about programming languages and their implementation.
          ○​ His work laid the groundwork for the modern study of programming language
             semantics and influenced formal verification techniques.
   5.​ Theoretical Computer Science:
          ○​ Lucas explored topics like syntax-directed translation, block structure in
             programming languages, and hierarchical representations of programs.
          ○​ His theoretical insights into language design and compiler construction have had
             long-lasting impacts on both academic research and practical compiler
             development.

Legacy

Peter Lucas’ work bridged the gap between theory and practice in early computing. His
pioneering efforts in parsing, formal language definition, and compiler design continue to
influence the development of programming languages and compilers. While his contributions
are often associated with foundational work in the 1960s, their relevance endures in modern
computer science.
