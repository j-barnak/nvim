
Compilation & Linking

     Compilation is the process of transforming code from a human-readable language
to a machine-readable one. The compiler parses the code, assigning memory locations
and registers for variables. It then processes each code unit (read: file) in turn, taking
its routines and emitting the code to implem ent them in the native instruction set.

    Compilation is highly specific, and the emitted code may vary with the compiler
used. Windows uses MSVC, and Darwin uses clang, which is also used in Android,
though Linux still uses the venerable gce. ARM has its own cross platform compiler
(Currently in version 6.9), part of the ARM DeveloRment Studio [adsl, and maintains its
own GNU toolchain [agt] as well.

      In reality, all of these hide several internal stages of the process:

 1.    Pre-p-rocessingl #include-ing headers, #define-ing and expanding macros.
 2.    Comp-ilation: Converting the high level language sources into machine-specific
       assembly, and then further assembling - i.e . converting to the machine code
       bytes in an object file.
 3.    Linkingl Integrating multiple object files and clearly marking the external
       dependencies, so they can be resolved at run-time.

     Each of these stages probably merits its own book. Numerous books deal with the
dark arts of compilation . A far more detailed work focusing on linking is the (somewhat
dated but otherwise) excellent Linkers & Loaders [ll] by John Levine (no relation to the
author). This chapter aims to focus on those specific aspects of particular importance to
efficient programming, optimizations, and debugging.

1.5. Pragmas

     A pragma is a compiler- specific directive, allowing developers to precisely define or
overrid e compi ler behaviors. They can be defined similar to preprocessor directives in
lines beginning with #pragma. As of C99, pragmas can also be defined using th e
_Pragma keyword, which enables th eir embedding into other macros.

    Some pragmas are stand ardized, but others vary with choice of compiler. These
usually follow the compiler lang (e.g. #pragma clang optimize off or #pragma gcc
... ), though clang honors a large number of gcc pragmas as well. A special class of
pragmas are those of amp. These enable OpenMP (Open Multi-Processing) directi ves,
which empower the compiler to parallelize th e generated code by automatically emitting
SIMD or even multithreadi ng code.

     Sometimes, #included, macro-expanded or other embedded code might need to
alter its own pragma settings, without affecting settings elsewhere. For this, push () and
pop() may be used . The com piler maintains a stack, enabling code to safely push() the
existi ng setting s, modify them in whatever way, and then restore them to what they
we re before using pop ( ). The recursive natu re of the stack makes it safe to use
push( )/pop() comb ination s multiple tim es, so lon g as the order is maintained (though
clang implicitly assumes an unpaired pop () reverts to the the settings at the beg inning
of the file).

     2.1. Optimization

          Modern comp ilers can do much more than just generate code - they also optimize
     it. Optimization generates code that is best suited for the task.

         Optimization often makes the assembly harder to read, preferring the more esoteric
     yet highly specialized instructions over the common ones . In the domain of C/C++,
     likewise quaint keywords which are rarely used can make the difference between truly
     optimized code and bug-ridden code . Indeed, the general paradigm is to perform
     rigorous debugging prior to compiling with optimization , as it may rarely introduce
     highly elusive bugs, particularly when concurrency is involved .

     2.1.1. Optimization Levels

     gcc (1) 's man page details each level of optimization with respect to what features it
     enables, whereas clang (1) 's man page remains more vague . gcc (1) can also display
     the details behind each optimization level using a combination of -Q and --
     he lp=opt imize rs.

         The -00 is used for the quickest, yet also most inefficient compilation . Code is
     compiled as is, with minimal passes and no re duction of redundant or dead code. This
     option is commonly used as the baseline for debugging, for two reasons:

       •   Debug-friendly' code: Most notably, code generated by -00 will save function
           arguments on the stack. This is not at all conducive to performance (since it

           instrumental for debugging. The function prolog is extended with code to save all
           arguments, which allows the compiler to easily switch to any frame in the ca ll
           stack (assuming no stack corruption) .

         2.4. GCC: Profiling (Linux)

             Programs can be built with profiling support. gcc's -pg switch inserts ca ll s to
         mcount (3!) on every function entry. This fun ction tracks the function cal l and time
         spent in function (and can also be called manually using the FUNCTION_PROFILER and
         PROFILE_HOOK built-in macros). On successful program ex it (2), the results are output
         into a gmon. out file. The file can then be passed (along with the -pged binary) to
         gprof(l), the GNU profiler, which can then produce a flat-profile, graph and/or
         annotated-source .

               This feature can also be used on shared object - using the LD_PROFILE environment
         varipble (with the name of the shared object) and the LD_PROFILE_OUTPUT environment
         va r iable (to specify an output directory wherein the libraryName.so .profile gprof (1)
         output will be generated.

             clang (1) does not support -pg and Darwin has no gprof (1), but ~g~~
         source g.perftools [gperf] is sometimes used, and offers TCMalloc, a heap (memory)
         profiler and a CPU profiler.

2.5.4. DWARF

    Both ELF and Mach-O store debug information using OWARF
(unofficially, a backronym for "Debugging with Arbitrary Record
Formats", but really a companion to ELF). DWARF has been
standardized, and is currently in Version S[dS) (with work on Version
6 underway), though gcc and clang both still use Version 4. ARM
has extended DWARF[adw) to encode the ARM64 registers. A
detailed presentation [dp] on the format is also available.

    Information in debugging sections of ELF and Mach-O is encoded as DWARF
Information Elements (DIE). The Information Elements are specified as OW_TAGs, and
each may have OW_ATtributes. The elements form a forest of trees. Each tree root is a
OW_ TAG_compi le_ uni t of a file . The OW_ATtributes of the compile unit specify the
compil er and file metadata, as well as the resulting object address range (from
DT_AT_low_pc to DW_AT_high_pc). Routin es in the file are encod ed with
DW_TAG_subprogram elements. Parameters to routines are encod ed with
OW_ TAG_ fo rma l_pa rameter elements. Variables are encoded as OW_ TAG_va riab le
eleme nts, within which additional OW_TAG_"._type elements encode the declaration
modifier. The standard is highly extensible, OT_TAGs and OW_ATtributes are added by
newer versions, or by vendor extensions*.

    A complete discussion of each element's formatting is outside the scope of this
book, and is deemed largely unnecessary, since debugging tools - from gdb and lldb
through dwarfdump - are capable of displaying the information. Output 2/2-11 (next
page) provides an annotated example.

2.5.5. ULEB128

    Dwarf information elements often make use of two proprietary binary compression
schem es, referred to as [Ujnsigned Little Endian Base 128 ([U]LEB128). The idea
behind both schemes is to optimize for cases wherein a list of binary numbers that are
not so far apart needs to be compre ssed. Whethere the scheme is LEB-128 or ULEB-128
depends only on if the list is monotonically increasing.

     Encoding a number into ULEB 128 first requires zero-extending such that the length
of its total bit representation is a multiple of 7 . Then, each seven bits are output
verbatim, with a '1' bit added as the most significant bit, save for the last byte.

    For example, encoding 0x1e20 and 0xlfc:

0x1e20 = 0001111000100000 ==> 00 0111100                    0100000
                                             I          I    I           I

0x1fc            000111111100                0000011         1111100
                                             I          I
                                             0000011        01111100

                                                 0x3              0x7c

Decoding takes each byte, copies its low order bits into the result starting with the least
signifi cant, and continues so long as the high order bit is not '1' . Using the example
above to decode we would have:

Byte: 0xa0, low order 7: 0x20, pas: 0, interim result: 0x20                              (MSb is 111 I continue)
Byte: 0x3c, low order 7: 0x3c, pas: 7, interim result: 0x1e20                            (MSb is '0' so stop)

Byte: 0xfc, low order 7: 0x7c, pos: 0, interim result: 0x7c                          (MSb is 111, continue)

          Libraries are object files which contain routines, indexed in some type of table of

     3.1. Static linking

           Static linking is performed as the last ste p of the co mpilation , if external
     dependencies can al l be located, and the developer chooses to do so . In these cases,
     the linker locates the code for the specific symbo ls required by the cal ler, and copies
     th em into the final executable object. By convention, the static linker is called "ld" (or
     ld 64), and may also be invoked as a single step on compiled-but-not-linked objects
     (i.e . created by cc -c). When invoked through the umbrella cc, the linker ca n be
     passed options with -Wl .

          "True" static linking (i.e. one wherein the resu lting binary is prelinked with all
     libraries, and needs no dynamic linking) is rather ra re in modern OSes, but fairly
     common in embedded environm ents . Bootload ers , for examples, are statically linked, as
     are many SoC firmware co mponents . Apple 's firmwa re files use "RTKit", a set of
     statica ll y linked archives prelinked into the firmware s.

     fact, since a statically linked binary needs no interpreter (= Iinker), binari es in either
     platform using common dependencies (i.e. no Androidi sms) will be able to execute
     correctly on both platform s, so long as the underlying architecture is th e same. To
     compile statically, use the -s tatic keyword .

     3.2.3. Load Time Linking

         Load-time dy:namic linking occurs before the binary 's actual entry pO int. The
     dynamic linker parses the binary, to determine both the imports and the stubs . It then
     searches for and loads w hichever external libraries are required, perform ing the linkage ,
     and running those libraries' initializers (if any ). Dynamic li nking is recursive , in th at any
     nested dependencies must be satisfied in the same way. Only after all dependencies
     have been resolved, the linker passes control to the bina ry' s entry pO in t .

          Should any library not be loaded properly, or a symbol not be found, the binary will
     crash before its entry pOint, as the linker will voluntarily abo rt (3). An exception to this
     are symbols defined using __ attribute( (weak) ) __ . If linkage of such symbols fails,
     th e linker silently co ntinues. The onus of error hand li ng then passes to the developer,
     wh o is expected to check the symbols against NULL.

           The temporal flow of load time linking makes it useful in ensuring proper library
     ini tialization, especially for security. Both macOS and Android use this trick to
     containerize binaries - in the App Sandbox (macOS, q.v. M-HI/8), or SECCOMP-BPF
     (An droid, q.V. A-HI/2).

           Of particular importance is the ability to specify additional libraries for load time
     lin king. This is performed through an environment variable - LD_PRELOAD in the case of
     Lin ux/Android, and DYLD_INSERT_LIBRARIES in Darwin . These are functionally
     equi valent to the binary's own dependenCies, in that they must be found and linked
     before the main () - which makes the environment variable a useful vehicle for injecting
     code into processes, as discussed in 10/1. Note, that because of the obvious security
     impl ications, the environment variable is voided for processes marked as AT_S ECURE
     (ELF) or restricted (Mach-O).

     3.2.4. Run Time Linking

          Run-time dy:namic linking occurs after control has been passed from the dynamic

     calls go directly to the symbo l, rather than (again) to the li nker itself. As with load-time
     lin king, failure to bind a symbol will cause an abo rt (3) .

      La zy bin ding was traditiona lly preferred in cases where in depend encies on man y
symbo ls may hinder process sta rtup tim e. Lazy symbo ls are lin ked on f irst use, there by
deferring the work and amortizing the computational overhead. In earl ier versions of
Darwin, lazy linking could be overridden with the -bind_at_load option, specified

3.3. Relocations

     Pos ition Independent Execu tables ( PIEs ) are commonplace. Dynamic libraries
natura lly fill this requirement, since the ir load address is not a priori known ( and cannot
be fixed , as it might collide with oth er addresses). Executables are also encouraged to
opt into this configuration (using -pie and -fPIC ), to benefit from Address Space
Layout Randomization (ASLR).

      From the ARM assembly perspective, PIE is inherently supported through
in stru ctions' PC-relative addressing (q.v. 1/2 . 1.1 for an example). A problem arises,
howev er, with pointer values inside the binary (commonly, in the data sections). These
originally assume some base load address, dictated by the binary format's
segm entation. The load address, however, will be slid by some value (per ASLR),
necessitating the rebasing or relocating of these pointer values.

    It is unfeasible to have the linker detect pointer values by " look" . Low pointer values
(such as those of ELF32 or ELF64, w hich assume a base of OxO) could be mistaken for
integers, and even high value 64-bit pointers (such as those of Mach -O, whi ch assume
as base of Ox100000000) could be m ista ken for 32-bit integer pairs . It's required,
therefore , that the binary format encode pOinter locations with some type of metadata
format.

   3.5. Linker Security

       With its omnipresence across processes, the linker is a critical component of system
   security. The main attack vector is through the environment variables, since powerful
   ones (particularly LD_PRELOAD/DYLD_INSERT_LI BRARIES) can be used to cajole the
   linker to insert foreign libraries into privileg ed processes, leading to privilege escalation .

   3.5.1. Linux/Android: AT_SECURE

       The ELF linkers defer the decision of whether the process is secure or not to the
   kernel. Th e value (AT_SECURE) is reported in user mode as part of the AUXiliary Vector,
   using getauxv (3) .

   3.5.2. Darwin: DYLD security
