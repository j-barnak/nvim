          The Executable & Library Format (ELF) was first developed to be the format of
     choice for the legendary UN*X System V Release 4 (SVR4), instead of the more
     venerable (and, by now, dead) a.out object format. Since its introduction , it has gained
     popularity in many other UN *X variants, becoming the file format of choice for virtually
     all (with the notable exception of Darwin, which uses its own proprietary Mach-O).

          ELF was designed to be extensible and cross platform, and is well documented in
     several references [~l . Indeed, over the past four decades it has been extended to
     support different architectures (most recently, ARMv8) and platforms (e.g . Android),
     through new constant values and section types. Th is discussion aims to recap the
     salient features of the file format, emphasizing the Linu x/ Android implementation .

     1.1. The ELF header
         The ELF header starts with 16 (EI_NIDENT) bytes. The first four of these are the
     "magic" bytes of 0x7F 0x45 0x4C 0x46 (0x464c457f in li ttle end ian) , which is the non
     printable \x7F followed by 'E' 'L' 'F'. Following the magic are five more bytes, indicating
     32/64 bitness, endianness, target OS, and ABI versions. The remaining seven bytes are
     deemed " reserved".

          The rest of the ELF header is contains some 13 other fields, indicating offsets/sizes
     of the rest of the two other head ers - the program header, and the section header. The
     overall size of these fields, however, varies depending on the bitness . In code, this is
     impl emented by two separate headers, El f32_Ehd rand El f64_Ehd r, respectively. The
     following listing collapses these into one pseudo-code definition:

             The other fields defined by the file header are :

         •    e_type, defining the file type. Although there is an ET_EXECutable type,
              executables and libraries alike use ET_DYN, specifying a shared object.
         •    e_mac hine, defining the target architecture . This work's focus is on ARM64
              binaries, wherein this field is set to EM_AARCH64 (183).
         •    e_version, defining the header version - this is set to EV_CURRENT (1).

         •    e_shnum Section Headers, each e_shentsize bytes, at p_shOff into the file,
              commonly at the end of the file.
         •    e_shst rndx, indicating the index of the section header string tables. This is
              required when iterating over the section headers, to display section names.

1.4.3. Symbol Tables ( . dynsym/ .symtab, OT _OYMSTAB, SHT_OYNSYM/SHT _SYMTAB)

     An ELF file contains one or more symbol tables. Each symbol table is connected to a
string table (holding the symbol names) using its section header's sh_link field, which
will hold the corresponding string table's section index.

    The symbol table required for dynamic linking is indicated by the PT_DYNAMIC's
DT_SYMTAB entry. It is commonly named. dynsym, and associated with. dynst r.

    Another important symbol table is the (larger) . symtab (not specified in the
PT_DYNAMIC, and typed as SHT_SYMTAB), usually associated with. st rtab . The pair
contains many more symbols, including internal ones useful for debugging, but are
usually not present in strip(l)ed binaries .

    The symbol tables are arrays of fixed sized (DT_SYMENT bytes) El f64_Sym
structures. Each structure is defined as follows:

                                                             Listing2l1-12: The Elf64_Sym structure
typedef struct {
         Elf64_Wo r d                                          st_name;                                   1* String table index of name. *1
         unsigned char                                         st_info;                                   1* Type and binding information. *1
         unsigned char                                         st_other;                                  1* Reserved (not used). *1
         Elf64_Half                                            st_shndx;                                  1* Section index of symbol. *1

    •      st_name holds the offset of the symbol name in the related string table (i.e. the
           one associated by the section header's sh_link).
    •      st_value holds the value of the symbol, which is 0 for unresolved symbols, or
           non-zero for adresses in the file.
    •      st_shndx holds the section index associated with this symbol (which can also be
           resolved in a slow path, via the st_value). For unresolved symbols, this is 0.
    •      st_info encodes binding information in the four least significant bits as
           STB_[LOCAL/GLOBAL/WEAK] (0/1/2, with 10-15 reserved for extensions), and type
           information as STT_ [OBJECT IFUNCI ... ] (0 .. 6 with 10-15 reserved) in the rest.
           ELF64_ST_ [BIND/TYPE] macros can be used to isolate the bit fields.
    •      st_other encodes symbol visibility in th e two least significant bits (using the
           ELF64_ST_VISIBILITY macro), leaving the others unused . ARM defines
           STO_AARCH64_VARIANT_PCS (0x80) here to indicate the symbol is using a different
           calling convention than the ARM pes.

    1.5.2. Android: SHT_ANDROID_REL[AJ

        Android 's linker (part of Bionic) allowed Google to experiment with several alternate
    formats for relocations. Starting with Android 6, SHT_ANDROID_REL[AJ (SHT_LOOS +1/2,
    with corresponding DT_ANDROID_REL[AJ [SlJ in the DT_LOOS +2/3/4 space) are used in
    place of the standard SHT_REL [AJ. These use a proprietary format, ident if ied by a magic
    of APS2.

        APS2 aims to improve of ELF RELA by utilizing ULEB128. As previously discussed in
    2/2.5 .5, ULEB128 excels in compressing offsets by first setting the base offset, and
    then encoding delta values. Because the deltae are relatively small with respect to the
    base, this often results in a significant space savings .

        APS2 was never formally documented, but was Part of Bionic's sources [aps2 ] from
    Android 6.0 through 9.0. The format has been deprecated in favor of RELR (discussed
    next), but may still be ex plicilty emitted by the Android NDK's linker when compiling
    with-Wl, --pack-dyn - re locs=and roid.

     1.5.3. RELR

         The SHT_RELR section type was introduced as illL..eXperimental relocation [relr)
     section by Google. As such, it originally (in API level 28) used the OS-specific
     extensions of SHT_ANDROID_RELR and DT_ANDROID_RELR*, before being standardized (in
     API level 30).

         The standard defines PT_DYNAMIC elements DT_RELRSZ, DT_RELR and DT_RELRENT
     (values 35-37), paralleling those of DT_REL . These effectively deprecate
     DT _ANDROID_REL[A] (which are still supported for backward compatibility). The two
     formats can coexist, as shown previously in Output 1-10.

         The idea behind SHT_R ELR is to improve the efficiency of SHT_RELA. Each entry is
     64-bits, but relocations are limited only to even addresses (those with a least significant
     bit of '0'), and entries with even addresses will be relocated. The first entry is always
     even, and serves as the base of all relocations.

         The trick lies in how odd entries (those with a least significant bit of '1') are
     handled. Because those, by definition , cannot encode addresses, they are instead taken
     as 63-bit bitmasks, covering the next 63 uint64_t entries which follow the previous
     entry. A bit of '1' in a position implies that the entry at the corresponding address needs
     to be relocated. The DT_RELR section often handles relocations in data. rel. roo

2.1. Prelude: Fat Files

     When Apple was making the transition from PPC to Intel, they encountered a
problem: How can they provide binaries that would target both architectures'
in stru ction sets at once?                            '

2.1.1. The fat header

    The solution chosen, touted as "universal binaries", was informally called "fat" files.
The possibly less appealing name was used because these files packaged multiple
binary "slices" into one larger, bloated file. The resulting file was effectively the size of
both arch itecture specific slices (along with a thin header, with a magic of 0xCAFEBABE),
but would prove more comfortable than maintaining the slices separately.

    XNU's binary loader logic (in bsd/ kern/ kern_exec.c's exec_activate_image ( ... )) wa s
extended to support a fat "image activator". When the kernel encounters a fat file, it
transparently "grades" the slices, to see which one would best fit the machine's
architecture . The user remains entirely oblivious to this, so that executing a fat file is
the same as any other.

    The CPU types and subtypes are specified in <mach/ machine .h>. The file is a
testament to NeXTStep's aspirations for a universal operating system , but most of its
architectures are obsolete * . Apple initially used this for side-by-side PPC/Intel slices,
then for i386/x86_64. With the imminent demise of Intel Macs, this leaves us at present
with side by side x86_64/arm64e (on macOS) and (rarely, in iOS's developer tools)
a rm64/a rm64e.

     As an example of just how obese fat binaries can get, one can consider / usr/li b/ dyld
(with three slices, including the obsolete i386), or / usr/lib/system/ libsystem_kernel. The
latter still has four slices, as demonstrated in Figure 3/2-1.

2.1.2. Architecture selection

   Although the grading often finds the best fit, the user still has the option of
overriding it, by calling posix_spawnattr _setarchpref_np(3) . This library call takes a
cpu_type_t pref and subpref, and returns attributes for use with posix_spawn (2).
From the command line, the arch (1) utility can also be used to specify an architecture.

    Apple 's binutils will often default to the best fit architecture when analyzing fat
binaries. The -a rch switch is often the standard way to select other slices . When
disarm(j) encounters a fat binary, it will require th e choice of best slice through the
ARCH environment variable, which allows you to set a default architecture by expo rting
the variable beforehand .

    The transparent handling of fat files makes th eir handling largely the same as their

      2.5.4. 5 . The Code Signat ure

            Mach - O code signatures were devised by Apple as far back as 10.5, and with every

    It is the Code Directory that is then further hashed (the so called "CDHash"). The
CDHash is then either signed (in the usual Public Key Cryptography manner) by a "CMS

been extended to support "Library Validation", which can limit which dylibs a process is
capable of linking with by their code signature.

     Apple originally devised code signatures to be used in the "traditional" sense of
digital signatures - that is, ensure software authenticity (as in, attribute it to a known
author) and integrity (to ensure it has not been corrupted or tampered with). Over the
years, code signatures have been extended with numerous related facilities, using
negative "slots", corresponding to additional blobs, which can be similarly hashed and
included in the signature . These include:

  •    Embedded Info.p-list: Either as part of the binary (as _TEXT ._info_plist),
       or separately (in the bundle's Contents/ directory).
  •   Code Reguirements: (deprecated) encode a grammar to specify pre-existing
      conditions for an executable or library to be loaded into memory. As of Darwin 20,
      this function is assumed and extended by Launch Constraints.
  •   Code Resources: for bundles only, in the ContentsCCodeSignature/CodeResources f ile.
      This is a property list containing hashes of non-executable resources.
  •    Entitlements: for executables only, providing declaratory permissions and
       capabilities claimed. Undoubtedly the most revolutionary extension to code
       signing and software security in general, these form an integral part of Darwin's
       security since around Darwin 12. Entitlements were originally specified as XML
       (as slot -5), but support for DER (slot -7) exists as of Darwin 16 or so.
  •    Launch Constraints: are the latest (Darwin 20) feature to be integrated into
       code signatures. These deprecate the earlier "Code Requirements", and provide a
       DER grammar to specify the exact circumstances under which a binary will be
       allowed to launch. Such constraints include the parent process or the one
       responsible for the launch, specific files, configurations, and more. This is also
       open to third parties, as documented by Apple at WWDC 2023 .l ww23 ]

      2.6. Darwin 20: Chained Fixups

          Darwin 20 abandons (outside macOS) LCDYLD_INFO and its opcodes in favor of
      chained fixups . This new method provides a different approach to rebasing and
      binding, and add s support for arm64e's Pointer Authentication Codes (PAC), since
      pOinter signing is mandatory in Apple's architectures .

      2.6.1. Pointer formats

           The crux of chai ned fi x ups lies in the observation that high ord er bits of pOinters are
      unused. Even 64-bit architectures use on ly arou nd 40-bits for address ing , leaving on
      order of 24 bits unused . Additionally, the entropy in each encoded pOinter is
      sig nificantly lower than 40-bits, due to the actual address space seldom spanning more
      than a fe w GB .

          As discussed earlier, these high order bits are repurposed by ARMv8 processors,
      whether through TBI, PAC or MTE . The chained fixu ps somewhat similarly reuse the
      high order bits , by encodi ng metadata into them, wh ich includes PAC requirements
      (wh ether or not to authenticate at runtime, with which key, and diversity data), binding
      information (whether or not to bind to an externa l). A few other high bits are
      repurposed to encode the next pOinter to fix up, effectively forming a chain (hence the
      name) of pOinters to be fi xed up.

         2.7. The DYLD Shared Cache

             No discussion of Mach-O can be considered com plete without at least a mention of
         the DYLD Shared Cache (DSC). The DSC is a collection of all the platform libraries and
         frameworks, prelinked into one (or, as of Darwin 20, more) files.

             Prelinking offers many benefits, not the least of which is a noticeable speedup of
         process launch: The work of the dynami c linker (dyld) is dramatically reduced, as load-
         time linking is now required only between the main binary and the cache, and not in
         between library calls.
             The size of the shared cache can be daunting - it was around 1GB when it debuted
         in iOS, and has since more than quadrupled(!), spanning multiple files. The number of
         prelinked images was about 2,880 in macOS 14, and has ballooned to 3,137 in macOS
         10.20. One extenuating factor, however, is that the majority of the cache (the read-only
         portion) only occupies a single copy in physical memory. Another is that unused
         libraries - especially clean ones - can be paged back to disk (or not even mapped),
         reducing the overall memory footprint of the cache.
             The location of the shared cache has also moved several times over the years,
         before settling into jSystem/VolumesjPrebootjCryptexesjlncomingjOSjSystemjlibraryjdyld. In the
         *OS variants this portion of the filesystem is part of the SystemCryptex dmg, allowing
         Apple to patch or update it independently of the rest of iOS, as part of the "Rapid
         Security Responses" (RSRs).

             The DSC has a proprietary header to hold numerous metadata items about its
         mappings and contents. The header is constantly changing, and every version of
         Darwin's dyld brings with it new fields, while obsoleting others*. The header format can

      2.7.6. Shared Cache Resliding (Darwin 20+)

          The shared cache has long suffered from security vulnerabilities, by design. On non
      PAC systems, even though ASLR is employed, the DSC loads at the same address
      (0x180000000), effectively neutering ASLR, and providing a reliable source of ROP and
      JOP gadgets for exploiters. Even on PAC systems some of the keys would have to be
      shared between processes, opening up a PAC bypass.

           Darwin 20 and later attempts to address these concerns, by assigning a "shared
      reg ion identifier":

         •   Through Darwin 22, a special posix_spawn action, PSPA_PTRAUTH_TASK_PORT,
             could be used to specify a SEND right to another task, whose shared cache signing
             key would be used. This was removed in Darwin 23 (XNU-10002, iOS 17).
         •   The default shared region ID is a null string
         •   Third party binaries with a Team ID are assig ned an automatic shared cache
             identifier from their ID, prefixed by "T-".
         •   Binaries entitled with SR_ENTITLEMENT (com . app le. pac. sha red_region_id) are
             assigned an identifier based on the entitlement <st ring> value, prefi xed by "E-".
         •   The shared cache can be explicitly reslid by specifying the undocumented
             _POSIX_SPAWr'CRESLIDE flag (0x0800) to pos ix_spawn (2). This is presently used
             by launchd (1) to respawn processes whose previous demise ended with a reason
             code of OS_REA SON_ FLAG_SHARED REGION_FAULT.

          Darwin 21 adds the shared_region_map_and_slide_2_np system call (#S36), and
      also deprecates a previous system call, shared_region_map_and_slide_np (#438).
      The system call maps a files_count of shared region files, into a mappings_count
      number of mappings. This new system call is used for subcaches.

2.8.5. In memory linking

    A rather unusual use case for linking is in-memory linking, which happens when
the process already holds a memory image of the object file, but it is one that was
obtained without the linker's kn owledge or help. One such example is when such an
image was downloaded from a network connection, as is common with obfuscated or
license-enforcing code.
    dyld offers NSC reateObj ectFileImageFromMemo ry , which takes a pOinter to a
memlmage and its memlmageSize, performs the in-memo ry linking, and populates an
out NSObjectFilelmage. This is used by the higher NSLinkModule (and public) APIs.
    As of Darwin 22, the code flow of NSL inkModule actually creates a temporary file -
/tmp/NSC reateObjecTFileFromMemory-XXXXxxxx ... and calls the traditional d lopen (3)
                                                                                  on it.
This behavior makes it easier to spot malicious use of the APIs, since the filesystem
event is very easy to detect via EndpointSecurity.framework and fsevent s APIs.
Additionally, the r-x map pings required durin g the dlopen(3) can be hooked by
Darwin 's MACF (specifically, AMFI and th e Sandbox), and potentially blocked.
