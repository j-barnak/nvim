
The Process Lifecycle

     Users are familiar with "Apps", "Widgets" and so on, but to the operating system,
these are all processes. A process is an instance of an executable file, loaded into its own
private, virtual memory space. It communicates with the outside world through various
types of descriptors (more on that in Chapter 8) , and - with the kernel - through system
calls.

    Internally, a process may execute serial logic, or may parallelize more threads. Most
process handling utilities and functions tend to ignore threads, focusing on the process-
level view when it comes to lifecycle and resource management. This chapter adopts
the same perspective, leaving Multithreading to be discussed in Chapter 7.

    This chapter explores the lifecycle of processes. Starting with a quick introduction of
system calls as a concept, then those used for birth, lifetime (identifiers) and (natural)
death (as opposed to gruesome accidents and murders, which are left for Chapter 12).

    The chapter then discusses resource utilization, presenting both the standard POSIX
metrics as well as Darwin's ledgers and Linux's cgroups. The latter, along with Linux
namespaces, make up the foundation for lightweight virtualization, a la Docker. Finally,
process level security is examined through the lens of respective system calls, the
proprietary Linux extensions, and Darwin's robust security features.

                      Generally speaking, any process can be thought of as having two types of
                  operations . The first type is that of in memory operations, which involve only moving
                  data items in -between re gisters and/or to/from virtual mem ory. These are non-blocki ng
                  operations, as they do not invol ve any kernel interaction .

                      The second class of operations involve kernel interaction - that is, the functionality
                  requires the process to ca ll on a kernel provided routin e, in order to perform the
                  req uired operation . Th ese are known as system calls .

                       In memory operation s amo unt to little more than register or memory operations, so
                  pra cti call y anything of consequ ence requires a system call . Anothe r way of looking at it
                  is, that any operation which exceeds the process' own virtual memory - must involve a
                  system call. This mean s any I/O operation (file, network or I PC) , process
                  co ntrol/scheduling, and eve n allocating more memory or contro lling it (via memory-
                  related system ca ll s, as we explore later in Chapte r 5).

      1.2. Bypassing system call wrappers

          System calls can be called directly, rather than using wrappers. While generally
      discouraged, there are some cases where this might be beneficial. Common examples
      are in attempting to obfuscate the code, or otherwise hamper reverse engineering.

      1.2.1. Using the generic syscall interface

         The syscall(2) interface is designed to allow for indirect system call invocation.
      The prototype defines this as a routine taking in an int or long system call number,
      and a variable number of arguments (those of the actual syscall to perform) that follow.

          Darwin's headers deprecate syscall(2) in macOS, and "prohibit" its use elsewhere
      using macros. This is malarkey, as there is always the option to #undefine the macros,
      use dynamic linking, or use in line assembly.

      1.2.2. Using inline assembly

          Since system calls are basically just an SVC instruction, it's trivial to re-create
      syscall(2)'s functionality using a simple inline assembly snippet. The code would
      move the first argument (X0) to the platform specific syscall register, and then shift
      other arguments (such that Xl moves to X0 , X2 to Xl, etc). Doing so is left as an
      exercise to the reader.

          It is common practice to in line such functions. This is done both for efficiency, and
      also as a relatively basic form of anti debugging - since it is harder to place breakpoints
      arbitrarily in code, than on a single routine boundary. This practice can easily be
      detected by disarm(j) along with grep SVc.

      1.3. The UNIX standard system calls

           The system call offering varies by operating system, but UN*X-like operating
      systems generally provide the "UNIX Standard" (the <unistd .h> header file). Along with
      other behavior specifications (e.g. process creation and control, threads, signals and
      many more), these make up the Portable Operating System Interface (POSIX) . * The
      built-in manual (specifically, section 2) serves as a good reference for most system
      calls, and The Linux Programming InterfaCe[lprf] > provides an extensive level of detail.

          This work does not aim to provide coverage of every single system call - but does
      discuss the main ones, which are loosely organized by category:

         •   Process op-erations: follow the process lifecycle - from birth to death, through
             setting its attributes and handling resource requirements. These are discussed
             later in this chapter.
         •   Signal handling,;, a limited form of asynchronous notifications. Since a fair
             amount of signals are lethal, they are discussed in Chapter 12.
         •   Memory~p-erations: the system RAM is a shared resource, and thus requires a
             system call for any physical allocations. These are detailed in Chapter 5.
         •   File op-erations: follow the file lifecycle - from open (2) ing to close (2) ing,
             through the various I/O operations (primarily, read(2)/write(2) variants), as
             well as filesystem-Ievel operations. Detailed in Chapter 8.
         •   IPC op-erations: these either use UNIX local IPC (pipes), or follow the socket
             lifecycle. IPC primitives are all special cases of file descriptors, so most I/O
             operations work in the same or similar manner. These are also discussed in
             Chapter 8 .
         •   s'v.stem Information: query statistics, counters or other information about the
             present system.

           In addition to the UNIX standard, operating systems may further extend their
      system call offering for proprietary operations. Such is the case with Linux, Darwin and
      the *BSD variants: the common subset is in the order of 120 syscalls, but Linux's range
      is in the 300+, and that of Darwin is at around 550 at the time of writing .

      * - Note, that while Darwin's macOS is POSIX certified, Linu x is largely "compliant" . Windows is nowhere

      Linu x (WSL, as of Windows 10) offers Linux support (and , thus, its POSIX-compatible APls). As of

      a bare-metal Linu x.

2.1. Birth: The fork(2)/execve(2) model
     POSIX systems (unlike Windows) have traditionally had no notion of creating a new
process. Th e only way to create a process is to perform a mitosis-like operation of
cloning a nearly identi ca l copy of the calling process, by calling the fork(2) system call .
Th e copy differs only in the return value of the fork(2) system call.

    The fork(2) system call is thus uniqu e, in that it can return up to twice (i.e. in both
the parent and the child). In practice, three roads diverge, according to the return value
of the call:

   •    Return value is p-ositive: Indicates the PID of the child process created, and
        that this process is the parent. The common pra ctice here is for the parent to
        continue executing, and usually wait*(2) for the chi ld.
   •    Return value is 0: Indicates that this process is the child. The common pra ctice
        here is for the child to deviate from the parent's flow, usually by loading some
        new binary. The ex ecve(2) is used for th is purpose, as it effectively "hollows out"
        t he process, maintaining its PID but clearing its memory to loa d anoth er binary
        image, and restart at the linker entry point.
   •    Return value is -1: Indicates that th e ca ll has failed, and that this process is
        (still) the parent. Thi s can occur on low resource (pri marily, memory) con dition s.
        The common practice here is to eithe r retry, or abort.

      2.3 . Lifetime: Process Identifiers

          Throughout its lifetime, every process is assigned and identified by a process id .
      This is a pid_t, ran gi ng from 1 to PID_MAX. This value is used at runt im e to refer to

                     shows "processes" by their TGID.

2.4. Death

        A process' lifecycle draws to its end in one of two general cases:

    •    Normal termination (exit)..;. When a process has fulfilled its purpose and its
         code flow has reached its end, it calls the exit (2) system call. The meaning of
         life is summed up in a single 32-bit value - its exit status, which is also the only
         parameter accepted by the system call. The convention here is to provide 0 as an
         indication of success, or some non-zero value as an error code.
    •    Abnormal termination (abend): When a process encounters an exception, it is
         signaled by the kernel. If the signal is not (or can not) be handled, the process
         crashes. Such untimely demises are discussed in detail throughout Chapter 12.

     Unlike real-life, it is the expected behavior for the parent process to outlive its
children * . The child process is usually created with some sub-task in mind , the output
of which can then optionally be used by the parent. The classic example here is that of
the terminal CLI shell. While the child (command) is running, the shell suspends itself,
calling one of the waih syscall variants (usually, wait4(2)) to wait for and collect its
child exit status (which becomes access ible in the $7 environment variable). Because
wait4(2) is a blocking call, an alternative is to listen for and handle SIGCHLD, indicating
the termination of a child process, and guaranteeing wait(4) will not block .

2.S. Un-Death: Zombies

    Waiting for the child (using wai t4( 2) or waitid (2)) is the common and responsible
practice. Failure to do so, however, is not only a sign of lousy parenting - but can also
result in the child entering a "zombie" state . This occurs when the child calls exit(2)
before the parent has issued a wait call for it.

    Normally, zombie is a momentary state, since the parent receives a SIGCHLD and
may then choose to wait [4/pidl (2), guaranteeing a non-blocking operation, to pick up
the child's return value. If the parent ignores the signal, however, the child remains
"stuck" in this state, and - like its namesake - is neither dead or alive, and cannot be
removed by any means (not even a kill -9). This lasts until the parent assumes
responsibility, or the parent itself terminates, at which point PID 1 "adopts" the zombie,
becoming its parent briefly, only to collect its return value and grant it eternal rest.

* - Linu x supports a "parent death signal as well, which can be requested through the
PR_ [GET /SETLPDEATHSIG cmd of pr ctl( 2). This applies to the thread that created the process,
however, and so might be sent while the parent is still alive and we ll.

      2.6. Linux: The /proc/ filesystem

           Linux's /proc pseudo-filesystem (procfs) presents process information as files in PID-
      derived directory entries. The directories in /p roc each correspond to one or another PID,
      though by default enumerating them only returns the PID == TGID case, i.e. what user
      mode calls "processes" or "kernel threads". Nonetheless, cd-ing to a /proc/pid entry will
      work for any valid PID in the system (at the moment of the cd), including threads . A
      process is always able to access its own TGID /p roc entry through the / proc/se lf symbolic
      link, or (at the thread level) through /proc/thread_self.

          As with all pseudo-filesystems, none of its directories and files are real, but rather
      they are created on the fly by the kernel as they are accessed from user mode. The
      kernel obtains the pid component from the /proc/pid/. .. path, and attempts to find the
      corresponding task_st ruct it uses to manage it. If found, it provides its information in
      an array of pseudofiles, shown in Table 4/2-9 and (mostly) documented in proc(S).
      Access to those psuedofiles yields the most up -to-date information, usually in clear
      human readable form, which is also 9 rep (l) friendly.

           The / proc filesystem is usually mounted with no options, but may also be restricted
      using the hidepid and gid mount options. hidepid=l restricts access to subdirectories
      by UID ownership (i.e . so that users can only see data relating to their own processes,
      but still be aware of other PIDs) . hidepid=2 further restricts, so that PIDs not owned by
      the caller are also invisible. The gid option allows the stated group members to see all

      3 .2.2. Ledgers

          Darwin's proprietary resource management consists of Ledgers. Introduced in
      Darwin 15, ledgers are Mach constructs which can be used to track resource usage at
      the level of tasks and coalitions.

          A ledger maintains a balance of a given resource class for a Mach task. It is
      comprised of credits and debits, which together make up a balance. Each ledger may

      times, wakeups, network, and more .

          If the ledger limit is met or exceeded the task may be throttled or killed . In
      practice, however, the only two ledgers that are limited are interrupt_wakeups (at
      45,000/300G) and phys_footprint (varies).

      4.1. Credentials

      it. For this, it assigns eac h process a set of credentials. Every UN *X process runs on

      privileges. Command line users are likely familiar w ith su (1) or sudo (8), which allow a
      "switch user" to root or others. This requires a com bination of both system cal ls and
      special filesyste m bits - the SetUID (chmod u+s) and/or SetGID (chmod g+s), as

          4.2.2. SELinux

              The 1970's model of permissions - for a specific user, a group, and for the rest the
          world - did not age well. At the filesystem level, extended access control lists (see
          8/1.2 . 1) were introduced to allow finer granularity to files and device nodes. This,
          however, brought the problem of management at scale: in large systems with many
          users and orders of magnitude more files, maintaining ACLs can get difficult and error-
          prone.

              Back in the 1990s, Solaris pioneered the notion of "Role Based Access Control"
          (RBAC), and security labels. One set of Labels can be applied to objects. Another set
          can be applied to requester processes . At that point, access control is a simple lookup in
          a table, of whether supplicant X can access label Y for whichever operation type .

              Security Enchanced Linux (SELinux) adopted this notion . The access table is part of
          a security policy, which is applied early during system boot. Once applied, the policy
          can (for the most part) not be removed or disabled, and forms a layer of Mandatory
          Access Control. This, as opposed to the Discretionary Access Control of classic
          UN*X, which does allow certain user discretion (via chmod(2)/chown(2)/chgrp(2) and
          the like). Both MAC and DAC must agree for an operation to be allowed.

              SELinux operation denials appear in user mode as a system call failure with the -
          EPERM e rrno ("Permission Denied". Since SELinux operates at the kernel level, it
          outputs messages to the kernel log (readable through dmesg(1)) as Access Vector

          4.2.3. SECCOMP-BPF

              Linux's SECure COMPuting (SECCOMP) was originally devised in 2.6.23 as a way to
          restrict processes to "computation only". The idea was to initially have a process open
          whichever files, sockets and other descriptors, and then restrict it by ca lling prctl(2)
          with SECCOMP _MODE_STRICT. From the moment the prctl(2) returns, all system calls
          besides I/O (read(2), write(2)), ex it(2) and sigreturn(2) would be disallowed.

             The model, however, proved impractical. The restriction was so strict that additional
          memory operations (e.g . mmap(2), thread creation (via clone(2) and even basic
          synchronization (which nowadays involves the futex (2) syscall) became impossible.

              Linux 3.5 introduced SECCOMP_MODE_FILTER as an alternative. This allows the
          loading of a dynamic filter, specified through the Berkeley Packet Filter (BPF) syntax
          (and th erefore commonly referred to as SECCOMP-BPF). The "packet" in this case is
          the system call number, and its arguments, in serialized form .

    "Andro id Sandbox " . The Chrome browser also emp loys SECCOM P-BP F, restri cting itself
    in all its Linu x and Android builds. The initial implementation was hard cod ed into

      4.3.1. The Sandbox

           Darwin's most important security component is, indubitably, the Sandbox. This,
      similar to SELinux, is a Mandatory Access Control component, but it takes an entirely
      different approach to security, one which permeates into almost every significant action
      on the system. It is discussed in detail throughout M-III/8, but this section provides a
      brief overview of its important capabilities.

          As a XNU MACF extension, the Sandbox kernel extension registers a policy, with a
      large set of operation hooks. These hooks are called out from the kernel from numerous
      operations, such as opening files, sockets, device nodes, sending IPC messages, and
      much more . Rather than use labels as SELinux does, however, the Sandbox works with
      extensible profiles, written in a Scheme-like dialect, which allows inspection of
      arguments to operations, including sophisticated regular expression matching. The
      profiles are compiled into specialized byte code , which can be quickly evaluated in
      kernel mode, to either allow or deny an operation .

          As with all good security policies, the profiles are set by default to deny all
      operations, unless explicitly allowed . The Sandbox can maintain profiles on a per-binary
      basis, as well as a platform profile, which applies as a baseline to all binaries . On
      macOS, this platform profile is responsible for the hardening measure known as System
      Integrity Protection (SIP) . An equally apt name is its internal moniker of "rootless" -
      implying the once omnipotent root user is now restricted, and can do much less.

           The Sandbox can also be consulted from user mode, which makes it highly suitable
      for IPC scenarios . In these, an often more privileged server is requested to perform an
      operation on behalf of a client . Using the sandbo x_check (3!) API, the server can
      consult the Sandbox to see whether or not its peer is allowed to perform the operation.
      A typical example of that is launchd (1), which checks requester's mach - lookup
      operations to see whether to allow the lookup of service port names .

          The Sandbox can also consult user mode. Using upcalls to tccd (8! ). The so called
      Transparency, Consent & Control Daemon (q.v. M-III/10) is responsible for the
      authorization dialogs which pop up on sensitive operations (from "Privacy & Security"
      Settings), which require interactive user permission (for example, using the camera or
      microphone). The tccd caches these authorizations in a protected database .

          Beginning with Darwin 20, the Sandbox has been further extended to selectively
      deny (i.e. filter) Mach and XPC messages. Additionally, it has been extended to support
      system call filtering (similar to Linux's SECCOMP-BPF) . Most system calls presently get
      intercepted at two levels: First, to check if the system call is even allowed, and -
      assuming it is - by a callout specifically from that system call, if applicable.

      4.3.2. Entitlements

          An overly restrictive Sandbox profile runs the risk of breaking functionality, which
      needs to be re -e nabled. Re-enablement, however, runs the risk of potentially breaking
      the security policy, by once again allowing an operation that is inherently insecure, and
      could open up a security vulnerability.

          The ingenious way devised by Appl e out of this Catch-22 is using entitlements.
      These are similar to Android's Dalvik permissions, in that they are usually nothing more
      than (commonly) reverse DNS notation strings, usually with a boolean value of true,
      indicating the entitlement is granted . The Sandbox profile can then be set to allow only
      an operation if the requesting process possesses the entitlement, and deny it otherwise,
      potentially even for root users.

           To fully secure entitlements, Apple embeds them in the binary's code signature. As
      explained in 3/2 .5.4.5, Darwin's code signatures have only one authority - Apple itself.
      Thus, so long as the code signing enforcement has not been somehow bypassed, the
      entitlements can be fully trusted . Apple's default platform binaries come pre-s igned and
      pre -e ntitled with those entitlements necessary for their normal operations.

          Entitlements find the balance between allowing privileges, but only under tighly
      controlled, secure circumstances. In this way, for example, root can still use a tool like
      gpt (8), and obtain the necessary raw disk access required to format the block device at
      a low level, thanks to the com.apple . rootless. restric ted-block - devices
      entitlement. Outside of using the tool (or another with the same entitlement), root
      cannot arbitrarily obtain raw disk access, for examp le to image the disk or overwrite
      crucial files or filesystem metadata .
