1.1.5. Linux: signalfd(2)

    The Linu x signalfd(2) facility provides an alternative method of handling sign als .
Rather than installing an asynchronous handler through signa l( 2) or s igact ion (2),

thread), or [elpoll(2) on it, and th en read the signalfd_siginfo records encoding
the signal data, as documented in the signalfd(2) manual page, and overlapping

2.1. Prerequisite: The AS_CORE Resource Limit
    Core generation in all UN*X f lavors is subject to the resource limit of AS_CORE.
Although most shells set this to 0 - effectively disabling core dumps - t his limit may be
increased by a non-root user. The increase is only allowed when the value is 0 by
default, so it is common practice to increase this to un limited, lest some other
specified value prove insufficient , resu lting in a pa rti al (and often broke n) core dump.

    The most common way to increase the core limit is via the ulimit(l) command, by
specifying ulimit -c unlimited. This actually applies the limit on the shell, but is
inherited by its subprocesses. Less commonly, it is poss ible to set t he core limit from
within the process. This requires a call to setrlimit(2) with AS_C ORE. In Darwin, the
limit for launchd (passed on to child daemons it spawns) can be changed through
launchctl limit core unlimited

      2 .2 .1. / proc/ pid/coredump_filter

          Core files encompass the entire process address space, so t hey can easily range in
      the gigabytes, making them hard to store and handle. Most of the core memory is
      comprised of rea d -o n ly f il e mappings, which can be ret r ieved f r om the disk . It is on ly
      the anonymous memory wh ich is usually of interest to post-mortem ana lysis.

          The coredump_filter pseudofile allows selective filtering of which memory segments
      get writte n . The fi le specifies a bitmask, interpreted according to this table:

                                                 -

              0x01        anonymous private mappings              0x20          private huge (2MB+) pages

2.2.2. Core dump filename control

     Linux core dump generation is controlled through three sysctl(S) MIBs in the
ke rne l namespace, which are also accessible through / proc/sys/kernel. These are
documented in co re (5), and summarized below:

                Table 12L 2-4' Core setti ngs (via sysctl (8) or / proc/sys/kernel)
        Setting                  Pseudo-file                                 Controls
  kernel. core_pattern   /proc/sys/kerneljcore_pattern               Core filename or handler
  kernel.core_uses_pid / proc/ sys/kern elj core_uses_pid     Append faulting PID to core_pattern

    Of the three core settings in Table 2-4, core_pattern merits further discussion . The
default value ('co re') implies the creation of a core file (potentially, with the faulting
PID appended, per core_uses_pid) in the current directory. Toggling the setting to a
central location (by specifying a full path) is already useful in and of itself - especially
when directed to an NFS server which can collect cores from multiple servers. An even
better setting, however, involves using pipes.

     The pipe character (' I ') allows specifying a path to a binary. Rather than dumping
the core to output, the kernel will automatically invoke the binary, and funnel the core
file to it via its standard input (hence, the binary is on the receiving end of the pipe).
This is done so long as the kernel. core_pipe_limit for simultaneous core dump pipes
has not been reached.

    Using pipes provides a new dimension of functionality, which can include automati c
response to program crashes (for example, restarting under different conditions, or
sending notifications or emails on repeated crashes), or - more commonly - automatic
proceSSing of the dump, as is done with systemd-co redump (S).

2.4. Live core dumps

    Cores provide a trove of information, a full snapshot of the process state at the
moment of death. If the same snapshot could be made of a live process, debuggers -
which can already process core dumps - could be used for a full inspection of the
process state. This idea first gained popularity thanks to Mark Russinovich, then a
vanguard of Windows Internals research, who implmeneted tools for live dumps - both
in user and kernel mode - in .5.v.sInternals.com .

2.4.1. Darwin/Linux: gcore(l)

    The gco re (1) tool has long been a standard in Linux to dump ELF cores of
processes, and is both open source and included in package repositories. The Darwin
version of the tool was developed on Darwin by Amit Singh - a true Darwin pioneer, for
his "Mac OS X Internals" book. The tool, however, was suitable only for the PPC
architecture, and the companion website has since been delisted from the Internet.

     Apple incorporated their version of this tool, gco re (1) into Apple's system_cmds
project (as of system_cmds_790, Darwin 20). Apple's version of the tool possesses the
limited com. app le. secu ri ty. cs. debugge r. read. root entitlement, which enables it to
dump cores of non-platform binaries when SIP is enabled.

    Apple's gco re (1) supports an undocumented and hidden "-x" switch to write
'extended' core information, through the use of experimental LCCOREINFO, LCFILEREF
(to embed open file information) and LCCOREDATA (cmd values of 0x140-0142, though
unofficial) *.

2.4.2. procexp(j) and memento(j)

    The Author recreated the live core functionality first shown by his predecessor for
p rocexp (j) and later incorporated it into the cross-platform memento (j ). Both tools are
freely available .

    A caveat, however, is that Apple has since hardened the requirements for memory
inspection APIs, requiring not only root privleges but further gating them by
entitlements. The tools can therefore only function on a SIP-disabled system (in which
AMFI disregards entitlements), or a jailbroken *OS device. It is recommended to disable
SIP only on a dedicated research machine, preferably a virtual one.

    The procexp(j) tool's core action will dump a core that is virtually identical to that
of gco re (1), with the exception that it will include mappings mp rotect (2) with no
permissions (such as guard pages). Such mappings are included as Mach-O
LCSEGMENT_64 commands or ELF sections, but not actually mapped unless they
actually contain any data.

    memento (j ) functionality is identical, with the same usage and behavior in both
Darwin and Linux systems. In Darwin, memento (j) uses the Mach VM routines (and
thus needs the task port entitlement). In Linu x, memento makes use of /proc/pid/maps to
obtain the process memory map, and can use p rocess_vm_readv (2), /pro c/pid/mem
and/or pt race (2) APIs to read the target process' memory.

     You'll recall that kernel-generated core dumps do not have any section headers.
memento (j) generated ones do, with the rationale that sections can have names - and
this allows memento(j) to embed the / proc/pid/ma ps information PR_SET_VMA_ANON_NAMEs
into the core dump into ELF Notes. The Darwin version makes use of the experimental
load commands introduced by Apple's gco re (1) .

      3.1. Crash Reporting in Darwin

          Apple highly values UX, and gives great care to crash re porting, aim ing to produ ce
      an d report as much detail ed information as possi ble on platform component crashes. At
      the same time, overly detailed crash reports could impinge on the user's privacy,
      another strong commitm ent.

      binary (part of / System/ Library/ CoreServices/ ) across all platforms. The binary performs an
      on-device analysis of the crash, summarizing the circumstances and other important
      factors, but disca rding the process memory.

      host's exception port RECEIVE right owner, as both LaunchAgent and LaunchDaemon
      (that is, whether or not the user has logged in) . Th is is done by spec ifying the
      <ExceptionSe rve r > key in its both property lists . Recall (from Figure 10/2-17) that th e
      host exce ption port is where the exception messages will be sent to, if not previously

3.2. Android: Tombstones
    Android disables core dumps in favor of tombstones. Tombstones are created
when the faulting's process signal handler intercepts the lethal signals, fork(2)s
(twice) and execve(2)s crash_dump64. The crash_dump64 process then uses
pt race (2) to attach to its (grand)parent, and perform an autopsy as the latter is left
hanging. When complete, the faulting process exits gracefully, and c rash_dump64
submits the diagnostic report to tombstoned, which places it in / data/ tombostones.

    A-II/2 discusses the exact logic of tombstone creation, with Bionic's li nker
intercepting lethal signals to invoke c rash_dump64 upon reception, double fo rk (2), and
then connect over an abstract UNIX socket to the undertaker, tombstoned. Tombstones
are created in / data/tombstones, up to a maximum of tombstoned.max_tombstone_count
(32) graves, after which the cemetery fills up, and the tombs need to be reused . As of
Android 12, tombstones are created both in human-readable and machine-readable
(protobuf, in core/debuggerd/proto/tombstone.proto) form. The human readab le form is
shown in the following figure (also A-II/2/4-S) :
