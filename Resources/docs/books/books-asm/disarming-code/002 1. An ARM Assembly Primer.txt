An ARM assembly primer

     The Architecture Reference Manual [aarm], a veritable bible, dedicates its "Part C"
(and nearly 5,000 of its overall 14,000+ pages) to explain the encodings and operations
of its instruction set. The documentation is superb, but is a bit overwhelming. ARM 's
Learn the Architecture [lta] document provides a much more reader-friendly explanation
of the key instruction classes, as do Many other documents in the series . Patterson &
Hennesey 's Com Ruter Organization & Desig.njARM Edition)[ pnh] is also a great
reference to a reduced in struct ion set (wh at the authors refer to as LEGv8), and goes
far deeper into the internals of processor design. For a free and well detailed book,
consider Introduction to ARM AArch64 Architecture and Low-level Programming[lIpb] on
GitHub.

    ARM has long been (quite literally) synonymous with Reduced Instruction Set Code
(RISC ) architectures. Nonetheless, the Aarch64 Instruction Set Architecture (I SA)
comprises many hundreds of instructions, some with many variants. Further, each annual
revision brings more instructions and feature extensions. With nearly no exception,
however, all the instructions operate on registers and/or memory . Thus, in a manner not
unlike a calculator, many instructions encode various arithmetic and logical operations on
the register operands.

    Th is chapter focuses on getting know this vast and always evolving architecture.
The chapter begins with an introduction to assembly, going back to the basics of bits,
bytes, words and quads, and introduces the "dramatis personae" - the processor
register sets. It then moves to establish the "working vocabulary" - covering only a few
of th e multitude of instructions - but the ones which can help establish fluency in the
languag e. Lastly, it presents all the ARMv8.x and ARMv9.x feature releases (to date),
and highlights some of their features.

        Irrespective of the choice of programm ing language, the CPU understands only one
    language - that of the machine. Sequences of bits encode operations and operands
    (the operation arguments ), and dedicated circuitry decodes the sequences and allow
    the CPU to perform them. These bit sequen ce s are referred to as instructions . Each
    instruction is encoded in 32-bits .

    processor - for lack of additional bit space - just discards them. This can ca use weird
    re sults in simple arithmetic operations. For exa mple:

                                              STP X28, X27,       [SP)

                 In other words, the instruction is the same as its unsigned offset variant, with
             the side effect of modifying the base register to reflect that offset.

          • Post-Index: Performs the modification by the immediate value, after the actual
             load/store operation. As an example. the instruction:

                                           LDP X28, X27,    [SP], #96

                 is semantically equivalent to:

                                              LDP X28, X27,       [SP)

                                                    ADD SP, #96

                 Again, in other terms - this is the same as reading directly from the base
             register (ignoring the offset), and only after applying the offset.

            The pre/post indexing variants are frequently used when the load/store applies to a
        stack pOinter based address. This is done as an optimization to adjust the local frame -
        either claim (pre-index, with a negative offset), or release (post-index, with a positive
        offset) memory. More examples, along with explanations of their application, can be
        seen in 6/1 -3 .

2.3. Branches, Exceptions &. System Instructions

    Instructions whose opl is 101x (that is, 0xA... or 0xB ... ) can be categorized as
controlling program flow or processor state. This includes branches of all types
(conditional and unconditional), exception generating instructions, and system
instructions .

2.3.1. Branches

     Normally, the Program Counter advances by one instruction (4 bytes) with every
instruction executed, so as to always pOint to the next one. There is no need for (nor
capability of*) setting the PC directly. If there is a need to redirect the instruction flow -
for example, for looping, conditionals, function calls, or gata instructions, a branch
instruction must be used.

     Branches are defined as any case wherein the current instruction sets the PC to a
different value. This causes the CPU to jump (per the Intel nomenclature) to the new
address, and resume the instruction flow from there (unless, of course, another branch
is encou ntered).

2.3.1.1. Relative vs. absolute branches

     Branches are either relative, or absolute. A relative branch takes as its argument
a 26-b it literal (that is, a constant offset from the present PC), logically shifted left by 2
bits (since instructions align on a 4-byte boundary) and sign extended (allowing for
negative offsets):

2.3.2. Exceptions

    A key part of processor operation is dealing with exceptions - events wh ich requ ire

2.3.4. Barriers

     Processors frequently reorder instructions to achieve better performance. It further
makes use of caches, so that memory access is first attempted on the faster cache, and
- in case of a cache miss - goes to the external memory (RAM).

    Normally, instruction reordering is entirely transparent, as the processor observes
address dependencies (for example, a load operation must complete before its value
can be used in a store operation or address calculation. A notable exception is with
conditional branches, which may involve bran ch prediction and speculative execution.
Another consideration is when using multiple processors or cores, which use different
caches, or devices using Direct Memory Access (DMA).

     A special class of instructions, 0x05033x xx, defines barriers. Barriers force all
instructions before them to complete, as further detailed in MemorY2Y~, Ordering,.
and Barriers [msobj documentation . Instruction s may still be reordered before and after
the barrier, but cannot cross the barrier. Several instructions here accommodate
different barrier types, with further instructions available as processor HINTs.

   •   The ISB instruction has the effect of flushing the instruction cache , slowing down
       execution. This is normally used at Ell or higher after changes to MSRs. There is
       only one argument here - SY, implying system-wide effect - which is often
       omitted.
   •   The OMB instruction is a lightweight barrier, which ensures instructions before the
       barrier do not get reordered after the barrier. It does not force completion of the
       instructions before the barrier.
   •   The OSB provides both guarantees, and has further aliases in SSBB and PSSBB
       ([Physical] Speculative Store Bypass Barriers).
   •   The SB instruction effectively disables speculative execution. Introduced with
       ARMvS.x's FEAT_SB, this aims to mitigate side channel attacks (such as those of
       Spectre & Meltdown).

    Data barriers further take an argument indicating the shareability domain they
apply to. Shareability domains can vary between SoC implementations, but are
generally considered to be:

   •   Non-shareable (NSH): applies to a single core (example: per-CPU memory)
   •   Inner shareable (ISH): applies to memory shared between cores, cacheable
   •   Outer shareable (OSH): applies to non-cacheable memory, especially memory
       shared between CPU and other devices
   •   System-wide (SY) - applies to all memory.

    Further modifiers can be if the barrier applies to both loads and stores (as above),
stores only (appending ST), or load-before and both after (appending LO). When
ARMvS.7's FEAT_XS is used, a special XS modifier applies to OSB.

     capabilities. The "scalability" refers to the fa ct that the vector length can range between
     128 and 2,048 bits, scaling automatically at runtime (i.e. without recompilation). ARM

     2.6.1. SVE Register sets

         SVE expands the processor with two sets of registers . The first, Z0-Z31, are 32-
     registers which extend the "legacy" 128-bit wide V0-V 31 of FP&SIMD (NEON) by
     multiples of 128-bit, up to 2,048 bit. The exact length is configurable at runtime (hence
     the "scalability", above) .

         The second set of registers SVE introduces are P0 -P 15 , the so-called predicate
     registers. Predication allows runtime determination if a given element lane of the
     corresponding vector register is active . The predicate register uses one bit for every
     byte of the vector register, so their size is 1/8. P0 -P 7 govern operations (loads, stores,
     and arithmetic), and PS-P 15 are used in loops .

         The Z0-Z31 registers are capable of packing multiple elements into them. The
     elements must be of the same bit-width, but may be integers, or floating point values
     (of same precision).

     3.1.1.1. Atomics (Large System Extensions) (FEAT_LSE)

     sequence, in which the value is first loaded into a reg ister, operated on, and then stored

     operations highly suitable for implementing locking in multithreaded programs, as
     described later in 7/3 .

3.1.1.2.   Privileged Access/eXecute Never (PAN/PXN) and FEAT_PAN3

    Privileged Access Never (PAN) is a feature designed to prevent privileged code
(kernel or higher) user- mode memory. This feature (similar to Intel's Secure Mode
Access/eXecution Prevention (SMAP/SMEP)) mitigates a class of attacks in which a user-
mode adversary can trick privileged code into accessing maliciously crafted memory.

    PAN is implemented through an MSR, so it can be periodically disabled during those
times privileged code needs to access user-mode memory (commonly, the kernel's
copy-[from/toLuser . This is discussed later in 13/2.4 .1. ARMv9.6's FEAT_LSUI adds
special load/store instructions which are "unprivileged" and therefore unaffected by
PAN.

3.1.1.3.   Virtualization Host Extensions

    ARMv8.1 adds Virtualization Host Extensions (FEAT_VHE). This enables a host

     3.2.0.4. Transactional Memory Extensions (FEAT_TME)

         As multithreaded core executes simultaneously on multiple cores, locking and
     synchronization cons iderations become increasingly complex. On the one hand, locks
     are vital to avoid race conditions. On the other - locking can dramatically degrad e
     performance .

         Transactional Memory aims to alleviate these concerns by providing atomicity to
     not one, but several memory instructions . Intel prov id es hardware support for
     transactions in its TSX, and ARMv9's TME provides the same functionality, through
     several instructions (TSTART, TCANC EL, TCOMMIT, and TTEST. These are discussed in
     more detail in ARM 's documentation, and later in th is work (q.v. 7/3.4).
