
Memory - II - The Process View

    As   far as most developers are concerned, there are to ways of obtaining memory.
The simplest is to just declare a vari abl e in the scope of whichever function . Su ch
automatic variables are transparently assigned a register or allocated by the compi ler
on the stack. Other dynamic allocated variables involve calling rna lloc (3) with some
size, to obtain a pointer to that size on the heap. For most, the inner workings of heap
allocations - which greatly vary by platform - are a black box.

     Ignorance is definitely bliss, but there is much to be gained by going into the
details. Knowledge of the stack is extremely helpful for reverse engineers, as they
literally unwind the stack to uncover the function call history and, when possible, the
arguments. Know ledg e of the various heaps' internal structure is of prime value for
ex ploiters, which can carefully tricky a process into an arbitrary, controlled memory
corruption, which can lead to code execution .

     This chapter begins with a discussion of the stack - particularly, the structure of
frames, and function prologs and epilogs. The discussion then moves to the heap, and
splits three ways - to discuss the Linux impl eme ntation (glibc), that of Android
(Scudo ) and, briefly, of Darwin (libsystern_rnalloc).

    Next, we discuss the various bugs which result from incorrect or careless memory
management. Since those bugs often result in critical vulnerabilities, ARMv8.3 and later
offer unique and novel processor-level countermeasures - Pointer Authenti ca tion Codes
(PAC) and Memory Tagging Extensions (MTE) - which go a very long way towards
mitigating exploitation.

     Last, we conclude with a discussion of the com plete address space - stack, heap,
loaded binaries, and more - and how to use APIs, platform diagn ostic tools, and those
of the Author in order to examine and introspect processes .

      1., Tbe Stack
           Most re ad ers ma y be familiar at this point with the well-known data structure that is
       a stack - a La st-I n- First-Out (LIFO) structure, to the top of which elem ent s may be
       pushed and from which these elements may be popped. Intel and ARM 32 assemb ly
       used dedicated PUSH and POP instructions. ARM64 uses the general purpose LDR/STR or
       LDP/STP using SP as the base register, and optionally with their post-index/pre-index
       variants for auto-adjustments.

            Each thread has its own stack, whose top is poi nted to by the Stack Pointer
        (ARM 64's X31, when not used as XZR, or Intel's RSP). Whatever thread state cannot put
        directly into the other registers - usually ends up on the stack (but may end up
        elsewhere, such as in Threa d Local Storage (TLS), or the heap).

           The stack poi nter in ARM64 must always be aligned on a 16-byte bound ary, unless
       disabled at a higher exception level by writing to SCT LR_ELl's SA and SA0 bits (#3 &
       #4).

           ARM64 further defines 128-bytes below the pO inter as a "Red Zone", which is
       guaranteed to not be modified by the OS, and may be used by code to allocate local
       variables, w ithout modifying the stack pOinter. Some optimizations use this red zone to
       save an instru ction, though thanks to ARM64' s post- index STP variant, the practice is
       uncommon outside leaf functions.

      1.2. The Frame

          The stack's LIFO nature also lends itself well to procedure calls. Each procedure, on
      entry, uses the current value of the stack pOinter (read: the top of the stack) as the
      base for its own local variables . This commonly referred to as the "Stack Frame" (or
      simply, the frame). All automatic variables are allocated in the frame, as is memory
      explictly allocated through a lloca (3) .

           When a routine is called, it puts its frame on top of its caller's - in what is effectively
      a sequence of stack pushes. When a routine exits, it restores the stack pOinter to its
      value of entry, effectively a sequence of stack pushes, which frees (but does not
      deallocate) the stack memory. Note, that a local frame is not always necessary - such
      as in cases where there are no local variables, or they may be optimized away.

          In some architectures (notably, Intel's legacy 32-bit x86/i386) the local stack frame
      could be used for passing arguments . Both Intel/AMD 64-bit and ARM calling
      conventions prefer the much faster registers (in the AArch64 case, X0-X 7 ), though in
      rare cases (with more than eight arguments) excess arguments may be passed on the
      stack. Another more common exception are variadic functions (those accepting a
      variable number of arguments), in which case the arguments after the ellipsis are
      passed on the caller's frame (starting with the first at SP).

      1.3. Prolog a nd Epilog

          Nearly all function calls require a stack frame, the compiler must generate code to
      set up the frame (on entry), and tear it down (on exit). The convention is for the callee
      (= called function) to do so, in two code blocks - the prolog and the epi log.

           The function prolog and epi log are inverses of each other. Whatever the prolog
      claims as the local frame, the epilog releases . Whatever registers the prolog claims, the
      epilog restores . This, and the adherence to the ARM PCS, makes prologs and epilogs
      fairly easy to detect in disassembly, with these following observations:

       1.   As previously discussed, the prolog commonly saves , at a minimum, the value of
            the previous frame (in X29 , the FP), and the return address (in X30 , a.k .a LR). The
            pair of registers is often saved with one STP instruction.
       2.   Any general purpose registers the PCS defines as preserved across subroutine
            calls (i.e. X19-X2S) must be saved in the prolog and restored in the epilog. Here,
            too, STP/LDP are often used, for efficiency.
       3. The stack (normally) grows downwards, so the prolog will decrement (SUB) the
            size of the local frame from the stack pOinter on entry. Any stack pOinter
            dereferences between its new size and its size on entry (likely saved in X29 ) will
            refer to local variables . Any other references are to globals.
       4.   When ARMv8 .3 pOinter authentication codes (PAC) are used, the prolog will
            commonly start with a PAC signing instruction for the stack pointer (PAC! [AB] SP),
            and the epilog will end with an authenticated return (RETA [AB]). This may be
            omitted on leaf functions, especially those with no memory copy/moves.

         1.4. Dynamic stack allocations with alloca(3)

            The a lloca (3) function is a lesser-used facility for memory allocation, but on the
        stack (rather than on the heap). The man page of alloca(3) discourages its use . This
        is due to its inability to detect or handle the error condition which results from
        overflowing the stack: alloca(3) will always return a stack-based pointer, with no
        regard for the RLIMIT_STACK limit. For large allocations, this will cause a segmentation
        fault.

            Nonetheless, when used carefully and stricly small allocation sizes - a lloca (3) is a
         powerful alternative to heap based allocations:

           •     Allocation Speed : is far faster than using the heap. The a lloca (3) operation is
                 simply a manipulation of the stack pOinter, so it may be implemented as a macro,
                 or always in lined code. Unlike heap allocations, there is no need for any
                 metadata maintenance.
           •     Memory Leaks: are largely avoided, since the function epilog restores the stack
                 pOinter value on entry, the a lloca (3) memory automatically clears up on exit
                 from scope .

             The implementation of a lloca (3) via a compi ler _builtin, which translates to the
         corresponding adjustment (i.e. subtraction) of the stack pOinter. This is either
         performed at the start of the block disassembly, or just tacked on the prolog of the
         containing function .

         1.5. Backtraces

             Depending on compiler optimizations, the stack pOinter on procedure entry may be
         saved (into ARM's X29, aptly referred to as the Frame POinter, FP) . In those cases, if one
         procedure calls another, (and the caller has its own frame), it will first have to save the
         value of the frame pointer it found on entry (Le . its caller's frame), so that it can be
         restored on exit. In case of a nested call, it is also important to save whichever return
         address was specified (in ARM's Link Register, LR), since a nested call will overwrite the
         return address the caller is expected to return to, with that of the caller itself.

             In a given frame, therefore, one commonly sees the previous values of the LR and
         FP as they were when the frame was set up. After these values are the "banked"
         register values, dictated by the calling convention as callee-saved. Finally, are any local
         variables. The saved FPs form a chain - as each saved FP pOints to the caller's frame
         (and, therefore, where the grandparent's frame was saved) . This chain, along with LRs
         saved next to it, is cardinal for unwinding the stack during debugging or crash
         reporting .

  2.1.1. Nomenclature

  allocated using mmap(2) . It is from a heap that maHoc(3) returns th e size bytes of
  memory requested. That block of mem ory is part of a chunk . A heap is, thus, an

  An allocation will find the closest sized chunk to the requested size, taking into account

      One or more heaps are grouped into an arena, which contains th e heap metadata.

       Memory allocations over DEFAULT_MMAP_THRESHOLD ( 128K) go directly to mmap(2),
  and their corresponding free(3) then munmap(3)s the memory, allowing the OS to

   Bins
     An array of bin headers for free chunks. Each bin is doubly
     linked. The bins are approximately proportionally (log) spaced.
     There are a lot of these bins (128). This may look excessive, but
     works very well in practice. Most bins hold sizes that are
     unusual as malloc request sizes, but are more usual for fragments
     and consolidated sets of chunks, which is what these bins hold, so
     they can be found quickly. All procedures maintain the invariant
     that no consolidated chunk physically borders another one, so each
     chunk in a list is known to be preceded and followed by either
     inuse chunks or the ends of memory.
     Chunks in bins are kept in size order, with ties going to the
     approximately least recently used chunk. Ordering isn't needed
     for the small bins, which all contain the same-sized chunks, but
     facilitates best-fit allocation for larger chunks. These lists
     are just sequential. Keeping them in order almost never requires
     enough traversal to warrant using fancier ordered data
     st ructu res.
     Chunks of the same size are linked with the most
     recently freed at the front, and allocations are taken from the
     back. This results in LRU (FIFO) allocation order, which tends
     to give each chunk an equal opportunity to be consolidated with
     adjacent freed chunks, resulting in larger free chunks and less
     fragmentation.
     To simplify use in double-linked lists, each bin header acts
     as a malloc_chunk. This avoids special-casing for headers.
     But to conserve space and improve locality, we allocate
     only the fd/bk pointers of bins, and then use repositioning tricks
     to treat these as the fields of a malloc_chunk*.

      2.2. Android: Scudo

           Scudo ("Shield" in Italian) is a memory allocator designed at mitigating heap-based
      vulnerabilties (see 3.3). It gained popularity when Google adopted it as the default
      allocator as of Android 11, in Fuchsia and Trusty. Scudo is part of LLVM, and is
      documented there .[scudo). A detailed analysis can also be found in blog posts by
      Tre nchant[sctr), Vectorize.re [vrs), unlfuzz[scul), and by ~y-nacktiv .cscsa)

      2.2.1. Nomenclature

           Scudo divides the heap into regions, which are backed by a number of mmap (2) ed
      pages. Each region is assigned a class, wherein a number of equal size chunks may be
      allocated, by a random order. Thus, different regions are used for different allocation
      sizes. Each allocation chunk is preceded by a header.

          As with other allocators, chunks may be regularly allocated or freed. Scudo,
      however, differs by additionally defining a state of quarantine, wherein a chunk is
      temporarily marked as unallocated, yet unavailable to be used. This is with the exp licit
      purpose of preventing Use-After-Free exploits (discussed in 3.3 .3). Quarantine requires
      a compile time option, which Android's configuration does not use.

              Scudo defines two allocators:

          o    The Primary' Allocator: Used for most allocations of under 64KB (technically,
               under 64K + 16) in size.
          o    The Secondary' Allocator: normally used for allocations larger than 64K .

          Scudo uses prctl( ... , PR_SET_NAME, ... ) (in its mmapWrapper( ... )) to name its
      allocator mappings, so they are clearly visible in /proc/pidmap s . Scudo's internal al locator
      metadata, however, is stored separately, in libscudo (or, in Android, Bionic libc.so) writable
      data segments .

2.2.5. Local Cache

    Unlike secondary allocator chunks, wh ich form a linked list, Scudo's primary chunk
headers provide no idea about the overall stru cture of the heap. That metadata is
deliberately stored outside the allocator regions.

    Further, Scudo is thread aware, and uses a TSD (Thread Specific Data, see 7/2.2)
structure to hold its state. The TSD cache is accessible from Scudo's TLS Slot, which (as
returned by Bionic's getPlatformAllocatorTlsSlot(}) is the TLS_SLOT_SANITIZER
(#6, see Listing 7/2-8). It is the CacheT's allocate(classld) method that is
responsible for locating, allocating and returning the chunk to the caller.

          Memory bugs are insidious. They take many forms, and are often very hard to
      reproduce. Though most cause the process to crash - whether by some sanity check
      abo rt (3) ing or by causing an invalid memory operation - others can cause corruption
      that can go unnoticed throughout the process lifetime.

          But none of the above are as bad as the potential impact on security. If a program
      crashes due to a memory bug it's bad enough - but, in the hands of a skillful hacker, a
      memory bug may turn into a vulnerability, which can then be exploited into affecting
      the process logic, or controlling it entirely. Memory bugs turned vUlnerabilities are
      highly sought after - not by process developers or QA folk, as they should - but by
      exploit mongers and "offensive security" companies. These weaponize the bugs into
      exploits, which are engineered to compromise the buggy code, and - through it - take
      control over the application or operating system component it runs in.

          The discussion in this section aims to cover and classify the common memory bug
      types. It begins with memory leaks - the all too common cases wherein memory gets
      allocated but never freed . These are generally not directly exploitable, but can
      nonetheless result in a "creeping death ": A scenario in which the process slowly eats up
      more and more memory, to eventually crash, or cause the demise of others . A plethora
      of glibc heap exploitation tutorials are available on the shell ph ish GitHub ,lshf]

          The discussion then moves to Memory Corruptions - wherein incorrect memory
      handling results in data being written where it shou ldn't. On the stack, this is common ly
      the result of an overflow. The heap, however, faces other possible corruptions, due to
      the myriad metadata it contains.

      3.1. Memory Leaks *

          Another insidious class of bugs are memory leaks. These occur when a process
      allocates, but neglects to free memory, leaving the memory technically in use, while it
      is no longer needed . Leaks are formally defined as those cases where the last reference
      to allocated memory is lost, without freeing it. This commonly happens as the result of
      a repeated allocation using the same pOinter, or if the pOinter drops from scope, as
      often happens when the function (in which it was allocated) returns.

          RAM is a finite resource, and so leaked memory may have a direct and adverse
      effect on system performance. Memory leaks are often small - sometimes only a few
      bytes at a time - and therefore may go unnoticed. Even seemingly small leaks,
      however, can add up over the application's lifetime. Further, since the smallest unit of
      physical memory is a page, a leaky allocation of a few bytes may still in some cases
      result in claiming a 4K (Linux) or 16K (Darwin, Android 15+) page of memory.

          Because leaks occur when memory is not freed, they are a bane only of the heap,
      and not the stack (which grows shrinks automatically as frames are created and
      destroyed) . Higher level languages with runtime environments (notably, Java) automate
      memory free operations by various algorithms for garbage collection, but may still be
      prone to leaks when not all object references are destroyed. In kernel mode, wherein
      memory is even more scarce and valuable with custom allocators, great care is taken to
      prevent them.

      3.2. Stack Corruptions

         The most common form of stack corruption is the stack overflow, which occurs
      when a copy operation to a buffer on the stack overflows past the buffer boundaries, to
      overwrite whatever data happens to be adjacent to it.

          Stack overflows were widely accepted as common bugs, but still generally
      discounted as potential security vulnerabilities. Despite being noted as a component of
      the Morris Worm [rfc], it wasn't until 1996, when "Smashing the Stack for Fun and Profit"
      - The seminal article by Aleph1 , in phrack # 49 [p49-14] first described them clearly. This
      unleashed a torrent of exploits in many OSes, particularly the SetUID programs over
      various UN *X distributions.

      * - The term "memory leak" also applies sometimes to an unrelated type of bug, wherein the process in
      question can be tricked into outputing some of its memory. In the hands of a sophisticated attacker, this
      can disclose potentially sensitive data, and be a conduit for further exploitation. This Author prefers the
      term "memory disclosure" for such vulnerabilities, which commonly arise from the use of uninitialized
      data (e.g. forgetting to bzero(3) buffers), or allowing an attacker unchecked, unbounded access to
      program memory.

3.3. Heap Corruptions

     With the stack being a fairly limited resource, most memory usage by the process is
in the heap. The heap, however, is not only far larger than the stack, but in many cases
more sparse. Overflows still happen here, but - due to the dynamic nature of allocations
- so do entirely new classes of bugs.

3.3.1. Heap Overflows

    Heap overflows occur for the same reasons as their stack-based counterparts, but
with varying effects. In fact, in many cases heap overflows may go unnoticed. Not only
do heaps start out sparse, but heap chunks work in fixed chunks, which are often more
than the requested size. Small enough overflows may go into validly allocated, but
normally unused space. Even larger overflows may be unnoticed - Depending on the
heap implementation : Such overflows spill on to corrupt the next chunk, commonly first
trampling its metadata. If the chunk whose metadata is corrupted by the overflow is
never freed, the bug might go unnoticed throughout the process lifetime .

3.3.2. Double Free

    A Double Free condition occurs when the same allocated chunk is free(3)d twice.
This might seem like something that wouldn't be possible, but it can, in fact, happen
because of not one, but two potential root causes:

  • The pOinter value is not set to NULL after the free (3).
  • Two different instances of the same pOinter value exist. One instance is
    free (3) d, while the other one - commonly, is some other thread - is free (3) d
    later.

    Setting a pOinter value to NULL after free(3) is a fairly simple (and highly
recommended!) practice, so the second cause is the more common one. Multithreaded
processes (not to mention the kernel itself) are especially prone to double free,
especially when complex reference counts are involved.

3.3.3. Use After Free (UaF)

    The last of the heap corruption bugs we consider here is when a buffer is free (3) d,
yet nonetheless used afterwards - hence, Use After Free, or UaF. The two root causes
are the same as those of the Double Free scenario, but with far more of an impact.

     Unlike the Double Free case, UaF directly leads to data corruption, when the
memory that was free(3)d is reallocated and thus reused. This leads to a case wherein
the same memory area is now accessibly by two different semantics - that of the
origina l, free (3) d pOinter, and the other by whichever new allocation reuses the same
space.

    When data is corrupted randomly, it is often nonsenSical, which leads to an
abo rt (3) or other type of crash. The severity of impact is greatly exacerbated,
however, if the data can be maliciously manipulated as a "fake object". If the object has
getters/setters, its fields can be manipulated, but since they cause and overlap with
attacker controlled data, this can be turned into a read/write primitive in the target's
memory. This type of attack is especially powerful as a kernel memory primitive, since
there exists no shortage of objects (sockets, process control blocks, etc), which can be
accessed (albeit indirectly) from user mode .

          The most straightforward path to exploitation of most overflows and corruptions
      involves overwriting a pOinter somewhere in the process address space. If the attacker
      can do so, then - depending on the exact semantics of the pOinter overwritten -
      exploitation may take place. For data pointers, different objects may be "swapped" . For
      function (text) pOinters, code blocks may be "swapped" (or crafted), diverting the entire
      code flow to malicious ends. There are other forms of exploitation, such as those which
      maliciously overwrite specific variables, but those are highly idiosyncratic to the faulty
      code.

          This work does not aim to explore the potential exploitation techniques for the
      various memory bugs. Your Author has done so before (in M-III and A-III), as have
      many others . The recurring exploitation of these bugs by malicious actors, along with
      the realization that programming bugs are inevitable, has led to a different approach:
      mitigation. This does not prevent any of the bugs - but allows their detection and
      immediate termination of the process. In this way, at least, they cannot be exploited.

          Stack-based overflows, due to their ubiquity, have resulted in several compiler-level
      defenses, which work across all architectures. ARM has additionally pioneered several
      CPU-level facilities aimed specifically at exploit mitigation. We consider all these next.

      4.1. Stack Canaries

          While any stack overflow is potentially hazardous, the most common path to "fun
      and profit" is by malforming the return address of a stack frame . Doing so effectively
      redirects the vulnerable function to return to an attacker controlled address, which may
      contain malicious "shellcode" injected by the attacker, or a ROPjJOP-chain.

           Stack canaries were created with the specific objective of protecting the return
      address . The "canary" is really nothing more than a 64-bit value. When the process
      starts, the canary value is generated from some random entropy. The exact process
      differs by platform:

        •   In Darwin, this is the stack_guard value of the apple[J vector, consumed by
            libsystem_c.dylib during startup and put into the global_stack_chk_guard
            variable .
        •   In Linux, the canary is provided as AT_CANARYLEN (17) bytes in the AT_CANARY
            (16) value of the AUXV.
        •   Android does not use canaries by default.

           The canary value is stored in some global on libc's heap. Next, when each function
      is entered, its prolog is expanded to also contain code to read the value, and place it
      into the local frame. The epilog is then expanded as well, to check for the canary value
      - i.e. compare the frame-stored canary to the global one - before returning.

          Figure 6/4-1 (opposite page) illustrates the use of the canary, incorporating a code
      snippet from a Darwin binary. Note the setting of the canary, right after the standard
      prolog, and its check, right before the epilog.

          So long as no stack corruption has occurred, the values will match, and the process
      could continue its execution, returning from the local frame into the saved return
      address (which, above, is further authenticated by PAC, as discussed later).

          If the values mismatch, however, this is clear indication of canary corruption, the
      most likely cause of which would be a stack overflow. Whether the saved return address
      was corrupted or not is immaterial at this pOint, as the code diverts to the
      _stack_chk_fail routine, which safely abort(3) the process. Like the eponymous
      canary in the coal mine, this detects danger, and prevents such classes over stack
      overflows. That said, canaries are from a panacea, as there are multiple ways to work
      around them (as discussed in the review questions).

          Canary use is considered a low overhead and relatively efficient strategy, so modern
      day compilers will enable them by default whenever a function uses stack allocated
      buffers . This can be disabled using -fno-stack-protector. Using -fstack-protector-
      [st rong I a llJ increases coverage to more functions .

4.2.2.3. PAC Variants of Branch Instructions

    The high bits of text pointers store the signature of the pointer's low bits with one

insruction variants (and on function return using RET variants). This is required only for
absolute branches, since those rely on values in pOinters, which may potentially be
subverted . The branch variants are appended by 'A' (to denote authentication) and the
instruction key used ('A ' or 'B'). Similar to the RETurn variants above, we have:

      4.2.2.5. Stripping PACs from a pointer

      XPACLRI (for the LR only). The instruction implementation can be likened to a bitwise

         •   If FEAT_FPAC is implemented, the processor triggers a specific PAC failure

      4.2.3. Operating System Support

4.3.3. MTE Pointer Arithmetic

    MTE will, by deSign, garble the top byte of a pOinter. ARM's Top-Byte-Ignore (TBI)
makes this irrelevant for pOinter access, but tags make pOinter arithmetic slightly more
complicated - as the (possibly different) tag value of each pOinter would have to be
removed prior to any calculation. Doing so is not hard, but would take several additional
assembly instructions for each pointer.

    To allow for pointer arithmetic with MTE pointers but without considering the tag,
ARMv8.5 extends the instruction set with two additional opcodes - SUBP, and SUBPS.
Like their integer arithmetic counterparts (SUB and SUBS), these instruction perform
subtraction (and, in the case of SUBPS, optionally set flags), but only operate on the
lower 56-bits, performing sign bit extension (so the top byte is set to all '0's or all 'l's).

   As with SUBS, setting Rd to 31 yields the co rresponding pointer comparison alias,
CMPP, since it sets the flags but (for lack of an Rd) discards the result.

4.4. ARMv9: Guarded Control Stack FEAT_GCS

    ARMv9-A's FEAT_GCS enables a Guarded Control Stack . The GCS acts as a
"shadow" stack (similar to Intel's and RISC-V' s) for the purposes of storing return
addresses. That is, executing BL [R] instructions stores the return address not just in LR

value of LR against that in the GCS.

segregated from the rest of virtual memory by page table permissions, which are
bypassed on the BL [R] /RET executions. The GCS Stack Pointer is maintained in a

              Memory analysis is a fundamental aspect of process analysis. This requires
           observing two aspects of memory: Its layout, and utilization metrics.

           S.1. Process Memory Layout

                Processes start up (mostly) deterministically, so their memory layout, at least
           initially, is quite predictable. Too predictable, in fact, that in the past two decades all
           operating systems adopted some form of Address Space Layout Randomization (ASLR).
           This, however, is seldom full randomization, and instead just adds a random "slide"
           value to offset all loaded objects. Once the slide is known, the address space is largely
           deterministic again - at least in terms of figuring out the load addresses of objects (but
           much less so for the heap).

                Determining the address space layout is of crucial importance for debugging - both
           live and post mortem. This is why all OSes provide (given the appropriate privileges)
           interfaces for retrieving layout details .

           5.1.2. Android

               As far as the kernel level is concerned, Linux and Android are essentially identical.
           In user mode, Bionic's linker64 fulfills the role of dynamic linker, but approximates the
           classic ld of Linux, with a few minor address space changes:

               As discussed before, Bionic's heap implementation is Scudo, which names its
           regions and reserve areas accordingly (anon: scudo: prima ry, anon: scudo: seconda ry
           and anon: scudo: prima rLreserve). Bionic also has its own allocator (discussed in A-
           11/2), which names its regions anon: bionic_a lloc_sma ll_obj ects, and
           anon: bionic_a lloc_lob (for large objects).

                Where things get a bit complicated is when the Android RunTime (ART) is involved.
           As explained later in 11/3 (And A-II/7), ART provides the runtime environment for
           Android's applications and its core process, system_server. ART is very memory
           intensive, and repurposes otherwise unused portions of the address space for its own
           libraries and heap.

               Another highly important aspect of ART is that all of its processes fork from one
           master process, Zygote64. True to its biological namesake, this process clone (2) s to
           create a child process which "specalizes" into the new app. Unlike the traditional
           fo rk (2) /execve (2) model, however, there is no execve (2) involved.

                Thus, children of Zygote64 are de-facto identical clones of the parent Zygote for its
           entire lifetime with an almost identical memory layout, as can be easily seen in the
           following output. The only child-related idiosyncrasies are those which arise from after
           the clone(2) - the loading of the Android PacKage (APK), and any subsequent memory

      5.2. Heap Introspection

          A stitch in time saves nine. The best countermeasures to memory corruptions and
      leaks are to program defensive and "green" programming, paying careful attention to
      buffer boundaries and lifecycle. Still, given that memory bugs are so easy to introduce,
      other run-time detections have been developed over the years.

      5.2.1. Linux

           Linux's offers two features for heap introspection using two hook types which are
      built into the malloc(3) implementations: mcheck(3) and mtrace(3).

          GLibc's mcheck functionality allows heap consistency checks, albeit at the cost of
     performance. The first is via the mcheck(3) API call (from <mcheck.h» , which should be
     called before any call to other allocation functions. A stronger variant,
     mcheck_pedantic (3) is also available, with more rigorous checks but also more chance
     at catc hing heap corruptions. With either of those in effect, the allocation and free
     functions run consistency checks to try and detect errors as soon as they occur.
     Consistency checks may be forced at any time through mprobe(ptr) on specific
     pOinters, or mcheck_check_alU).

         The default behavior of mcheck (3) on error can be toggled through ma llopt (3)
     with the M_CHECK_ACTION code (-5), or the MALLOCCHECK_ environment variable. The
     value expected is a 3-bit integer. Bit 0 controls the printing of an error message. Bit 1
     causes a call to abort(2). Bit 2 simplifies the error message.

         Newer versions of glibc have been known to break this functionality. In particular,
     the tcache has its own double-free integrity check, which can abo rt (3) the process
     before the mcheck(3) hooks catch the error.

          The mtrace(3) API (also in <mcheck.h > installs hooks as well, but ones geared to
      provide a tra ce of the function calls and their arguments. This is less helpful in finding
      heap corruptions, but more effective in detecting leaks.

     5.2.2. Android: libmemunreachable

     GetUn reachab leMemo ry () - but behind the scenes is a rather complex operation which

           5.2.3.2. Interposing with libgmalloc .dylib

                Darwin provides libgma Hoc( 3) as a powerful facility to locate memory bugs. The
           library (Iusr/lib/libgmalloc.dylib) can be used by force injecting it (using
           DYLD_INSERT_LIBRARIES) into the targ et process at startup. The library then
           automatically replaces the default implementation of all the libmalloc interface (from
           Table 2.2) with custom implementations, through a process of function interposing (see
           10/1.3).

                The custom implementations in libgma Hoc (3) allocate program memory at the
           end of a given physical page, and furth er claim the next page to be a guard page . This
           ensures any overflow from the allocated memory causes an EXC_BAD_ACC ESS exception,
           killing the program on the spot. Runnin g the program under a debugger can thus break
           at the precise moment of the heap overflow occurrence .

               As a library, libgmaHoc(3) is configurable through MALLOC* environment
           variables. A full list of these variables can be found in the manual page.
