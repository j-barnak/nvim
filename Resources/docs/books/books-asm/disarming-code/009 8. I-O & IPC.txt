I/O & IPC
    A  process is meaningless without Input and Output (I/O) . Sooner or later, files
have to be read or written to, or other processes need to be contacted by Inter Process
Communication (IPC) . This chapter explores these aspects, inherent to all processes .

     The discussion begins by overviewing th e rich spanse of I/O related system calls.
File I/O, metadata (permissions, attributes, status, etc.) and device I/O as well. Special
focus is given to outside monitoring of I/O done by processes, from the per-process
perspective (Rather than the system-wide one, which is explored in the next chapter) .

     What follows next is a discussion of IPC in UN * X. The classic facilities - shared
memory, System V and POSIX facilities, and of course sockets - are overviewed, from
the system call perspective, with again an emphasis on monitoring and tracing runtime
use. This is clearly a case where a single chapter couldn't even begin to cover the vast
ex panse, and the reader is encouraged to check out the definitive references by the late
Richard Stevens ("UNIX Network Programming ", but also of the "TCP/IP Illustrated"
Trilogy fame) .

    Next, the main problem of I/O - blocking - is considered, and its alternatives -
non/blocking, multiplexed and asynchronous - are considered. Arguably, multithreading
obviates most of these APls (since it's far simpler to just spin a thread per I/O
descriptor, and let it block) , but their relatively little use contributes to these APls'
obscurity, which I hope to elucidate.

    Finally, two proprietary I/O facilities are considered . Darwin's Mach messages (and,
on top of it, XPC), and Android's Binder. Again , these do not aim to be comprehensive
discussions (more detail can be found in M-I/ll,14 and A-II/g). The perspective is,
once more, of traCing and monitoring these important IPC channels, which dominate
their respective platform's IPe.

                  UN*X visualizes its world as a filesystem, which can contain directories, and files of
              multiple types - ordinary files, hardware devices, and even IPe constructs (like named
              sockets and pipes). Unlike Windows, there is only one "root" filesystem (/), though
              other filesystems (and Darwin "Volumes") can be connected to it by using directories as
              m ount points, an operation known as mounting.

                  There are myriad filesystems, however, and each has its idiosyncrasies with relation
              to how its files are managed. The seminal Solaris was the first to pioneer the layer
              known as the Virtual Fi lesystem Switch (VFS), which enables multiple filesystem
              drivers of different types, local or remote, to operate seamlessly with the kernel - so
              long as they provid e a standard interface to their fi les and object. Irrespective of the
              interna l organization of the filesystem - be it file lists, b-trees, hash tab les - for VFS, f ile
              lookups eventually end up at an index node (inode). At this level, all that VFS needs is
              to resolve the file name into an inode number, and for the inode to provide the
              necessary file metadata - access/creation/modification times, attributes (both standard
              and extended) and, of course, a pointer to the file contents.

                  Each filesystem provides easier lookups of its inodes by organizing them in to
              directories. These are specialized inodes (of type 'd'), whose blocks contain lists of file
              names and their inode numbers, referred to as directory entries (dentries). Traversing
              the pathname iterates through the dentries - with the familiar separator character (/)
              separating each directory dentry. For regular inodes, the inode holds the underlying
              blocks where t he actual data is read from or written to. Thus, what is in user mode a
              simple lseek(2) or a read(2)/write(2) to some offset, can be resolved into one or
              more blocks addresses on disk.

                   Helping further to optimize I/O access are multiple caches: Frequently looked up
              path components are stored in a dentry cache. Frequently accessed files are held in
              t he inode cache . And - most importantly - file data blocks are maintained in I/O
              caches (Linux: page cache, Darwin : Unified Buffer Cache). Ignoring the caches, the
              object hierarchies can be presented in this following diagram.

    The file path specified for open (2) ing is either absolute or relative. Absolute paths
are resolved relative to the root directory, or to another directory which may have been
set by ch root (2) system call. Relative paths are constructed using the process'
current working directory. The path components are walked in turn, neceSSitating
execute permissions for directories to be searched. Linux's path_reso lution (7)
manual page provides a detailed explanation of this process.

    Sin ce a process can be started in any directory, the library call getcwd (3) is useful
for determining that directory during runtime. The chdir(2) (to a path name) or
fchdir(2) (to a directory file descriptor) system calls can be used to change the
current working directory. These system calls affect all threads, but Darwin adds
_pthread_[fl chdir(2) to do so for the call ing thread only.

     Keeping track of the current working directory can be cumbersome and lead to
potential security vulnerabilities. The ... at suffixed calls, which all operate on a path,
help simplify this, by prepending an fd argument. For an absolute path, the system calls
work exactly the same way. For a relative path, however, The fd argument's directory is
taken as the base for the path, rather than the process' current working directory. In
this wa y, a process can hold on to a number of file descriptors, with which relative paths
can be reliably resolved.

arguments instead of three, with the third argument (previously, flags) now a pOinter to
a open_how structure, of size bytes (in the fourth argument). The open_how is an
extensible structure (hence the need for the size), which contains flags and mode

      1.1.2. Directory Entry Manipulation

          The directory entry holds the file name, and "li nks" it to this or that inode.
      Therefo re, a file can be moved around , or even removed from the file system by
      operating on its dentry. The oft used mv(l) and rm(l) commands are therefo re
      directory-level operations, and are subj ect to directory-level permission checks. At the
      system call level, these are carried out by rename( 2 ) and unlink(2) system calls. As
      with open(2), these have correspond ing ".at vari ants .

          Directory entry manipulation poses a security risk, which may arise from race
      co nditions during file renaming or removal. Darwin's extensions - renamex_np (2) and
      renameat x_np(2) take a flags argument. This may be RENAME_SWAP, to make the
      rena ming operation atomic. An other flag, RENAME_EXCL, will refuse the operation if the
      destination already exists . Finally, RENAMEJOLLOW_ANY will bail if symbolic links are
      detected during path name resolution.

           1.5. Device I/O
                A well known trope is "in UN *X, everything is a file". This has much truth to it,
           because the standard has long special "device nodes" to abstract hardware devices as
           files . Over time, though, there have been deviations from this: network interfaces have
           no filesystem representation at all, and can only be accessed using sockets . Linux, for
           example, deviated from device nodes to sysfs objects (arguably, though, still
           pseudofiles). Darwin accesses some hardware devices over IOKit (Mach port messaging
           toin kernel drivers). That said, the UN *X device model is still preval ent to this day.

           1.5.1. Device nodes

                 When tradition al devices are used, they are of two distinct types:

             •     Block Devices: abstract their data as block units, of some given block size
                   (usually 512 or 4,096 bytes) . These are com monly mass storage devices - disk
                   drives, (somewhat antiquated) optical media, and the like. Because they are
                   usually Mass Storage of many GB or TB, their I/O is buffered through the cache
                   layer (see 5/3-2), and further abstracted by filesystems.
             •     Character Devices: abstract their data as a stream of bytes. In many cases,
                   these are "forward only" devices, which can only read new inputs, but ca nnot go
                   back to previously read data. The classic exam ples here are the nY, keyboard,
                   mice, and other serial devices . Access to character devices is therefore direct, and
                   unbuffered. With that in mind, block devices can also be used in "character"
                   mode, for operations which require bypassing the caches (such as fsck(1)).

                Creating a new device has to be done at the kernel level. Usually, the kernel already
           contains hard-coded support for the device in question, or is capa ble of loading a driver
           (in Linux, a kernel module, in Darwin, a kernel extension, or "kext"). The support
           creates the device abstraction in the kernel, wherein it is uniquely identified by the
           tupl e of (major, minor). The major can be thought of as a number identifying the
           device driver code, and the minor as the number of that specific device, when more
           than one device is handled by the driver.

               Enabling a device for use in user mode requires a device node to be created. This
           is done with the mknod(2) system call (or the mknod(l) utility). This takes in the major,
           minor and path name to the device, which resides in a special virtual file system, of type
           devfs, conventionally mounted under /dev.

               Creating a node requires the major,minor of the node to precisely match the in -
           kernel combination. Fortunately, in modern UN*X the node is either automatically
           created by the kernel (as is the case in Darwin), or by a user mode helper (Linux's
           udevd or Android's ueventd), which listens for kernel notifications (in Linux:
           netlink(7) sockets), and calls mknod( 2) behind the scenes.

2.1.4. Linux: memfd_c reate (2)

    The mmap (2) system call has long had the problem, that memory mapped with the
intent of sharing must be associated with a file descriptor. While simple, this does
require that the memory be backed by a readable/writable file somewhere on the
system. For unrelated processes with different user and group IDs, this necessitates a
world-writable directory.

    Normally, such files are created in /tmp, which is world-writable by design especially
to allow any process to read and write temporary files. There are other considerations,
however. World-writable files open up a slew of security vulnerabilities. Further, the
existence of /tmp or other world-writable locations is not at all guaranteed. Android, for
example, does away with /tmp.

     For lack of a world-writable directory, Android managed to circumvent this
restriction. This required an "Androidism" - one of the rare cases where Android
deviates from mainline Linux, in creating a new class of shared memory - The so called
Anonymous Shared Memory (ASHMem). ASHMem is implemented by a kernel
module, which exported a character device node (ldev/ashmem) to user mode, and a set
of ioctl(2) codes to perform the mapping . Once a /dev/ashmem instance was mapped,
its open file descriptor could be passed to another process. This worked well throughout
Android 12, but, being an Androidism, was not available in Linux .

    Linux 4 .5 introduces the Memory File Descriptor (memfd) system calls. The first,
memfd_create(2), takes a name and MFD_* flags (usually, MFD_CLOEXEC, but also

2.3. UN*X: System V IPC

     Back in the early days of UNIX, AT&T's System V implementation evolved alongside
BSD, and implemented its own set of synchronization primitives. These were not
inducted into POSIX, but are still supported by both Darwin and Linux (though not in
Android) . In addition to the already discussed System V Shared Memory, they also
include semaphores and message queues. Linux documents its support of System V IPe
in svipc(7) .

      2.5. Linux: eventfd(2)

          Linux provides a special IPC mechanism suitable for simple notification with Event
      File Descriptors. These are created by a proprietary system call, eventfd (2), which
      takes in a 64-bit initval. A second system call, eventfd2 (2) also takes flags of
      EFD_ [CLOEXEC INONBLOCK] (with the usual semantics) and/or EFD_SEMAPHORE. Either call
      returns the descriptor in an already open(2)ed states.

          Once created, the descriptor can be read(2) from and write(2)n to, but only in 8
      byte buffers (64-bit values). The value supplied to write(2) is added to the present
      value associated with the descriptor (initially, initval). The resu lt can then be read (2),
      and (for a non semaphore) it is automatically reset to 0. If any read(2) is attempted
      while the value is 0 (i .e. no otherwrite(2) followed), the read(2) blocks .

          When EFD_SEMAPHORE is specified, the eventfd emulates a semaphore. If the value
      is non-zero, '1' is returned to the caller, and the actual value is decremented by 1. Here,
      too, if the value is 0, the call blocks until some write(2)r can increment it to a non-
      zero value. This brings eventfd(2) to be on par with POSIX or System V semaphores.

2.6. UN*X: Sockets

    The socket programming model can indubitably be considered one of the most
important developments in OS history. Developed around 1983 by UC Berkeley, it was
the first API to standardize interprocess communication in both a local system scope,
and a global one. It was soon incorporated into POSIX, and its application for the
TCP/IP protocol suite earned it a largely identical port into Windows' Winsock .

    A socket is defined as a communications end point. It is created through a call to
the eponymous system call, which takes three arguments:

      (IPv4/IPv6 - local or network). The platform extend with proprietary families.

    A fundamental property of the UN*X I/O model is that it is blocking - read (2)
variants will not return until there is data to be read, and write(2) variants will not
return until the data can be verified to have been written (at least, to the cache) .

    Blocking I/O simplifies the model greatly, but introduces a major problem - an
uncooperative descriptor can cause the program to block indefinitely, stuck until the I/O
operation can complete. No longer so simple, this greatly complicates handling multiple
descriptors, since reading/writing out-of perfect synchronization would inadvertently
block the program flow . To further exacerbate an already bad situation, there is often
no way to get out of an I/O block (unless I/O can be completed), short of signaling or
outright killing the process .

3.1. Non-Blocking I/O

    The simplest approach to dealing with blocking I/O is to simply switch to non-
blocking mode . This can be done on a per file descriptor basis - either open (2) ing it or
later using fcntl(2) to F_SETFL the O_NONBLOCKing flag. Sockets also support this
through the FIONBIO ioctl(2) code.

    Using the option changes the behavior of the I/O calls to fail, rather than block. The
errno is set to EWOULDBLOCK or EAGAIN, to disambiguate it from other errors.

3.2. Multiplexed Synchronous I/O

    Non-Blocking I/O is not a true fix for blocking I/O. It forces the process to
contin uously attempt its read (2) /wri te (2) operations, which is inefficient and highly
resource intensive for naught. It also does not scale well for multiple descriptors.

    This predicament required development of an I/O mod el which allowed
Multiplexed Synchronous I/O: Allowing a process to peek at any or all of its
descriptors simultaneously, checking their availability for I/O, and only performing the
I/O whe n availability could be guaranteed. The guarantee ensures that the I/O call
would not block, returning immediately, and allowing the process to continue.

3.2.1. The standard model: select(2)/pselect(2)

    The select(2) system call works with fd_set objects to allow the caller to specify
readfds, wri tefds and exceptionfds to observe (for readability, writability, or
exceptional conditions) within a specified timeout. The syscall also accepts an nfds,
which must be set to the highest numbered descriptor in any set, plus one.

    When used in this manner, the system call simultaneously blocks on all the sets,
returning with an indication of whichever one is ready for I/O, or after the timeout. The
timeout is a pOinter struct with tv_sec (seconds) and tv_usec (microseconds).
Passing a NULL pOinter allows blocking indefinitely.

 3.3. Semi-Synchronous (signal driven) I/O

      The fcnt l( 2) syscall's supports the O_ASYNC flag to F_SETFL a file descriptor to
 signal driven I/O. The flag indicates asynchronicity, but a more apt name would be
 "semi synchronous", since it enables SIGIO to be sent when the descriptor is available
 for I/O, or SIGURG on an exception condition . Similar functionality can be achieved on
 sockets through the FIOASYNC ioct l( 2) code

     This is an alternative to blocking on the descriptor, as select(2) would do: The
 program can avoid blocking I/O, and perform it only on signal reception, which ensures
 that the I/O would immediately complete. Though not commonly useful for files, this is
 used with sockets.

     Further, the F_ [GET/SET] OWN standard fcntl( 2) cmd codes allow the caller to
 get/set a PID that will be sent the signal. POSIX calls this to be a process or process
 group ID. Linux, however, extends this by F_SETOWN_EX, which allows the signal to be
 sent to F_OWNER_ [TID/PID/TGID] . Linux further supports the F_ [GET/SET] SIG cmd
 code, which enables changing the signal from the default SIGIO.

           o   Ports are accessed by rights. Port rights allow either SEND [_ONCE] or RECEIVE .
               Port rights can be duplicated ( "copi ed") or transferred ("moved").
           o   At any given time a port has exactly one RECEIVE right, which allows its holder to
               receive messages, or mint any other rights (but an additional RECEIVE) to the
               port. The holder of the RECEIVE is thus the owner of the port.
           o   There may (or may not be) any number of SEND right holders - those can send
               messages, but will be unable to receive th em .

4.1.3. MIG

    Mach messages can be handled manually, but serializatio n and deserialization are
time consum in g and error-prone. As with other RPC mechanisms, there is a large
amount of "boilerpl ate " code involved, and so an automated tool - the Mach Interface
Generator (MI G) is used to handle these tasks, and automatically generate the code.

    Th e mig (1) tool uses .defs files as input. Though it's uncommon to find .defs in
Appl e's (few) open sources, XNU still contains several (in osfmk/ ma ch), and many closed
source daemons use MIG, as is evidenced by their dependency on the (otherwise never
used) _NDR_record symbol.

     Alth ough formally deprecated, MIG is alive and well - present in nearly all of Apple's
older daemons, including critical and world-reachable ones, such as macOS's
WindowServer and the * OS's backboardd (and friends) . The legacy code, coupled with
insufficient validation, and its susceptibility to basic reverse engineering techniques,
have al l long made MIG code a prime source of vuln erabi liti es . A discussion on reversing
its data structures can be found in 14/2.6.

4.2. XPC

   Starting with Darwin 13, Apple introduced XPC as a new API and transport for IPC.
Deep under the hood, XPC messages are still serialized payloads inside Mach messages.
There is, however, a fundamental difference here.

    Whereas legacy Mach messages are , at best, serialized by MIG, XPC messages are
dictionaries, and thus se lf-describ ing . Message arguments are serialized as key/value
combination s, with the values conforming to one of several datatypes. Addition al ly,
Darwin 12's Grand Central Dispatcher (GCD ) is tightly ingrained into XPC, providing
asynch ronous APIs and support for blocks.

    XPC has since evolved tremedously, and has not only displaced Mach Messages, but
also revolutioned Darwin application architectures. Dra wing inspiration from microkernel
architectures, XPC al low developers to refactor their apps in to a main process and any
number of child processes - XPC Services - which can be called on from the main app .

    These service processes can be launched on demand and kill ed when no longer
needed. Further, each XPC service can be defined with a different security profile, via
entitl ements or sandbox restrictions. Darwin 23 further improves on this, by allow
Laun ch Constraints (from the Mach-O Code Signature) to limit XPC service launch to
their designated responsible PIDs.

4.2.2. Hooking/Tracing XPC Messages

    Security researchers devote a great deal of time and interest into researching XPC
messaging. XPC, having deprecated MIG as the message transport of choice, provides
an interesting attack surface.

   Tracing a synchronous cl ient is easy, since all it takes is a breakpoint on
xpc_connection_send_message_with_rep lLsync (3) - going in, the message
argument will be in Xl' On return, the reply is the return value, in X0 .

    Asynchronous clients and servers are more difficult, since one would have to
breakpoint on the block . This requires attaching to the debuggee in at least two points,
or reverse engineering the block address from the disassembly (see 14/2-5). There is,
however, a bit of a hack-ish alternative.

     Once the reply is received, by any of the above means, it will be processed with one
of the xpc_d ict iona ry _get_ * APIs . These APIs are type-s pecific, but it's safe to
assume that all xpc_dictionary_t messag es con tain [ulint64, string, bool, and
possibly other types. Breaking on the xpc_d ictio na ry _get_ * APIs is th erefore a
guaranteed way of intercepting all incoming XPC traffic - both messages to servers and
replies to clients.

    The obvious downside is that xpc_dictionary_get_* APIs are called once for every
key. Since a dictionary may contai n multipl e keys, the API s may be called several times
on the same dictionary. This, however, can be worked around.

    Due to SIP protections, dynamic attachm ent of any kind is nearly impossible on
macOS, and likewise on *OS variants, leaving only kdebug codes which Ubxpc. dyUb
emits. Those, however, are of limited value, since they do not provide much
information. Disabling SIP (or jailbreaking) opens up many more options for tracing XPC
(and debugging in general), including library injection and dynamic tracing (see Chapter
10). Numerous tools can be used, including the powerful (but aggressive) Frida, the
Author's (dylib-injection based) xpoc e (j ), or (debugger-API) based xpoce2 (j ) .

      4.3. Darwin IPC Security

          Darwin makes uses of Audit Tokens to identify IPe peers. Audit tokens are sent in
      Mach message trailers. These trailers can only be generated by the kernel, so their
      content is implicitly trusted.

          Audit tokens are intentionally left opaque, but in practice they are a simple array of
      8 uint32_t fields, including the PID and UID/GID (effective and real), and an audit
      session/user ID. (an example can be seen in eslogger( 1) 's output, 9/3 .2). These
      common ly match the credentials of the peer, but tokens may be used transitiviely.

          Just knowing the peer's PID and UID/GID, however, is a really feeble form of
      security (as discussed in a Review Question). Darwin therefore goes above and beyond,
      by providing two undocumented yet highly versatile system calls - csops (2!) (# 169)
      and csops_auditt oken(2!) (#170). The two syscalls are ioctl(2) style, taking in a
      PID (and an audit token, respectively), as well as an operation code, with dependent
      arguments. Several of the operation codes (#def ined in the kernel's bsd/sys/codesign.h)
      are profoundly important for security :

           •   CS OPS STATUS (#0),;, returns the code signing validity status of the remote
               process . This is often overlooked, since in * OS variants (and, slowly but surely,
               macOS as well), the system will immediately kill any invalidated code signed
               processs .
           •   CS OPS IDENTITY (#11),;, populates the buffer argument with the code Signing
               identity of the process . This is a simple reverse DNS notation string - e.g.
               com. apple. ps - but because of its embedment in the (valid) code Signature, it
               can be considered unique and trustworthy. In this way, a server may not even
               bother to process an incoming request from unknown/untrusted/unapproved
               identities.
           •   CS OPS ENTITLEMENTS BLOB UaJ~ (later deprecated by (but still used alongside)
               CS_OPS_DER_ENTITLEMENTS_BLOB, #16) fills the buffer argument with the XML or
               DER entitlements, if any, held by the operation target. This forms the substrate
               for all of xpe security. libxpc. dylib's xPc_c oPLenti tlemenh APIs all wrap the
               two system ca ll s, and parse the returned blobs.

 S.1. Abstraction: The Android Interface Definition Language

      Most developers, and even Android's code itself, seldom need to use Binder directly.
 At the Android source level Binder is completely hidden through the abstraction of
 Remote Procedure Call - the Binder send-message-and-receive-a-reply operation -
 referred to as a transaction is hidden several layers deep. Each RPC call uses a
 different, AIDL-assigned transaction code , and serializes its arguments into the
 transaction payload buffer, which in Binder-ese is called a "Parcel".

      A high-level Android Interface Definition Language tool - aidl - is used to pre-
 process definition files into (usually) Java wrappers. The tool (part of the SDK's bui ld-
 tools generates two classes:

      •   The Proxy. class: provides the caller end . It exports the method interface, but its
          implementation which merely serializes the method arguments into a medium
          message (i.e. the Parcel), and transfers it to the remote.
      •   The Stub class: is on the callee's end. It obtains the incoming message,
          deserializes the arguments, and calls the concrete implementation. Once the call
          is complete, any out arguments and return values are serialized into a reply
          message, which is sent back to the Proxy.

     The handle returned from Context.getSystemService(name) is stashed inside the
 Proxy class, and further boxed into the "Manage roo object. Thus, "Manage roo method
 invocations are transparently Proxy calls. The Stub (an abst ract class) runs on the
 server side, and is extended by the concrete service class, which provides the method
 implem entatio ns.
