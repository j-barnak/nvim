
Memory - I - The System View

    Sooner or later, everything a process does amounts to manipulating bits in
memory. The very definition of a "process" is, primarily, the isolated, virtual memory
within which it operates.

    This work begins its examination of memory by first looking at from the OS
perspective: The management of the physical memory and its abstraction, virtual
memory, through paging . We examine the page lifecycle, and the attributes of paging
which affects memory management.

    Next, we look into the POSIX virtual management APls, which both the Linux and
Darwin platforms offer as APls, with the usual minor deviations from the standard to
allow for OS idiosyncrasies. We then look at specific extensions Darwin allows - such as
tagging allocations and automatically purging memory. The section concludes with a
discussion of how both Linux and Darwin deal with low memory conditions ("Memory
Pressure"), and how Android further builds on Linux with its Low Memory Killer daemon.

    Finally, we look at the standardized metrics, as seen through the Linux / proc/memin fo
and Darwin's system utilities.

                Every process uses RAM, but none use it directly. Virtual Memory serves as an
           abstraction over the physical memory, ena blin g every process to operate in its own
           private memory space, isolated from other processes in the syste m . Indeed, it is the
           virtu al memory space that is the de facto definition of a process, along with its
           descriptors.

             •      Paging Out: Th e system normally maps memory to and from files on disk . Such
                    memory is refered to as named memory. If the physical RAM runs low, pages not
                    in use can be freed, in favor of their on-disk copy. Pages that have not been

                    system call.
             •      Paging In: Paging also works in reverse - that is, if virtua l memory is needed but
                    is not mapped to RAM, a page fault occurs. The faulting thread is t empora rily
                    sto pped, whil e the necessary page is paged in .
             •      SwaP-Ring,;, When memory that is not mapped to/from a file (called anonymous
                    memory) needs to be paged out, it is written to a dedicated large file (or
                    partition), cal led the swap . In some OS confi gurations (notably, Android and
                    iOS), the swap space may be another segment of RAM, using compression to
                    reduce pag e utilization.

  •   Lazy. allocations: Memory that is allocated, but not yet used, need not be
      backed by any physical or disk pages. Only a reservation exists, until the memory
      is actually accessed. It is then that a page fault happens, and the initial mapping
      of the page is created, claiming the actual RAM. This helps defer and amortize the
      cost of the allocation.
  •   Memory' sharing,;. By translating virtual address A in one process and virtual
      address B in another to same physical address P, the system can provide shared
      memory between the two. This makes for a powerful interprocess communication
      (IPC) facility: Once set up, processes can continue simply reading and writing to
      their respective virtual addresses, as only one sole physical copy, shared by both
      processes.
  •   Imp-licit sharing,;. When two processes map the same file, the system can opt to
      reuse the same physical memory page and map it into the different virtual
      memory spaces. Unbeknownst to the processes (which 'think' they mapped the
      pages privately), they thus share the same mapping, implicitly. This provides a
      dramatic reduction in overall physical memory (RAM) utilization, as commonly
      used files (notably, runtime libraries) are only mapped once.

          So long as the mapping remains read-only (that is, unmodified by either
      process), no further handling is required, save for tracking the number of
      references on the physical page (so that it may be eventually freed). If one
      process modifies its virtual copy, however, its mapping has to be re-established,
      by cloning the original physical mapping - i.e. allocating a new page and copying
      the contents. This "Copy-on-Write" operation is costly, but fairly infrequent.

     These tenets of memory management go a very long way in enabling efficient use
of the available RAM. Most processes only use a small working set of their full virtual
memory space, so lazy allocations already provide a huge reduction in the amount of
physical RAM required. Of this RAM, a large part of it is from files, and is thus pageable
(and likely implicitly shared), while the rest is swappable. Disk space is orders of
magnitude larger than RAM (and easy to hot-swap), meaning that virtual memory is
practically near-limitless .

     The translation of virtual memory to physical is done by a hardware component
called the memory management unit (MMU). The MMU performs the translation
according to page table entries (PTEs). The entries are looked up in a multi-level table,
using a process discussed in ARM 's documentation [mmul, and later in 13/2.3, which
remains largely invisible to the operating system .

    The salient pOint, however, is that kernel maintains a separate table for each
process (in the TTBR0_ELl register). The table (read: the register value pointing to it) is
swapped every time a process enters execution. Processes can't control their page
tables - that is up to the kernel to maintain (and, in Apple Silicon, now placed even
outside the kernel's reach, in the Secure Page Table Manager, SPTM). In other words, a
user mode process has no means (outside of any OS API) to access memory belonging
to other processes. Thus, physical memory isolation can be maintained.

1.2. Page Lifecycle

    Sooner or later RAM will be exhausted, which will force pages to be somehow
reused (or else the system will crash). It follows, therefore, that (most) RAM pages will
be in a state machine with respect to their virtual memory contents. There are several
possible states to consider:

  •   Free: The physical page is not presently used. Its contents are undefined - may
      be zeroed out, or left over from some previous non-free state of the lifecycle.
      Free pages can immediately be repurposed for virtual memory.
  •   Active: The physical page is in use, or has been used recently. Its contents are
      virtual memory of whichever process, or the kernel itself. The OS's virtual
      memory manager keeps track of these pages and orders in a Least Recently Used
      (LRU) list.
  •   Inactive: The physical page is still in use by some process, or the kernel (as per
      "Active"), but has not been used recently. This makes the page a likelier
      candidate for removal.

      1.3. Swapping

           When more memory is needed, least recently used pages are paged out. In the
      case of named memory pages - those obtained from files - they are written back to the
      files whence they came (if dirty), or simply purged (if clean, since they are identical to
      the already existing file). In the case of anonymous memory, however, this requires the
      use of swap space.

          Swap consists of any number of areas, designated as a store for anonymous pages.
      Commonly, a single swap file or partition suffices. Linux supports either configuration,
      and provides swap destination control through the swapon (2) /swapoff (2) system cal l
      and the swapon (S) utility. Darwin, on the other hand, swaps only to 1GB files (in the
      hardcoded paths of /System/Volumes/VM (on macOS * ) or / private/var/vm (*OS) . Darwin
      further hardens its swap files - both by encrypting them on disk, and applying a
      "swapfile pager" to return NUL bytes if directly read from .

           In systems with flash storage, however, swapping can prove detrimental to the
      flash , due to the high number of write operations, which wear down the flash with PIE
      cycles. As an alternative, Darwin introduced the Compressor Pager - which
      compressing the contents of swapped pages, and stores them elsewhere in RAM.
      Although this still weighs on RAM usage, it is significantly lighter, since multiple pages
      can be compressed in this way, and the compression ratio is commonly very efficient.

          Compressed RAM is used across all Darwin variants (though, in some cases, macOS
      and iPadOS do also swap to flash, in the paths mentioned above). Linux adopted similar
      ideas - zram (as a virtual block device) or zswap (as a compressed cache for swap pages)
      - which are used in Android.

          System administrators often keep a close eye on swap usage, since running out of
      swap space is tantamount to an out of memory condition . As discussed later, this
      involves killing or "jettisoning" processes to quickly reclaim memory. In Darwin, the
      swap utilization is shown through the vm. swapusage sysctUS) MIB. In Linu x/Android,
      the information is in / proc/meminfo and /proc/swaps . The / proc/sys/v m/swa ppiness pseudofile
      (or vm. swappiness sysctUS) indicates a value between 0 (avoid swap) to 100 (swap
      agg ressively).

      1.4. Page Size

          An important aspect of paging is determining the size of a page . This has
      traditionally been 2 12 =4,096 bytes, or 4KB, but conte mporary OSes and CPUs have
      begun to deviate from that .

          ARM refers to the page size as the "translation granule", and can configure it at the
      processor level through the TGn bits of TCR_ELl. Apple has long opted to use a larger
      page size of 214 = 16,384 (16KB), which is now also supported in Android (as of
      Android 15) .

           Page addresses must be aligned - in both physical and virtual memory. This means
      that a 4K page address will usually end with 3 zero hex digits (i.e. 0x ... 000), since 12
      bits (= 3 hex digits) define the page size . With 16K pages this increases to 14 bits, so
      page addresses end with either 0x ... 0000, 0x .. .4000, 0x ...S000 or 0x ... C000 . **

          A larger page size provides both benefits and drawbacks. On the one hand,
      performance is improved due to reduced paging and small page tables . On the other,
      the minimal amount of memory required for a physical allocation is quadrupled . The
      Android Deyelopers Blog [abI16k] cites a 5-10 % performance boost, at the cost of about
      9% additional memory.

          Using the heap (in user mode) and zones/slabs (in kernel) helps offset some of the
      overhead. Most user-mode applications remain agnostic to the page size, and well
      coded ones that do rely on page size can call getpagesize(3). The binaries, however,
      need to be rebuilt to reoptimize segmentatio for the larger page size .

          There are cases wherein a program might want huge pages: These are pages
      which take up entire L2 or L1 page table entries (discussed in Chapter 13). The page
      sizes can range into the GBs. Linux provides the MAP_HUGETLB mmap (2) flag for this
      purpose, but Darwin's XNU does not offer this at present.

      2.1.5. m[un]lock[all](2)

          Paging is normally transparent to a process, since page faults occur outside its
      schedul ing quanta. There are rare instances, however, in which page fau lts are better
      avoided. One such case is when handling secret data in memory, which may be at risk if
      swapped to persistent media . Another is when the scheduling overhead associated with
      a page fault (i.e . the cost of the resulting context switch while the fault is serviced) is
      deemed too high.

           The m[un Jlock*( 2) function pair can be used to restrict paging on a given memory
      address of size bytes, rounded up to the nearest PAGE_SIZE . Calling mlock(2) locks or
      "w ires" (in Mach parlance) the memory, so it cannot be paged out until explicitly
      munlock(2)ed, munmap(2)ed, or the process is killed.

          Outside the rare cases wherein it might be justified, locking memory is generally
      frowned upon. RAM is limited, and mlock(2)ing too many pages can adversely affect
      other processes, causing them to vie for less available physical memory, and thus cause
      excess swapping . To prevent a process from mlock(2)ing too much memory, the
      resource limit of RLIMIT_MEMLOCK (set by a call to set rlimit (2») cannot be exceeded.
      Darwin also imposes a system wide limit - vm.global_user_wire_limit. Linux, by
      contrast, no longer (as of 2.6.9) limits privileged processes .

          POSIX also defines m[un Jlocka ll( 2) , but those are deemed as such bad practice
      that Darwin does not support them at all, instead returning -ENOSYS . Darwin's Mach
      APls allow locking through vm_wire, thread_wire and task_wire, though the first two
      are part of the host_priv subsystem, and thus require root.

      2. 1 .6 . msync(2)/f s ync(2)/sy nc(2)

          The system normally flushes pages to the backing store periodically, finding the
      delicate balance between not introducing overhead (by doing it too frequently) and
      potential ly losing data (risking a crash without a previous flush). User mode can
      override this practice by requesting a flush, known as a sy nc operation.

          Several system calls handle syncing. The first is sync( 2), which takes an addr, len,
      and MS_* flags specifying either MS_SYNC (a blocking operation) or MS_ASYNC (non-
      blocking), and (optional ly) MS_INVALIDATE (to invalidate all mappings of the the synced
      data in the I/O caches .

          It usually makes sense to flush an entire file, so msync (2) is rarely used. Instead,
      fsync(2) takes a fi le descriptor, and iterates in kerne l over all its associated mappings,
      performing msync (2) internally.

          In rare cases, the sync(2) takes no arguments, but flushes al l cached data blocks -
      not just those of the ca ll ing process. Thus, a process wi ll rarely have need of this
      system call, which can block for a considerable time . The only use case of this is the
      sync(8) utility, which an administrator would use before ejecting removable media, or
      emergency maintenance of the system.

          2.3. Memory Pressure

               With RAM being the limited resource, it will inevitably run low or out. Such low
          memory conditions are effectively a system emergency, because memory allocations
          will fail, crashing processes left and right. The kernel, therefore, has to avoid low
          memory conditions, and respond to memory pressure as early as possible.

          2.3.1. Linux: OOM

               Linux assigns every process in the system an oom_score, which is an indirect
          function of the actual memory consumption, yielding a value between 0 and 1,000. The
          score can be seen in the process' / proc/pid/ oom_ score entry. It is calculated as a function
          of the process' runtime and memory utilization, increasing with the latter.

               Normally, the score is just another metric . When the system encounters memory
          pressure, however, the kernel's page fault handling logic diverts to oom_ki ll_process.
          This routine iterates over the process list, and select the one whose oom_score is the
          highest, killing it outright with a SIGKILL . This triggers the process reaping logic, which
          (among other things) frees up that process' physical memory footprint . As a result,
          menory is made available for the page fault to be retried, and satisfied. The OOM Killer
          is an in-kernel facility, leaving traces only in the kernel log, in the output of dmesg (1) :

      "deserved to die", since its score was the highest, implying inefficient, irresponsible, or

      have no recourse, and their death (by a SIGKILL) leaves no trace .

      process memory utilization . Android sets that for in it and its progeny.

      2.3.2. Android: Low Memory Killer Daemon (jsystem/bin/lmkd)

           Once Android's system_server has finished booting and the system UI starts,
      Android applications follow the Activity Lifecycle . A better discussion of the lifecycle can
      be found in the Android documentation and A-II/3, but the salient point is that only a
      limited number of activities (usually, just one) can be "active" at any time - that is, be
      visible and command the UI.

          Users are well familiar with this model, as the limited screen space of a mobile
      device forces them to actively task switch between applications. At the system level, it
      does not make sense to keep activities running in the background (Android defines the
      "service" components for that). Activities not in the foreground are therefore
      suspended, so as not to consume unnecessary CPU cycles.

          But what of the memory of applications in the background? With RAM being a
      precious resource (and limited swap, if any), it is only a matter of time before too many
      background applications will weigh on available RAM, depleting it. Normally, this is
      where the underlying Linux OOM killer would come into play. The problem, however, is
      that it is heuristic driven - and may therefore kill the wrong processes, negatively
      impacting the user experience, or - worse - system stability.

           The init process and his daemonic cabal need not worry much, since they are all
      pre - set with an oom_sco re_adj of -1000. But that only solves part of the problem .
      Android therefore considers Applications to be "managed" processes . The manager on
      duty is ActivityManager (part of system_server). Android applications register all
      their components (that is, activities, but also services, receivers and providers) with it.
      This enables the ActivityManager to be aware at all times of their usage, and visibility
      (in the case of Activities) or (service) bindings.

           The ActivityManager then informs a dedicated Android daemon - the Low Memory
      Killer Daemon (lmkd) of the application state changes in the form of messages (over
      /dev/socket/lmkd) . Each message informs lmkd of the victim PID and the requested
      oom_sco re_adj value. The daemon directly writes to that PID's /proc/pid/oom_score_adj.

          At the system level, there is no sense to the term "memory layout" . RAM is shared
      by the kernel and so many processes, each of which in their own distinct virtual address
      space. While in some rare cases RAM layout may be interesting, the rapid frequency of
      paging makes it far too volatile to consider, outside predefined reservations.

          What are commonly observed at the system level, therefore, are memory metrics .
      These present statistics on just how much overall memory is used by which subsystem,
      and whether the system as a whole is fine, or under "memory pressure", wherein more
      RAM is needed.

      3.1.1. High-Level memory statistics

             High-Level memory statistics consist of three elements:

         •    MemTotal: is the total amount of RAM usable by the platform. This is commonly
              the amount of the device installed RAM, minus any reservations made by other
              hardware components, or in the platform's device tree.
         •    MemFree: is the total amount of RAM which is presently unused. In other words,
              MemTota l - MemF ree is in use .
         •    MemAvailable: is the total amount of RAM which is available for use.

         It might seem odd that in some cases (like the above), MemAvai lab le is larger than
      MemF ree. This is because of cache memory, which we discuss next.

3.1.2. Cached memory statistics

    The OS normally uses memory first and foremost for the kernel, and then for
whichever user processes require it. This does, however, normally leave large amounts
of RAM unused. The OS therefore takes liberty in repurpos ing this otherwise unused
memory for caching.

   Traditionally, I/O has always been a slow operation. Legacy hard drives spin at some
7200RPM, which puts their average seek delay at around 69ms. While but an instant by
human standards, this is on order of years fo r a processor running in nanoseconds.
Even solid state drive (SSD) access can similarly seem like days at a time .

     The solution, therefore, is to minimize I/O device access as much as possible . The
initial access cannot be avoided. But, once data is read, it can be cached in memory, so
that subsequent reads of the same I/O block need not access the device again.

      Linux keeps two I/O caches:

  •     The Page Cache : is a cache of RAM pages, which are associated with file I/O. A
        file read will populate that file's read data in the page cache, possibly (at the
        filesystem's discretion) reading ahead more of all of the file's contents. The user
        process' mmap(2)ed pages wi ll be mapped over the page cache pages (but with a
        virtual address in that process' address space).
  •     The Buffer Cache: is a cache of blocks, which are not directly associated with
        file I/O. This is usually for directory entries, supporting metadata, or raw blocks
        (such as those accessed by fd is k (1) or dd ( 1) over the raw device.

     The caches are transparent from user mode, but nonetheless have a profound effect
on system performance, since they can minimize block device access. A hi gh level v iew
of this is demonstrated in the following figure :

3.1.3. Memory Activity Statistics

    The kernel provides a view of page active/inactive state. These metrics are amongst
the most frequently modified ones. In any case, the following formulae hold:

• Active(file) + Inactive(file) = All file backed memory
• Active(anon) + Inactive(anon) = All anonymous memory
• Active + Inactive = All memory used

3.1.4. Unevictable/Locked Memory Statistics

    Memory can be made unevictable when it is used by DMA, ramfs, or is part of
System V shared memory marked as SHM_LOCK. A subset of unevictable memory is
Mlocked memory, which processes acquire using mlock(2). Unevictable or locked (in
Darwin-speak, "Wired") memory must be explicitly munlock(2). Otherwise, it will
remain resident and never be swapped or purged, until the death of its process.

               Using mlock(2) is generally considered bad practice, as it appropriates
               RAM, a shared resource, exclusively for the caller* . The maximum
               amount of RAM lockable by a process can (and definietly should) be
               limited through setrlimit(2)'s RLIMIT_MEMLOCK (or ulimit -1).

3.1.5. Swap/Compressed RAM Statistics

     The SwapTotal and SwapFree are in line with the amount reported by swapon(1),
which takes its data from the /proc/swaps psuedofile. The swap figures account to both
physical swap (i.e. swap files or devices) as well as compressed RAM. ZSwap or Zram
(if present) refer to compressed RAM footprint only.
