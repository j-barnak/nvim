System-Wide Tracing, Profiling &
Auditing

    Oftentimes, there is a need to assess the overall performance of a group of
processes, and find potential bottlenecks or slow- running code. While this can be
accomplished by tracing or hooking each individual process (as discussed in the next
chapter) , this can be quite tedious : Not only will this provide copious output for each
process, it may also impact system performance.

    This is where a system-wide approach comes in: Rather than focusing on every
function call's arguments, profiling is focused on gathering the timestamps associated
with functions - on call and return - and pinpointing those functions which take longer
than they should .

    Another method is to calion specific kernel interfaces, which record every
significant operation the kernel performs on behalf of processes . Such system wide
traces serve to capture a detailed history of what took place over a certain time period.

   A specific subset of tracing is auditing, which focuses on those operations which
have a security implication - starting processes, accessing files and other resources,
and - even more importantly - failure to perform such actions .

    The voluminous output produced by the various methods often requires further
processing. At the Simplest, timestamps can be sorted, so that - in the case of profiling
- the longest running functions are easily found. A more complicated, but highly
desirable processing of profiling data is visualization, which transforms the raw data into
a more understandable graph .

    The system -wide and configurable nature of the tracing facilities presented in this
chapter makes them all very useful for reverse engineering. A highly effective method
of analyzing a suspect binary is to place it into a test system or virtual machine with
auditing enabled, and let it run its course - all the while recording every operation.

     Lastly, this chapter shows a glimpse of two immensely powerful facilities for not just
tracing - but extending the system from user mode. MacOS's DTrace and Linux's eBPF
are described with a tour de force of their capabilities .

           Linux offers two powerful facilities for system profiling: The event trace pOints of
      tracefs, and the remarkably powerful pe rf (1) .

1.1.2. The raw_syscalls event tracer

     The raw_syscalls event tracer captures every system call issued by every process,
in real time. The 'raw' aspect refers to the fact that no attempt is made to parse or
process the data . Each system call is logged on entry with its number and six argument
registers (even if it takes less than six), and - on e xit - with its return value.

    Because the data is raw, it will require post processing . The numbers can be
resolved to their names via the <unistd. h file, though arguments are n't always useful. In
the case of file descriptors, / proc/pidfd can be used, with the proviso that the descriptor
could be closed or reused by the time it is resolved (and, thus, be resolved incorrectly).
User buffers (such as arguments to read(2)/write(2) are too volatile to be
meaningful.

2.1. System/Process level: kdebug

    Darwin doesn't provide any kernel-level modification interfaces save for DTrace,
which is in macOS only and crippled by SIP. Nonetheless, Apple's OSes have no
shortage of profiling capabilities, thanks to the powerful kdebug facility.

     Though entirely undocumented, kdebug is widely used across all flavors of Darwin.
Kdebug is a highly optimized facility allowing real-time event tracing, mostly from
kernel to user mode, but also open to user mode clients. It is similar in some respects
to Linux's event tracing, since trace messages are emitted by specific callouts to the
facility. Each call includes a numeric 32-bit kdebug code, and up to five arguments,
whose semantics are dependent on the debug code .

     The aim of kdebug is to find a balance between extensive profiling on the one hand,
and minimizing performance impact on the other. To achieve this, facility calls in kernel
are made through the KERNEL_DEBUG_CONSTANT* macros, which are attributed as
_imp robab le, to optimize for branch prediction when the facility is not in use or is
filtered . The actual ke rne l_debug_wri te is simply a few memory set operations.

   Over the years, kdebug has been extended to relay events from the coprocessors
(128-137), and, most recently, exclaves.

      3;.J Audiiti.!l9J
            Auditing tracks operations on the system which may have a potential impact on
        security. This includes a variety of (mostly I/O related) system calls performed by the
        kernel, and other operations user-mode daemons opt to record . Depending on the
        audit policy, which is configurable by the administrator, auditing may be tweaked to
        record only the success or failure of certain operations, or users .

             The primary use of auditing is to evaluate and monitor the system's security policy,
        wi th an emphasis on failed operations - since these are prohibited by the security policy,
        and are therefore not expected from compliant processes.

            As an integral function to platform security, auditing is built into both Linux and
        Darwin. Darwin, however, has deprecated its longtime implementation of Solaris BSM
        auditing (10.5-10.18, also discussed in M-III/3) in favor of the proprietary (and kext-
        implemented) EndpointSecu ri ty. f ramewo rk.

        3.1. Linux: auditd
            Linux auditing is implmented over AF _NETLINK sockets. This proprietary address
        family supports is designed for kernel to user multicasting . It ena bles user mode clients
        to specify one of many "netlink families" (see netlink(7)) as the "protocol" . Auditing
        uses NETLINK_AUDIT (#9), along with a SOCK_RAW.

             The kernel-end of the socket is established early on during startup, in
        audit_init() (kernel/audit.c). The routine also creates the kauditd kernel thread, which
        is responsible for generating the audit messages. The thread spends its life poring over
        three (main, retry, and hold) qu eues, ca lling kauditd_send_Queue( ... ) to send
        messages to its registered clients .

            The main (and usually, only) netlink client is the user-mode auditd. The daemon
        parses its configuration file, auditd .conf, which resides in /etc/audit, along with its rules
        and plugins. By default, the daemon parses messages from the netlink socket, and
        writes them in human readable format to /var/log/aud it/audit.log, and/or the s ys log (8),

    So far this chapter has explored powerful capabilities for system-wide tracing and
monitoring. But there are cases where even these might fall short, as very specific and
particular functionality may be required, which would necessitate actual hooks.
Normally, this would be the domain of kernel extensions, since it takes code running in
kernel to be able to work across all processes. Both Darwin and Linux, however, have
in-kernel facilities, which interface with user mode clients, to achieve just that.

4.1. Darwin: DTrace

    DTrace is but one of several features FreeBSD "borrowed" (almost verbatim) from
Sun's Solaris, but it is indubitably the most powerful. DTrace is faci lity for not only
profiling and monitoring system events, but also running code in response to them.

     The 'D' in DTrace refers both to "dynamic" and to the D Programming Language. D
hybridizes C and AWK syntax, omitting C's flow control in favor of AWK's pattern -action
syntax . D scripts attach probes to providers . Providers a priori register with the
facility, providing the points where the probes may attach. When the probe point "hits",
the provider calls the probe code, which executes with the visibility of the provider
allows. Registered providers can be seen with dt race -l.

    User mode programs can register providers through a special
_TEXT. _dt race_dofs section. This section, with "DTrace Object Formats" is picked up
by automatically by dyld, which uses jdevjdtracehelper for provider registration. Some
examples of that are launchd(l), libxpc, libojc, libcache and dispatch.

    Other providers are in the kernel itself. These include sysca II and mach_trap, but
also the even more powerful Function Boundary Tracer (fbt) , which provides almost
6,000 kernel function entry and return probes, and some 86,OOO(!) ones in kernel
extensions.

    DTrace is as potentially disruptive as it is powerful, and - depending on probes -
may impair or compromise the system performance . For most profiling, kdebug is a
much more efficient alternative - but it is not-extensible, nor intrusive. Additionally,
DTrace is (understandably) not available in *OS variants, and all but neutered by
macOS's SIP, which effectively kills the in-kernel providers, leaving only the user-mode
ones .

    It's worth experimenting with DTrace and trying out its powerful dynamic tracing
and reversing capabilities on a macOS VM with SIP disabled. This will also re-enable the
dt russ (1) command, which is the rough equivalent of Linux's st race (1).

     A much more detailed discussion of DTrace can be found in M-l/15 (the user mode
perspective) , M-2/6 (the Kernel mode perspective), and in Gregg & Mauro's definitive
DTrace tome .l ddt ] That book's website [ddw] contains many examples - from one-liners
to complete scripts - demonstrating the immense power of this facility. Further, DTrace
"lives on" in Linux implementations of BPF and SystemTap, described later in this
chapter.

      4.2. Li n ux/ Android: eBPF

           One of Linux 4.0's most exciting features is the enhanced Berkeley Packet Filter
      facility, or eBPF. This facility combines two already powerful features - Linux kprobes
      and the BPF interpreter - to provide a truly powerful substrate for user-mode installed
      system extensions and kernel hacks. eBPF is actively developed with more features
      added in newer kernels [bpfl), and its popularity has even earned it an official Microsoft
      port for Windows .[ebw)

           Linux introduced kprobes as far back as 2004 (2.6.9) . Kprobes enable the insertion
      of "kernel probes", which are breakpoint handlers that can be set on nearly every
      instruction in the kernel. This powerful mechanism supplies the foundation for ft race
      (discussed earlier). Its one drawback, however, is that breakpoint handling must also be
      performed in the kernel - necessitating a kernel module for utilizing this functionality.

          eBPF changes that, by placing a generic kprobe handler, but - instead of a kernel
      module - allowing the logic to be specified in enhanced BPF bytecode . BPF bytecode was
      originally developed for a very particular function - packet filtering - yet its parser and
      interpreter have been used (and abused) in kernel mode for decades. Linux started
      extending BPF in 2010, first with SECCOMP-BPF, and then eBPF. In 2015 eBPF was
      married to kprobes - and unleashed a dizzying array of capabilities.

           BPF programs are loaded through the bpf(2) system ca ll. This is an ioctl(2)-style
      syscall, whose BPF _PROG_LOAD cmd takes the program insns to load from the bpCattr
      (a union). The program is subjected to bytecode verification, to ensure it does not pose
      a risk to system security or robustness. BPF code flow control is very limited, and it
      cannot write arbitrary kernel memory (although reading is still possible).

          Once verified, the BPF code can be Just In Time compiled to native code, using an
      in-kernel JIT compiler. This allows the code to run at native speeds . Communication
      back with user mode is done through Maps of several types, which can be accessed by
      both user mode and the BPF program . Programs and maps are both represented by file
      descriptors, usually anon_inodes, though some get representation in /sys/fs/bpf.
