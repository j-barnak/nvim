Runtimes & Higher-Level Languages

    As computing has evolved, so have programming languages. In the beginning,
there was low level assembly, to abstract the byte-level opcodes. C followed,
abstracting assembly even further by introducing variables and types, while maintaining
direct access to memory through pointers. C++ improved on C by adding object
orientation.

     Languages developed in the '90s further evolved, enhacing object orientation with
dynamic object construction and metadata querying (reflection) and all but abandoning
direct memory access in favor of managed memory. This necessitated the introduction
of a runtime environment, which handles the low-level allocation and freeing of object
memory, alleviating the programmer of such concerns, and the potential security
vulnerabilities they harbor. Even the very notion of compiling a program to mach ine
instructions started losing appea l, as interpreters - such as those of Python and
Javascript - became wildly popular.

     Today, few people outside kernel and hardware developers ever resort to low-level
assembly. C and C++, once the most popular programming languages, are steadily
falling from grace, and other languages from that era (Pascal, anyone?) are nearly
extinct. Rust has emerged as a popular as an alterative to CjC++ (due to its strong
typing and resilience to memory bugs), and has made its foray into kernel
programming.

    Elsewhere, runtime-based languages are all the rage. Apple, which once
championed Objective-C, has publicly deprecated it in favor of Swift, but both are
prevalent in Darwin. Android uses Kotlin and Java, both of which initia lly compile to the
intermediate form of Dalvik Executable (DEX), and run within the bounds of the Android
RunTime (ART) environment.

    This chapter exam ines three runtimes of interest: Darwin's Objective-C, and its
successor, Swift, and AndrOid Runtime. Although each runtime has its own classes and
frameworks, the similarities between them will become evident. The main perspective
here is that of reversing, and in particular, reflecting - that is, reconstructing the
higher leve l objects from their lower level in-memory representation.

             Objective-C served as the language of (little) choice for advanced Darwin
         development, from its NextSTEP origins. Indeed, the concept of "framework" and "kit"
         predate macOS X by more than a decade. When Apple acquired NeXT, it brought in
         most of its user-mode frameworks, all coded in Objective-C. Apple continued to use and
         extend Objective-C, introducing version 2.0 in 10.5 (around 2005). Though considered
         esoteric, the language gained popularity almost overnight, as throngs of developers
         rushed to code apps for iPhone. This lasted for over a decade, until the advent of Swift,
         which builds over (and effectively hides most of) the Objective-C underneath it.

             It is assumed that the reader is already familiar with the Objective-C nomenclature,
         as the language is well documented bY--AR.~ .laocl, and this work does not aim to teach
         the language. At a high level, the reader should remember that:

            o   An Objective-C class is the same idea as in all Object-Oriented languages: An
                object type. Variables of the class type are instances.
            o   Classes have methods - routines which operate on either an instance of the
                class, or on the class itself.
            o   Objective-C treats its methods as messages, which are identified by selectors -
                These allow specifying arguments by name, rather than by position, as would be
                in C/C++. This yields the familiar syntax of:
                                          ClassOrlnstance selectorWithNoArgs                1;

                                                           or

                              [ ClassOrlnstance selector ArgA:valueA               ArgB:valueB 1;

            o   A Protocol defines one or more method prototypes that conforming classes
                should implement. A given class can conform to no, one, or several protocols, but
                must implement the methods of whichever protocols it conforms to.
            o   Classes can be extended at runtime using Categories.

             Of the runtime environments discussed in this chapter, Objective-C is the lightest.
         As will be shown, the well known syntax of Objective-C gets rewritten by the compiler
         to pure C, and then linked to the message passing implementations in libobjc.dylib.

1.3. Calling Convention

    Objective-C, like SmaliTalk, is built around message passing. Unlike CjC++, in
which a method invocation is carried out by a vtable lookup (read: a function pointer
array lookup) in the target object, Objective-C method invocations - the selectors - are
resolved by the Objective-C runtime. The arguments to the method may be specified in
any order, with the runtime also managing the calling convention.

    The well-known syntax of Objective-C message passing is the [objectDrCIass
selector] notation. This, however, is just syntactic sugar. In other words, the compiler
rewrites this code as a call to obj c_msgSend , with the objectOrClass specified is the first
argument, and the selector as the second argument. Any additional arguments are then
put into position according to the selector protocol.

           1.4. Reversing Objective-C

                Objective-C is omnipresent in Apple's frameworks, and even with the move to Swift
           (d iscussed later), Objective-C still provides a lot of the APIs under the hood. Add to
           this, that Apple's most powerful APIs - the PrivateFrameworks - are intentionally
           undocumented - making Objective-C reversing highly lucrative.

           1.4.1. The Class Menagerie

               One of the main challenges faced by reversers is the lack of header files. Functions
           are easy to enu merate in a binary, but the semantics of their arguments can often
           remain hard to decipher. This is not an issue with Objective-C binaries, since messages
           have clearly defined selectors and protocols, which can be extracted - both dynamically
           and statically. Further, the class metadata enables both dynamic (runtime) and static
           reconstruction of all classes used, whether from public frameworks or private ones.

          surfa ce in th e past, courtesy of Obj ective-C.

           1.4.3. Swizzling

              The runtime APIs shown in 1.4.1.1 don 't only offer getters, but also have setters,
          which can be used to dynamically alter objects and class definitions at runtime . In
          particular, method_getImplementation ( ".) can be used to get a selector IMP (i.e .
          function pointer), and method_setImplementation(".) can set it to some other
          implementation. This practice of swapping method implementation is commonly
          referred to as Swizzling.

               Using these two functions is commonly enough to swizz le, but there are also cases
           wherein it might fail, due to some selectors having already been resolved to their IMPs,
           and cached. The preferred approach is to therefore use a third runtime API ,
           met hod_ex changeImplementations ( ml, m2 ) which performs the switch and flushes the
           method caches.

              Method swizzling can be used to override the original functionality, or (by keeping
          the original implementation pointer) extend it.

           The process can therefore be summarized as follows:

 1.         Find the class definition of the desired object, by locating its containing ART
            header, and then enumerating that ART's class list to find the classdef.
 2.         Scan the heap ([anon: dalvik- main space]) region(s) for 32-bit references to
            that classdef.
 3.         The references you've found are shadow_ fields, where object instances of the
            desired class begin. Iterate over instances:
 4.         Read the classdef i fie lds_, iterating over them to enumerate the field
            definitions.
 5.         For each field definition, find the field's shadow, dexFieldld and offset.
 6.         Get each field's data.
 7.         Repeat at step # 4 for superclass, until reaching java.lang.Object.
