Hooking & Injecting

      In the Von Neumann Architecture, code is in memory, and memory can be code.
This opens up entire new dimensions of functionality, as code can rewrite itself on the
fly (JIT), or can be modified externally.

    Injecting into, or hooking other processes yields immense benefits for traCing,
debugging and reverse engineering. Nonetheless, these are dwarfed by the potential
hazards when these very same techniques are used for malicious ends. The techniques
described here have a profound effect on application and system security. Any code that
has been modified, whether by itself or externally, can no longer be trusted, as must
deemed compromised.

    This chapter demonstrates hooking and injection techniques, from several
perspectives:

  o    Load time hooking and intergosingl When the process environment can be
       controlled before starting it.
  o    Debug.ger interfaces: Which the platforms must provide, else legitimate
       debugging would be impossible.
  o    Runtime hooking;, Which (ab)uses the very same debugger interfaces to alter
       the code flow of a victim process at runtime.

         The chapter then concludes with two working examples of code injection - for
      Android/Linux and Darwin.

          For the methods in this chapter to work, Linux requires only basic privileges
      (same UID or root) . Darwin, however, piles up bulwarks and barricades, from code
      signing, through entitlements, and the ever vigilant AMFI, ready to ki 11 -9 any
      m inor transgression, no questions asked. That said, if this sentinel can be
      outsmarted or avoided, all bets are off.

1.2. Overriding dependencies (hooking)
    ELF symbol resolution operates by "first come first served". The first shared
object to export the symbol in question is the one whose symbol will be bound.
Using LD_PRELOAD, it's easy to ensure in this way that the injected library (which
precedes all the others in the load order) will be the one to provide a symbol
dependency, effectively hooking all calls to the symbol from the main.

   There is, however, a problem. While it's simple to override any function in this
way, one often still needs to call the original function . Consider, for example, the
simple case of open(2). Intercepting the operation is straightforward, but how
does one actually perform the file open?

    Rather than attempt to reimplement the original function, a hook will often
perform whatever pre-processing logic it needs (if any), then call the original, and
optionally perform additional post-processing.

      This means the hooking function needs to be able to find the original target, as
if it (the hook itself) weren't already installed. This involves calling back into the
lin ker, and asking it to dynamically locate and load the original symbol - with the
easiest method of doing so being dlsym(3). The following listing shows a simple

           2.1.2. Darwin

               Debugging APIs in Darwin are all supplied by Mach, and carried over Mach
           messages using MIG routines . Th e routines all require the targeCtask, which is
           essentially (in Windows parlance) a handle to the target process. In Mach
           terminology, this is referred to as a SEND rig ht to the target task's Mach port. This
           enables the sending of control messages to the kernel, which holds the RECEIVE
           right for that port, and will service the requests on the target task object. Every
           task uses its own control port, which it can obtain through a call to
           mach_task_self().

           right to the task port is effectively equivalent to the task itself.

2.S.3. debugserver hardening

   Apple has long wrestled with finding balance between allowing debugging on
*05 devices (for developers), but restricting the interfaces so that even developers
would be restricted to their own applications.

    *OS's debugserver does not possess the entitlements required to get SEND
rights to task ports, which are a prerequisite for controlling their memory and
threads. Instead, the would-be-debuggee processes have to voluntarily give up
their tas k port, using the get-task-a llow entitlement. Th is dangerous entitlement

debugserver is similarly handicapped, making it unable to attach to platform
binaries unless SIP is disabled.

system . On the one hand, it packages debug server as part of the root filesystem
(in /usr/libexec) rather than the DOL On the other, the code -signature embedded
launch constraints prevent debugserver from being started outside of developer
mode, or exce pt by laun chd .

      3.1.2.1. Tools: dtruss(l) and kdebug

          Darwin's equivalent of strace(1) is dtruss(l) . Since it is a DTrace tool,

      3.1.2.2. Programmatic Tracing

          Unlike Linu x, Darwin's ptrace(2) system cal l, though present, is intentionally
      neutered, and lacks the ability to intercept system calls, as well as the register and
      memory inspection capabilities. This is likely by design, as the latter capabilities
      can easily be met (and, in some cases, surpassed) by use of Mach APIs .

          On systems with no DTrace support, kdebug based tracers would still work, and
      the programmatic operation is simila r t o the tool-based one. Getting arguments,
      however, requires one of three (all invasive) approaches :

        o   Hook the libsystem kernel. dylib sy'stem call wrap-p-ers: which would
            offer the simplest and most efficient way to intercept the system call
            invocation while still in user mode. The caveat, however, is that a given
            binary may deliberately invoke SVC (or statica lly link the system call
            wrappers) to defeat this approach .
        o   Breakp-oint and single-step- the p-rocess: which would guarantee a fool-
            proof way of hooking all system calls . This, however, will greatly impede
            performance - as each assembly instruction would now involve an IPC to the

        o   Disassemble the targ~p-rocess and selectively_p-Iace hooks: As a

      3.2. Hooking external functions (via import tables)
          Recall, that external, exported symbols are dynamically resolved by the linker
      through import tables. The import table format will vary by binary format, but
      nonetheless the flow is the same, as the table is referenced through stubs.

      3.3. Hooking both internal and external functions (via
      breakpoints)

      thus, not exported) do not have an import table entry or associated trampoline.

      breakpoint, or - since a tracer must be attached anyway - some invalid address.
