
MultiThreading

    Modern CPUs have multiple cores, and each core maintains a separate register
state, allowing parallelized execution. The greatest benefits can be utilized by threads of
the same process, and so multithreaded programming has become the prevalent
paradigm.

    The view of processes, presented in Chapter 4, was deliberately simplified. In
actuality, it is not the "process" which executes, but rather its threads. The process is
just the container. It it the threads which "own" the CPU . For a single-threaded process,
the terms are often used interchangeably. The correct terminology, however, would be
that when a " process " is executing, it is one or more of its threads which are doing so.

    This chapter begins with a high level overview of threading. It then looks at the
standard POSIX thread API (pthreads): First, at the standard calls and extensions, and
then at the low level implementations on Android, Linux and Darwin. A discussion of
concurrency challenges and primitives follows, before ending with aspects of scheduling,
timing and delaying execution .

              The main paradigm of programming over the years has been mUlti-process
          programming. This enab led the simple approach of having distinct processes - either
          one at a time (on uniprocessor system) , or co ncurrently (on mu lti -processor (AMP/SMP)
          systems) . By definition, each process would have its own address space and
          descriptors, and be isolated from the others. Processes would thus communicate, only if
          necessary, over IPC, using one or more of the techniques exp lored in the next chapter.

               Not without its merits, this approa ch was also not devoid of disadvantages . The cost
          of context switching was (and remains) quite expensive, as switching between
          processes - a major context swit ch - involves invalidating processor bu ffers, flushi ng
          caches, and possib le paging operation s. Another cha llenge was blocking system ca ll s,
          w hich - even though largely resolved through I/O multiplexi ng - can needlessly
          comp licate programs . Lastly, asynchronous, event driven programming is diffi cult to
          implement.

               Enter: Threads. At the basic level , a "thread" is nothing more than a register state,
          defining a different code f low in the same address space. When one thread blocks, t he
          scheduler can check if other threads of the same process are runnab le. Th is can
          dramatically affect performance, by both ma ximizing time slice utilization, and
          minimizing the cost of context switching : A co ntext switch between two re lated threads
          is a minor context s witc h , involving only a simple save and restore of the register
          state - without the overhead associated with a change of address space. Minor context
          switches can further benefit from data left in the processor's caches.

1.1. Risks

    Threads provide far more efficiency in programming, and with the advent of
multicore processing, it's no surprise that multithreaded programming is the norm. This
is not, however, without risks.

      Contrary to the mUlti-process model, threads all live in the same process, and thus
have to get by sharing the same address space . 54-bit addressing means that the
address space size is hardly a factor (even 2 39 should be enough for everybody). The
problem, however, is that of robustness. An unhandled exception in anyone of the
program's threads will lead to a forced termination (by signal) to the entire process,
killing any and everyone of its threads.

     2.2.1. CPU-level support: TPIDR_ELx and TPIDRRO_EL0

         The processor holds a thread-specific value in a designated register - TPIDR_ELx.
     The _ELx suffix implies there are different registers for each exception level, so user-
     mode code employs TPIDR_EL0 and kernel-mode code uses TPIDR_ELl. GeC's
     _ bui l tin_th read_pointer() emits an MRS of TPIDR_EL0. There is also a read -o nly
     counterpart in user- m ode, TPIDRRO_ELx, (but settable from kernel - mode) whi ch is used
     in Darwin .

         The operating system kernel can put whatever value into TPIDR_ELx, but a common
     con ven tion is to place a pOinter there. The value of the pOinter will naturally be different
     for every thread, and thus allows for Thread Specific Data (TSD): an area of memory
     private for each thread.

          Although all threads can access TSD using the same interfaces, t he values returned
     will depend on TPIDR*, and will thus be different for different callers. This achi eves
     "privacy" for each thread, while at the same time allows "global" visibility (i.e.,
     accessibility from anywhere inside that thread's scope). Note, however, that the
     different TSD areas - being in the same address space - are still all technically
     accessible from anywhere in the process .

3.2. Memory Ordering

    Atomic operations will not be interrupted - mitigating plenty of race condition
concerns. This still does not imply, however, that the compiler - or sometimes even the
processor itself, through speculative executi on or caching - may not reorder other
memory operations.

    Thi s is where C11's memory ordering comes into play. Memory ordering allows
specifying a particular sequence of store and load instructions, which is guaranteed not
to be reordered in any way - not just for the atomic operations themselves, but all
memory operations. In a nutshell, they ensure a temporal relationship, such that :

  •    Any memory operations stated before a released store do not get reordered, and
       actually happen before it.
  •    Any memory operations stated after an acquired load also do not get reordered,
       and actually happen after it.

    Release and Acquire are the two basic memory orderings defined, but there are
several others, which build upon them:

      3.3. Synchronization Primitives

           With processor support allowing for atomicity, higher level co nstructs may be
      provided. Here we exam ine those of POSIX, as well as th e OS -s pecific objects, which
      ofte n underlie the POSIX objects , but may be used directly (at t he cost of porta bility) .

           In the discussion of the following, it is common etiquette (and safe programming)
      to follow common sense , i.e.
            •     Respect the owner: do not attempt to free/unlock/release a primitive which was
                  not previously acqu ired by the same caller. Attempting to do so often leads to
                  undefined behavior, and in som e cases (e.g. Darwin' s os_unfair _l ock(3! ) s,
                  di scussed later), will be lethal.
            •     Beware recursion: Only in specifi c cases can a primitive be acquired multiple
                  times by the same caller. Outside these cases, known as recursive locking , this
                  often leads to the most embarrassing form of deadlock - the lock ow ner blocks
                  ind efinitely, waiting for itself to release it.

      3.4. Transactional Memory Extensions (ARMv9 FEAT_TME)

          ARMv9 supports Hardware Transactional Memory (HTM), which greatly simplifies
      concurrent memory access by shifting the onus of synchronization to the processor. The
      transaction is such that it is guaranteed to either fully succeed, or be rolled back - to
      come undone, as if it were never attempted . At the hardware level, the processor needs
      to recognize transaction boundaries through special instructions, save interim memory
      modifications, and be able to restore state and co ntext on failure.

           ARM refers to this feature as FEAT_ TME - Transactional Memory Extensions . The
      feature is optional in ARMv9 and later, and its implementation may be tested through
      bits 24-27 of ID_AA64ISAR0_ELl. It can be enab led by the TME bit (#53) of SCTLR_ELl
      (fo r Ell) and TME0 (#52, for ELO). A detailed overview of usag..e[tmedoc j can be found in
      the official documentation.

      4.4. Delayed/Deferred Execution
          Processes or threads sometimes need t o pause their execution for a short period of
      time, or until a certain date/time . The UN * X c r on (8) or at (1) facilities, for example,
      can schedule processes for periodic execution at certain dates/times, or to request one-
      time execution at some time in the future .

      4.4.1. Micro and Nano Delays

           The C-runtime sleep (3) has long been used by processes to delay for a set number
      of seconds. With today's faster processes, a few seconds amount to more than a
      lifetime .

           There are circumstances in which a dela y of some short period - often in th e
      nanosecond to microsecond range - may be required . ANSI C provides the standard
      us leep (3) (for microseconds) and nanos leep (3 ) (for nanoseconds) . Linu x further adds
      c lock_nanos leep (2) as an alternative to the latter, which allows selecting the
      reference clock, and/or setting an absolute, rather than relative duration.

          Both these routines, however, preempt the calling thread, and therefore the delay
      amount specified is the minimum, but the actual delay might be orders of magnitude
      higher, due to the overhead of a potential context switch .

          The common alternative to avoiding a context switch is to perform a tight loop for a
      specified number of instructions - i.e. , busy wait - which should approximate the delay
      as cl osely as possible . There are, however, several problems with this approach:

         • The accuracy...;. of timing instru ctions in the tight loop can prove elusive, as the
           processor speed will directly affect the time spent in the loop. Even if the
           processor speed can be reliably determined, this is further exacerbated by
           dynamic processor frequencies.
        •    ~p-ower imp-act: of a tight loop is considerable, since the processor is
             constantly executing wasteful instructions . When performed rarely, this can be
             overlooked, but when the delays are frequent the power drain can be
             considerable.

           ARM provides a precise counter and timer facility through two special MSRs. The
      first, CNTVCTSS_EL0 is available with ARMvS .6's FEAT_ECV, and provides a self-
      syn chronizing, read-only, monotonically increasing counter valu e. The second,
      CNTFRQ_ EL0 holds the counter frequ ency, (normally, IGhz, as set by a higher EL). This
      solves the accuracy problem.

          To mitigate the power impact, ARMvS.7's FEAT_WFxT provides the WFIT and WFET
      instructions. These either wait for interrupt (WFIT) or an Event (WFET), with the timeout
      specified by a minimum value of CNTVCTSS_ EL0, while putting the processor in a low-
      power mode. Using WFET thus achieves an accurate delay, while minimizing the power
      drain.

4.4.2. Timers

    Other circumstances may necessitate the use of timer based execution, which might
require delays as well, but aligned with the "wall clock" (of gettimeofday(3)) or the
system's clocks.

     Linux supports timer file descriptors as a way to use timers through blocking file
I/O. A call to timerfd_create(2) returns such a descriptor, based on a clock_id
(CLOCK_MONOTONIC or CLOCK_ [BOOTTIME IREALTIME l_ALARM and flags
(TFD_ [NONBLOCK I CLOEXEC 1). A call to time rfd_settime (3) can then (dis)arm the timer
value . A subsequent read (2) will then block, until the timer fires, at which paint a 64-
bit value is returned, noting the number of expirations .

4.4.3. Timer Slack

    Programs using timers and delays might cause spurious wakeups - situations
wherein the core is unn ecessarily brought out of a low power state. This has a
detrimental effect on battery life, especially in cases where adjacent timers/delays keep
expiring.

    Developers know that any delay or timer are only guaranteed at minimum, but may
actually "drift" or delay by longer, due to interrupts or other scheduling constraints.
Apple was the first to introduce timer coalescing - allow the as to deliberately delay
certain timers, so as to bring them to expire in or around others, thereby grouping the
timers, and allowing longer in-between idle periods.

    Linux (and thus, Android) was quick to also allow timer coalescing, and offers the
PR_[GET/SETLTIMERSLACK prctl(2) to query/modify the allowed timer slack value of
the calling process (also settable through the / proc/pid/timerslack_ns entry).
