Beyond User Mode

    So   far, this book has discussed the enormous landscape of user-mode
programming , as that is where all applications and most developers "live". There are,
however, higher planes of existence - in fact, as far as ARM is concerned - there are
three of them. It is there that the kernel, hypervisor, and the secure monitor may
reside .

    This chapter begins by exploring the foundation for this planar separation - ARM's
model of Exception Levels. From there, the discussion focuses on each exception
level, in turn:

    Beg inning with Ell - where mosts kernels operate - we discuss the chief
responsibilities of the kernel: System call serviCing, and memory management - both its
own virtua l memory, and the machine's physical RAM. Special focus is given to XNU's
groundbreaking security enhancements, and their reliance on Apple Sil icon specifics.

     We then move on to EL2 - traditionally, the domain of hypervisors providing
virtuali zation services, but in some cases uses for kernel monitoring and memory
protections. Lastly, comes EL3 - where the Secure Monitor of ARM's TrustZone resides,
and prov ides a variety of security services, such as encryption, authentication and
attestation.

           The earlier discussion (in 2/2.3.2 ) of Exceptio ns presented, in very broad strokes,
      the idea that ARMv8 and later processors operate in any of four Exception Levels.
      These levels, dubbed EL0 through EL3 , correspond to privilege levels, in that EL0 -
      ass igned to user mode - is the least privileged, Ell - kernel mode - has more
      privil eges, and EL2/EL3 (optionally assigned to the hypervisor, or secure monitor), are
      more privileged still.

          A high level view of excepti on levels is as an application of hierarchical protection
      domains. This is a Venn diagram like way of presenting available privil eges as "rings"
      (mu ch like the Intel model). Unli ke a classi c Venn diagram, however, the inner rings are
      more priv ileged than the outer ones, as shown in Figure 13/1-1 :

        1.3. The Ex ceptio n Vector

        predefined Exception Vector. This vector provides 16 entries, which cover the four
        possible exception types times the possible execution modes they might occur in. Each
        vector entry is 128 bytes, which allows for up to 32 instructions. Padding to entry
        boundary is commonly performed using NOPs or NUL bytes (DCD 0x0).

        level's Vecto r Base Add r ess Reg ister - VBAR_ELx - with the address of the vector

1.4.3 . Taking and Servicing an Exce ption

     A key design idea is that code remains oblivious to exceptions of all types. When an
exce ption occurs, the processor immediately saves the PSTATE into the SPSR_E Lx, and
reco rd s the PC into the ELR_x, before setting it to the VBAR_E Lx entry co rre sponding to
t he exception type . All other registers remain as they were.

      VBAR_ELx code, implemented by the kernel, hypervisor or secure monitor, may
either handle it in the 32 instructions of the entry, or may call some other handler
ro ut in e. The common practice is to use up to 32 instructions to save the register st ate,
ca ll elsewhere to actually perform handling, and then restore the register state and
issue an ERET. Output 1-8 showed the XNU example, which simply performs all handling
elsewhere, using only one instruction to unconditionally branch, and NOPing out the
rest .

     Th e ERET is effectively a jump to the saved ELR_x, possibly lowering the EL and
all ow ing the code which executed before the exception to return. Should the exception
handli ng code decide otherwise, both ELR_x and the restored register state can be
altered. This is how operating systems implement context switching.

2.1. System Call Internals (Part II)
    As previously discussed (Part I, 4/1.1), the kernel provides an interface to user
mode programs through its system calls. These naturally vary between operating
systems, but the principle is always the same . Since there is only one defined gate
instruction - SVC, its kernel mode handler must act as a multiplexer, able to branch to
the specific system call requested . Further - since the arguments to the calls are
populated in the X0 to X7 registers, the system call itself needs to be specified in a
register.

    The previous discussion (ibid.) also showed the slightly different conventions for the
system call ABI - Darw in's X16 versus Linux 's X8 use for the system call number. Once
the number is figured out, both kernels use a system call table - an array of function
pOinters - to find which call is to be serviced, and transfer control to it.

         2.1.4. "Reverse System Calls" and Kernel -+ User interaction

             Most interaction between user mod e and kernel mode is at the behest of the user
         mode client . There are cases, however, wherein kernel mode code requires cooperation
         with user mode code, and it is the initator of the request. This can involve cases when
         user prompting is required, significant I/O, or comp licated algorithms like PKI.

             The pattern requires a user mode lackey to block in a reading I/O system call (or, in
         Darwin, wait on mach_msg [2Ltrap) . The kernel code wishing to initiate the request
         readi es it as an I/O buffer or iovec, unblocks the user mode helper. It, in turn,
         processes the request, acts accordingly, and in a subsequent writing I/O system call,
         delivers the results . It then resumes blocking until the next request, and so on.

             Module code requiring this type of interaction will commonly create some device
         node, that its daemon will block on. Linux offers an alternative through netlink(7)
         sockets, which obviate the need for a device, in favor of one or another NETLINK_           *
         family. Darwin uses the "Host Special Ports" (M-1/12-4), whose RECEIVE rights are
         owned by user mode daemons, but can be obtained from kernel mode without the
         usual launchd (8) service name lookup .

   2.2.1.2. Slab Hardening

       The kernel slabs hold many objects which are both directly and indirectly affected
   through user mode system cal ls. A malicious user could attempt to perform "S lab Feng

   could target memory corruption. Slabs therefore are a battlefront in Linux kernel
   exploitation, and many exploits, as well as some research RQR..eIS[elo] detail or rely on
   predictability in the slabs and their freelists.

   2.2.1.2.1. Freelist shuffling

        In the interest of efficiency, objects are allocated and returned from the first entry

       The CONFIG_SLABJREELIST_RANDOM setting adds more randomness, while stil

      •   init_cache_random_seq: is called from do_kmem_cache_create( ... ) to pre-
          initialize the random sequence cache
      •   init_freelist_randomization(): Is called from kmem_cache_init()
      •   shuffle_freelist(): is called from allocate_slab( ... ). This calls
          next_freelist_entry() internally.

      2.2.2. XNU: The Zone Allocator

          What Linux calls "slabs" - preallocated regions in which objects of a fixed size can
      be allocated - XNU calls "zones". XNU's zone allocator has been discussed in great detail

2.2.2.4. Zone Hardening

    Kernel memory corruption attacks are a key component of advanced exploitation.
Even if kernel text is read only (as it is, thanks to Darwin's KTRR) , an adversary with
arbitrary kernel memory write capabilities to kernel data can still fully compromise the
system.

2.2.2.4.1. Zone Sequestering

    A common kernel memory exploitation method - often used with Use-After-Free
vulnerabilities - is to leave a live user-mode controllable reference to some kernel
object, which is freed. The user-mode reference translates to the (former) kernel
address of the object, which has since been repurposed to some other, new object. If
the type of the new object can be reliably determined, some or all of the memory can
be contro ll ed, corrupting the new object in predictable ways.

       Apple details Zone Sequestering as a significant mitigation in an official security.
.I;liQ9_Rost .l asbl The idea here is to prevent the virtual address reuse of one zone's range
for another, which may ensue after a garbage collection. Physical memory is still freed,
but the virtual address range remai ns allocated (under the zone's structure z_pageq_va
list. This way, the virtual memory cannot be claimed by some other zone, associating
the address forever to its original type.

    To deal with the problem of the generic data zones of ka 110c*, which are classified
only by element size, and not particular data types, XNU now splits what used to be
ka 11oc. size zones into data. ka 110c. size and sha red. ka 11oc. size, and (in *OS
variants) into kalloc_type* and even kalloc_type_*_var*. The types are assigned on
boot, and thus vary in sufficiently unpredictable ways to prevent deliberate repurposing
of memory. This approach is comparable to Linux's CONFIG_RANDOM_KMALLOCCACHES.

2.2.2.4.2. Read only zones

      A common method used by attackers is corrupting kernel objects. That is, locating
the kernel address of some lucrative object, (e.g. a process descriptor), and modifying
its fields so as to change the object attributes (e.g. the process credenti als or
privileges). This can go as far as the construction of entirely fake objects - crafted by
the attacker and then passed by some one way or another as legitimate objects.

   Darwin's read-only zones mark a significant development in protecting kernel
memory. A read-only zone is designed to hold objects which, once created, either
undergo very little changes, or none at all. Note, these are not zones whose pages
merely lack the write protection - since an adversary with sufficient capab ilities cou ld
possibly mach_vm_protect() or otherw ise modify the page tables directly.

    As an example of read only zones, consider process attributes. Some attributes
(e.g. runtime statistics) are mutable, and change over the lifespan of the process,
whereas others - particularly security sensitive ones (credentials, proc and task
structure linking, code signing flags, and more) are constant, once created, or only
changeable under rare and very well -determined circumsta nces (e.g. setuid (2)).

    With read only zones, the process (and underlying task) structures are redesigned
into two separate objects (each), so that the mutable data goes into the proc_task,
and the non-mutable data is placed in the proc_ro zone. This makes these attributes
(reasonably more) trustworthy even in cases of potential kernel compromise.

    Read only zones need hardware support. This is where Apple's Pag e Protection
Layer (PPL) and (later, in A14) the Secure Page Table Manager (SPTM) come into play,
as discussed later.

2.3. Physical Memory Management

    The CPU operates with virtual memory addresses, which the MMU translates to
physical ones. The MMU, however, needs to work with multi-level translation tables, and
those are managed by the kernel. This requires maintaining the virtual page tables for
each address space in the system - those of the individual processes, as well as that of
the kernel itself - in the format dictated by the MMU, through the processor Page Table
control registers. ARM describes physical memory management in a Learn the
Architecture [lta] document.

2.3.1. Translation Lookaside Buffer

    Before getting into the discussion about the structure of page tables, it's worth
looking at the Translation Lookaside Buffer - the TLB. Page table lookups are relatively
expensive, and seldom change for a given process (at least so long as the virtual
address is in use). The TLB caches the results of successful page table lookups, and can
be thought of as a lookup table with entries converting virtual addresses to physical
ones, with their attributes.

    The TLB interface is through a single special instruction, TLBI. The instruction is
used to invalidate cached virtual address, which is required when an address space is
context switched or destroyed (on process death or exit). Flushing the TLB (i.e.
invalidating all of its entries) has a serious impact on performance, so there needs to be
a way to selectively invalidate some entries, while keeping others.

    Recall (from the discussion of barriers in 1/2 .3.4 that ARM defines inner shareable
and outer shareable domains . L1 and L2 caches are generally inner shareable , and L3
caches (if any) or RAM are considered outer shareable. In systems with multiple core
types (e.g. on most Android devices), core clusters are commonly put into the same
inner shareable domain . The shareability attribute of memory plays a role in cache and
TLB decisions, and TLBI has som e three dozen va r iants, based on the values of opl , em
and op2 .

    ARMv8.4 extends TLBI to the outer shareable domain (FEAT_TLBIOS, and with
range instr uctions (FEAT_ TLBIRANGE), as reported by the TLB bits of
ID_AA64ISAR0_ELI.

2.3.2. The AT command

            2.3.3. Address Spaces

                We've long established that different processes in the system have different address
            spaces. The processor can distinguish between address spaces by the different values of
            the page table root, but it is easier and more efficient to do so using an Add re ss Space
            IDentifier (ASID). This way, what seems to the process as a virtual address is, in fact,
            not just the address but also the ASID (and , in case of virtualization, a Virtual Machine
            Identifier, VMID, as well) .

                It is up to the kernel to manage the ASIDs . The TLB is aware of ASIDs, which
            enables cached entries from different address spaces to coexist. This is why TLBI can
            be used to invalidate an ASID. ARMv9.S's FEAT_ASID2 supports the concurrent use of
            two ASIDs.

      2.3.6. Address Translation

         After familiarizing ourselves with the registers, we can turn to the practice of
      address translation itself. ARM address translation occurs in two stages:

       1.    Stage 1: From the input Virtual Address (VA) to "Intermediate (physical)
             Address" (IA) of the next level page table.
       2.    Stage 2: From the intermediate physical address to the "Output (physical)
             Address", of the target page or block in memory.

           The flow is illustrated in figure 2-25 (to the right), taking in two inputs: The
      virtual address (in some Xd, holding a pointer value, possibly with PAC/MTE/TBI),
      and the TTBRy_ELx - The Translation Table Base Register, holding the initial (L0)
      Table for the lower VA range (y = 0, user) or y = 1, kernel/HV).

       1.    The L0 bit chooses the first level (Ll) table, which holds the lower or higher
             128TB address range.
       2.    The Ll table index bits point into the Ll table (x sizeof (void *)), to find
             the IPA of the L2 table to use.
       3.    The L2 table index bits point into the L3 table (again, x sizeof (void *)),
             to find the PA of the L3 table to use .
       4.    At the L3 table, each entry is a target page. The L3 table index bits thus
             point to the entry (again, x sizeof (void *)) with the target page
             address, and resolution is complete .

           2.4.1. PAN

               Modern operating systems map the ke rnel into the high portion of all user
           spaces. Normally, this is not a concern ., since memory protections at the MMU
           level prevent user space from accessing kernel memory.

               When the as kernel acts on behalf of a user mode cli ent, however, the
           opposite may becom e a concern. Th e kernel regularly ha s to read and write to
           user-mode memory (with the classic examp les being when servicing the write (2)
           and read (2) system ca lls, respectively). The problem which may arise is if a
           kernel pOinter gets corrupted, and accidentally points to user-mode. Because the
           corruption is unexpected, data in user mode may be mistaken for kernel data, or -
           malicious user code cou ld be mistaken for the kernel's.

              There is a need, therefore, to explicitly define those cases wherein user-mode
           memory access by kernel is allowed (again, in servicing specific system ca lls) , and
           when it is not. All kernels have some copy_ [to/fromLuser function, rather than a
           memcpy (3) /bcopy (3), to explicitly mark memory operations on user mode. There

           in EL0 will cause an exception . When set to #0, the restriction is disabled, allowing

2.4.4. Darwin: KTRR

      Apple has long implemented custom instructions and system registers in their
si licon. AI0 and later processor introduced three new system reg isters, to enab le a

     KTRR operates at the MMU level by specifying a contiguous virtual address
subrange of kernel memory. Two system registers are used for this:
53_ 4_c15_c2_3 specifies the lower end of the VA range, and 53_ 4_c15_c2_3
specifies the upper. The values are determined at runtime, computed from the
kernel text base address modified kernel ASLR slide, to the _LA5T segment. Once
known, and the kernel initialization is complete, a call to machine_lockdown ()

3.2. Hypervisor Traps

   The aim of the Hypervisor is to enable virtualization with the least possible
overhead. This, however, is not without risks. Running guest code may attempt to
execute instructions which are either of interest or dangerous to the Hypervisor.

    One approa ch to detect specific instructions and act upon them would be if the
Hypervisor logic could inspect instructions ahead of executing them. This, however, is
tantamount to interpreting code, or single stepping in a debugger, with an unacceptable
overhead.

    The approach chosen by ARM is to enable trapping of specific instructions and
register access to the Hypervisor at EL2. In effect, this is equivalent to setting
breakpoints in the guest code, which - invisible to the guest code - enable the higher
level code to modify the operation in whichever way is desired. This is accomplished
through several control registers :

      3.2.2. Fine Grained Traps

          ARMv8.6's FEATJGT goes even further by enabling "fine grained traps". The feature
      adds the HFG [R/W] TR_EL2 and HDFGRTR2_ EL2 registers. Each provides some 50 bits,
      corresponding to most system registers in Ell (and a few in EL0) . For example, bits 4-8
      correspond to APD [AB] Key, APGAKey, and API [AB] Key (respectively), enabling the
      Hypervisor to take over ARMv8.3 PAC key management from the guest.

           Another register, HFGITR_EL2, adds a rich bitmask for the various system
      instru ctions - SVC_EL [011], GCS*, and the many TLBI and DC instruction variants,
      among others.

         ARMv8.9/9.5's FEATJGT2 goes further still, adding the HFG [R/WlTR2_EL2 and
      HDFGRTR2_EL2 registers. These presently each provide only a few bits (controlling
      PFAR_ELl and FEAT_THE's RCWSMASK_ELl), but it is reasonable to assume they will
      expand as more features are introduced with ARMv9.7 and beyond.

      3.3. Nested Virtualization (FEAT_NV and FEAT_NV2)
           Hypervisors will normally run in EL2, but there may be cases when the Hypervisor
      itself needs to be virtualized (for example, running a guest inside a guest ). This is
      referred to as Nested Virtualization , and is also supported, with ARMv8 .3's FEAT_NV,
      as indicated by ID_AA64MMFR4_EL1's NV. When this is used, the Host Hypervisor (at
      EL2) can run a Guest Hypervisor (at Ell), without the latter being "aware" of its
      virtualization.

          To achieve this, the Host needs to trap the guest's access to HCR_EL2 and other
      registers at EL2. Toggling HCR_EL2's NV bit traps EL2 register access and exception
      returns. This appears to the EL2 Hypervisor code as a Synchronous Exception from the
      lower EL, with EC syndrome values of 0x1A (for ERET*) or 0x18 for other instructions.
      Most importantly, Cu rrentEL access in Ell returns 2, comp leting the illusion of running
      at a higher exception level.

         As an improvement on this, FEAT_NV2 transparently redirect HCR_EL2, SPSR_EL2,
      ESR_EL2 and ESR_ELl to their _Ell counterparts, rather than trapping them.

         ARMv9 .6's FEAT_NV2p1 further links the bits of EL2 registers to those of Ell, further
      improving nested virtualization.

      3.4. Paravirtualization

          There are case s wherein a guest as would like to calion the hypervisor to assist.
      This is referred to as paravirtualization , and is commonly used for guest/host
      communications.

          Just as a voluntary EL0/ELl traversal is accomplished by an SVC (supervisor call),
      transfer to EL2 is accomplished by an HVC (hypervisor ca ll) . This is automatically
      trapped to EL2 as a Synchronous Exception from a lower EL (i.e. through VBAR_ EL2 +
      0x400), with ESR_EL2's EC of 21. As with SVC, the exact service requested may be
      multiplexed through the immediate of the HVC (which shows up in the ESR_EL2's ISS) or
      through some register, along with arguments.

         HVC is normally only disallowed in EL0, but the choice rests in the hypervisor logic:
      some hypervisors (notably, Corellium's) may allow the instru ction to be valid in EL0 .
      Control over this in struction and other trap handling is set through HFGRTR_EL2.

3.5. Virtualization Host Extensions (FEAT_VHE)

     ARMvS.2's FEAT_VHE extends the EL2 infrastructure so as to allow a host operating
system to run in EL2. The option is enabled through the HCR_EL2 register's E2H bit
( # 34), and automatically redirects key Ell register access to their EL2 register
counterparts when in EL2. The ELl2 register are mapped to the Ell equivalents, rather
than EL2 , when HCR_EL2 . E2H is set to 1.

    EL2 was, for the longest time, left out of Apple's processors, since originally * OS
variants needed no virtualization capabilities. This changed with the M-series chips (and
A14+), which brought EL2 back in order to allow virtualization support for macOS on
Apple Silicon .

     macOS's XNU runs in EL2, rather than Ell, making it both the host operating
system and the hypervisor. In this way, guest operating systems can be run under the
host macOS, with XNU doing the virtualization. Apple provides the user-mode
Hypervisor.framework and Virtualization.framework, which ca li on XNU's built-in
Virtual Machine Management logic. This enables user-mode applications (e.g. Parallels,
VMWare Fusion, VirtualBox, etc), to delegate the low-level virtualization to the kernel,
without needing any kernel extension.

3.6. EL2 code for ELl monitoring and attestation
     EL2 code does not need to provide full virtualization. In fact, for a while (prior to
13.0), Android devices used EL2 code for Ell monitoring and attestation. The idea here
is to use the higher EL code to inspect the memory and code of the lower EL, in order to
ensure its integrity has not been compromised . This is an alternative to going all the
way to EL3 (The Secure Monitor), and provides less latency. Further discussion is in the
next section, dealing with Secure Monitors.

          Secure Monitors are to EL3 what Hypervisors are to EL2 and kernel are to Ell. They
      register the corresponding exception vector (VBAR_EL3), to interce pt interrupts and
      traps in the same manner. The voluntary traversal here is through SMC, which is
      analogous to HVC and SVC , and can only be executed in Ell or higher.

          Secure Monitors, however, are not designed for virtualization. Not only do they
      predate it (and, in fact, ARMvS itself, since they were introduced back in ARMv7 as
      "TrustZone"), but they have a different goal: That of estab lishing an entirely different,
      secure mode of execution.

      4.1. The Secure World

           As was the case with EL2, executing in EL3 allows all the benefits of "looking down"
      at the lower EL code. All memory from all levels is fully access ible here, but none of the
      lower ELs can access memory designated as EL3 only.

          EL3 , however, allows an entirely different mode of execution, accessible only
      through it - that of the "Secure World". The Secure World provides a Trusted
      Computing Base (TCB) - a compartmentalized envi ronment, wherein code can run
      entirely separate from the "Normal World". So long as the "Secure World" remains
      secure, it can run with more privileges than the "Norma l World", which includes access
      to Secure Memory, and/or specific hardware .

          The Secure World is a parallel plane of existence, with its own EL0, Ell and (as of
      ARMvS.4) EL2. This allows running a "Trusted OS" in the Secure Ell and Secure EL0,
      comp lete with its own kernel and "trustlets" - trusted lightweight applications . Note,
      again, that the id ea is not to provide another virtualized instance of an operating
      system, but rather to provide a different, minimal operating system, to provide security
      services (see Figure 13/1-2).

      4.2. EL3 registers

          Access to the secure world is governed by a special register - SCR_EL3. This is a
      register with some 55 flags, similar in principle to HCR_EL2 . Of these bits , the key one is
      NS - the least significant one. When its value is "1", the processor is in the Not-Secure
      state, i.e. the normal mode of execution . But when the value is "0", the processor is in
      the (Not-Not)-Secure state.

          ARMvS.4's FEAT_SEL2, which allows hypervisors to run in the Secure World, uses
      an other bit, SCR_EL3. EEL2 (#lS) to indicate that the hypervisor is active.

        •   Voluntarily: : Via an SMC instruction from Ell or higher. This is unless bit 7 of

4.3. Monitoring and Attestation
    The operating system kernel - commonly running in Ell - is a prime target for
exploitation. Once arbitrary memory write is achieved, the adversary can easily patch
the kernel, thereby compromising the entire operating system. This is usally performed
in one of two ways:

  •   Patching kernel code: which enables hooking or redirecting kernel logic to
      attacker supplied code. Common code targets here are:
         o system calls: as they are commonly invoked from user mode. This enables
           the adversary to gain instant visibility into all processes in the system, and
            intercept particular system calls which may be used to detect the presence
            of malicious code on the system.
        o   security related routines: primarily those dealing with credentials. This
            enables the adversary to modify the privileges of any user mode process.
            This is commonly used to bestow root access on a chosen process, which
            serves as the user-mode component of the malware.

  •   Patching kernel data: is not as straightforward, but can nonetheless achieve
      similar objectives, and may be the only way available to the attacker if the kernel
      code cannot be modified (for example, due to Apple's KTRR). The primary target
      here would be process metadata, specifically credentials, as they provide an
      alternative to patching the security related routines.

    If kernel code is compromised, such a compromise could be hard to detect from
within the kernel itself. After all, the compromising code could ostensibly patch the code
used to detect the patching (say, by NOPing it entirely). This is where the higher EL
comes into play. An Ell compromise that cannot somehow also reach into a higher EL,
could not avoid detection by the higher EL code.

    Such monitoring and attestation features require a higher EL, but not necessarily
EL3. Some implementations may opt to do the monitoring at EL2. The rationale here is
that - if a Virtual Machine Monitor is not desired - EL2 code can provide less latency by
performing whichever integrity checks right there and then, rather than going to down
through the Secure OS kernel all the way to the attestation trustlet, and back. Samsung
pioneered this approach with their TIMA (Trusted Measurement Integrity and
Attestation), which was first implemented as far back as 32-bit ARMv7 with TrustZone,
but later in ARMv8 moved its components to EL2, leaving EL3 and the trusted OS for
the "traditional" uses of Crypto and DRM.

    As explained further in A-III/2, attestation requires a both voluntary traversals and
involuntary ones:

  • The voluntary' traversals: protect "hotspots", which are the prime targets for
    patching, discussed above. Samsung refers to this as "Realtime Kernel
    Protection", or RKP.
  • The involuntary' traversals: piggyback on IRQs and FIQs to periodically enter
    the higher EL, and trigger the attestation logic, to perform integrity checks on the
    lower EL memory. Samsung refers to this as "Periodic Kernel Measurement", or
    PKM .

    Both approaches are necessary, because RKP upcalls to the higher EL could
potentially be patched out by the adversary. PKM, however, is hobbled by the severe
time constraints of working during an IRQ or (worse) a FIQ. A statistical approach of
taking a certain "budget" of pages to hash and verify on each non-voluntary traversal is
used.

    It follows, therefore, that PKM cannot cover all lower EL memory at all times.
Although interrupts cannot be blocked by the lower EL, this nonetheless leaves a time
window, in which a sophisticated enough adversary may be able to patch code or data,
exploit it, and quickly unpatch, thus remaining undetected and defeating the whole
mechanism. The window can be minimized, but not fully eliminated, by biasing towards
the hotspots.

     PKM was also briefly used by what Apple dubbed "Kernel Patch Protection" (KPP,
better known by its internal name of "WatchTower") for a while (in AS and A6
processors), before moving (in A7 and later) on to the much stronger KTRR, discussed
earlier, which eliminates the PKM window problem and provides full kernel (read-only
memory) patch protection.

      4.4. ARMv9.2 Realms (FEAT_RME)

          ARM prides itself on being a hardware-enforced secure architecture, and one of
      ARMv9 .x's key features is security, dubbed by ARM as the Confidentia l Compute
      Architecture (CCA).

          ARMv9 .2's FEAT_RME introduces the concept of "Realms", which is integral to CCA .
      As explained in the Realm Management Extension Guide /me this modifies the existing
      ELx separation, redefining TrustZone and adding a new state for Realms, as shown in
      Figure 4-3 (opposing pag e) and listed here:

        •    The Non-Secure State: is the same as before , with Ell and EL0 for the "Rich
             OS", and EL2 reserved for a Hypervisor.
        •    The Realm State: provides a protected execution env ironment. Each "Realm" is
             an isolated space, mutually excluded from others. The Realms are managed by
             the Realm Manager Monitor (a dedicated Realm-EL2 component), and can
             commu nicate with it using a Realm Services Interface (RSI)
        •    The Secure State: is the equivalent of the "Secure World", but this time for EL2
             and below only, excluding EL3.
        •    The Root State: is EL3 only, reserved for firmware and monitor.

         The key advantage of using Realms is guaranteeing a secure execution
      environment, whose memory and code cannot be read by any other state, save for the
      Root. This addresses a key weakness of TrustZone, wherein compromi se of the TEE
      amounted to full system compromise, since the TEE (Secure World) could access any
      non-secure memory.

           Code in a Realm can be assured its data is safe from modification, since the Root
      state would be reserved to secure firmware. Further, Realm code could use the Realm
      Services Interface (RSI) to query the Realm Management Monitor (RMM, a Realm-
      only hypervisor) for attestation services . Meanwhile, the RMM also provid es a Realm
      Management Interface (RMI) to allow the host system to maintain the Realm
      lifecycle.
