                                    String and String Slice Representation in Memory
                                    Let us examine the memory representation of strings. Understanding the memory layout of strings is
                                    essential for grasping how one passes around and manipulates them.
                                    In Rust, the types String and &str represent strings. We will look at each of these types in detail.

                                    String
                                    In Rust, a String is a growable, mutable, owned, UTF-8 encoded string type represented in memory as a
                                    three-part data structure. This structure includes a pointer to the raw string data (ptr), the string’s byte
                                    length (len), and its total capacity (cap). The length indicates the actual size of the string. In contrast, the
                                    capacity represents the total buffer size, often larger than the string to accommodate growth without
                                    frequent memory reallocations. While the stack stores all this metadata, the actual string data resides on
                                    the heap. This memory representation strongly resembles the Vec<T> struct.

                                    The String is a wrapper around Vec<u8>.

                                    pub struct String {
                                        vec: Vec<u8>,
                                    }

                                    &str (String Slice)
                                    In Rust, &str, commonly known as a “string slice”, is a reference to a string and often appears in function
                                    signatures to accept any string. Comprising two parts, a string slice consists of a pointer to the string data’s
                                    start and the byte length of the slice. Notably, a string slice does not own the memory it references and
                                    lacks capacity information, rendering it unmodifiable and non-resizable. However, its smaller size makes it
                                    more efficient to pass around than a String.

                                    and returns their concatenation as a new string. The first string is an owned String, and the second is a

                                    Builder Pattern: Optimize Away the Builder Struct
                                    The builder pattern, a design pattern suitable for the step-by-step construction of complex objects, is
                                    effective when the same construction process can yield several types or representations of the object. It
                                    proves especially useful for objects with numerous optional or configurable properties. In Rust,
                                    implementing the builder pattern involves using a struct and a corresponding builder struct. This builder
                                    struct includes methods for setting the values of the struct’s fields. It also features a build method that
                                    consumes the builder, returning a new struct instance.

                                    Builder for Address
                                    Let us look at an example of a builder for an Address struct:

                                    pub struct Address {
                                        pub street: String,
                                        pub city: String,
                                        pub postal_code: u64,

                                    }

                                    #[derive(Default)]
                                    pub struct AddressBuilder {
                                        street: String,
                                        city: String,
                                        postal_code: u64,
                                    }

                                    impl AddressBuilder {
                                        fn new() -> AddressBuilder {
                                            AddressBuilder::default()
                                        }

                                            fn street(mut self, value: String) -> Self {
                                                self.street = value;
                                                self
                                            }

                                            fn city(mut self, value: String) -> Self {
                                                self.city = value;
                                                self
                                            }

                                            fn postal_code(mut self, value: u64) -> Self {
                                                self.postal_code = value;
                                                self
                                            }

                                            fn build(self) -> Address {
                                                Address {
                                                    street: self.street,
                                                    city: self.city,
                                                    postal_code: self.postal_code,
                                                }
                                            }
                                    }

                                    pub fn make_address(street: String, city: String, postal_code: u64)
                                                        -> Address {
                                        AddressBuilder::new()
                                            .street(street)
                                            .city(city)
                                            .postal_code(postal_code)
                                            .build()
                                    }

                                    Let us break down the preceding code:
                                        •    Address is a public struct that represents an address. It has three public fields: street, city and
                                             postal_code.

                                        •    AddressBuilder is a public struct that is a builder for the Address struct, containing the same
                                             fields as Address. The #[derive(Default)] annotation above the struct definition enables the
                                             creation of a default AddressBuilder instance, where all fields are set to their default values.

                                       •     The impl AddressBuilder block provides methods for the AddressBuilder struct:

                                               –     new is a function that creates a new AddressBuilder instance with default values.
                                               –     street, city, and postal_code are functions that take a mutable reference to self (the
                                                     current AddressBuilder instance) and a value to set for the respective field. They each
                                                     return self, allowing the methods to be chained together.
                                                –    build takes self and constructs an Address instance with the current state of the
                                                     AddressBuilder.
                                       •     make_address is a public function that takes street, city, and postal_code as parameters,
                                             creates an AddressBuilder, sets the fields with the provided values, builds the Address, and
                                             returns it.

                                    The use of the builder pattern makes the code more readable and flexible. For example, if developers add
                                    additional fields to the Address struct in the future, they can also add them to the AddressBuilder in a
                                    way that does not break existing code.
                                    We wish to answer the question: Does the builder pattern have a runtime cost? In the next section, let us
                                    look at the assembly generated for the make_address function.

                                    Builder Pattern Assembly
                                    The generated assembly shows that the builder pattern is a zero-cost abstraction. The main function inlines
                                    the make_address function, leading to the optimization of the AddressBuilder struct. Additionally, the
                                    compiler optimizes away the new, street, city, and build functions, resulting in no generated code for
                                    these functions.
                                    After the optimizations, the effective code for make_address is as follows:

                                    pub fn make_address(street: String, city: String, postal_code: u64)
                                                       -> Address {
                                        Address {
                                            street,
                                            city,
                                            postal_code,
                                        }
                                    }

                                    Emoji Arithmetic: Overloading the + Operator
                                    Now, let us look at a more complex example. The following code defines an Emoji struct representing a
                                    single emoji. The Emoji struct implements the Add trait to add two emojis together. The add_two_emojis
                                    function adds two emojis, and the add_three_emojis function adds three.

                                    Note that the add function returns an Option<Emoji> because the code may not support the addition of
                                    two emojis. For example, the code defines the addition of the and    emojis, but it does not support the
                                    addition of the    and     emojis.

                                          Learn More: Option<T>
                                    The Option<T> type represents an optional value. It can be Some(T) or None. Where T is the type of the
                                    optional value. The Option<T> type is an enum defined as follows:

                                    pub enum Option<T> {
                                        None,

                                         Some(T),
                                    }

                                    The representation of enums in Rust is like that of unions in C. An additional discriminator field is added to
                                    the struct to indicate which enum variant is stored. In many cases, Rust can optimize away the
                                    discriminator field. We will see an example of this optimization in the assembly code for the add function.

                                    Emoji Example
                                    #[derive(PartialEq)]
                                    pub struct Emoji(&'static str);

                                    impl std::ops::Add for Emoji {
                                        type Output = Option<Self>;

                                         fn add(self, rhs: Self) -> Self::Output {
                                             let Emoji(self_emoji) = self;
                                             let Emoji(rhs_emoji) = rhs;

                                              match (self_emoji, rhs_emoji) {
                                                  (" ", " ") => Some(Emoji("                 ")),
                                                  (" ", " ") => Some(Emoji("                 ")),
                                                  (" ", " ") => Some(Emoji("                 ")),
                                                  (" ", " ") => Some(Emoji("                 ")),
                                                  _ => None,
                                              }
                                         }
                                    }

                                    pub fn add_two_emojis(a: Emoji, b: Emoji) -> Option<Emoji> {
                                        a + b
                                    }

                                    pub fn add_three_emojis(a: Emoji, b: Emoji, c: Emoji) -> Option<Emoji> {
                                        (a + b)? + c
                                    }

                                    .L__unnamed_2:
                                        .ascii "\360\237\230\236"                       ; UTF-8 representation of "               " emoji

                                    add_two_emojis Assembly
                                    pub fn add_two_emojis(a: Emoji, b: Emoji) -> Option<Emoji> {
                                        a + b
                                    }

                                    The add_two_emojis function is a simple wrapper around the add function. The compiler uses tail call
                                    optimization to avoid allocating a new stack frame for the add function. Instead, it reuses the stack frame of
                                    the add_two_emojis function for the add function.

                                    example::add_two_emojis:
                                        ;     Jump to the add method of Emoji. When the add method returns,
                                        ; it will directly return to the caller of add_two_emojis.
                                        jmp      qword ptr [rip + <example::Emoji as Add>::add@GOTPCREL]

                                    Part E Strings, Dispatch, and Recursion
                                           Learn More: Tail Call Optimization
                                    Tail call optimization allows the compiler to reuse the current function’s stack frame for the following
                                    function call. This optimization is possible under the following conditions:
                                       •      The last operation of the current function is a function call.
                                       •      The arguments of the following function call are already in the proper registers.
                                       •      The return value of the current function is the return value of the following function call.
                                    This optimization proves beneficial for wrapper functions, allowing the compiler to bypass allocating a new
                                    stack frame for the wrapped function. Similarly, it is advantageous for recursive functions, enabling the
                                    compiler to reuse the stack frame for each recursive call. We will explore recursive functions in greater
                                    detail later in the book.

                                    add_three_emojis Assembly
                                    pub fn add_three_emojis(a: Emoji, b: Emoji, c: Emoji) -> Option<Emoji> {
                                        (a + b)? + c
                                    }

                                    This function starts by saving the pointers to the third emoji and its length in r14 and r8, respectively. It
                                    then delegates to the Add implementation to add the first two emojis.

                                    If the result is None, it returns None. Otherwise, it calls the Add implementation again to add the third emoji
                                    to the result of adding the first two. Finally, it restores the saved registers and returns the result. This logic
                                    implements the expression (a + b)? + c. The expression is equivalent to the following code:

                                    if let Some(a_plus_b) = a + b {
                                        a_plus_b + c
                                    } else {
                                        None
                                    }

                                    Input:

                                       •      rdi =     a.ptr
                                       •      rsi =     a.len
                                       •      rdx =     b.ptr
                                       •      rcx =     b.len
                                       •      r8 =     c.ptr
                                       •      r9 =     c.len

                                    Output:

                                      •   rax =   result.ptr or   None
                                      •   rdx =  result.len
                                    example::add_three_emojis:
                                    push    r14                 ; Save r14
                                    push    rbx                 ; Save rbx
                                    push    rax                 ; Save rax

                                    mov         r14, r9                       ;   Move c.len to r14
                                    mov         rbx, r8                       ;   Move c.ptr to rbx

                                      •        a.ptr,    a.len,     b.ptr,      b.len are already in rdi, rsi, rdx, rcx
                                      •      The arguments are already in the right registers for the add. Call add method of Emoji for a + b
                                    call       qword ptr [rip + <example::Emoji as Add>::add@GOTPCREL]

                                    ; Test the return value (the result of the add operation is not None)
                                    test    rax, rax

                                    je          .LBB2_1               ; Jump if it is None

                                    mov         esi, 4                ;      Move 4 (emoji string length of a+b) into esi

                                    mov         rdi, rax              ; Move result of a+b value into rdi

                                    mov         rdx, rbx              ;      Move c.ptr into rdx
                                    mov         rcx, r14              ;      Move c.len into rcx

                                          Call add method of Emoji for (a + b) + c

                                    call        qword ptr [rip + <example::Emoji as Add>::add@GOTPCREL]

                                    jmp         .LBB2_3               ; Skip setting eax to 0 as the result is not None

                                    .LBB2_1:
                                    xor      eax, eax                 ;      Returning None. Zero out eax.

                                    .LBB2_3:
                                    mov      edx, 4                   ;     Move 4 into edx (length
                                                                      ; of the None return value)

                                    add         rsp, 8                ; Add 8 to rsp to balance the stack

                                    pop         rbx                   ; Restore rbx
                                    pop         r14                   ; Restore r14

                                    ret                               ;      Return    result.ptr in rax and
                                                                      ;      result.len in rdx

                                        Key Takeaways
                                    •    String is a struct that contains the following fields:

                                           –     Pointer to a heap-allocated buffer
                                           –     Capacity of the heap-allocated buffer
                                           –     Length of the string
                                    •    &str is a struct that contains a pointer to a string slice and length.

                                    •    If a String parameter transfers ownership, the caller passes a pointer to the String struct. The
                                         called function is responsible for deallocating the heap-allocated buffer in the String when the
                                         function is going out of scope. We saw this in the combine_strings function.

                                    •    If a function returns a String, the caller passes a pointer where the called function should store the
                                         result String. We saw this in the combine_strings function.

                                    •    The compiler uses two registers to pass a string slice ptr and length len. We observed this in the
                                         add_three_emojis function.

                                    •    For small strings, the compiler can treat a string’s UTF-8 bytes as a single integer. This optimization
                                         allows the compiler to generate efficient code for string comparisons. We saw this in the Emoji
                                         struct’s add method.

                                    •    Tail call optimization reduces the overhead of stack preparation. We saw this in the
                                         add_two_emojis function. This optimization reduces the overhead of calling wrapper functions.
                                         We will see in later chapters that this optimization is also helpful for recursive functions.

                                    •    The Rust compiler removes the discriminator for None and Some variants for non-nullable types. It
                                         represents the None variant as a null pointer and the Some variant as a valid pointer. We observed
                                         this in the add_three_emojis function.
