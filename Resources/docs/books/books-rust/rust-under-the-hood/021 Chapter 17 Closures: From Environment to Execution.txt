                                    Rust Closures Traits - Fn, FnMut, and FnOnce
                                    In Rust, closures serve as anonymous functions with the capacity to capture variables from their defining
                                    scope. You can utilize closures in multiple ways - passing them as arguments to functions, returning them
                                    from functions, or assigning them to variables.
                                    In terms of invocation, closures provide versatility—you can call them repeatedly or exclusively once.
                                    Additionally, closures demonstrate adaptable behavior in handling borrowed variables. They can borrow
                                    these immutably, ensuring no alteration to the variables or, mutably, allowing variable modifications.
                                    Furthermore, closures can assume ownership of captured variables.
                                    Implementing the Fn, FnMut, and FnOnce traits achieves this broad range of capabilities. Here is a brief
                                    overview of these traits:
                                      •    The Fn trait applies to closures that take a borrowed version of the environment. It allows a closure
                                           to be called multiple times without altering the environment.

                                      •    The FnMut trait is for closures that mutably borrow the environment. These closures can be called
                                           multiple times, but each call must be sequenced.

                                      •    The FnOnce trait is for closures that take ownership of the environment. These closures can be
                                           called only once, as they consume the environment upon being called.

                                    In this context, “environment” refers to the captured variables.

                                           Learn More: Closure Environment
                                    In Rust, the closure environment refers to the scope in which the closure is defined and includes any
                                    variables from the scope that the closure captures or “closes over”.
                                    When a closure captures a variable from its environment, it can do so in one of three ways:
                                      1.     By reference (&T): The closure takes an immutable borrow of the variable, allowing it to utilize its
                                             value without any modifications. The original variable remains accessible and usable.
                                      2.     By mutable reference (&mut T): The closure takes a mutable borrow of the variable, enabling it to
                                             alter its value. The original variable is no longer usable for modifications within the same scope as
                                             the closure.
                                      3.     By ownership (T): The closure takes ownership of the variable. For types implementing the Copy
                                             trait, the value remains available after being consumed. For complex types, ownership of the data
                                             itself is transferred. Using move might be necessary to ensure the closure can access the captured
                                             variable even after its original scope ends. This approach prevents dangling references and upholds
                                             memory safety.
                                    These mechanisms determine how a closure interacts with the variables from its environment, shaping its
                                    behavior and usage.

                                           Learn More: Closures and Move Semantics in Rust
                                    Rust’s closure traits, Fn, FnMut, and FnOnce, come with distinct behaviors and use cases, especially when
                                    considering concurrency and ownership. The Fn trait allows a closure to be called simultaneously from
                                    multiple threads, making it suitable for concurrent applications, as demonstrated by its use in Rayon’s
                                    ParallelIterator interface. In contrast, FnMut closures, used in the standard Iterator interface, are
                                    not inherently thread-safe and are designed for single-threaded contexts.
                                    Ownership in closures is another critical concept. While all three closure types can capture and own
                                    environment variables upon creation, FnOnce is unique in its ability to consume those variables within the
                                    closure body. This property stems from its design, which permits only a single call.
                                    The concept of move semantics in Rust plays a vital role with closures. This mechanism ensures the original
                                    variable becomes inaccessible after the move, preventing dangling references and upholding Rust’s

                                    Stack and Heap-Allocated Closures
                                    Before we proceed, let us explore two common methods for working with closures in Rust:
                                      •     impl Fn: We use this notation when a function returns a closure without specifying its exact type.
                                            The compiler infers that the closure implements the Fn trait. While impl Fn does not inherently
                                            specify where to store the closure (stack or heap), we typically store closures typed this way on the
                                            stack unless explicitly boxed.
                                      •     Box<dyn Fn>: This denotes a heap-allocated closure that employs dynamic dispatch (indicated by
                                            dyn). This method proves useful when you cannot statically determine the exact type of a closure or
                                            when the type might vary. Boxing a closure ensures its storage on the heap and facilitates the
                                            return of closures from functions or their storage in data structures without precise type
                                            knowledge.
                                    Here is a basic example illustrating the difference between impl Fn and Box<dyn Fn> in Rust:

                                    // A function that returns a closure, typically stored on the stack
                                    pub fn returns_impl_fn() -> impl Fn(i32) -> i32 {
                                        let capture_var = 10;
                                        move |x| x + capture_var
                                    }

                                    // A function that returns a boxed closure stored on the heap
                                    pub fn returns_dyn_fn() -> Box<dyn Fn(i32) -> i32> {
                                        let capture_var = 20;
                                        Box::new(move |x| x + capture_var)
                                    }

                                    implementation in assembly.

                                          Key Takeaways
                                      •     The Rust compiler captures and stores the environment in a closure environment struct.
                                      •     Closures returned as impl Fn typically store their environments on the stack.
                                      •     The compiler may completely inline a closure. In such cases, it does not store the closure
                                            environment.
                                      •     If the function returns a closure as Box<dyn Fn>, it stores the closure environment on the heap and
                                            returns a fat pointer to the caller. This fat pointer includes the address of the closure environment
                                            and the vtable address.
                                      •     For closures in the form of Box<dyn Fn>, passing a &dyn Fn as an argument to a function is more
                                            efficient. Passing Box<dyn Fn> is less efficient since the compiler must handle the dropping of the
                                            Box.
                                      •     The vtable includes the destructor for the closure environment, the size and alignment of the
                                            closure environment, and the closure’s call method.
                                      •     Prefer returning impl Fn over Box<dyn Fn> as it stores the closure environment on the stack and
                                            eliminates the need for heap memory allocation. In many cases, impl Fn is more efficient since the
                                            compiler can inline the closure.
