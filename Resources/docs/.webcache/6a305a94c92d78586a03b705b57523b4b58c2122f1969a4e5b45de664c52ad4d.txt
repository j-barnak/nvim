# How Far We Have Come: Testing Decompilation Correctness of C Decompilers

In *Proceedings of the 29th ACM SIGSOFT International Symposium on Software Testing and Analysis (ISSTA '20)*, July 18–22, 2020, Virtual Event, USA. ## Abstract

A C decompiler converts an executable (the output of a C compiler) back into source code; ideally the recovered code, once recompiled, yields an executable with the same functionality as the original. The authors observe a mismatch between industry and academia: although C decompilers are widely used commercially, academic work rarely reuses their final-stage output (the recovered C code), preferring intermediate representations instead. This conservatism reflects a "widespread and pessimistic" view of decompilation correctness. The paper tests that view empirically. Using Equivalence Modulo Inputs (EMI) testing and extensive manual inspection, the authors detected 1,423 inputs that trigger decompilation errors across four popular decompilers, and identified 13 bugs in two open-source decompilers. Their conclusion is nuanced: the pessimistic stance causes researchers to *underestimate* modern decompilers, which do care about functional correctness and are making promising progress, yet long-studied problems such as type inference and optimization still impede quality output more than the literature reflects, and these issues rarely receive enough attention.

## 1. Introduction

C decompilers are among the most fundamental reverse engineering tools, underpinning malware analysis, off-the-shelf software hardening, legacy migration, and exploit development. The market includes expensive commercial tools (IDA-Pro, JEB3), community free tools (RetDec, Radare2), and the NSA's Ghidra. Despite this, the authors note that academia rarely reuses the recovered C code directly. For example, to fix a flaw in an executable the convention is binary patching after reverse-engineering the layout, rather than the more direct route of decompiling, instrumenting the C code, and recompiling.

The authors argue that recent progress on "functionality-preserving" disassembly and C-style control-structure recovery shows that recompilable decompilation of unobfuscated, not-highly-optimized executables is now largely a matter of engineering effort (at some cost to readability). They therefore study C decompilers "in a realistic setting" to delineate up-to-date correctness. They target **x86-to-C** decompilation and answer three research questions:

- **RQ1**: How difficult is it to recompile the outputs of modern C decompilers?
- **RQ2**: What are the characteristics of typical decompilation defects?
- **RQ3**: What insights can be deduced from analyzing those defects?

This is described as the first comprehensive study targeting C decompilers. The method reuses **EMI testing**, a random-testing technique highly successful at finding compiler bugs, in this new setting, combined with about 530 man-hours of manual inspection by security analysts. From 10,707 programs, they found 1,423 exposing errors across four decompilers (commercial IDA-Pro and JEB3; free RetDec and Radare2/Ghidra), and manually confirmed 13 buggy code fragments in the two open-source tools. All findings were reported to developers; typical defects were promptly confirmed by commercial vendors. Tools and findings were released, and the artifact earned the ISSTA Functional badge.

## 2. Background of Research

### 2.1 Pipeline of C Decompilers

A modern decompiler runs a multi-stage pipeline where each stage's output feeds the next. The **front end (disassembly)** translates binary code into assembly and then lifts it into an analysis-friendly intermediate representation (IR); raw assembly is seldom analyzed directly. The **middle stage (high-level program recovery)** is the paper's central focus: from the lifted IR it recovers variables, types, and high-level C control structures. Variable recovery uses static analysis; type recovery uses constraint-based inference systems; control-structure recovery matches IR regions against predefined structure templates with iterative refinement. Modern decompilers also apply optimizations (dead-code elimination, "untiling") and iterate modules back and forth to resolve "chicken-and-egg" dependencies between data-flow and control-flow analysis. The **back end (code generation)** translates IR statements into C statements; this stage is mostly mundane but can still contain bugs.

### 2.2 Equivalence Modulo Inputs (EMI) Testing

EMI testing is a compiler-testing technique. Given program *p* with input space *dom(p)*, two programs *p* and *q* are **equivalent modulo inputs** if `∀i ∈ I [[p]](i) = [[q]](i)` where `I ⊆ dom(p) ∩ dom(q)`; *q* is an EMI variant of *p*. The key benefit is that no reference implementation is needed: any EMI variant *q* must behave identically to *p* on inputs in *I*, providing an explicit oracle. To adapt EMI to decompilers, the authors generate a mutated program *q*, decompile the executable compiled from *q* to obtain decompiled source *q\**, which is itself an EMI variant of *p*, and apply the oracle. The original EMI work mutates by profiling *p* and inserting/deleting statements in code blocks not covered by *I*; improvements insert code guarded by always-false opaque predicates into live regions, and use statistical methods (MCMC) to select statements. The authors employ all three mutation strategies.

## 3. Motivation

The section argues the topic is central and timely, exposing a mismatch between the conservative use of decompiled C code and the progressive development of decompilation techniques.

### 3.1 Research Using C Decompilers

Reusing decompiled x86 and ARM binary code is widespread in industry: hackers have decompiled and reused complex real-world software such as video games and firmware. In academia, decompilers are heavily used (searching "IDA Pro" on Google Scholar returned 1,370 records since 2015), spanning code comprehension, code reuse, and security hardening/vulnerability detection, but researchers typically extract *intermediate* information rather than reusing final decompiled C. Binary patching and replication, the usual alternative, are error-prone and costly. The authors attribute this to the traditional belief that recovered C cannot be recompiled, and counter that recent "fool-proof" disassembly and decompilation techniques make functionality-preserving recovery a matter of engineering effort, making now the ideal time for systematic testing.

### 3.2 Analysis and Instrumentation with IR

Using a decompiler's IR (e.g., LLVM IR) does *not* eliminate the need for decompilation. Beyond having to reimplement infrastructure (like symbolic execution engines) for custom IRs, IR lifted from binaries faces the *same* variable- and type-recovery challenges as decompilation. Fig. 2 in the paper contrasts LLVM IR generated from source C with LLVM IR lifted from the corresponding binary, showing that high-level information (proper types, local vs. global memory distinctions, function boundaries) is lost in the lifted IR. This "multilingual" trap of mediating source-level analyses with low-level code and incompatible memory models again argues for improving decompilers so that source-level analysis can integrate seamlessly with low-level study.

## 4. Methodology and Study Setup

The workflow: generate random C programs with **Csmith**, mutate each seed *p* via EMI into variant *q*, compile *q* to executable *e_q*, decompile *e_q* to source *q'*, instrument *q'* into a recompilable program, compile it to *e'_q*, and compare execution outputs against the reference. The study captures three issue kinds:

- **Decompilation failures**: crashes/errors from the decompiler (usually a simple decoding bug); recorded but not the main focus.
- **Recompilation failures**: compiler errors when recompiling decompiled output, indicating decompiler bugs or limits.
- **Decompilation defects**: deviant execution results, implying the semantics of the input were broken, likely from a decompiler bug.

Recompilation failures and decompilation defects are the primary focus. The study assumes disassembly is reliable (current algorithms work well in practice) and deliberately excludes obfuscated and highly-optimized code, limiting to unobfuscated, unoptimized 32-bit x86 binaries; the goal is to understand how well modern decompilers handle *conventional* C programs.

### 4.1 Equivalence Modulo Inputs (EMI) Testing

Algorithm 1 specifies the procedure. `Testing(P)` iterates over Csmith programs; `IsDeviant(p, q)` compiles both, decompiles *e_q* into *q'*, instruments and recompiles it into *e'_q*, then executes and compares outputs. Csmith programs need no user input; each returns a checksum of its global variables, which is compared directly. For each seed, the authors first check recompilation correctness of the seed itself, then run up to **MAX_ITER = 30** EMI mutations. `Mutate` covers both dead-code mutation (inserting/removing unreachable statements) and live-code mutation (inserting all three opaque-predicate schemes from prior work); live code regions are identified by running the program and recording covered statements via gcov. Rather than blind statement selection, they reimplement an **MCMC-guided** mutation strategy: each new variant is compared to the previous one by a program distance, and accepted with an acceptance ratio, progressively favoring more diverse (higher-distance) variants.

### 4.2 Manual Inspection

When a deviant checksum is found, analysts debug backward: starting from a global variable with a deviant value, they trace its assignments recursively until reaching the erroneous statement in the decompiled variant. This is costly: examining suspicious findings took two experienced reverse-engineering analysts (with CTF experience) about **180 man-hours**; locating the 13 buggy code fragments in the open-source decompilers took about **350 man-hours** over six weeks.

### 4.3 Study Setup

The framework is implemented in Python (3,707 LOC). Key challenges and solutions:

- **Recompilation challenge**: decompiled outputs contain many undefined symbols (e.g., ELF/GOT symbols in global data sections), so they are not directly recompilable.
- **Instrument**: Csmith is configured to emit exactly one function besides `main`; that decompiled function is a "closure" of well-defined local symbols, so it is extracted and spliced back into the source, sidestepping the undefined global-section symbols and reviving recompilability.
- **Discarded global names**: because compilation discards names and decompilers rename to `v0, v1, ...`, the authors create a **ghost local variable** for each global and replace global uses with the local (synchronizing through a setter), since the checksum depends on globals. Csmith is configured to avoid pointers, so no alias analysis is needed.
- **Configuration**: Csmith 2.3.0, gcc 7.4.0 (32-bit x86, no optimization), gcov 7.4.0. To keep manual inspection feasible, Csmith is restricted to a C subset excluding structs, unions, arrays, and floating point, but still producing complex control flow, arithmetic, and type casting.

The **four decompilers** (Table 1) are IDA-Pro and JEB3 (commercial), RetDec (community; an LLVM-based frontend), and Radare2/Ghidra (community + NSA; Radare2 front end with Ghidra 9.1 decompiler, which is more accurate than Radare2's native decompiler). These represent, in the authors' judgment, the best two commercial and best two free decompilers; Snowman was tried but produced worse output. All are used out-of-the-box in the standard setting, since optimization/algorithm options are not configurable.

The dataset (Table 2): **1,000** Csmith seed programs (142,888 LOC total; ~148 LOC each) yielding **9,707** EMI variants (2,361,590 LOC total).

## 5. Findings

Overall (Table 3), out of 9,706 test cases (excluding one decompilation failure), **408 (4.2%)** recompilation failures were found; **1,014 (10.4%)** outputs were erroneous (deviant execution). **JEB3** performed best, with the fewest decompilation defects. Defects are classified into five characteristics by manual analysis: **type recovery (377), variable recovery (432), control-flow recovery (52), optimization (147), and others (6)**. Average decompilation time is about **5.0 CPU seconds** per case, so decompilers are efficient on common binaries. Developers were responsive: the JEB3 developer confirmed the selected cases and hoped to include some in the next update, and the IDA-Pro author acknowledged internally using Csmith and knowing not all cases are handled yet, interpreted as evidence that commercial developers do care about functional correctness.

### 5.1 Identify Buggy Code Fragments in Decompilers

Root-cause analysis is only possible on the open-source tools. Analyzing all 913 RetDec flaws (178,732 LOC) and all 179 Radare2/Ghidra flaws (Ghidra plugin 112,999 LOC) yielded **13 buggy code fragments** (Table 4). One bug can cause several error categories: e.g., Bug8 is a Radare2/Ghidra type-recovery bug that directly produces 31 type errors and, via optimization treating mis-typed variables as parts of others, 87 missing-variable errors. All 13 are **logic bugs producing wrong output** (not crashes). Twelve are in the middle stage (four in type recovery, two in variable recovery, six in optimization); one (Bug13, Radare2/Ghidra) is in code generation, lifting an unsigned shift in the Ghidra IR into a signed shift in C. Notably Radare2/Ghidra "freerides" Radare2's type-recovery utility, and Bug8 actually roots in Radare2's incorrectly recovered types.

### 5.2 Recompilation Study (RQ1)

**Full-scale recompilation (5.2.1)**: recompiling default Csmith outputs directly, *none* of the decompiled outputs recompiled into functional executables, due to undefined symbols (ELF-specific, decompiler-specific, or undefined variables). Recompilation is evidently not a top priority for these tools.

**Recompilation failure (5.2.2)**: for the 408 instrumented-output failures, two key causes emerge. (1) **Erroneous variable recovery**, e.g. JEB3 emitting `unsigned int v0, v0;` (a re-declaration) for a single local. (2) **Incorrect function-parameter recovery**, e.g. declaring `set_var(a, b)` but calling `set_var(a)`. All 187 RetDec recompilation failures root from just two function-prototype bugs (Bug6, Bug7). Undefined symbols still appear in IDA-Pro output (ELF/GOT symbols), while the other three largely avoid them.

**Result implication (5.2.3)**: making non-trivial C recompilable is "essentially the last mile" of modern decompilers. After straightforward syntax-level tweaks, most outputs recompile: Radare2/Ghidra had **zero** recompilation failures, both commercial tools under 5%, and RetDec's 187 failures trace to only two easily-fixable bugs. First finding:

> "By applying straightforward syntax-level changes without any manual tweaks, modern C decompilers already show good support of recompilation for many non-trivial C programs."

### 5.3 Decompilation Defects (RQ2)

**Type recovery (5.3.1)**: type errors break semantics via both control and data flow. Example: a source `int i` recovered as `unsigned int i` turns an unreachable loop body into a reachable one, altering control flow; and `int32_t a = 0xaaffff` recovered as `int16_t a` truncates to the low 16 bits, altering data flow. RetDec's 315 type errors root from two bugs (Bug1 mishandles `movsx` sign extension/truncation; Bug4 misses call parameters); Radare2/Ghidra's 35 stem from Bug8/Bug11/Bug13.

**Variable recovery (5.3.2)**: RetDec's 338 variable errors all root from one parameter-recovery bug (Bug2). Radare2/Ghidra misses locals when Bug8 assigns a variable an oversized type so that adjacent variables overlap and get optimized out. JEB3 produces seven undefined-behavior cases using uninitialized values (e.g., `unsigned int v0; unsigned int v1 = v0 >> 16;`); the authors urge initializing such variables to zero.

**Control-flow recovery (5.3.3)**: 52 deviant outputs. In RetDec and Radare2/Ghidra these all actually stem from type/optimization bugs, e.g. an always-false opaque condition being optimized away as "true," making an unreachable branch reachable (Bug3–4 in RetDec, Bug9–13 in Radare2/Ghidra). IDA-Pro also mistakenly **reorders** independent `if` statements, altering execution flow.

**Optimization (5.3.4)**: optimizations meant to improve readability can break functionality via erroneous constant folding/propagation (e.g., Bug5 ignores bit length; Bug11 uses a 32-bit Ghidra ghost variable to replace a 16-bit one). Six of the 13 bugs are in optimization. Over-optimized code becomes too concise; readability was measured by average LOC and moss code-similarity vs. inputs:

| | IDA-Pro | JEB3 | RetDec | Radare2/Ghidra |
|---|---|---|---|---|
| LOC | 90 | 85 | 54 | 104 |
| Similarity | 0.51 | 0.50 | 0.54 | 0.49 |

Decompiled output is far shorter than the input average (~143 LOC) and similarity is low, so aggressive optimization notably harms readability.

### 5.4 Others

Six errors show syntax-level differences (e.g., arithmetic operators) from the source with unknown root cause (closed-source tools), suspected to be sloppy errors in the C-statement translation stage that developers could fix easily.

### 5.5 Result Implication (RQ3)

Two findings emerge. First, modern decompilers have not fully implemented well-established research: function-recognition research reaches ~99% accuracy on x86, yet RetDec still makes many prototype/parameter errors; principled recursively-constrained type inference exists, yet decompilers rely on simple heuristics and predefined patterns.

> "The de facto decompilers still have not fully leveraged the research outputs in this field to improve reverse engineering accuracy."

Second, on optimization:

> "De facto decompilers extensively simplify their outputs, even though readability and decompilation correctness are undermined simultaneously."

Highly simplified erroneous output was hard even for expert analysts to read, indicating a mismatch between the literature's readability goals and actual behavior. The authors urge developers to embrace research products and to make optimization passes **configurable**, as compilers do.

## 6. Discussion

**Limitations / threats to validity**: *construct validity* — dynamic testing and manual inspection cannot guarantee full functional correctness (an assumption shared by prior reverse-engineering testing work); a defect not reflected in the checksum could be missed, mitigated in future by static whole-program comparison. *External validity* — the framework is language- and platform-independent by design, so it should generalize beyond the current x86/C scope. **Cross comparison**: decompiling the same 500 executables with all four tools and measuring moss similarity gives an average cross-similarity of only **0.68**, since each decompiler uses its own tactics and templates; this argues for more consistent representations. **Other settings**: bytecode decompilation (e.g., Android) is easier and higher-quality, while non-trivial C++ (recovering class hierarchies) remains open; generalizing the methodology to these is left as future work. The authors also stress developers' responsibility to embrace semantics-preserving reverse engineering so output becomes recompilable "in the first place," and the need for principled techniques to *verify* decompilation correctness.

## 7. Related Work

Prior testing of static reverse-engineering tools includes differential testing of disassemblers (N-version disassembly) and symbolic-equivalence checks to find bugs in IR lifters, plus empirical studies of disassembler accuracy. For dynamic tools, "red pill" testing and differential/random testing compare VM vs. physical execution or high- vs. low-confidence emulators. A thorough, complete testing of *decompilers*, however, remained the missing piece, which this work fills given decompilation's indispensable role in cybersecurity and software reuse.

## 8. Conclusion

The systematic study of four popular commercial and free C decompilers found considerable flaws and produced concrete, developer-facing lessons. Modern C decompilers have progressively improved and generate quality output more than the pessimistic academic stance assumes, but classic challenges — chiefly **type recovery** and **optimization** — still frequently prevent well-formed output. The work offers guidance for researchers and industry practitioners who use and improve C decompilers and is presumably adaptable to other decompilation settings.

To recover C-style control structures, modern decompilers implement a set of structure templates and search to determine whether
an IR code region matches the predefined patterns. Some advanced
techniques enable an iterative refinement to polish the recovered
structure. To date, techniques have been designed to guarantee
the structure recovery correctness and also to improve readability [17, 67]. In addition, modern decompilers usually design optimizations to polish the lifted IR code, including dead code elimination and untiling [17, 21, 38]. Also, reverse engineering of C
executable files might encounter łchicken and eggž problems (e.g.,
data flow analysis relies on precise output of control flow analysis,
and vice versa). Indeed, modules within the middle stage can be

3.1

C decompilers are one of the most critical reverse engineering
tools that enable various cybersecurity and software re-engineering
missions. To date, reusing decompiled x86 and ARM binary code has
been a widespread practice, and industry hackers have successfully
decompiled and reused complex real-world legacy software, such
as video games [1, 3] and complex firmware [4].
In contrast, while decompilers are also extensively used in academia
(searching a popular decompiler, łIDA Prož, in Google Scholar returns 1,370 records since 2015), reusing decompiled C code is not a
common approach. Overall, the major application scope of C decompilers in academia includes code comprehension (e.g., similarity
analysis) [18, 25, 26], code reuse [27, 37], and various security hardening and vulnerability detection applications [22, 32, 35, 37, 63].
However, our observation is that instead of directly taking finalstage decompiled outputs, intermediate information or representations are usually extracted and leveraged in the conducted research.
For instance, instead of directly reusing the decompiled C programs,
binary code reuse tasks would be launched with executable patching or replication after reflecting the code layouts and fragments
with decompilers [27]. Note that binary patching and replication
are usually error-prone and incur a very high cost.
We attribute this conservative and potentially mismatched usage
of decompilers to the generally pessimistic views of the decompiled
programs: it is traditionally believed that the recovered C code
cannot be used for recompilation (unlike conventional C code).
Nevertheless, within recent years, promising lines of research have
proposed fool-proof techniques for binary disassembling and decompilation [17, 31, 64ś67]. As a result, functionality-preserving
disassembling of non-obfuscated and not-highly-optimized binary
code becomes practical, and it could be accurate to assume recovering functionality-preserving C code becomes a matter of engineering effort, although a certain amount of readability of the generated
code is sacrificed, e.g., due to the usage of inline assembly or springboard [29, 31]. Indeed, some popular binary analysis frameworks
have implemented the proposed techniques [55]: the decompiled
output can be smoothly recompiled into an executable that preserves the original semantics [28]. Overall, existing research has
shown a practical need to advocate the functionality-preserving łrecompilabilityž as a critical design goal of C decompilers. Given the
encouraging development of functionality-preserving reverse engineering, we see this as the perfect time to launch systematic testing
of C decompilers, as a means to demystify their full capability.

2.2

Equivalence Modulo Inputs (EMI) Testing

We briefly introduce a well-established testing technique that has
achieved prominent success in testing compilers, the Equivalence
Modulo Inputs (EMI) testing [40]. Soon, we will show that EMI
testing can be used to test decompilers in a highly effective manner.
Given a program p and its legitimate input space as dom(p), the
output of p for an input i ∈ dom(p) is denoted as [[p]](i). Therefore,
two programs p and q are defined as equivalent modulo inputs (EMI)
in case ∀i ∈ I [[p]](i) = [[q]](i) where I ⊆ dom(p) ∩ dom(q). Here, q is
referred as the EMI variants of p. The main benefit of EMI testing
is the functionality-preservation of q w.r.t. inputs i ∈ I ; therefore,
this method does not require a reference implementation and it
provides an explicit testing oracle such that any EMI variants q must
behave identically compared with p. The EMI equivalent property
alleviates the notion of łprogram equivalence.ž It consequently
provides a viable way to produce programs for testing compilers.
To extend the above formulation in testing decompilers, we start by
generating q, which is a mutated program of p (mutation strategies
are introduced in the next paragraph). Then, we decompile the
executable file compiled from q and generate the decompiled source
code q ∗ . Obviously, q ∗ is an EMI variant of p and we use the above
oracle for testing.
The first EMI implementation [40] generates a mutated program
q by profiling p with inputs i ∈ I and deleting or inserting additional
statements within uncovered code blocks w.r.t. to any input i ∈ I .
Since any modified code region in q is not executed w.r.t. I , q is
naturally an EMI variant of p. Some improvements insert code
into the live code region; the inserted code is guarded by opaque
predicates that are always evaluated as false during runtime [60].
Some statistical methods are also adopted to optimize the selection
of statements for mutations [41]. We employ all three EMI mutation
strategies in our new setting (see Sec. 4.1).

As mentioned above, in this research, we reuse a well-developed
compiler testing technique named EMI testing [19, 40, 60]. Recall
during decompilation (Sec. 2.1), modern decompilers perform data
flow and control flow analyses and transformations, which are
conceptually comparable to compiler passes. Therefore, we envision
that the full-scale mutations enabled by the EMI technique can
adequately expose decompiler defects. Our study confirms this
intuition: EMI testing is highly effective in this new setting (for
details, see our findings in Sec. 5).

deviant outputs of two given programs. In particular, IsDeviant

respectively; then, it decompiles eq into another piece of program q ′

Manual Inspection

As mentioned above, Csmith-generated C code computes a checksum of its global variables as the execution output. Once a deviant
output is identified, we manually pinpoint erroneous statements
causing such deviants in the decompiled C code. The manual inspection forms a typical debugging process: starting from a global
variable that yields a deviant value, we identify all of its assignments
and recursively backtrack the deviant values used for assignments
until we identify the root cause (i.e., the erroneous statements) in
the decompiled EMI variants.
This step is costly: examining and checking all suspicious findings took two reverse engineering analysts about 180 man-hours.
Each analyst has an in-depth knowledge of reverse engineering and
rich experience in binary code analysis and CTF competitions. In
this way, we ensure the accuracy of our study and the credibility of
our findings to a great extent. We have reported our findings to the
developers, and some typical cases have been promptly confirmed
and to be fixed (see Sec. 5). Moreover, with about 350 man-hours,
we locate 13 buggy code fragments in open-source decompilers
that lead to erroneous statements in the decompiled C code (see

5.2.3 Result Implication. Our study on full-scale recompilation

both commercial decompilers have less than 5.0% recompilation

further indicates the possibility to safely remove some of them since
the linker will need to create these symbols in the ELF executable

failures, our root cause analysis shows that these errors are due to
only two bugs in the function parameter recovery module, which
shall be fixed together smoothly.

5.3.1 Type Recovery. The lack of fool-proof type recovery is one
key limit of existing decompilers. While for C code, not all the
type recovery failure breaks the semantics, in this study we flag a
considerable amount of recovered variable types breaking semantics
(in terms of both control and data flow). Consider an example below:
// source code
int i = 0;
for ( i =6; i < -12; i -=6) {
... // not reachable

5.3.3 Control-Flow Recovery. We find a total of 52 deviant outputs
due to control-flow errors in the decompiled C code. We note that
after taking a close look at the buggy code fragments, all failures in
RetDec and Radare2/Ghidra are actually due to wrong type recovery
and optimization bugs. Consider a simplified input program below:

// decompiled code
unsigned int i = 0;
for ( i =6; i < -12; i -=6) {
... // reachable
}

where the Csmith-generated C code has a for loop, but will execute
for zero iterations. Contrarily, the type recovery incorrectly annotates i with unsigned int in the decompiled C code, and the loop
body becomes reachable in the decompiled output. In other words,
the type recovery alters the control flow, and further changes the
semantics.
We also find a considerable amount of type recovery failure that
leads to an erroneous data flow. Consider a case below found:
// source code
int32_t a = 0 xaaffff ;

// condition generated by EMI
if ( opaque_condition ) { // evaluated to false
statement1 ; // not reachable
}

where the opaque_condition will be evaluated to false during
runtime. However, we report that the if condition was optimized
out in the decompiled program since the condition is incorrectly
evaluated to łtruež due to type recovery or optimization errors.
Hence, the unreachable branch becomes reachable, reflecting a
łcontrol-structurež error in the decompiled C code. We report that
Bug3−4 found in RetDec and Bug9−13 in Radare2/Ghidra all lead to
such issues, although they represent different buggy code fragments
in the type recovery and optimization modules.
We also find issues where the statements are mistakenly reordered in IDA-Pro outputs. Consider the case below:

// decompiled code
int16_t a = 0 xaaffff ;

In the decompiled output, the variable type int32_t is incorrectly recovered as int16_t. As a result, a is initialized with a
different value, since a variable of int16_t type can only take the
lowest 16 bits (0xffff).
As reported in Table 4, 315 type errors in C code decompiled
by RetDec root from two bugs (Bug1 and Bug4 ). Bug1 happens by
converting signed mov statements (movsx) in x86 assembly into IR
statements without correctly considering extensions and truncations. Bug4 missed certain function call parameters when analyzing
the call site stack push operations. Bug8 , Bug11 , and Bug13 cause in
total 35 type errors in Radare2/Ghidra. Bug8 cannot precisely infer
the łlengthž of stack variables, while Bug11 performs constant propagation optimization and uses a ghost variable defined in Ghidra of
wrong type to replace original variables. As aforementioned, Bug13
lifts unsigned shift in IR into signed shift in C code.

5.3.4 Optimization. Academic researchers design decompiler optimizations to make decompiled code close to the input source code
and thus more łreadablež [17, 67]. However, optimizations, particularly the erroneous constant folding and constant propagation, can
make decompiled C code mal-functional. As aforementioned, from
the 13 bugs reported in Table 4, six are within the optimization
modules of decompilers, for instance performing constant folding
without correctly taking bit length into account (Bug5 ), or incorrectly using a 32-bit ghost variable defined in Ghidra to replace a
16-bit variable during constant propagation (Bug11 ).

Finding: De facto decompilers extensively simplify
their outputs, even though readability and decompilation correctness are undermined simultaneously.
We encountered major difficulty when manually inspecting erroneous outputs that are highly simplified. We suspect that if it
was not even presentable for us Ð reverse engineering analysts
Ð to comprehend the decompiled outputs, it should be accurate
to assume the outputs are often not readable enough for layman
users. This clearly indicates a mismatch between expectations in
the literature and the actual capabilities of modern decompilers.
Note that in academia, the optimization module of decompilers is
designed following the principle of enhancing the readability and
making it close to the original C code [17, 67].
Although optimization can help to simplify code emitted by
decompilation passes and can usually output one succinct highlevel statement by folding several statements, we advocate finegrained calibration. Currently, modern decompilers seem to go
too far and notably hurt readability of their outputs. Meanwhile,
motivated by how compiler optimizations are provided for usage,
we urge decompiler developers to make their products configurable

Result Implication

In this section, we present discussion and result implication to
answer research question RQ3: what insights can we deduce from
analyzing the decompilation defects?

6
Support of Cutting-Edge Research Outputs. We have found
plenty of type, variable, and control structure errors in the decompiled C code, and explained their corresponding buggy fragments
in the decompilers. Although academic researchers are believed to
have mostly addressed such reverse engineering challenges (since
we are evaluating non-trivial but not extreme cases), one observation is that modern decompilers have not fully implemented
those well-established research products. For instance, while the
state-of-the-art research has been working on function prototype
recovery for years and achieved promising results (e.g., close to
99% accuracy for function recognition in x86 binaries [14, 20, 58]),
still, the de facto decompilers (e.g., RetDec) have not implemented
the proposed methods and therefore make lots of errors in recovering function prototypes and parameters. Also, recovering
types from x86 binary code have been formulated as a recursivelyconstrained type inference approach with sub-typing, recursive
types, and polymorphism [42, 49]. Contrarily, C decompilers, from
the disclosed documents and our observation, only implement simple inference techniques combined with heuristics and predefined
patterns [33, 38, 53].
Finding: The de facto decompilers still have not fully
leveraged the research outputs in this field to improve
reverse engineering accuracy.
Although research products cannot be used to address every corner case, most defects exposed in this study, such as RetDec’s obvious limit in recovering function prototypes, shall be fixed smoothly.

DISCUSSION

Limitations and Threat to Validity. We now give a discussion of
validity and shortcomings of this paper’s approach. In this research,
construct validity denotes the degree to which our metrics actually reflect the correctness of C decompilers. Overall, we conduct
dynamic testing and manual inspection to study the outputs of
de facto decompilers. Hence, while this practical approach detects
decompiler bugs and reveals inspiring findings, the most possible
threat is that our testing approach cannot guarantee the functional
correctness of decompilers. We clarify that our work roots the same
assumption as previous works in this line of research that aim to
comprehend the functionality of reverse engineering toolchains
with dynamic testing rather than static verification [36, 51].
We check the correctness of decompiled C code by comparing its
execution output with its reference input program. Considering the
execution output of each Csmith generated program is a checksum
of all its global variables, decompilation errors on global data or
its involved computations can be faithfully exposed. However, a
possible threat is that defects can be neglected in the decompiled
C code, in case they do not contribute to the execution output.
One promising mitigation is to enable a static viewpoint of the
decompiled output. Instead of executing the decompiled code, we
envision opportunities to perform whole-program comparison and
pinpoint inconsistency. We leave exploring this direction for future
work.
Besides, there exists the potential threat that the proposed decompiler testing framework may not adapt to other types of programs,

Decompiling bytecode (e.g., Android apps) is easier, and the quality of decompiled code is generally deemed as higher. Indeed, the

In contrast, decompiling non-trivial C++ code, for instance recovering its class hierarchy, is still an open problem [56]. We leave it
as one further work, to generalize methodologies proposed in this
work on studying other popular decompilation settings.

Decompiler Developers’ Responsibility. We consider that developers should take the responsibility to constructively address the
findings in this research. Our work serves as the first and systematic
effort to provide guidelines. In Sec. 5.5, our findings have shown
that modern decompilers still have not leveraged the full potential
of research outputs. Our research sheds light on where developers can start to enhance their products, e.g., avoiding extensively
simplifying the decompiled C code (see Sec. 5.3.4).
Looking ahead, we also advocate decompiler developers to embrace breakthroughs of łsemantics-preservingž reverse engineering [17, 31, 47, 64, 65]. Therefore, decompiled outputs could become
fool-proof łrecompilablež in the first place. We also envision the
need to deliver more principled techniques to verify the functional
correctness of decompilation. Meeting this need will have a prominent, long-term impact in the reverse engineering community.

RELATED WORK

Testing techniques have been used to measure static reverse engineering tools. For instance, differential testing has been used to
validate disassemblers [51]. Recent research uses symbolic equivalence checks (with symbolic execution and constraint solving) to
pinpoint bugs in IR lifters of binary executables [24, 36]. The security community has also conducted remarkable empirical studies
regarding the accuracy and usage scenarios of de facto disassemblers [11].
State-of-the-art dynamic reverse engineering activities mostly use
symbolic execution techniques and virtual machine (VM)-based
monitoring to capture abnormal and malicious behaviors of suspicious binary code. Existing research has proposed various testing
techniques to examine the security and reliability of these dynamic
reverse engineering tools. Red pill testing [44, 45, 57] leverages the
random or differential testing (typically with a black-box setting)
to compare the behavior of a VM and that of a physical machine
when executing with the same input. Recent research has promoted
the testing of a low-confidential emulator with inputs generated
by analyzing a highly confidential emulator [43].
Existing research has laid a solid foundation on testing static
and dynamic reverse engineering tools. However, a thorough and
complete testing of decompilers is still the missing piece in the
understanding of today’s reverse engineering landscape. There is a
demanding need to gain insights into how much of a problem decompilation is, given its indispensable role in building cybersecurity
and software reuse applications.

CONCLUSION

We have performed a systematic study to investigate decompilation
correctness of modern C code decompilers. Our large-scale evaluation on four popular commercial and free decompilers successfully
found considerable decompiler flaws. In addition, we elaborately
explained findings and summarized lessons we have learned from
this study. We show that modern C decompilers have been progressively improved to generate quality outputs. Nevertheless, some
classic reverse engineering challenges, including type recovery and
optimization, still frequently impede modern decompilers from generating well-formed outputs. This work could provide guides for
researchers and industry hackers that aim to use and improve C decompilers, and is presumably adaptable to test other decompilation
settings.

The average cross similarity score is indeed low (on average 0.68),
which sheds light on practical needs to advocate more consistent
representations and regulations. Overall, we leave it as one future
work to explore practical methods to perform cross comparison,
for instance by extracting certain łsemantics-levelž invariants.
Other Settings. The main focus of this study is C decompilation,
one challenging and fundamental task commonly encountered in
real-world cybersecurity and software re-engineering missions.
While the current experiments is conducted on x86 platforms, given
popular decompilers like IDA-Pro and RetDec can handle different
processors and formats (e.g., ARM and NIPS), we envision opportunities for the research community to generalize our findings, since
the key issues, including both recompilation and decompilation
defects, are mostly platform and language independent.
