**BIOS** (Basic Input/Output System) is a system firmware, which is pre-installed on the computer's motherboard, that performs the hardware initialization during the booting process, and loads the [Bootloader](https://wiki.osdev.org/Bootloader "Bootloader"), offering generalized low-level services to the PC system programmers. During the DOS era, the operating systems used BIOS services as the standard interface to interact with keyboard, display, disks, and other I/O devices. The more modern operating systems typically only use BIOS to load the kernel, which then uses its own device drivers, instead of the ones of the BIOS.

These BIOS services are often named "BIOS functions". In [Real Mode](https://wiki.osdev.org/Real_Mode "Real Mode"), they can be easily accessed through [software interrupts](https://wiki.osdev.org/index.php?title=Software_interrupts&action=edit&redlink=1 "Software interrupts (page does not exist)"), using [assembly](https://wiki.osdev.org/Assembly "Assembly") language.

The original BIOS firmware was proprietary to the IBM PC, and had to be reverse-engineered by the other manufacturers, becoming a de facto standard, and was then standardized around mid-1990s. As the result, many BIOSes (especially in the earlier hardware, and even the older versions of firmware used in x86 emulators and VMs) contain quirks, requiring the bootloaders to have many workarounds to be bootable on all the systems. This, among with the clunky BIOS interface and other problems, is the reason for the [Real Mode OS Warning](https://wiki.osdev.org/Real_Mode_OS_Warning "Real Mode OS Warning") and the usual recommendation to start with an existing [Bootloader](https://wiki.osdev.org/Bootloader "Bootloader") (which doesn't in any way stop the OS developer with writing their own later on) when starting out with the OSDev.

The BIOS has now been replaced with [UEFI](https://wiki.osdev.org/UEFI "UEFI"), which is universally available on x86 starting with late 2000s/early 2010s hardware (since it is required by Microsoft to have Windows 8 and newer pre-installed). Compared to BIOS, UEFI provides more functionality/has fewer limitations, has a more convenient interface, offers better security, and provides faster start-up times. On some earlier (class 1-2) UEFI machines, the BIOS operating systems might still be loaded through CSM (Compatibility Support Module). However, a lot of newer (UEFI class 3) hardware (notably, produced in the 2020s) has started to drop the compatibility support, and only allow booting natively with UEFI.

## BIOS functions

To access a BIOS function, you generally set the AH [CPU register](https://wiki.osdev.org/CPU_Registers_x86 "CPU Registers x86") (or AX, or EAX for some functions) to a particular value, and then do an INT opcode. The value in AH (or AX, or EAX), combined with the particular interrupt number selected requests a specific BIOS function. (Other CPU registers hold any "arguments" to the function, and often the return values from the function, also.)

It is simplest to create a listing of BIOS functions by specifying the interrupt number, and the value of AH (or AX, or EAX) that selects the function. It is also easiest to refer to particular BIOS functions this way in discussions. For example, INT 0x13, AH=0 is a BIOS function that resets hard disks or floppy disks.

Note: the INT and AH values are always listed in hexadecimal notation. Accidentally using a decimal value in an INT opcode is a very common source of errors when using BIOS functions.

To an extent, the BIOS functions are organized by interrupt number:

- INT 0x10 = video display functions (including [VESA/VBE](https://wiki.osdev.org/VESA "VESA"))
- INT 0x13 = mass storage (disk, floppy, CDROM) access
- INT 0x14 = [serial port](https://wiki.osdev.org/Serial_Ports "Serial Ports") functions
- INT 0x15 = memory size, miscellaneous system functions
- INT 0x16 = keyboard functions
- INT 0x17 = [parallel port](https://wiki.osdev.org/Parallel_port "Parallel port") functions
- INT 0x1A = [RTC](https://wiki.osdev.org/RTC "RTC"), [PCI](https://wiki.osdev.org/PCI "PCI"), ...

The exhaustive list of BIOS functions is available from [RBIL](https://wiki.osdev.org/RBIL "RBIL").

Unfortunately, the PC industry has never been good about maintaining standards. So each PC manufacturer and each BIOS manufacturer randomly made up new BIOS functions. It is also possible to "hook" any of these interrupts, and insert extra functions that mimic BIOS functions. Early PC hardware and software manufacturers did this often. So there ended up being literally thousands of BIOS functions (or mimics). The RBIL list is enormous, and is mostly filled with functions that only work when combined with some completely obsolete computer, BIOS, or piece of hardware or software.

### Common functions

Unfortunately, the [RBIL](https://wiki.osdev.org/RBIL "RBIL") does not clearly indicate which BIOS functions are "generic" (in some sense). That is, the ones that are always available, and that everyone uses. Partially this is because the "standard" BIOS functions grew over time, so if you go back far enough in time you can usually find a computer that does not support almost any specific BIOS function. But there is definitely a set that is commonly used in most current OSes.

### Assembly notes

Each BIOS function (as described in RBIL) has a specific set of "result" registers. Beyond those listed registers, the BIOS functions are supposed to perfectly preserve all the other register values. Early versions of [Bochs](https://wiki.osdev.org/Bochs "Bochs") (below 2.3) had a small problem with this. The lower halves of all the 32bit extended registers (ie. EBX, ECX) were preserved properly, but the upper words of some of the registers got trashed.

The BIOS functions themselves should never crash. On any error they will:

- almost always set the carry flag (test with JC),
- sometimes return "AH = 0x86 (unsupported function)",
- sometimes return "AH = 0x80 (invalid command)"
- or (for seriously buggy BIOSes) return with nothing changed.

Try to always test these error returns, because in many circumstances the BIOS functions might appear to be returning valid (but very wrong) data -- rather than an error code.

## BIOS in Protected Mode

Unfortunately, in [Protected mode](https://wiki.osdev.org/Protected_mode "Protected mode"), almost all BIOS functions become unavailable, and trying to call them nonetheless will result in exceptions or unreliable responses (because of the different way **segment** values are handled). Some newer services however (such as [SMBIOS](https://wiki.osdev.org/SMBIOS "SMBIOS"), [PCI](https://wiki.osdev.org/PCI "PCI"), [PnP](https://wiki.osdev.org/PnP "PnP"), or [VBE](https://wiki.osdev.org/VBE "VBE")) offer an interface that is compatible with 32-bit Protected Mode, known as [BIOS32](https://wiki.osdev.org/BIOS32 "BIOS32").

If you must use Real Mode BIOS functions after the CPU has been switched into Protected Mode, then see [Virtual 8086 Mode](https://wiki.osdev.org/Virtual_8086_Mode "Virtual 8086 Mode"), or perhaps exit Protected Mode, and momentarily return to [Real Mode](https://wiki.osdev.org/Real_Mode "Real Mode"). Both methods have caveats, therefore any calls to the BIOS should be done before any physical device is programmed by your code:

- BIOS calls may use interrupts, which means that you need to forward IRQs or map the PIC back to its original configuration.
- BIOS calls may access devices that you have already configured - notably the [PIT](https://wiki.osdev.org/PIT "PIT") and [PIC](https://wiki.osdev.org/PIC "PIC")
- BIOS calls can enter protected mode on their own to access MMIO registers, which is beyond the limits of virtual 8086 mode.
- In real mode, you have no way of managing interrupts and your drivers may get stuck for interrupts being lost.
- In real mode, you have no control over time, performance and security guarantees.

The only device that's mostly exempt from these problems is the Video BIOS, which is not generally bundled with your motherboard and therefore can't rely on BIOS services either. Most current OSes - commercial and hobbyist alike - use a v8086 monitor or emulator to support graphics devices without a native driver so many BIOSes have been tested against such a set-up.

## BIOS in Long Mode

Just like in [Protected Mode](https://wiki.osdev.org/Protected_Mode "Protected Mode"), BIOS functions are unavailable in [Long Mode](https://wiki.osdev.org/Long_Mode "Long Mode") too. Unfortunately there's no [Virtual 8086 Mode](https://wiki.osdev.org/Virtual_8086_Mode "Virtual 8086 Mode") to come to the rescue. It is necessary to momentarily switch to [Real Mode](https://wiki.osdev.org/Real_Mode "Real Mode"), or to emulate a CPU and interpret opcodes by software. All necessary information for the latter approach can be found in Intel and AMD documentation.

## Additional Information from the BIOS

Most of the useful information you get from the BIOS will come from calling BIOS functions. However, there is a small amount of additional information that can be acquired.

Some of the BIOS detection/state result is stored in the [BIOS Data Area](https://wiki.osdev.org/Memory_Map_(x86)#BIOS_Data_Area_.28BDA.29 "Memory Map (x86)").

Additional information is kept in the [CMOS](https://wiki.osdev.org/CMOS "CMOS") chip.

## Compatibility on Modern Machines

BIOS has been replaced by [UEFI](https://wiki.osdev.org/UEFI "UEFI") on modern x86 machines starting from the 2010s, whose UEFI firmwares keep supporting the "legacy" BIOS functions through an emulation layer, the CSM (Compatibility Support Module).
