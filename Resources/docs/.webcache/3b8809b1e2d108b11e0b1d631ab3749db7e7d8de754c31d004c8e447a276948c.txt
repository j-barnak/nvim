# SmartDec: Approaching C++ Decompilation

*Cited in the Decompilation Wiki: Applied Research Overview*

Alexander Fokin, Egor Derevenetc, Alexander Chernov, and Katerina Troshina. "SmartDec: Approaching C++ Decompilation." In *2011 18th Working Conference on Reverse Engineering (WCRE)*, pp. 347-356. IEEE, 2011. DOI: 10.1109/WCRE.2011.49.

## Abstract

Decompilation reconstructs a program in a high-level language from a low-level one, and its typical uses are software security assessment, malware analysis, error correction, and reverse engineering for interoperability. The paper observes that native-code decompilation has traditionally been studied only for C, and that C++ raises new problems because "the rules of translation from C++ to assembly language are far more complex than those of C." The authors present methods for partial recovery of C++ specific constructs from low-level code produced by a C++ compiler, describing the challenges (reconstructing polymorphic classes, class hierarchies, member functions, and exception handling) and an approach to overcome them. They introduce SmartDec, a native-code-to-C++ decompiler developed at Select LTD that reconstructs expressions, function arguments, local and global variables, integral and composite types, loops, compound conditionals, C++ class hierarchies, and exception handling constructs, and they provide an empirical study of it. Keywords: C++, Decompilation, Reverse Engineering, Class Hierarchy Reconstruction, Exception Reconstruction.

## I. Introduction

The authors motivate decompilation by the common need to audit third-party components shipped without source, and to fix, optimize, or adapt legacy software with no available source. Correct decompilation must yield source that, when compiled, produces an executable with the same behavior as the original, though the output "won't be textually equivalent to the original source code, and is likely to be less comprehensible to a human."

Decompilation research has concentrated on C, where existing methods work well and several commercial tools exist (Hex-Rays, Boomerang, REC), but these "generally do not perform well for C++ programs." Because much modern software is written in C++ using complex class hierarchies and exceptions (they cite C++ exceptions used for error reporting in the kernel of the MongoDB database), reconstructing C++ specific constructs is important. Decompiling C++ into C produces undesirable artifacts such as unrelated compound types and unions in place of an inheritance hierarchy.

The paper targets the C++ ABIs of Microsoft Visual Studio (Windows) and GNU C++ (Linux), using MSVC 10.0 and g++ 4.5.0 for the empirical study, though SmartDec also works with other compiler versions sharing the same ABI. The remaining sections cover related work (II), challenges and solutions (III), the SmartDec architecture (IV), experimental results (V), and conclusions (VI).

## II. Related Work

The authors state that no existing decompiler is capable of reconstructing C++ code, though the latest Rec Studio has some C++ support (mangled names, class inheritance). They review prior efforts:

- **Skochinsky** gave detailed descriptions of RTTI (run-time type information) and exception-handling structures used by MSVC, plus tools for reconstructing polymorphic class hierarchies and exception handling, but these are based on pattern matching, do not always give correct results, and are MSVC-only.
- **Sabanal and Yason** proposed an RTTI-based approach plus a technique using vtable (virtual function table) and constructor analysis that works even without RTTI. Constructors are identified by finding `operator new` calls followed by a function call, vtable analysis identifies polymorphic classes, and class relationships are inferred from constructors. Their techniques do not consider failure cases such as `operator new` overloading, constructor inlining, and optimization-driven elimination of vtable references, and they rely heavily on the MSVC-specific `thiscall` convention.
- Reference [8] (the authors' own prior work) proposed automatic class-hierarchy reconstruction that does not rely on RTTI and performs well under aggressive optimization.

## III. Challenges of C++ Decompilation

C++ adds polymorphic classes and hierarchies, virtual and non-virtual member functions, and exceptions with handling. When decompiling C++, C-oriented tools decompile catch blocks as unreferenced functions, fail to recognize virtual calls, and do not reconstruct classes. The authors list the constructs that quality C++ decompilation must recover: virtual functions, classes, class hierarchies (inheritance relations), constructors and destructors, types of pointers to polymorphic classes, non-virtual member functions, layout and types of class members, calls to virtual functions, and exception raising and handling statements.

### A. Virtual functions

A virtual function is one "with behaviour that can be overridden within an inheriting class by a function with the same signature." The standard does not mandate the dispatch mechanism, but GCC and MSVC ABIs implement it with vtables (arrays of pointers to virtual functions), so identifying virtual functions reduces to locating all vtables. SmartDec locates vtables by scanning the data segment and checking each location as described in reference [8].

### B. Classes and class hierarchies

Two approaches are implemented. The first uses RTTI: the compiler emits an RTTI structure per polymorphic class containing parent information, and examining all such structures reconstructs the complete hierarchy. Since a pointer to a class's RTTI structure always precedes its vtable in both ABIs, finding RTTI reduces to locating vtables; once the ABI-defined layout is known, RTTI can be parsed to recover the exact hierarchy and (from mangled names) class names. However, RTTI is often disabled (it increases binary size and imposes runtime overhead) in code-size-critical and embedded applications, and frameworks such as Qt and LLVM replace it with hand-rolled solutions. When RTTI is absent, a second approach based on analysis of vtables, constructors, and destructors (reference [8]) is used. Both approaches are implemented in SmartDec.

### C. Constructors and destructors

SmartDec detects constructors and destructors for polymorphic classes only, since those of non-polymorphic classes are indistinguishable from ordinary member functions (a direction for future work). They are detected by the operations they perform. A constructor (1) calls constructors of direct base classes, (2) calls constructors of data members, then (3) initializes vtable pointer field(s) and runs body initialization. A destructor reverses this order: (1) initializes vtable pointer field(s) and runs body destruction, (2) calls destructors of data members, then (3) calls destructors of direct bases. Interprocedural data-flow analysis detects consecutive vtable pointer initializations, locating constructors and destructors and even detecting inlined ones. A key heuristic distinguishes the two: in a constructor the vtable pointer field is overwritten in a base-to-derived order and initialized after the base-class constructor call, whereas in a destructor it is overwritten derived-to-base and initialized before the base-class destructor call.

### D. Class pointers

A single class pointer may take several values across contexts (multiple assignments, a function called from many sites with different classes from one hierarchy, or multiple exit points returning different classes). A reconstructed pointer type must be compatible with all assigned values (a superclass of all of them, or a generic `void*`). This is solved with a lattice model. A type lattice (C, ⊑) is built where C consists of pointers to all recovered class types, the `void*` pointer, and a special unknown pointer type. The partial order ⊑ is defined by inheritance, adding "A ⊑ void*" for roots of the hierarchy and "unknown ⊑ A" for leaves (illustrated with a Hasse diagram in UML notation). A pointer's type starts as unknown; on each assignment it is set to the least common ancestor of its current type and the assigned value's type. Constructors identified earlier return known class types, and this information is propagated iteratively through assignments and function calls.

### E. Member functions

For non-virtual functions, one wants to know whether a function is a member and which class it belongs to. Under the GCC ABI, member functions are indistinguishable from free-standing functions with a `this` pointer as the first parameter, so reliable reconstruction is generally impossible and must be done manually. MSVC by default uses the `thiscall` convention, passing `this` in ECX, so member functions can be reliably distinguished and the owning class determined from the type of the `this` parameter.

### F. Composite types

Standard type-reconstruction algorithms assume copies of the same pointer always reference the same type, an assumption broken in C++ because a pointer may point to objects of different classes in one hierarchy. This causes composite type reconstruction to merge base-class field information with subclass fields, producing type clashes. SmartDec solves this using reconstructed class-pointer information: it examines all accesses to class fields (memory at constant offsets from an object pointer), and for each access sums the constant offset and the accessed location's size, taking the maximum of these sums per class as an underapproximation of the class size. A modified version of the type reconstruction algorithm from reference [19] avoids merging information about fields lying outside the approximated object size, preventing type clashes.

### G. Virtual function calls

Completing virtual-function reconstruction requires reconstructing the calls too. Optimizations may devirtualize or inline virtual calls; when not, a virtual call compiles to a sequence that extracts a function pointer from the vtable and performs an indirect call (an MSVC example loads the vtable pointer, then the function pointer at an offset, pushes the argument, sets `this` in ECX, and calls). Virtual calls are reconstructed after variable types are recovered: once the object pointer's type is known, pattern matching detects the call. Each detected call can supply additional parameter-type information, so type analysis is rerun for the affected virtual functions.

### H. Exception handling

Exception handling changes normal control flow and is used for uniform error reporting. The standard defines the semantics but leaves implementation to vendors. The authors consider two schemes. MSVC's continuously updates exception-handling structures to reflect program state, adding an element to the stack frame that records available handlers, which the runtime uses to locate and execute the appropriate handler when an exception is thrown. GCC's is table-driven with no runtime overhead when exceptions are unused: statically allocated tables relate program-counter ranges to program state, and on a throw the runtime looks up the current PC to determine which handlers to check.

Exception handling involves low-level manipulations that do not translate well into C, and many control-flow analyses ignore it, causing catch blocks to be isolated into separate functions. Proper reconstruction therefore requires intervention at several stages and cannot be a post-processing fix. In SmartDec, exception-handling structures are located and parsed after the control flow graph is built, and special-kind edges are inserted connecting catch blocks to their owning functions, preventing isolation; this edge-kind information later guides catch-block reconstruction. Because destructors for non-polymorphic classes are frequently inlined, SmartDec cannot yet fully recover them, so destructor code is currently emitted as comments to be integrated manually.

Because implementations differ, there is no universal way to reconstruct try blocks and throw statements; the authors describe the GCC case. **Exception handling in GCC** uses the Dwarf2 table-based unwinding mechanism by default on x86/x64. Each function has a set of call sites (code that can throw, e.g. function calls or throws), each associated with a landing pad (a code block that calls destructors and transfers to the catch block). For each call site a call-site record is emitted containing the call-site displacement in the function, the call-site length, the address of the landing pad, and a pointer to a list of action records; each action record holds an index into the type-info pointer table, and the list describes exception types handled by the landing pad. To recover exception handling, catch blocks, try blocks, and throw statements must be reconstructed. Each catch block is referenced from its landing pad and runs from a call to `__cxa_begin_catch` to a call to `__cxa_end_catch`, so it can be reconstructed by examining the landing pad and the locations it references. Because different destructors must run for throws from different call sites, the compiler generates several landing pads per try block, but the dispatch portion is shared; call sites belonging to the same try block are identified when their landing pads share the same dispatch block, and the try block extent is the union of its call sites' extents. Throw statements are reconstructed by locating calls to `__cxa_throw` (which takes the exception pointer, a `type_info*`, and a destructor pointer) and finding its parameter values.

## IV. Decompiler Architecture

SmartDec is an experimental tool that transforms assembly into high-level C or C++, following a pipeline model. The phases are: (1) parse the input assembly listing; (2) build the control flow graph and isolate functions; (3) parse statically allocated exception-handling structures and fix the CFG; (4) transform assembly into a platform-independent representation; (5) reconstruct classes and hierarchies; (6) analyze functions via (a) joint reaching-definitions and constant-propagation analysis, (b) liveness analysis and dead-code elimination, (c) reconstruction of local variables, arguments, and return values, (d) data-type reconstruction, and (e) structural analysis; and (7) high-level program generation, optimization, and output.

**A. Parsing.** A separate disassembler must supply the assembly listing. SmartDec parses GNU objdump and Microsoft dumpbin output and integrates with IDA Pro, importing from its internal structures. It creates a platform-dependent instruction sequence and an image object exposing binary sections.

**B. Isolation of functions.** A CFG-based algorithm divides instructions into basic blocks (boundaries at jump/call destinations and instructions following jumps or empty memory), adds edges per control transfers, and discovers functions as connected components of the undirected CFG.

**C. Intermediate representation.** Functions are translated into an IR called **Formulae**, whose statements are commands for a virtual machine that partially simulates the input program. The VM's memory model is a set of independent, integer-identified address spaces with bit addressing, letting registers, stack offsets, and global addresses be tracked uniformly. Statements take expression-tree arguments whose nodes are called **terms** (integer constants, memory-location access, dereference, unary and binary arithmetic operators). Statement types are Assignment, Kill (forget prior assignments to a location), Jump, Conditional jump, Call, and Return.

**D. Dataflow analysis.** A joint reaching-definition and constant-propagation analysis builds the most complete set of reaching definitions per term, each analysis feeding the other, iterating to a fixed point.

**E. Liveness analysis and dead code elimination.** Liveness finds terms participating in useful calculations (those that can affect program input, output, or control flow) by propagating usefulness through Formulae; non-useful code is then eliminated. In the authors' experience this "reduces the number of terms in a program almost twofold" for x86 programs, speeding later analyses.

**F. Type reconstruction.** A set of attributes per term is deduced iteratively to a fixed point and used to generate type declarations. Attributes: `size` (bits), `integer`, `float`, `pointer`, `pointee` (dereference type), `signed`, `unsigned`, `factor` (minimal increment/decrement, used for arrays), and `offsets` (map from offset to field type, used for composite types). Basic inference follows references [18] and [26]; composite types follow reference [19].

**G. Structural analysis.** A variant (reference [27]) of structural analysis reconstructs high-level control statements. It operates on CFGs whose nodes are regions (a basic block or a subgraph with at most one entry node). Region types include cyclic regions (generic loop, while, do-while), conditionals (if-then, if-then-else, compound condition), block regions, and unknown regions. Analysis proceeds by pattern matching: when a subgraph matches a region type, a new region is created and the subgraph's nodes and edges are folded into it (duplicate edges removed). Compound conditions are reduced first to correctly identify loop types and avoid reconstructing them as nested `if` statements. Then cyclic regions are reduced (removing break/continue edges to recover those statements, recursing into new cyclic regions), then block statements, then if-then and if-then-else regions. The fully reduced graph drives code generation, with control conveyed via C statements plus explicit `break`, `continue`, and `goto` (computed gotos become `goto` with expression arguments).

## V. Implementation and Experimental Results

SmartDec was tested on a variety of open-source C++ software and hand-crafted tests. Because SmartDec cannot yet produce directly compilable code, output could not be verified by recompilation and had to be checked manually; the paper shows a decompiled example (a `BinaryFunction` hierarchy with `GCD` and `Pow` subclasses) whose recovered C++ preserves the class hierarchy and virtual methods.

**Exception handling.** Reconstruction was verified manually across tests from notepad++ (Parameters.cpp: 1 try, 1 catch, 4 throw), shareaza (Security.cpp: 5/5/0 and DownloadGroups.cpp: 3/3/0), mongodb (database.cpp: 3/3/3), and a hand-crafted test (2/3/2). In all tests, "all exception handling constructs present in source file were reconstructed correctly. No spurious constructs were recovered."

**Class hierarchy.** Correctness was measured automatically: the program is compiled with optimizations and RTTI enabled and the RTTI-aware algorithm (which "always provides correct results," per reference [8]) collects the true hierarchy; the program is recompiled with optimizations but without RTTI and the non-RTTI algorithm is applied; debug information restores the correspondence and the two hierarchies are compared. For all analyzed applications every vtable in the assembly was found. Two categories are not treated as mismatches because they do not change program semantics: classes overriding no base virtual functions (whose vtables may be optimized away) and classes with no data members and no constructor/destructor actions (whose hierarchies can be freely rearranged). The results (Table II):

| Application | mysqld | shareaza | notepad++ | doxygen |
|---|---|---|---|---|
| Vtables found | 950 | 1128 | 95 | 415 |
| Non-vtables | 0.2% | 0% | 0% | 0% |
| Vtable mismatches | 3.1% | 2.8% | 4.0% | 4.8% |
| Classes found | 918 | 1101 | 95 | 397 |
| Class mismatches | 5.5% | 5.0% | 10.5% | 6.3% |

"Non-vtables" are reconstructed vtables absent from the source (e.g. static arrays of function pointers used like vtables). "Vtable mismatches" are vtables whose reconstructed parent differs from the real one, most caused by the parent vtable residing in a shared library (SmartDec does not yet support joint analysis of several low-level programs) or by optimized-away vtable pointer initializations. "Class mismatches" are classes whose reconstructed vtables or parents contradict the real ones, mostly classes containing mismatched vtables or classes containing other polymorphic classes as fields (where inheritance and aggregation may be indistinguishable, so such mismatches do not necessarily misinterpret semantics).

## VI. Conclusion and Further Work

The authors describe the challenges of C++ decompilation and propose methods to overcome them, enabling automatic reconstruction of polymorphic classes and hierarchies, virtual and non-virtual member functions, constructors and destructors, calls to virtual functions, types and layout of class members, types of variables holding pointers to polymorphic classes, and exception raising and handling statements. These were implemented in SmartDec, developed at Select LTD, which was tested on a variety of open-source C++ software with good results. The primary direction for future work is generating C++ code that can be compiled and tested without prior manual editing (recovery of non-polymorphic constructors/destructors and inlined destructors being part of this).
