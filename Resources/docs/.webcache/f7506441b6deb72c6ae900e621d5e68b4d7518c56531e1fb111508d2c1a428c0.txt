Expand description

An RAII implementation of a “scoped lock” of a mutex. When this structure is dropped (falls out of scope), the lock will be unlocked.

The data protected by the mutex can be accessed through this guard via its [`Deref`](https://doc.rust-lang.org/std/ops/trait.Deref.html "trait std::ops::Deref") and [`DerefMut`](https://doc.rust-lang.org/std/ops/trait.DerefMut.html "trait std::ops::DerefMut") implementations.

This structure is created by the [`lock`](https://doc.rust-lang.org/std/sync/nonpoison/struct.Mutex.html#method.lock "method std::sync::nonpoison::Mutex::lock") and [`try_lock`](https://doc.rust-lang.org/std/sync/nonpoison/struct.Mutex.html#method.try_lock "method std::sync::nonpoison::Mutex::try_lock") methods on [`Mutex`](https://doc.rust-lang.org/std/sync/nonpoison/struct.Mutex.html "struct std::sync::nonpoison::Mutex").

Makes a [`MappedMutexGuard`](https://doc.rust-lang.org/std/sync/nonpoison/struct.MappedMutexGuard.html "struct std::sync::nonpoison::MappedMutexGuard") for a component of the borrowed data, e.g. an enum variant.

The `Mutex` is already locked, so this cannot fail.

This is an associated function that needs to be used as `MutexGuard::map(...)`. A method would interfere with methods of the same name on the contents of the `MutexGuard` used through `Deref`.

A [`MutexGuard`](https://doc.rust-lang.org/std/sync/nonpoison/struct.MutexGuard.html "struct std::sync::nonpoison::MutexGuard") is not `Send` to maximize platform portability.

On platforms that use POSIX threads (commonly referred to as pthreads) there is a requirement to release mutex locks on the same thread they were acquired. For this reason, [`MutexGuard`](https://doc.rust-lang.org/std/sync/nonpoison/struct.MutexGuard.html "struct std::sync::nonpoison::MutexGuard") must not implement `Send` to prevent it being dropped from another thread.
