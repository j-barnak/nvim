The **Common Intermediate Language** (**CIL**, formerly **MSIL**) is a byte code intermediate language used in the [.NET Framework](https://wiki.osdev.org/index.php?title=.NET_Framework&action=edit&redlink=1 ".NET Framework (page does not exist)"). Code which compiles to CLI byte code is considered 'managed code' and can be created by any [CLI](https://wiki.osdev.org/CLI "CLI") compatible compiler (such as the [C# Compiler](https://wiki.osdev.org/C_Sharp "C Sharp"), and executed by the [Virtual Execution System](https://wiki.osdev.org/index.php?title=Virtual_Execution_System&action=edit&redlink=1 "Virtual Execution System (page does not exist)") (VES). It is CPU and platform independent.

Most of the time, developers will not be programming directly in CIL but use a higher level language such as [C#](https://wiki.osdev.org/C_Sharp "C Sharp"), [C++/CLI](https://wiki.osdev.org/index.php?title=C%2B%2B/CLI&action=edit&redlink=1 "C++/CLI (page does not exist)"), [Visual Basic .NET](https://wiki.osdev.org/index.php?title=Visual_Basic_.NET&action=edit&redlink=1 "Visual Basic .NET (page does not exist)") and [J#](https://wiki.osdev.org/index.php?title=J&action=edit&redlink=1 "J (page does not exist)"). However, CIL has its own assembly language which can be assembled by ILAsm (`ilasm.exe`). To display the byte code in assembly language, the CIL disassembler ILDAsm (`ildasm.exe`) is used. However, some specialized tools such as .NET Reflector can represent the byte code as any of the supported higher level languages, such as C#, including the classes, methods and other metadata.

## Safe and unsafe code

CIL byte code can either be considered safe or unsafe. By default, all C# is safe, which means that the execution system knows where all the data is, all the time. Therefore it is not possible to use pointers in safe code. Thanks to this property, the most common security and stability problems are eliminated, such as buffer overflows and dangling pointers. A [garbage collector](https://wiki.osdev.org/Garbage_collection "Garbage collection") is employed to use the memory as efficient as possible.

### Unsafe code

Although pointers are not possible in safe code, CIL supports unsafe code which does have support for pointers. Unsafe code is contained in blocks of code which is marked 'unsafe', and in C# it uses the same syntax as C and C++. Objects can be *pinned* so that the [garbage collector](https://wiki.osdev.org/Garbage_collection "Garbage collection") doesn't move the data around and pointers remain valid. Using unsafe code is perfectly legal, although discouraged in normal application programming, and may be used to write kernel-level methods.

## Executing CIL Code

CIL code is executed by a [Virtual Execution System](https://wiki.osdev.org/index.php?title=Virtual_Execution_System&action=edit&redlink=1 "Virtual Execution System (page does not exist)") much like Java byte code. Usually this is in the form of a [Just In Time compiler](https://wiki.osdev.org/index.php?title=Just_In_Time_compiler&action=edit&redlink=1 "Just In Time compiler (page does not exist)"), which translates the byte code into a native machine code, usually utilizing optimizations specific to that processor (for example SSE if available). [Mono](http://www.mono-project.com) is an open-source .NET project, which consists of an CIL JIT'er (and interpreter for unsupported architectures) as well as a C#-\>CLI compiler. The JIT'er and can be [embedded](http://www.mono-project.com/Embedding_Mono) in to any program or stand alone. The basic JIT'er and compiler is written in C and only requires the C Standard Library to run.

## Metadata

The CIL byte code is only half of an .NET assembly. The other half is metadata, which is used by the VES to find which method needs to be called. This makes it possible to inherit or extend classes and override methods while the correct overridden method will be called at run-time without recompiling the calling assembly.
