# Design of a Retargetable Decompiler for a Static Platform-Independent Malware Analysis

*Cited in the Decompilation Wiki: Schema-based Structuring*

Lukáš Ďurfina, Jakub Křoustek, Petr Zemek, Dušan Kolář, Tomáš Hruška, Karel Masařík, and Alexander Meduna. "Design of a Retargetable Decompiler for a Static Platform-Independent Malware Analysis." Brno University of Technology, Faculty of Information Technology. In T.-h. Kim et al. (Eds.): ISA 2011, CCIS 200, pp. 72-86, 2011. Springer-Verlag Berlin Heidelberg.

## Abstract

The paper responds to the growing number of malware threats targeting smartphones, tablets, and other smart devices, a diversity of platforms that security companies are poorly prepared for. The authors propose the concept of a retargetable reverse compiler (a decompiler), described as being "in an early stage of development," that transforms platform-specific binary applications into a high-level language (HLL) representation that can be analyzed uniformly. The stated goal is to support static, platform-independent malware analysis. The distinctive element of their approach is the reuse of two systems that were not originally intended for this purpose: the architecture description language (ADL) ISAC for describing platforms, and the LLVM Compiler System as the decompiler core. They claim the tool can already produce "highly readable HLL code." Keywords: decompilation, reverse engineering, malware, LLVM, Lissom, ISAC.

## 1. Introduction

The authors distinguish the two basic kinds of malware analysis. Dynamic analysis inspects run-time behavior by monitoring the system and network (for example WinAPI calls, registry modifications, new services, network traffic). Static analysis instead views and walks the code with reverse-engineering tools such as disassemblers or decompilers, giving the analyst the source either at the assembly level (disassembly) or at a higher level such as C (decompilation). Static analysis is emphasized as crucial because some malware (for example polymorphic and metamorphic code) cannot be properly analyzed dynamically.

The motivation is that for roughly 20 years malware primarily targeted personal computers (x86 and x86-64), where analysis techniques were well optimized and security companies could keep pace. The rapid expansion of smart devices, which run varied processors and operating systems and now hold sensitive user data, has broken this: existing solutions are oriented toward classical platforms and cannot protect new ones, so malware for the new platforms grows steadily.

The paper's contribution is an overview of a retargetable decompiler not tied to any particular target platform, whose primary use is static platform-independent malware analysis. By producing a more abstract, unified representation while preserving functional equivalence, it frees analysts from needing deep knowledge of each target instruction set and architecture. The decompiler's front-end is generated from an ISAC platform description, and its core is based on LLVM, which is used to reverse-translate a binary into a Python-like language. The authors outline the paper structure: state of the art (Section 2), the two enabling technologies ISAC (Section 3) and LLVM (Section 4), the decompiler design (Section 5), experimental results (Section 6), and future work (Section 7).

## 2. State of the Art

The authors trace machine-code decompilation back more than 50 years to the D-Neliac decompiler (1960), the first to show that programs working "in a reverse way to compilers" were feasible. The closest project in spirit is the PILER System (1974), which used three parts and two intermediate representations: an interpreter running on the source machine that emits a three-address low-level "Micro Form," an analyzer (using data-flow and timing analyses) that produces a high-level "Intermediate Form" suited to FORTRAN, COBOL, and similar languages, and a converter that emits HLL source. PILER was designed to be flexible and general but, according to available information, was never completed.

Four contemporary decompilers are discussed and compared in Table 1:

- **dcc** (C. Cifuentes): targets a single architecture and OS (i80286 MS-DOS executables) but is well structured, with a compiler-like front-end, middle-end, and back-end, two intermediate representations (a low one between front-end and middle-end, a high one between middle-end and back-end producing C), and a control-flow graph built in the front-end. It also recognizes compilers and library routines so that start-up and library code need not be decompiled. No longer developed.
- **Boomerang** (M. van Emmerik): the open-source successor idea, a retargetable decompiler with a modular architecture emphasizing easy substitution of parts. Supports x86 (except SIMD), Sparc, and PowerPC inputs in ELF or PE, targeting C. No longer developed.
- **REC Decompiler**: not open source but free, with published design. Supports the most architectures and formats of the group (x86, x86-64, MIPS, m68k, Sparc, PowerPC; PE, ELF, MachO), implements complex control-flow-graph algorithms, and can reconstruct advanced constructs such as switch statements.
- **Hex-Rays Decompiler**: proprietary, sold as an add-on to IDA Pro. Well-developed recognition of compilers, start-up and statically-linked code via FLIRT (Fast Library Identification and Recognition Technology), which allows adding new library and compiler signatures.

The authors also note projects that are not complete decompilers but only generate source from an intermediate representation, citing emscripten (LLVM bitcode to JavaScript) and llvm-js-backend.

## 3. ISAC Language

ISAC was developed within the Lissom project at Brno University of Technology. The project has two scopes: developing an ADL for describing Multiprocessor Systems-on-Chip (MPSoC), and transforming MPSoC descriptions into software tools (C compiler, simulator, etc.) or into a hardware realization. ISAC is a "mixed ADL," meaning a processor model has several parts. The **resource part** declares resources such as registers and memory hierarchy; the **operation part** describes the instruction set with instruction behavior and micro-architecture. A model can be written instruction-accurate or cycle-accurate; the decompiler currently uses the instruction-accurate level.

Within operations, the **assembler** and **coding** sections capture instruction format in assembly and machine language (textual and binary forms), and the **behavior** section defines the semantics of each operation using a subset of ANSI C. Figure 1 gives a worked example: a `RESOURCES` block declaring a program counter, a 16-entry register file, and RAM, and an `op_add` operation whose `ASSEMBLER`, `CODING { 0b0001 rd rs rt }`, and `BEHAVIOR { regs[rd] = regs[rs] + regs[rt]; }` sections define the instruction textually, in binary, and semantically.

## 4. LLVM Compiler System

LLVM was originally a compiler framework for transparent, lifelong program analysis and transformation, providing high-level information at compile-, link-, run-, and idle-time. Its uses now span compilation, video decoding, signal processing, static checking, and language implementation. Key features include a universal, language-independent instruction set and type system, the intermediate representation LLVM IR, many built-in optimization passes, link-time optimization, JIT code generation, and APIs for several languages.

Using a factorial function in C (Figure 2) compiled to LLVM IR (Figure 3), the authors highlight IR properties central to their design:

- A **RISC-like instruction set** captures ordinary processor operations while avoiding machine-specific constraints. Most instructions are three-address (one or two operands, one result), covering arithmetic (`add`, `mul`), bitwise (`shl`, `and`), memory access (`load`, `store`, `alloca`), conversion (`trunc`, `zext`), and others (`icmp`, `call`). Every basic block ends with a terminator instruction (`br`, `ret`) that names its successor blocks.
- Virtual registers are in **Static Single Assignment (SSA)** form (evidenced by the `phi` instruction), where each variable is assigned exactly once, simplifying many optimizations.
- A **language-independent type system** gives every instruction and SSA register a type under strict rules, enabling optimizations that would otherwise be hard. Primitive types include void, boolean, variable-sized integers, and floating-point; derived types include pointers, arrays, structures, and functions. The `cast` instruction performs the only permitted type conversions, and `getelementptr` performs address computation.
- LLVM IR exists in three equivalent forms (textual, binary, in-memory), interconvertible without loss of information.

## 5. Design of a Retargetable Decompiler

The decompiler's objective is to analyze binary code and transform it into an HLL while preserving functional equivalence (necessary for accurate later analysis), a hard task given missing information from compiler optimizations and malware obfuscation. Usage is straightforward: the user describes the target architecture in the ISAC ADL, a tool-chain generator automatically produces the decompiler, and binaries for that architecture can then be reverse-translated.

The structure mirrors a classical compiler (front-end, middle-end, back-end; Figure 4), and only the front-end is platform-specific. The binary coding and semantics of each instruction are extracted from the ISAC model, so the decompiler need not be manually reconfigured for a new architecture. The authors assert that "at present, there is no other competitive method of automatically-generated retargetable decompilation."

### 5.1 Front-End

The front-end translates architecture-specific machine code into a sequence of low-level LLVM IR instructions. Because malware inputs are usually packed and protected, the first step is code unpacking (treated as out of scope, referencing existing literature). Next, the platform-specific file format is converted into a unified internal **COFF-based file format**, with conversions currently supported from Windows PE, Unix ELF, Symbian E32, and Android DEX.

To build the instruction decoder, the binary coding and semantics of instructions are extracted from the ISAC model by a tool called the **semantics extractor**, which transforms the ANSI C behavior section of each instruction into an equivalent sequence of LLVM IR instructions, mapping instruction semantics to machine code. From this, an instruction decoder (similar to a disassembler, but emitting LLVM IR basic blocks rather than assembly) is generated automatically, based on a formal model. When statically-linked code is detected, its representation is emitted instead of raw instruction semantics.

Statically-linked code detection is inspired by FLIRT. Static libraries contain object files of differing formats; these are extracted, transformed into the internal object file format, and packed into a single archive so that later processing deals with one format (an advantage over FLIRT, which needs separate tooling per object-file format). Signature creation has two parts: extracting a pattern for each object file, then building a signature from a group of patterns (Figure 5).

The final front-end stage is static analysis of the emitted LLVM IR, focused on control-flow analyses and transformations to produce code more suitable for later stages (for example function detection, elimination of "jump register" instructions, and annotation). The authors note this part "is not implemented yet" and needs more research.

### 5.2 Middle-End

At this stage the LLVM IR is very low-level: each basic block represents a single assembly instruction (decompiled in isolation), there are many redundant instructions, and no high-level constructs are visible. The middle-end improves the IR and prepares it for HLL emission through three kinds of passes:

- **Search for idioms**: recognizing code sequences whose combined meaning is not apparent from individual instructions (for example replacing xor of a register with itself by an assignment of zero). Idioms may span several instructions and be replaced by equivalent ones; this pass also includes analyses such as constant and expression propagation.
- **Retrieval of high-level constructs**: identifying if/else statements, switches, and loops (headers and bodies of loops, common post-branch destination blocks, etc.) so that unstructured `goto`s are used as little as possible.
- **Optimization of the code**: connecting successive basic blocks and eliminating redundant instructions.

The authors prefer LLVM's existing, sophisticated optimization and analysis passes over their own whenever possible. To aid this stage, the front-end annotates the IR using LLVM metadata attached to instructions, including markings of function-body entry points and application-binary-interface information (calling conventions, system calls, etc.).

### 5.3 Back-End

The back-end transforms optimized LLVM IR into an HLL, currently a **Python-like language**, with support for other back-ends planned. The HLL is non-typed, block structured, and uses whitespace indentation rather than braces or keywords, emphasizing readability for human analysts. Where Python lacks a needed construct, C-like constructs are used: C-like switch statements for fall-through, the address and dereference operators, lists instead of arrays, and dictionaries instead of structures. An explicit `goto` remains a necessary addition for cases that cannot be fully structured (for example an irreducible control-flow subgraph).

Generation walks the control-flow graph, using middle-end analysis information to emit proper high-level constructs. A final textual post-processing phase improves readability by eliminating redundant brackets and expressions introduced by the back-end.

## 6. Experimental Results

Because the decompiler is early-stage, the authors compare only their back-end against the C back-end currently included in LLVM (real-world decompilation examples exist but are not yet in publishable form). The C function in Figure 6 was compiled with llvm-gcc 4.2.1 at -O3 directly into LLVM IR (LLVM 2.8, --emit-llvm), then emitted by both back-ends (Figures 7 and 8).

The Python-like back-end output (Figure 8) reduces a multi-line, goto-laden, heavily cast C back-end output (Figure 7) to four readable lines. The authors list the key differences their back-end achieves:

- No useless variables are introduced (unlike `llvm_cbe_tmp__1` in the C back-end output).
- Basic-block bodies are inlined instead of using `goto`s wherever possible, and likewise for loops and switches.
- String literals are inlined rather than accessed through a structure.
- Redundant code (for example unnecessary pairs of brackets) is removed to increase readability.
- Because the HLL is non-typed, no sequences of casts are needed, which would otherwise reduce readability even when type-correct.
- As little boilerplate code as possible is generated (though this is not visible in the figures).

## 7. Conclusion

The paper proposed a retargetable decompiler for static platform-independent malware analysis whose front-end is generated from an ISAC ADL processor description and whose middle-end and back-end are built on LLVM. The authors present this reuse of ISAC and LLVM as innovative, enabling automatic retargetability, which they consider their major advantage over similar projects. They report they can already convert platform-specific machine code into platform-independent LLVM IR and then into human-readable HLL, claiming their back-end achieves better reverse-translation results than existing solutions.

They also identify substantial remaining work. The front-end static analyzer must be finished to yield more accurate LLVM IR. The middle-end can gain new analyses (for example pushing a negation into a condition so that `if not (a == b)` becomes `if a != b`, or replacing a chain of if/else-if with a single switch). The back-end can improve construct emission: loops are currently always emitted as `while True`, so proper detection of induction variables in the middle-end is needed for more natural loops, and other HLLs (possibly with type information and conversions) could be considered.
