IBM 4758 Secure Co-Processor
• Extreme physical security
• Clock Glitching: Use phase locked loops and independently generated internal clocks
• Voltage Glitching: Add detection and monitor circuits to watch for voltage changes
• X-ray fault injection: A radiation sensor
• Electromagnetic side channels: Solid aluminium shielding and a low-pass filter (a Faraday cage)

• But broken by software-level logic flaw

Expensive. Other secure processors only
focus on a limited set of physical attacks.

• There is a flaw in key management, allowing an attacker to chain multiple legal
API calls to leak secrets

Targeted Row Refresh (TRR)
• Implemented as vendor-proprietary counters/heuristics in DRAM chips
• Problem 1: Limited tracking capacity
• Most TRR implementations track only a small number of hot rows.
• Why?

• How to bypass this mitigation?
• Many-sided row hammer.
• If k is 5, then activate sequence can be: R1, R2, R3, R4, R5, R6, R1, ……., R6….

Targeted Row Refresh (TRR)
• Problem 2: Threshold/Window mismatch
• TRR tracks activation counts within 64m window
• Why?
if activations(row) > 100K in 64ms:
refresh neighbors

Industry’s Next Step: PRAC
• Introduced into the DDR5 spec update (April 2024).
• PRAC: Per-Row Activation Counting
• Track every row’s activations (not just top-K)
• Signal controller when activation reaches threshold
• Memory controller issues targeted row refresh
• Throttling/backoff: temporally stall or slow requests to a given bank
• Reschedule requests to the target row

• PRAC is a framework. Security depends on implementation quality.
• Tradeoff?
