# Evaluation

In broad terms, the evaluation of a Racket program proceeds in four stages:

1.

    A [source file](https://beautifulracket.com/appendix/glossary.html#source-file) may have a [reader](https://beautifulracket.com/appendix/glossary.html#reader) attached (via [the \#lang line](https://beautifulracket.com/explainer/lang-line.html)). If so, this reader transformation is applied to the code.

2.

    Any forms that introduce [bindings](https://beautifulracket.com/appendix/glossary.html#binding), like [require](http://docs.racket-lang.org/reference/require.html#(form._((lib._racket/private/base..rkt)._require))) or [define](http://docs.racket-lang.org/reference/define.html#(form._((lib._racket/private/base..rkt)._define))), are resolved.  + For the specifics, see [introducing bindings](http://docs.racket-lang.org/reference/syntax-model.html?q=evaluation#%28part._intro-binding%29) in the Racket Reference.

3.

    [Macros](https://beautifulracket.com/explainer/macros.html) are expanded, starting with the outermost forms and progressing inward. This stage of evaluation is known as [compile time](https://beautifulracket.com/appendix/glossary.html#compile-time) or [phase 1](https://beautifulracket.com/appendix/glossary.html#phase-1). Macro expansion is recursive: if a macro expands to become another macro, the new macro is also expanded. Eventually, there will be no macros left, leaving only [core syntactic forms](https://beautifulracket.com/appendix/glossary.html#core-syntactic-form). This is called the [fully expanded program](https://beautifulracket.com/appendix/glossary.html#fully-expanded-program).

4.

    If any [identifiers](https://beautifulracket.com/appendix/glossary.html#identifier) in the fully expanded program still don’t have [bindings](https://beautifulracket.com/appendix/glossary.html#binding), then evaluation fails with an error. Otherwise, all [expressions](https://beautifulracket.com/appendix/glossary.html#expression) in the fully expanded program are evaluated, starting with the innermost expressions and progressing outward, as in the example below. This stage of evaluation is known as [run time](https://beautifulracket.com/appendix/glossary.html#run-time) or [phase 0](https://beautifulracket.com/appendix/glossary.html#phase-0). Whatever remains is the program result.

This process is recursive: each phase of evaluation can trigger the import of other modules (for instance, using [require](http://docs.racket-lang.org/reference/require.html#(form._((lib._racket/private/base..rkt)._require)))). This, in turn, causes the evaluation of these imported modules.

### [Order of evaluation](#order-of-evaluation)

Run-time expressions are evaluated from the inside out. But macros are evaluated in the *opposite* direction—from the outside in. The necessity for this should be apparent: a macro can rewrite any code inside it, so there’s no way to know in advance whether the inner expressions can or should be evaluated at all. Consider this example—do you end up with a zombie apocalypse, or baby pandas?

(define-macro (unleash INNER-EXPR) \#''baby-pandas)
(unleash (zombie-apocalypse))

    1
    2

    (define-macro (unleash INNER-EXPR) #''baby-pandas)
    (unleash (zombie-apocalypse))

But this difference in evaluation order can also defeat certain intuitions about expressions, especially when nesting macros inside each other, or using macros that have side effects. Here, notice how using functions instead of macros changes the output:

(define (ofunc inner) (displayln "outer func"))
(define (ifunc) (displayln "inner func"))
(ofunc (ifunc))
