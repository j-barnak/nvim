Expand description

A pointer which pins its pointee in place.

[`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") is a wrapper around some kind of pointer `Ptr` which makes that pointer “pin” its pointee value in place, thus preventing the value referenced by that pointer from being moved or otherwise invalidated at that place in memory unless it implements [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin").

*See the [`pin` module](https://doc.rust-lang.org/std/pin/index.html "pin module") documentation for a more thorough exploration of pinning.*

### Pinning values with [`Pin<Ptr>`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin")

In order to pin a value, we wrap a *pointer to that value* (of some type `Ptr`) in a [`Pin<Ptr>`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin"). [`Pin<Ptr>`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") can wrap any pointer type, forming a promise that the **pointee** will not be *moved* or [otherwise invalidated](https://doc.rust-lang.org/std/pin/index.html#subtle-details-and-the-drop-guarantee "pin subtle details"). If the pointee value’s type implements [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin"), we are free to disregard these requirements entirely and can wrap any pointer to that value in [`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") directly via [`Pin::new`](https://doc.rust-lang.org/std/pin/struct.Pin.html#method.new "associated function std::pin::Pin::new"). If the pointee value’s type does not implement [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin"), then Rust will not let us use the [`Pin::new`](https://doc.rust-lang.org/std/pin/struct.Pin.html#method.new "associated function std::pin::Pin::new") function directly and we’ll need to construct a [`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin")-wrapped pointer in one of the more specialized manners discussed below.

We call such a [`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin")-wrapped pointer a **pinning pointer** (or pinning ref, or pinning [`Box`](https://doc.rust-lang.org/std/boxed/struct.Box.html "Box"), etc.) because its existence is the thing that is pinning the underlying pointee in place: it is the metaphorical “pin” securing the data in place on the pinboard (in memory).

It is important to stress that the thing in the [`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") is not the value which we want to pin itself, but rather a pointer to that value! A [`Pin<Ptr>`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") does not pin the `Ptr` but rather the pointer’s ***pointee** value*.

The most common set of types which require pinning related guarantees for soundness are the compiler-generated state machines that implement [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future") for the return value of `async fn`s. These compiler-generated [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future")s may contain self-referential pointers, one of the most common use cases for [`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin"). More details on this point are provided in the [`pin` module](https://doc.rust-lang.org/std/pin/index.html "pin module") docs, but suffice it to say they require the guarantees provided by pinning to be implemented soundly.

This requirement for the implementation of `async fn`s means that the [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future") trait requires all calls to [`poll`](https://doc.rust-lang.org/std/future/trait.Future.html#tymethod.poll "Future::poll") to use a `self: `[`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin")`<&mut Self>` parameter instead of the usual `&mut self`. Therefore, when manually polling a future, you will need to pin it first.

You may notice that `async fn`-sourced [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future")s are only a small percentage of all [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future")s that exist, yet we had to modify the signature of [`poll`](https://doc.rust-lang.org/std/future/trait.Future.html#tymethod.poll "Future::poll") for all [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future")s to accommodate them. This is unfortunate, but there is a way that the language attempts to alleviate the extra friction that this API choice incurs: the [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin") trait.

The vast majority of Rust types have no reason to ever care about being pinned. These types implement the [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin") trait, which entirely opts all values of that type out of pinning-related guarantees. For values of these types, pinning a value by pointing to it with a [`Pin<Ptr>`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") will have no actual effect.

The reason this distinction exists is exactly to allow APIs like [`Future::poll`](https://doc.rust-lang.org/std/future/trait.Future.html#tymethod.poll "Future::poll") to take a [`Pin<Ptr>`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") as an argument for all types while only forcing [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future") types that actually care about pinning guarantees pay the ergonomics cost. For the majority of [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future") types that don’t have a reason to care about being pinned and therefore implement [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin"), the [`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin")`<&mut Self>` will act exactly like a regular `&mut Self`, allowing direct access to the underlying value. Only types that *don’t* implement [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin") will be restricted.

#### Pinning a value of a type that implements [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin")

If the type of the value you need to “pin” implements [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin"), you can trivially wrap any pointer to that value in a [`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") by calling [`Pin::new`](https://doc.rust-lang.org/std/pin/struct.Pin.html#method.new "associated function std::pin::Pin::new").

``` rust
use std::pin::Pin;

// Create a value of a type that implements `Unpin`
let mut unpin_future = std::future::ready(5);

// Pin it by creating a pinning mutable reference to it (ready to be `poll`ed!)
let my_pinned_unpin_future: Pin<&mut _> = Pin::new(&mut unpin_future);
```

#### Pinning a value inside a [`Box`](https://doc.rust-lang.org/std/boxed/struct.Box.html "Box")

The simplest and most flexible way to pin a value that does not implement [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin") is to put that value inside a [`Box`](https://doc.rust-lang.org/std/boxed/struct.Box.html "Box") and then turn that [`Box`](https://doc.rust-lang.org/std/boxed/struct.Box.html "Box") into a “pinning [`Box`](https://doc.rust-lang.org/std/boxed/struct.Box.html "Box")” by wrapping it in a [`Pin`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin"). You can do both of these in a single step using [`Box::pin`](https://doc.rust-lang.org/std/boxed/struct.Box.html#method.pin "Box::pin"). Let’s see an example of using this flow to pin a [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html "Future") returned from calling an `async fn`, a common use case as described above.

``` rust
use std::pin::Pin;

async fn add_one(x: u32) -> u32 {
    x + 1
}

// Call the async function to get a future back
let fut = add_one(42);

// Pin the future inside a pinning box
let pinned_fut: Pin<Box<_>> = Box::pin(fut);
```

If you have a value which is already boxed, for example a [`Box<dyn Future>`](https://doc.rust-lang.org/std/boxed/struct.Box.html "Box"), you can pin that value in-place at its current memory address using [`Box::into_pin`](https://doc.rust-lang.org/std/boxed/struct.Box.html#method.into_pin "Box::into_pin").

``` rust
use std::pin::Pin;
use std::future::Future;

async fn add_one(x: u32) -> u32 {
    x + 1
}

fn boxed_add_one(x: u32) -> Box<dyn Future<Output = u32>> {
    Box::new(add_one(x))
}

let boxed_fut = boxed_add_one(42);

// Pin the future inside the existing box
let pinned_fut: Pin<Box<_>> = Box::into_pin(boxed_fut);
```

There are similar pinning methods offered on the other standard library smart pointer types as well, like [`Rc`](https://doc.rust-lang.org/std/rc/struct.Rc.html "Rc") and [`Arc`](https://doc.rust-lang.org/std/sync/struct.Arc.html "Arc").

#### Pinning a value on the stack using [`pin!`](https://doc.rust-lang.org/std/pin/macro.pin.html "pin!")

There are some situations where it is desirable or even required (for example, in a `#[no_std]` context where you don’t have access to the standard library or allocation in general) to pin a value which does not implement [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin") to its location on the stack. Doing so is possible using the [`pin!`](https://doc.rust-lang.org/std/pin/macro.pin.html "pin!") macro. See its documentation for more.

### Layout and ABI

[`Pin<Ptr>`](https://doc.rust-lang.org/std/pin/struct.Pin.html "struct std::pin::Pin") is guaranteed to have the same memory layout and ABI^([1](#fn1)) as `Ptr`.

##### Safety

This constructor is unsafe because we cannot guarantee that the data pointed to by `pointer` is pinned. At its core, pinning a value means making the guarantee that the value’s data will not be moved nor have its storage invalidated until it gets dropped. For a more thorough explanation of pinning, see the [`pin` module docs](https://doc.rust-lang.org/std/pin/index.html "mod std::pin").

If the caller that is constructing this `Pin<Ptr>` does not ensure that the data `Ptr` points to is pinned, that is a violation of the API contract and may lead to undefined behavior in later (even safe) operations.

By using this method, you are also making a promise about the [`Deref`](https://doc.rust-lang.org/std/ops/trait.Deref.html "trait std::ops::Deref"), [`DerefMut`](https://doc.rust-lang.org/std/ops/trait.DerefMut.html "trait std::ops::DerefMut"), and [`Drop`](https://doc.rust-lang.org/std/ops/trait.Drop.html "trait std::ops::Drop") implementations of `Ptr`, if they exist. Most importantly, they must not move out of their `self` arguments: `Pin::as_mut` and `Pin::as_ref` will call `DerefMut::deref_mut` and `Deref::deref` *on the pointer type `Ptr`* and expect these methods to uphold the pinning invariants. Moreover, by calling this method you promise that the reference `Ptr` dereferences to will not be moved out of again; in particular, it must not be possible to obtain a `&mut Ptr::Target` and then move out of that reference (using, for example [`mem::swap`](https://doc.rust-lang.org/std/mem/fn.swap.html "fn std::mem::swap")).

For example, calling `Pin::new_unchecked` on an `&'a mut T` is unsafe because while you are able to pin it for the given lifetime `'a`, you have no control over whether it is kept pinned once `'a` ends, and therefore cannot uphold the guarantee that a value, once pinned, remains pinned until it is dropped:

``` rust
use std::mem;
use std::pin::Pin;

fn move_pinned_ref<T>(mut a: T, mut b: T) {
    unsafe {
        let p: Pin<&mut T> = Pin::new_unchecked(&mut a);
        // This should mean the pointee `a` can never move again.
    }
    mem::swap(&mut a, &mut b); // Potential UB down the road ⚠️
    // The address of `a` changed to `b`'s stack slot, so `a` got moved even
    // though we have previously pinned it! We have violated the pinning API contract.
}
```

A value, once pinned, must remain pinned until it is dropped (unless its type implements `Unpin`). Because `Pin<&mut T>` does not own the value, dropping the `Pin` will not drop the value and will not end the pinning contract. So moving the value after dropping the `Pin<&mut T>` is still a violation of the API contract.

Similarly, calling `Pin::new_unchecked` on an `Rc<T>` is unsafe because there could be aliases to the same data that are not subject to the pinning restrictions:

``` rust
use std::rc::Rc;
use std::pin::Pin;

fn move_pinned_rc<T>(mut x: Rc<T>) {
    // This should mean the pointee can never move again.
    let pin = unsafe { Pin::new_unchecked(Rc::clone(&x)) };
    {
        let p: Pin<&T> = pin.as_ref();
        // ...
    }
    drop(pin);

    let content = Rc::get_mut(&mut x).unwrap(); // Potential UB down the road ⚠️
    // Now, if `x` was the only reference, we have a mutable reference to
    // data that we pinned above, which we could use to move it as we have
    // seen in the previous example. We have violated the pinning API contract.
}
```

###### Pinning of closure captures

Particular care is required when using `Pin::new_unchecked` in a closure: `Pin::new_unchecked(&mut var)` where `var` is a by-value (moved) closure capture implicitly makes the promise that the closure itself is pinned, and that *all* uses of this closure capture respect that pinning.

``` rust
use std::pin::Pin;
use std::task::Context;
use std::future::Future;

fn move_pinned_closure(mut x: impl Future, cx: &mut Context<'_>) {
    // Create a closure that moves `x`, and then internally uses it in a pinned way.
    let mut closure = move || unsafe {
        let _ignore = Pin::new_unchecked(&mut x).poll(cx);
    };
    // Call the closure, so the future can assume it has been pinned.
    closure();
    // Move the closure somewhere else. This also moves `x`!
    let mut moved = closure;
    // Calling it again means we polled the future from two different locations,
    // violating the pinning API contract.
    moved(); // Potential UB ⚠️
}
```

When passing a closure to another API, it might be moving the closure any time, so `Pin::new_unchecked` on closure captures may only be used if the API explicitly documents that the closure is pinned.

The better alternative is to avoid all that trouble and do the pinning in the outer function instead (here using the [`pin!`](https://doc.rust-lang.org/std/pin/macro.pin.html "macro std::pin::pin") macro):

``` rust
use std::pin::pin;
use std::task::Context;
use std::future::Future;

fn move_pinned_closure(mut x: impl Future, cx: &mut Context<'_>) {
    let mut x = pin!(x);
    // Create a closure that captures `x: Pin<&mut _>`, which is safe to move.
    let mut closure = move || {
        let _ignore = x.as_mut().poll(cx);
    };
    // Call the closure, so the future can assume it has been pinned.
    closure();
    // Move the closure somewhere else.
    let mut moved = closure;
    // Calling it again here is fine (except that we might be polling a future that already
    // returned `Poll::Ready`, but that is a separate problem).
    moved();
}
```

##### Safety

This function is unsafe. You must guarantee that you will continue to treat the pointer `Ptr` as pinned after you call this function, so that the invariants on the `Pin` type can be upheld. If the code using the resulting `Ptr` does not continue to maintain the pinning invariants that is a violation of the API contract and may lead to undefined behavior in later (safe) operations.

Note that you must be able to guarantee that the data pointed to by `Ptr` will be treated as pinned all the way until its `drop` handler is complete!

*For more information, see the [`pin` module docs](https://doc.rust-lang.org/std/pin/index.html "mod std::pin")*

If the underlying data is [`Unpin`](https://doc.rust-lang.org/std/marker/trait.Unpin.html "trait std::marker::Unpin"), [`Pin::into_inner`](https://doc.rust-lang.org/std/pin/struct.Pin.html#method.into_inner "associated function std::pin::Pin::into_inner") should be used instead.

Gets a shared reference out of a pin.

This is safe because it is not possible to move out of a shared reference. It may seem like there is an issue here with interior mutability: in fact, it *is* possible to move a `T` out of a `&RefCell<T>`. However, this is not a problem as long as there does not also exist a `Pin<&T>` pointing to the inner `T` inside the `RefCell`, and `RefCell<T>` does not let you get a `Pin<&T>` pointer to its contents. See the discussion on [“pinning projections”](https://doc.rust-lang.org/std/pin/index.html#projections-and-structural-pinning "mod std::pin") for further details.

Note: `Pin` also implements `Deref` to the target, which can be used to access the inner value. However, `Deref` only provides a reference that lives for as long as the borrow of the `Pin`, not the lifetime of the reference contained in the `Pin`. This method allows turning the `Pin` into a reference with the same lifetime as the reference it wraps.
