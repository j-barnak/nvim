In [computing](https://www.wikiwand.com/en/Computing "Computing"), **just-in-time** (**JIT**) **compilation** (also **dynamic translation** or **run-time compilations**)^([\[1\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Michigan-1)) is [compilation](https://www.wikiwand.com/en/Compiler "Compiler") (of [computer code](https://www.wikiwand.com/en/Computer_code "Computer code")) during execution of a program (at [run time](https://www.wikiwand.com/en/Run_time_(program_lifecycle_phase) "Run time (program lifecycle phase)")) rather than before execution.^([\[2\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEAycock2003-2)) This may consist of [source code](https://www.wikiwand.com/en/Source_code "Source code") translation but is more commonly [bytecode](https://www.wikiwand.com/en/Bytecode "Bytecode") translation to [machine code](https://www.wikiwand.com/en/Machine_code "Machine code"), which is then executed directly. A system implementing a JIT compiler typically continuously analyses the code being executed and identifies parts of the code where the speedup gained from compilation or recompilation would outweigh the overhead of compiling that code.

JIT compilation is a combination of the two traditional approaches to translation to machine code—[ahead-of-time compilation (AOT)](https://www.wikiwand.com/en/Ahead-of-time_compilation "Ahead-of-time compilation"), and [interpretation](https://www.wikiwand.com/en/Interpreter_(computing) "Interpreter (computing)")—and combines some advantages and drawbacks of both.^([\[2\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEAycock2003-2)) Roughly, JIT compilation combines the speed of compiled code with the flexibility of interpretation, with the overhead of an interpreter and the additional overhead of compiling and [linking](https://www.wikiwand.com/en/Linker_(computing) "Linker (computing)") (not just interpreting). JIT compilation is a form of [dynamic compilation](https://www.wikiwand.com/en/Dynamic_compilation "Dynamic compilation"), and allows [adaptive optimization](https://www.wikiwand.com/en/Adaptive_optimization "Adaptive optimization") such as [dynamic recompilation](https://www.wikiwand.com/en/Dynamic_recompilation "Dynamic recompilation") and [microarchitecture](https://www.wikiwand.com/en/Microarchitecture "Microarchitecture")-specific speedups.^([\[nb 1\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-3)[\[3\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Notario-4)) Interpretation and JIT compilation are particularly suited for [dynamic programming languages](https://www.wikiwand.com/en/Dynamic_programming_language "Dynamic programming language"), as the runtime system can handle [late-bound](https://www.wikiwand.com/en/Late_binding "Late binding") data types and enforce security guarantees.

## History

The earliest published JIT compiler is generally attributed to work on [LISP](https://www.wikiwand.com/en/Lisp_(programming_language) "Lisp (programming language)") by [John McCarthy](https://www.wikiwand.com/en/John_McCarthy_(computer_scientist) "John McCarthy (computer scientist)") in 1960.^([\[4\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEAycock20032._JIT_Compilation_Techniques,_2.1_Genesis,_p._98-5)) In his seminal paper *Recursive functions of symbolic expressions and their computation by machine, Part I*, he mentions functions that are translated during runtime, thereby sparing the need to save the compiler output to [punch cards](https://www.wikiwand.com/en/Punch_card "Punch card")^([\[5\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-McCarthy1960-6)) (although this would be more accurately known as a "[Compile and go system](https://www.wikiwand.com/en/Compile_and_go_system "Compile and go system")"). Another early example was by [Ken Thompson](https://www.wikiwand.com/en/Ken_Thompson "Ken Thompson"), who in 1968 gave one of the first applications of [regular expressions](https://www.wikiwand.com/en/Regular_expression "Regular expression"), here for [pattern matching](https://www.wikiwand.com/en/Pattern_matching "Pattern matching") in the text editor [QED](https://www.wikiwand.com/en/QED_(text_editor) "QED (text editor)").^([\[6\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEThompson1968-7)) For speed, Thompson implemented regular expression matching by JITing to [IBM 7094](https://www.wikiwand.com/en/IBM_7094 "IBM 7094") code on the [Compatible Time-Sharing System](https://www.wikiwand.com/en/Compatible_Time-Sharing_System "Compatible Time-Sharing System").^([\[4\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEAycock20032._JIT_Compilation_Techniques,_2.1_Genesis,_p._98-5)) An influential technique for deriving compiled code from interpretation was pioneered by [James G. Mitchell](https://www.wikiwand.com/en/James_G._Mitchell "James G. Mitchell") in 1970, which he implemented for the experimental language *LC²*.^([\[7\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEAycock20032._JIT_Compilation_Techniques,_2.2_LC²,_p._98–99-8)[\[8\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Mitchell1970-9))

[Smalltalk](https://www.wikiwand.com/en/Smalltalk "Smalltalk") (c. 1983) pioneered new aspects of JIT compilations. For example, translation to machine code was done on demand, and the result was cached for later use. When memory became scarce, the system would delete some of this code and regenerate it when it was needed again.^([\[2\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEAycock2003-2)[\[9\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Schiffman1984-10)) Sun's [Self](https://www.wikiwand.com/en/Self_(programming_language) "Self (programming language)") language improved these techniques extensively and was at one point the fastest Smalltalk system in the world, achieving up to half the speed of optimized C^([\[10\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Self-11)) but with a fully object-oriented language.

Self was abandoned by Sun, but the research went into the Java language. The term "Just-in-time compilation" was borrowed from the manufacturing term "[Just in time](https://www.wikiwand.com/en/Just_in_time_(business) "Just in time (business)")" and popularized by Java, with James Gosling using the term from 1993.^([\[11\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEAycock20032.14_Java,_p._107,_footnote_13-12)) Currently JITing is used by most implementations of the [Java Virtual Machine](https://www.wikiwand.com/en/Java_virtual_machine "Java virtual machine"), as [HotSpot](https://www.wikiwand.com/en/HotSpot_(virtual_machine) "HotSpot (virtual machine)") builds on, and extensively uses, this research base.

The HP project Dynamo was an experimental JIT compiler where the "bytecode" format and the machine code format were the same; the system optimized [PA-8000](https://www.wikiwand.com/en/PA-8000 "PA-8000") machine code.^([\[12\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Bala-13)) Counterintuitively, this resulted in speed ups, in some cases of 30% since doing this permitted optimizations at the machine code level, for example, inlining code for better cache usage and optimizations of calls to dynamic libraries and many other run-time optimizations which conventional compilers are not able to attempt.^([\[13\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Jannotti-14)[\[14\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Dynamo-15))

In November 2020, [PHP](https://www.wikiwand.com/en/PHP "PHP") 8.0 introduced a JIT compiler.^([\[15\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Tung-16))

## Design

In a bytecode-compiled system, [source code](https://www.wikiwand.com/en/Source_code "Source code") is translated to an [intermediate representation](https://www.wikiwand.com/en/Intermediate_representation "Intermediate representation") known as [bytecode](https://www.wikiwand.com/en/Bytecode "Bytecode"). Bytecode is not the machine code for any particular computer, and may be [portable](https://www.wikiwand.com/en/Software_portability "Software portability") among computer architectures. The bytecode may then be interpreted by, or run on a [virtual machine](https://www.wikiwand.com/en/Virtual_machine "Virtual machine"). The JIT compiler reads the bytecodes in many sections (or in full, rarely) and compiles them dynamically into machine code so the program can run faster. This can be done per-file, per-function or even on any arbitrary code fragment; the code can be compiled when it is about to be executed (hence the name "just-in-time"), and then cached and reused later without needing to be recompiled.

By contrast, a traditional *interpreted virtual machine* will simply interpret the bytecode, generally with much lower performance. Some *interpreter*s even interpret source code, without the step of first compiling to bytecode, with even worse performance. *Statically-compiled code* or *native code* is compiled prior to deployment. A *dynamic compilation environment* is one in which the compiler can be used during execution. A common goal of using JIT techniques is to reach or surpass the performance of [static compilation](https://www.wikiwand.com/en/Static_compilation "Static compilation"), while maintaining the advantages of bytecode interpretation: Much of the "heavy lifting" of parsing the original source code and performing basic optimization is often handled at compile time, prior to deployment: compilation from bytecode to machine code is much faster than compiling from source. The deployed bytecode is portable, unlike native code. Since the runtime has control over the compilation, like interpreted bytecode, it can run in a secure sandbox. Compilers from bytecode to machine code are easier to write, because the portable bytecode compiler has already done much of the work.

JIT code generally offers far better performance than interpreters. In addition, it can in some cases offer better performance than static compilation, as many optimizations are only feasible at run-time:^([\[16\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Croce-17)[\[17\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-stackoverflow-1-18))

1.  The compilation can be optimized to the targeted CPU and the operating system model where the application runs. For example, JIT can choose [SSE2](https://www.wikiwand.com/en/SSE2 "SSE2") vector CPU instructions when it detects that the CPU supports them. To obtain this level of optimization specificity with a static compiler, one must either compile a binary for each intended platform/architecture, or else include multiple versions of portions of the code within a single binary.
2.  The system is able to collect statistics about how the program is actually running in the environment it is in, and it can rearrange and recompile for optimum performance. However, some static compilers can also take profile information as input.
3.  The system can do global code optimizations (e.g. [inlining](https://www.wikiwand.com/en/Inline_expansion "Inline expansion") of library functions) without losing the advantages of dynamic linking and without the overheads inherent to static compilers and linkers. Specifically, when doing global inline substitutions, a static compilation process may need run-time checks and ensure that a virtual call would occur if the actual class of the object overrides the inlined method, and boundary condition checks on array accesses may need to be processed within loops. With just-in-time compilation in many cases this processing can be moved out of loops, often giving large increases of speed.
4.  Although this is possible with statically compiled garbage collected languages, a bytecode system can more easily rearrange executed code for better cache utilization.

Because a JIT must render and execute a native binary image at runtime, true machine-code JITs necessitate platforms that allow for data to be executed at runtime, making using such JITs on a [Harvard architecture](https://www.wikiwand.com/en/Harvard_architecture "Harvard architecture")-based machine impossible; the same can be said for certain operating systems and virtual machines as well. However, a special type of "JIT" may potentially *not* target the physical machine's CPU architecture, but rather an optimized VM bytecode where limitations on raw machine code prevail, especially where that bytecode's VM eventually leverages a JIT to native code.^([\[18\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-stackoverflow-2-19))

## Performance

JIT causes a slight to noticeable delay in the initial execution of an application, due to the time taken to load and compile the input code. Sometimes this delay is called "startup time delay" or "warm-up time". In general, the more optimization JIT performs, the better the code it will generate, but the initial delay will also increase. A JIT compiler therefore has to make a trade-off between the compilation time and the quality of the code it hopes to generate. Startup time can include increased IO-bound operations in addition to JIT compilation: for example, the *rt.jar* class data file for the [Java Virtual Machine](https://www.wikiwand.com/en/Java_virtual_machine "Java virtual machine") (JVM) is 40 MB and the JVM must seek a lot of data in this contextually huge file.^([\[19\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Haase-20))

One possible optimization, used by Sun's [HotSpot](https://www.wikiwand.com/en/HotSpot_(virtual_machine) "HotSpot (virtual machine)") Java Virtual Machine, is to combine interpretation and JIT compilation. The application code is initially interpreted, but the JVM monitors which sequences of [bytecode](https://www.wikiwand.com/en/Bytecode "Bytecode") are frequently executed and translates them to machine code for direct execution on the hardware. For bytecode which is executed only a few times, this saves the compilation time and reduces the initial latency; for frequently executed bytecode, JIT compilation is used to run at high speed, after an initial phase of slow interpretation. Additionally, since a program spends most time executing a minority of its code, the reduced compilation time is significant. Finally, during the initial code interpretation, execution statistics can be collected before compilation, which helps to perform better optimization.^([\[20\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-HotSpot-21))

The correct tradeoff can vary due to circumstances. For example, Sun's Java Virtual Machine has two major modes—client and server. In client mode, minimal compilation and optimization is performed, to reduce startup time. In server mode, extensive compilation and optimization is performed, to maximize performance once the application is running by sacrificing startup time. Other Java just-in-time compilers have used a runtime measurement of the number of times a method has executed combined with the bytecode size of a method as a heuristic to decide when to compile.^([\[21\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Schilling-22)) Still another uses the number of times executed combined with the detection of loops.^([\[22\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Suganuma-23)) In general, it is much harder to accurately predict which methods to optimize in short-running applications than in long-running ones.^([\[23\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Arnold-2000-24))

[Native Image Generator](https://www.wikiwand.com/en/Native_Image_Generator "Native Image Generator") (Ngen) by [Microsoft](https://www.wikiwand.com/en/Microsoft "Microsoft") is another approach at reducing the initial delay.^([\[24\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-MSDN-25)) Ngen pre-compiles (or "pre-JITs") bytecode in a [Common Intermediate Language](https://www.wikiwand.com/en/Common_Intermediate_Language "Common Intermediate Language") image into machine native code. As a result, no runtime compilation is needed. [.NET Framework](https://www.wikiwand.com/en/.NET_Framework ".NET Framework") 2.0 shipped with [Visual Studio 2005](https://www.wikiwand.com/en/Visual_Studio_2005 "Visual Studio 2005") runs Ngen on all of the Microsoft library DLLs right after the installation. Pre-jitting provides a way to improve the startup time. However, the quality of code it generates might not be as good as the one that is JITed, for the same reasons why code compiled statically, without [profile-guided optimization](https://www.wikiwand.com/en/Profile-guided_optimization "Profile-guided optimization"), cannot be as good as JIT compiled code in the extreme case: the lack of profiling data to drive, for instance, inline caching.^([\[25\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Arnold-2005-26))

There also exist Java implementations that combine an [AOT (ahead-of-time) compiler](https://www.wikiwand.com/en/Ahead-of-time_compilation "Ahead-of-time compilation") with either a JIT compiler ([Excelsior JET](https://www.wikiwand.com/en/Excelsior_JET "Excelsior JET")) or interpreter ([GNU Compiler for Java](https://www.wikiwand.com/en/GNU_Compiler_for_Java "GNU Compiler for Java")).

JIT compilation may not reliably achieve its goal, namely entering a steady state of improved performance after a short initial warmup period.^([\[26\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEBarrettBolz-TereickKillickMount20173-27)[\[27\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTETrainiCortellessaDi_PompeoTucci20221-28)) Across eight different virtual machines, [Barrett et al. (2017)](https://www.wikiwand.com/en/Just-in-time_compilation#CITEREFBarrettBolz-TereickKillickMount2017) measured six widely-used microbenchmarks which are commonly used by virtual machine implementors as optimisation targets, running them repeatedly within a single process execution.^([\[28\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEBarrettBolz-TereickKillickMount20175-6-29)) On [Linux](https://www.wikiwand.com/en/Linux "Linux"), they found that 8.7% to 9.6% of process executions failed to reach a steady state of performance, 16.7% to 17.9% entered a steady state of *reduced* performance after a warmup period, and 56.5% pairings of a specific virtual machine running a specific benchmark failed to consistently see a steady-state non-degradation of performance across multiple executions (i.e., at least one execution failed to reach a steady state or saw reduced performance in the steady state). Even where an improved steady-state was reached, it sometimes took many hundreds of iterations.^([\[29\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTEBarrettBolz-TereickKillickMount201712-13-30)) [Traini et al. (2022)](https://www.wikiwand.com/en/Just-in-time_compilation#CITEREFTrainiCortellessaDi_PompeoTucci2022) instead focused on the HotSpot virtual machine but with a much wider array of benchmarks,^([\[30\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTETrainiCortellessaDi_PompeoTucci202217-23-31)) finding that 10.9% of process executions failed to reach a steady state of performance, and 43.5% of benchmarks did not consistently attain a steady state across multiple executions.^([\[31\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-FOOTNOTETrainiCortellessaDi_PompeoTucci202226-29-32))

## Security

JIT compilation fundamentally uses executable data, and thus poses security challenges and possible exploits.

Implementation of JIT compilation consists of compiling source code or byte code to machine code and executing it. This is generally done directly in memory: the JIT compiler outputs the machine code directly into memory and immediately executes it, rather than outputting it to disk and then invoking the code as a separate program, as in usual ahead of time compilation. In modern architectures this runs into a problem due to [executable space protection](https://www.wikiwand.com/en/Executable_space_protection "Executable space protection"): arbitrary memory cannot be executed, as otherwise there is a potential security hole. Thus memory must be marked as executable; for security reasons this should be done *after* the code has been written to memory, and marked read-only, as writable/executable memory is a security hole (see [W^X](https://www.wikiwand.com/en/W%5EX "W^X")).^([\[32\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-Bendersky-33)) For instance Firefox's JIT compiler for Javascript introduced this protection in a release version with Firefox 46.^([\[33\]](https://www.wikiwand.com/en/Just-in-time_compilation#cite_note-De_Mooij-34))

[JIT spraying](https://www.wikiwand.com/en/JIT_spraying "JIT spraying") is a class of [computer security exploits](https://www.wikiwand.com/en/Computer_security_exploit "Computer security exploit") that use JIT compilation for [heap spraying](https://www.wikiwand.com/en/Heap_spraying "Heap spraying"): the resulting memory is then executable, which allows an exploit if execution can be moved into the heap.

## Uses

|-----|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|     | This section does not [cite](https://www.wikiwand.com/en/Wikipedia:Citing_sources) any [sources](https://www.wikiwand.com/en/Wikipedia:Verifiability) . ( June 2021 ) |

JIT compilation can be applied to some programs, or can be used for certain capacities, particularly dynamic capacities such as [regular expressions](https://www.wikiwand.com/en/Regular_expression "Regular expression"). For example, a text editor may compile a regular expression provided at runtime to machine code to allow faster matching: this cannot be done ahead of time, as the pattern is only provided at runtime. Several modern [runtime environments](https://www.wikiwand.com/en/Runtime_environment "Runtime environment") rely on JIT compilation for high-speed code execution, including most implementations of [Java](https://www.wikiwand.com/en/Java_(programming_language) "Java (programming language)"), together with [Microsoft](https://www.wikiwand.com/en/Microsoft "Microsoft")'s [.NET](https://www.wikiwand.com/en/.NET ".NET"). Similarly, many regular-expression libraries feature JIT compilation of regular expressions, either to bytecode or to machine code. JIT compilation is also used in some emulators, in order to translate machine code from one CPU architecture to another.

A common implementation of JIT compilation is to first have AOT compilation to bytecode ([virtual machine](https://www.wikiwand.com/en/Virtual_machine "Virtual machine") code), known as *bytecode compilation*, and then have JIT compilation to machine code (dynamic compilation), rather than interpretation of the bytecode. This improves the runtime performance compared to interpretation, at the cost of lag due to compilation. JIT compilers translate continuously, as with interpreters, but caching of compiled code minimizes lag on future execution of the same code during a given run. Since only part of the program is compiled, there is significantly less lag than if the entire program were compiled prior to execution.
