# Recovering C++ Objects From Binaries Using Inter-Procedural Data-Flow Analysis

*Cited in the Decompilation Wiki: Type Recovery Overview*

Wesley Jin, Cory Cohen, Jeffrey Gennari, Charles Hines, Sagar Chaki, Arie Gurfinkel, Jeffrey Havrilla, and Priya Narasimhan. "Recovering C++ Objects From Binaries Using Inter-Procedural Data-Flow Analysis." In *Proceedings of the 3rd ACM SIGPLAN Program Protection and Reverse Engineering Workshop (PPREW '14)*, San Diego, CA, January 25, 2014. ACM 978-1-4503-2649-0/14/01. http://dx.doi.org/10.1145/2556464.2556465

## Abstract

Object-oriented (OO) programming makes reverse engineering harder, and it is increasingly used by malware authors. Unlike procedural code, OO code forces the analyst to understand complex interactions between methods and the shared data structures they operate on, a tedious manual process. The paper presents a purely static approach that uses symbolic execution and inter-procedural data-flow analysis to discover object instances, data members, and the methods of a common class. The core idea is to track the propagation and usage of a unique object-instance reference, the *this pointer* (called ThisPtr throughout). The approach is implemented in a tool named OBJDIGGER, which produced "encouraging results when validated on real-world malware samples."

## 1. Introduction

As malware grows more sophisticated, analysts increasingly encounter samples written in the OO model, where recovering class information is essential but painstaking. Procedural programs are organized around functions with well-defined boundaries and simple data structures (C-style structs), so control and data flow survive compilation in a recoverable form. OO programs, by contrast, are organized around data structures (C++ objects) with complex relationships; compilation hides these behind sets of methods with no obvious organization. To reverse engineer such a program, an analyst must (1) determine which methods belong to the same class, and (2) understand how they interact.

The approach leverages the ThisPtr, a reference assigned to each unique (up to allocation instruction address) object instance. Using symbolic execution and static inter-procedural data-flow analysis, the tool tracks individual ThisPtr propagation and usage within and between functions. Although prior authors (notably Fokin et al. and Sabanal et al.) used ThisPtr tracking, this work is distinct for two reasons: (1) it documents heuristics for identifying OO methods and structures expressed as detectable data-flow patterns, and (2) it relies only on static analysis and symbolic execution, allowing recovery of artifacts that may never be created during execution.

The tool is built on the ROSE analysis framework, which supplies disassembly, symbolic execution, and control/data-flow analysis. OBJDIGGER targets binaries compiled with Microsoft Visual Studio C++ (MSVC) and records potential constructors, data members, and methods. The stated contributions are: a purely static approach that tracks object references in MSVC binaries; an implementation that produces lists of potential constructors/builders, methods, and data members; techniques for detecting inheritance and embedded objects; and experimental demonstration on both open-source programs and closed-source malware.

## 2. Implementing Object Oriented C++ Features

This section reviews C++ object internals as generated by MSVC's `__thiscall` convention, using a running example of classes `Sub`, `Add`, and `Add1` (`Add1` inherits from `Add`, which embeds a `Sub`). When an object is created, the compiler allocates memory sized by the number and size of data members plus alignment padding. Every instantiated object is referenced by a pointer to its start in memory, the ThisPtr, which "is maintained for the lifetime of the object." It is passed among methods, used for data-member accesses and virtual calls. For example, if `tPtr` points to an `Add1` instance, `[tPtr+12]` points at variable `one` and `[tPtr+8]` points at the embedded `Sub` object.

Only one instance of a function exists, but many object instances can exist, so the ThisPtr disambiguates which instance's data members are operated on. In MSVC, the ThisPtr is passed as a hidden parameter in the **ECX** register per the `__thiscall` convention. The section walks through the assembly of `sum()` to show `[ThisPtr+12] = 1` corresponding to `one=1`.

Inheritance appears in memory by embedding a superclass object inside the subclass object. Accessing an inherited member adjusts the ThisPtr by the offset of the embedded parent, then dereferences. Virtual functions use virtual function tables (vtables) whose address is stored as an implicit data member at offset zero (accessed via `[thisPtr]`); indirect calls dereference the table and call the target. On instantiation a child overwrites the parent's vtable reference so the most specific table is installed; with multiple parents having virtual functions there are multiple vtable references, one per embedded parent object.

## 3. Problem Statement

Given a binary compiled from C++ source without debugging information, the goal is to recover: unique constructors and builder methods for instantiated classes; methods associated with object instances; and the location and size of data members used in those methods.

The stated goal is to expedite recovery of OO structures to aid program understanding, not to recover original source code. Two reasons are given: compilation is not injective, so different sources can yield the same binary, making source recovery impossible in general; and from the malware analyst's viewpoint, understanding compiled-code details (method relationships, class layouts) matters more than high-level abstractions.

## 4. Definitions

The section formalizes data-flow abstractions. A computer system is `C = <P, M, R>`, where `P` is a program and `M`, `R` are memory locations and registers. Each program is a set of functions `F`, each a sequence of instructions; `I` is the set of instructions and `V` the values they manipulate.

Two mappings are defined. `Use(i)` maps an instruction to the set of pairs `<v, a>` where `v` is the value read by `i` and `a` is a memory address or register storing `v`. `Def(i)` is the analogous mapping to locations the instruction writes. An instruction depends on another if it reads a value the other set; `DepOn(i)` maps instruction `i` to triplets `<v, a, j>` where `j` wrote value `v` to location `a` and `<v,a> ∈ Use(i) ∩ Def(j)`. `DepOf` is the inverse of `DepOn`.

Finally the section defines **data flow order**. For a caller `X` invoking `A`, `B`, `C` (with `B` calling `D` before returning), all passed value `v`, the flow order `[A, B, D, C]` means all four contain instructions that use `v` (sharing a reaching definition) and that the instructions of earlier functions dominate those of later ones in the control-flow graph.

## 5. Approach

The approach has a preliminary stage and iterative analysis passes. Binaries are disassembled with ROSE; data- and control-flow analysis builds the `Use`, `Def`, `DepOn`, and `DepOf` maps, which are then mined for OO structures. ROSE supplies x86 instruction semantics and symbolic emulation. The key idea is to track propagation of unique ThisPtr instances within and between functions. The tool identifies the set of `__thiscall` functions `FM`; uses heuristics about heap allocators (e.g., `new()`) and stack allocation patterns to find where a ThisPtr is created; tracks those pointers into `FM` functions via inter-procedural data flow; and by data-flow order marks methods as constructors or member/inherited functions. Within functions, memory transfers based off the ThisPtr yield the offset and size of data members.

### 5.1 Data and Control Flow Analysis

To build the four maps, the authors implement the classic work-list algorithm for data-flow analysis (Procedure `buildDependencies()`). It maintains per-basic-block symbolic **states** capturing register and memory contents. For each block and each instruction in flow order it: (i) symbolically executes the instruction; (ii) updates the block state with the result `r`; and (iii) adds the instruction to `r`'s list of "modifiers" (all instructions that contributed to the value). When a later instruction reads the same location, a dependency is established by consulting this modifier list (illustrated with `add [eax], 5` at `0x00405630`).

Each block's entry state is the **merge** of its predecessors' states: identical symbolic values are preserved, differing values become unknown with the union of modifier lists. After executing a block, if its state changed, successors are re-queued. The algorithm terminates when no block's state changes.

### 5.2 Identifying __thiscall Functions

Because most methods follow `__thiscall`, identifying them first restricts and speeds later analysis. The heuristic exploits that ThisPtr arrives in **ECX**: the tool looks for a function `f` containing an instruction that uses ECX whose value was defined externally to `f`. Formally:

`FM ← {f | ∃i∈f ∃j∉f  <*, ECX, j> ∈ DepOn(i)}`

The authors note this is not precise enough to fully separate `__thiscall` from some `__fastcall` cases (a complete algorithm would also verify EDX is not used to pass a parameter), but it cheaply eliminates many non-methods. Procedure `findThisCall()` returns pairs `<func, instr>` where `instr` is the first instruction in `func` to read ECX; "a `__thiscall` method" thereafter means one identified by this procedure.

### 5.3 Identifying Object Instances and Methods

Related methods are grouped into object instances by finding those that share a common ThisPtr. The tool first identifies a ThisPtr pointing to stack or heap, then finds OO methods passed that pointer in ECX. Heap ThisPtrs come from allocators like `new()`; calls to `new()` are found by parsing the import section or by fingerprints/hashes of known `new()` implementations across Visual Studio versions. After a `new()` call, the ThisPtr is the value first read from **EAX** (`findReturnValueOfNew()`), since `new()` returns its result in EAX.

For each function calling `new()`, the tool: (1) retrieves the ThisPtr (`thisPtrFromNew`) from the first EAX-reading instruction; then (2) iterates the `__thiscall` methods called in that same function, keeping those with an instruction reading ECX with a matching value:

`objectMethods = {f∈FM | ∃i∈FM  <thisPtrFromNew, ECX> ∈ Use(i) ∧ i∈f}`

The worked example (Fig. 5) shows `new()` returning the pointer in EAX, saved to a temporary, moved to ECX before both a constructor call and a later method call; sharing a ThisPtr means both belong to the same class. Stack objects are handled analogously beginning at an `lea` instruction referencing local stack space.

Identifying **constructors** is complicated: constructors must return a ThisPtr (distinguishing them from many but not all methods); vtable-pointer initialization reliably identifies them when virtual functions are present, but not all classes use them. The authors' heuristic labels the constructor as the first method called after allocation that returns the same ThisPtr passed to it. This can misidentify builder/factory methods (deemed effectively indistinguishable at the binary level and not counted as an error) and can miss legitimate constructors (e.g., ones that construct other object types).

### 5.4 Data Members

For each associated `__thiscall` method, the tool retrieves the ThisPtr from the pair `<thisPtr, ECX> ∈ Use(j)` (where `j` is the first ECX read), then scans other memory-dereferencing instructions for `<*, thisPtr + offset> ∈ Use(i)`. Procedure `findDataMembers()` produces `MemberMap`, mapping a method to a set of data members represented as `<offset, size>` pairs. In the worked example (Fig. 6) the ThisPtr moves ECX→EAX and `[ThisPtr+0xC]` is read as 32 bits, yielding a data member at offset 12 of size at least 4 bytes.

### 5.5 Virtual Function Tables

Objects with vtables initialize memory at ThisPtr offset zero with the table's address; this write occurs in a constructor as `mov [reg], vtableAddr` where `reg` holds a ThisPtr. Finding such writes inside identified constructors records `<vtableAddr, thisPtr> ∈ Def(i)` as a potential vtable address. Calls into the table are found among the dependents of that `mov`:

`Q = {q | <vtableAddr, thisPtr, q> ∈ DepOf(i)}`

Following the pointer symbolically from those instructions to a call, the tool records each call's branch target and its offset from ThisPtr as a vtable entry.

### 5.6 Inheritance and Embedded Objects

Inheritance detection is described as partially implemented. Inheritance is inferred by analyzing constructors: a subclass constructor calls the parent constructors, passing its ThisPtr (directly for single inheritance; ThisPtr plus the embedded-parent offset for multiple inheritance). The problem is that **embedded objects** produce the same pattern. To disambiguate, a reliable discriminator is whether the subclass **overwrites the parent's vtable address** in its constructor, but parents are not required to have virtual functions.

The proposed method (`lookForInheritance()`) is to: (1) collect calls from constructors to other constructors; (2) compare ECX values (possibly plus a constant) to detect a shared ThisPtr, indicating inheritance or embedding; and (3) check whether the caller overwrites the passed address with a new vtable pointer, in which case the callee is labeled a parent; absent such an overwrite the object may be embedded. Fig. 7 illustrates a constructor calling two parent constructors (at ThisPtr+0 and ThisPtr+0x10) and then overwriting both locations with two new vtable addresses. The authors state that reliably distinguishing embedded objects from multiple inheritance without virtual functions "is an open problem."

### 5.7 Object Instance Aggregation and Reporting

Results are grouped by unique constructor (and some builder methods). Data members and methods seen across object instances produced by the same constructor are merged; information from constructors known to share a common vtable is also merged. The authors claim this yields output more useful than individual instances yet not full class definitions; with better inheritance/embedding detection these merged instances should "converge on complete class definitions," though that result is not claimed here. Fig. 8 shows merged output for class `XmlText` (with PDB symbols substituted for raw addresses), which correctly reports methods, members, and vtable info but wrongly attributes `XmlNode::XmlNode()` and `XmlNode::SetValue()` (from the parent `XmlNode`) to `XmlText` — the embedded-vs-inheritance ambiguity in practice.

## 6. Experiments

Validation used open-source SourceForge packages (with ground truth) and real-world malware (no source). The authors propose an evaluation framework mixing tool output, debugging information, and compiler-generated class-member layouts.

### 6.1 Open-source Tests

Packages tested: The Lean Mean C++ Option Parser 1.3, Light Pop3/SMTP Library, X3C C++ Plugin Framework 1.0.2, PicoHttpD 1.2, and CImg 1.0.5, each compiled with MSVC. Ground truth came from three sources: MSVC compiler layout (class layout and data members), PDB symbol information (mapping function addresses to demangled names via `undname`), and the test-program source. Methodology: compile and generate layouts; run OBJDIGGER (which reports method addresses and layouts without names); extract PDB symbols via IDA Pro; correlate addresses to names; compare discovered members to compiler-reported ones; and manually inspect source, excluding methods/members not in the control flow (e.g., functions the compiler included but never called).

Three recall metrics were measured — unique classes found, methods found, and data members found — each over the count present in the binary, excluding standard-library classes and provably-unused methods/members. Results (Table 1, recall/true-positive rate):

| Package | Classes | Methods | Members |
|---|---|---|---|
| PicoHttpD 1.2 | 8/9 (89%) | 31/47 (66%) | 18/25 (72%) |
| x3c 1.0.2 | 4/5 (80%) | 21/24 (88%) | 6/8 (75%) |
| CImg 1.0.5 | 7/7 (100%) | 61/83 (73%) | 33/42 (79%) |
| OptionParser | 10/10 (100%) | 37/52 (71%) | 33/35 (94%) |
| Light Pop3/SMTP | 8/9 (89%) | 29/35 (83%) | 16/23 (70%) |

**6.1.2 Discussion.** Table 1 lists recall; precision was **100% in all tests** (no false positives), and every identified method/member was verified to belong to its reported class. Missed methods were often correctly recognized as `__thiscall` but could not be tied to a specific class because no constructor was positively identified. A single missed constructor causes a **cascading effect**: without it, methods and their accessed data members in that instance cannot be attributed to a named class. For PicoHttpD, the one missed class was a global variable whose ThisPtr pointed into `.rdata`; OBJDIGGER only tracks local stack addresses and `new()`-allocated space, so it conservatively did not report a new instance. Misses in CImg and Light Pop3 are attributed to implementation bugs (problems tracking objects passed as parameters and methods called indirectly through vtables) rather than the approach. A fundamental limitation is that only methods actually called and members actually accessed by the analyzed program can be detected.

### 6.2 Closed-source Malware Case Study

OO malware often encapsulates critical functionality in C++ data structures, so recovering those structures can be prerequisite to understanding behavior. Manual recovery is tedious and error-prone; OBJDIGGER automates it. On a sample (md5 `019d3b95b261a5828163c77530aaa72f`), of the **585 functions** in the sample the tool identified **nine object instances** with their constructors, methods, data members, and vtables. In the walked example, the `main` function (Fig. 9) contains three methods; OBJDIGGER (Fig. 10) correctly reported all three as one object, with `sub_403000` the constructor and `sub_401470` and `sub_401f20` its methods, plus member offsets/sizes and vtable contents. This immediately tells the analyst the malware's functionality is organized around at least one object instantiated in `main`, focusing effort on the object's internals.

## 7. Related Work

Sabanal et al. first described heuristics for recognizing C++ objects by monitoring ThisPtr use; this work captures those heuristics as machine-recognizable data-flow patterns and additionally tracks ThisPtr propagation between functions to group members and methods. Tröger and Cifuentes pioneered data-flow analysis on binaries to recover vtables but relied on dynamic execution. Lee et al. (TIE), Balakrishnan and Reps (DIVINE), and Ramalingam et al. focus on variable/type recovery rather than class structure. Srinivasan et al. infer class hierarchy from dynamically observed call relationships, but are limited to executed code and do not recover data members. Slowinska et al. (DDE) and Lin et al. do dynamic type discovery of variables, tracking memory-location use to infer size/type similarly to this work's member-size inference. Adamantiadis explains constructors/destructors/vtables at the binary level but proposes no automated technique. Dewey et al. use similar techniques but target vtable-escape vulnerabilities in non-malicious code. Fokin et al. adopt a very similar approach with less data-flow detail; their earlier work offers insights on aggregating object instances into classes.

## 8. Conclusion and Future Work

The paper presents a purely static approach for recovering object instances, data members, and methods from x86 MSVC binaries, implemented in OBJDIGGER. Open-source tests against compiler-generated ground truth show the technique meets its goal effectively, and malware tests show it aids reverse engineering. Identified future work includes: recovering objects instantiated as **globals** (currently unsupported); reliably distinguishing **embedded objects from multiple inheritance** without virtual functions (an open problem); accurately identifying **destructors** to better track object scope; supporting advanced features such as **virtual inheritance** (which uses virtual base class tables that change object layout); understanding the effects of **compiler optimizations** such as inlined constructors/destructors; extending analysis to **non-MSVC compilers** (preliminary analysis suggests GCC uses similar mechanisms) and possibly other languages such as Delphi; and improving the tool's output, perhaps as an IDA Pro plugin, to show method/object relationships more quickly.
