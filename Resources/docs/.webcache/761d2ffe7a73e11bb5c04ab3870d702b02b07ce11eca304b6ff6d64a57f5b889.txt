The BOOTBOOT loader has exactly the opposite philosophy than [GRUB](https://wiki.osdev.org/GRUB "GRUB"), it is not a Grand Unified Loader, rather a set of simple and small loaders which provide the same boot environment for your kernel on different platforms.

## History

This loader was created to an easy alternative to the complex GRUB by one of the OSDev forum members.

## Supported Platforms

BOOTBOOT can load your 64 bit kernel on the following platforms:

- Raspberry Pi (AArch64)
- Legacy BIOS (x86_64 with MBR)
- Legacy BIOS boot with any arbitrary boot manager (x86_64, chainloaded from VBR)
- Legacy BIOS boot with a single OS on a forward-compatible GPT disk (x86_64, booted from PMBR)
- Legacy BIOS for embedded systems (x86_64, in BIOS Expansion ROM)
- UEFI (x86_64)
- UEFI for embedded systems (x86_64, in PCI Option ROM)
- CDROM, El Torito "no emulation" BIOS boot (x86_64, hybrid GPT/ISO9660 image)
- CDROM, El Torito UEFI boot Extension (x86_64)
- ISOLINUX / LILO / BOOTLIN / etc. (x86_64 via the Linux kernel boot protocol)
- COREBOOT: as a primary payload in ROM (x86_64)

For GRUB compatibility, BOOTBOOT is also Multiboot compliant, so you can add it to the grub.cfg in it's own entry. This is useful if want to dual boot multiple OSes.

## Supported Sources

Your kernel can be wrapped in an initial ramdisk archive ([USTAR](https://wiki.osdev.org/USTAR "USTAR"), cpio, James Molloy's initrd format etc.), which in turn can be a simple file on a [FAT16/32](https://wiki.osdev.org/FAT "FAT") partition; or can occupy the whole partition as well using a file system of your choosing ([SFS](https://wiki.osdev.org/SFS "SFS") among others). BOOTBOOT uses GPT partitions, so your boot partition should be either an [ESP](https://wiki.osdev.org/EFI_System_Partition "EFI System Partition"), or it should have the bootable flag (attribute 2) set.

If despite the warning you decide to [Roll Your Own Filesystem](https://wiki.osdev.org/Roll_Your_Own_Filesystem "Roll Your Own Filesystem"), then BOOTBOOT is definitely for you. You can either write an FS module (one function), or just make sure the kernel is the first executable in the archive / on the partition. BOOTBOOT is capable of loading kernels from unknown file systems as well.

Optionally you can load your OS from ROM (see qemu's -option-rom command line argument, or bochs rc file; or with [coreboot](https://coreboot.org) as a BIOS using qemu -bios), and the Raspberry Pi version can also load the ramdisk over serial line. Although it's not implemented as of yet, the BOOTBOOT protocol allows loading the initrd from a TFTP server.

## Your Kernel

You can use ELF64 or PE32+ formats for your kernel. You must link it as a [Higher Half Kernel](https://wiki.osdev.org/Higher_Half_Kernel "Higher Half Kernel"), and your entry point should point to [Long Mode](https://wiki.osdev.org/Long_Mode "Long Mode") code. That's all. Unlike all the other boot protocols (e.g. [Multiboot](https://wiki.osdev.org/Multiboot "Multiboot") and [stivale](https://wiki.osdev.org/Stivale "Stivale")), there's absolutely no need for special sections nor for magic structs, unimplementable in some languages. No real mode nor protected mode trampoline code needed either, which simplifies your build environment significantly. Example linker script provided for both x86_64 and AArch64. There are [example kernels](https://gitlab.com/bztsrc/bootboot/tree/master/mykernel) written in [C](https://wiki.osdev.org/C "C"), [C++](https://wiki.osdev.org/C++ "C++"), [Pascal](https://wiki.osdev.org/Pascal "Pascal"), [Ada](https://wiki.osdev.org/Ada "Ada"), [Rust](https://wiki.osdev.org/Rust "Rust") and [Go](https://wiki.osdev.org/Go "Go").

BOOTBOOT passes a configuration to your kernel in a newline separated, zero-terminated UTF-8 string. Each line contains a *key=value* pair, where only two keys, "screen" and "kernel" are reserved. You are free to use any other keys that your kernel wishes to use.

## Console

BOOTBOOT does not support VGA text mode, it sets up graphic mode regardless to the platform. You don't have to mess around with [VESA](https://wiki.osdev.org/VESA "VESA") or [GOP](https://wiki.osdev.org/GOP "GOP") any more, you will get the frame buffer ready to use. The example Hello World kernel provided with the BOOTBOOT source has a minimal puts() example, which outputs text on that frame buffer using [PC Screen Font](https://wiki.osdev.org/PC_Screen_Font "PC Screen Font") (same that Linux Console uses). You can also use the [Scalable Screen Font](https://wiki.osdev.org/Scalable_Screen_Font "Scalable Screen Font") library's *ssfn_putc()*.

The loader also initializes the [serial console](https://wiki.osdev.org/Serial_Ports "Serial Ports") for you with 115200 baud, 8 data bits, no parity and 1 stop bit. Your kernel can send debug messages from the start.

## How to Install

You can install BOOTBOOT yourself following the [bootable disk](https://wiki.osdev.org/Bootable_Disk "Bootable Disk") tutorial and using one of the provided mkboot.c utilities. But the simplest way is to use the multiplatform (Windows, MacOSX, Linux) disk image creator tool, [mkbootimg](https://gitlab.com/bztsrc/bootboot/tree/master/mkbootimg) which is very similar to [grub-mkrescue](https://wiki.osdev.org/GRUB "GRUB").

For input, you provide the contents of your initrd in a directory, and a JSON configuration describing what disk image you would like. The rest is taken care for you.

## There's more...

Besides of the pre-compiled boot loader binaries, BOOTBOOT also provides dependency free tools written in ANSI C to map GPT [EFI System Partition](https://wiki.osdev.org/EFI_System_Partition "EFI System Partition") into MBR, install boot sectors or send your ramdisk over serial line from another machine. The aforementioned Hello World kernel can be used as a skeleton for your kernel. Forget the boot process, you can start by implementing your kernel right away.

For all the features and available options, read the PDF documentation. It describes how to install an initial ramdisk with your kernel in it on a disk image, what are the exact memory mappings, which C structure is used to pass information to your kernel, how to tell bootstrap processor from application processors apart, etc.
