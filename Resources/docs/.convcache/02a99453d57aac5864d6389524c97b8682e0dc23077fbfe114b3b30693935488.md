**Notes:**

What is Ghidra?

- Integrated development environment (IDE) for Reverse Engineering (RE) tasks

- Written in Java - mostly platform independent

- Five major parts:

- - Programs
  - Plugins
  - Tools
  - Project Manager
  - Server

***Notes:***

- Ghidra is a highly extensible application for performing software reverse engineering.
- Ghidra is built upon a completely generic application framework. Each Application-specific capability is provided by small software bundles called plugins, and each one provides one or more features.
- There are five major parts of Ghidra including: Programs, Plugins, Tools, Project Manager, and the Server . Each of these parts will be discussed in more detail later on in the course.

Programs

  

- All data is stored using Ghidra's custom database

- All data added by the user also gets added to the Ghidra program database:

- - Symbols
  - Bytes
  - References
  - Instructions
  - Data
  - Comments
  - Etc...

***Notes:***

Plugins

  

- Ghidra is a library of plugins. Each plugin provides specific functionality.
- All plugins communicate with each other within the tool that they are docked in.
- Plugins can be added or removed without restarting Ghidra so that users can customize the tool however they like.
- Users can write their own plugins.

***Notes:***

Tools

  

- Collections of plugins and their configurations
- Ghidra has several preconfigured tools which can be customized to suit individual requirements
- All tools can be customized
- New tools can be created by adding plugins to an empty tool
- Tool configurations are saved for the next use

***Notes:***

Project Manager

  

- Manages projects, tools, and data for a particular group of programs
- Programs must be imported into a project before work can be done
- Project configurations are saved for the next use

***Notes:***

Ghidra Server

  

- Ghidra projects can share project data by connecting to a Ghidra Server

- The Ghidra server:

- - Is used when multiple users want to work together on the same program or set of programs
  - Is a simple service running on any computer that a group of users has access to.
  - Provides network storage for the shared project.
  - Controls user access
  - Allows files to be versioned
  - Supports check out, check in, version history

***Notes:***

Why use Ghidra?

  

- Tools can dynamically share data.
- Supports teaming.
- Highly configurable environment
- Very extensible.
- Runs on multiple platforms
- Has undo!

What happens during  
Auto-Analysis?

  

- At a minimum:

- - Starts at Entry Points
  - Disassembles by following flows
  - Creates functions at called locations
  - Creates Cross References

- Depending on what options you have selected, Auto- Analysis will do other things as well

***Notes:***

- During Auto-Analysis, Ghidra:

- - Starts at Entry Points
  - Disassembles by following flows
  - Creates Functions at called locations
  - Creates Cross References

- Depending on what options you have selected, Auto-Analysis will perform other functions such as:

- - Using operand references to create code or data where operand points to
  - Make switch statements using decompiler information
  - Make function signatures based on decompiler information
  - Demangle mangled names
  - Recognize and name library functions
  - Perform specific functions depending on the binary type
  - Look for images

- If you would like to cancel Auto-Analysis at any time, you can click on the little red square at the bottom of the listing.

- Look at the log in the bottom right of the Program Manager to see which analyzers were run and how long they took.

Auto-Analysis

- Useful to take a layered approach by running analysis with basic options first and run one-shots later

- - Focus on options that will get function starts and data first
  - Turn off stack analysis if you have a large binary, can run it individually by function

- Learn how to recognize and fix problems

- - Many useful scripts for this

***Notes:***  

- For many binaries, analysis gives better results with a layered approach. This means the user should run analysis with basic options first, then rerun with other options later.

- **Initial analysis:**

- - Turn off anything speculative or extra, such as stack analysis, especially if you have a large binary. You can turn these options back on after an initial analysis and rerun analysis on selected functions or the whole program.
  - In general, you should leave on reference analyzers, data analyzers, and function analyzers in order to determine what is code and what is data.

- **Follow-on analysis:**

- - Can rerun analysis with different options **OR** turn on one-shot analyzers, which are analyzers that run one type of analysis at a time

- One-shot analyzers can be run from the **Analysis-\>One-Shot** menu. Some common ones are:

- - Decompiler Parameter ID
  - Decompiler Switch Analysis
  - Stack

- **Recognize and fix problems:**

- - Red x's indicate bad flow. The error bookmarks might indicate what analyzer caused the problem so the user can rerun with better options.

  - Analysis may not completely determine all code and data in a program, especially if certain analyzers are turned off.

  - Use analysis scripts to recognize and fix problems. Here are some examples:

  - - **FixupNoReturnFunction.java** fixes functions that do not return and the resulting bad flow from the call to the function
    - **FindPotentialDecompilerProblems.java** runs decompiler and indicates potential issues like unaffected registers and input values that might be global
    - **FindSharedReturnFunctions.java** finds potential places where the function is jumping to another function to share a return. If you do not fix these, the function analyzer and decompiler will merge the two functions
    - **FindInstructionsNotInsideFunctionScript.java** identifies code that is not in functions yet
    - **CreateFunctionsFromSelection.java** allows user to quickly make functions recognized by user when analysis does not find them all, etc.

***Notes:***

- - **Ghidra Zip file (GZF)** uses custom format to compress all information contained in a Ghidra program so that users can share program information.
  - **XML** Used to export information about the current program, to other tools if an importer has been written to recognize it in the other tool.   - **C** exports selection or entire program as C code (Including corresponding .h file)
  - **Ascii** exports selection or entire program as printable Ascii file
  - **Original File** Writes a program back to its original file layout. By default, any file-backed bytes that were modified by the user in the program database will be reflected in the new file. Optionally, the program can be written back to its unmodified file bytes, discarding all user modifications.
  - **SARIF** Creates SARIF files that contains information from a Ghidra program so that users can share program information.

Function Graph

- Represents function as a directed cyclic graph

- Edges (branching or jumps) represent flow control

- - Conditional positive (success): green
  - Conditional negative (failure, pass through): red
  - Unconditional: blue
  - Switch: also blue

- Nodes (blocks) represent a unit of code

- Note: Calls do not break block

***Notes:***

- To open the Function Graph window go to **Window-\>Function Graph**.
- There is a Satellite View inset window at the bottom right of the window. If it gets in your way, you can right-click on the Function Graph canvas window and deselect its option.
- If you hover on an edge, it will present a popup window showing you the branch/jump statement, and the code at the target destination. This can obscure a large portion of your window. If you would like to turn it off you may from the right-click menu.
- If you desire, the edge colors can be changed on the tool options screen.

Function Graph Basic Controls

- Click-drag on whitespace moves the "canvas"

- Click on block navigates in listing (and focuses)

- Double-click on edge navigates to jump target destination

- - Double-click again and it will navigate to jump source (branch statement)

- Double-click on block centers, zooms to 1:1

- Mouse wheel zooms in and out

***Notes:***

- The **focused** block is the block containing the current cursor location in the listing. The block (node) in the graph surrounded by a yellow highlighted oval is the focused block.
- The focused block always contains the current cursor location in the program; however, it does not mean the cursor location is at the top of the block. If you click on a block, the cursor is placed at the top. But if you navigate using the listing or decompiler or other window, your current location can move to a place within the block (but not at the top). If you navigate the current location outside the current block, the focus will follow and the new block containing the current location will be highlighted.
- You will learn more about what focus is useful for (besides a visual indicator of location) in a few slides.
- The **hovered** block is the block that your mouse is currently over. You will also learn more about this in a few slides.
- **NOTE**: When double-clicking on an edge to navigate blocks, note that you are actually taken to the block furthest away from your current canvas position. Usually that results in the behavior described in the slide; you double-click on an edge coming out of a block, and you are taken to the destination of the jump. But if you see an edge "out in space" (i.e., you don't see its source or its destination block), remember it will take you to the block that is furthest away, which might not be the destination block the first time you double-click it.

Function Graph Hover/Focus

- Scoped Flow To/From Block

- - Blocks after "From" must have passed through hover/focus
  - Blocks before "To" must eventually pass through hover/focus

- Paths To/From Block go from entry block to return block(s)

- Loops Containing Block shows local loop neighborhood

***Notes:***

- For those unfamiliar with dominance in graph theory, the basic idea is that some nodes are more "important" than others because they act as dispersing or condensing "gateways" for flow.
- Show Scoped Flow From Block will encompass all blocks in the flow after the principal block that can ONLY execute if the principal block executes. In other words, if control never makes it to the principal block, none of the neighborhood blocks will execute.
- Show Scoped Flow To Block will encompass all blocks in the flow before the principal block, such that all blocks in the neighborhood MUST have executed if the principle block executes.
